# V15.0 Adversarial Review — Local PSD/PSB Read-only Inspector

Review date: 2026-10-31, implementation follow-up: 2026-10-31
Scope: V15.0 read-only scanner, local Agent, typography extraction, UI and failure handling.
Decision: **Continue as a constrained developer preview. Do not claim production readiness.**

## 1. Product truth challenge

**Challenge:** A user may interpret “PSD scan complete” as proof that every Photoshop text property and rendering behavior was captured correctly.

**Control:** The scanner reports parser confidence, notes, unsupported flags and explicit unknown values. It does not render the document or approve layout. The UI labels the tool as a read-only structural scanner. The project continues to disclose that Photoshop write and visual approval are separate milestones.

**Residual risk:** Real parser behavior must be compared against representative PSD/PSB files and Photoshop on Windows.

## 2. Source-file integrity challenge

**Challenge:** Could scanning overwrite, flatten, resave or otherwise mutate the user's original design file?

**Control:** The browser uploads only the user-selected file bytes to a task-scoped local copy. There is no arbitrary local-path scan endpoint. The parser process opens the task copy and reads layer properties only. The agent calculates SHA-256 before and after scanning and refuses to mark the job complete if the task copy changes. The UI explicitly describes the hash result as task-copy integrity verification.

**Residual risk:** The agent does not obtain or open the original filesystem path. The browser's selected File object is read and uploaded; the original file is never passed to a write API.

## 3. Local API and browser security challenge

**Challenge:** Could a malicious web page use the local agent to inspect files or trigger tasks?

**Controls:**
- Uvicorn binds to `127.0.0.1` only.
- Host header is restricted to loopback/local hostnames and the configured port.
- Cross-origin requests are rejected.
- API routes except health/session require a random per-process bearer token.
- The session endpoint is guarded by Host and Origin validation.
- No endpoint accepts arbitrary filesystem paths.
- Only files explicitly selected in the browser are uploaded.
- Deleting queued or scanning jobs is rejected to avoid removing a task directory while the worker is reading it.
- SQLite foreign-key enforcement is enabled for scan/layer cleanup.

**Residual risk:** A compromised local machine, browser profile or same-origin script remains inside the trust boundary. Do not expose the agent through a reverse proxy or LAN binding.

## 4. Malformed file and denial-of-service challenge

**Challenge:** Can a renamed non-PSD file, malformed document or crafted file crash the main agent or exhaust resources?

**Controls:**
- Extension allowlist and upload byte limit.
- Full 26-byte Photoshop header validation: signature, version, reserved bytes, channel count, canvas dimensions, depth and color-mode code.
- `psd-tools>=1.23` is required so structural `ParseLimits` are available.
- Parser uses a separate worker process with a configurable timeout (default 20 minutes); timeout terminates the worker and fails the task.
- Parser structural limits: max single read 1 GiB, total read 2 GiB, 500,000 parsed objects and nesting depth 64.
- Worker JSON output is capped at 512 MiB before loading into the main process.
- Parser errors fail closed and are recorded in the job/event log.

**Residual risk:** `psd-tools` allocation budgets do not constitute a complete process memory cap, and parsing itself still has memory/time costs. The worker has a timeout but no Windows Job Object memory ceiling in this milestone. Large-file behavior requires real Windows measurements.

## 5. Typography extraction challenge

**Challenge:** Can a single font field represent a text layer with mixed character styles?

**Finding:** No. psd-tools exposes a structured `typesetting` API, a `font_names` convenience property, and raw EngineData/FontSet information. The `Font` value in a raw style record may be an index into `resource_dict['FontSet']`, not a font name.

**Controls:**
- Use `TypeLayer.typesetting` run data and `TypeLayer.font_names` first.
- Map raw integer Font indexes through `resource_dict['FontSet']` only as a fallback.
- Preserve `font_names`, `style_run_count` and available per-run text/font/size/style/leading/tracking fields.
- Summary typography fields identify the first style run; mixed-run layers remain `partial` and `font_metadata_scope=first_style_run_only`.
- EngineData scalar wrappers are unwrapped through their `.value` property when applicable.

**Residual risk:** Not every text engine property is exposed by every parser version or document. Real mixed-script and variable-font PSDs still need validation. A font name extracted from PSD metadata does not prove that the font is installed on the Windows host.

## 6. Object identity challenge

**Challenge:** Is the generated object ID a permanent Photoshop layer ID?

**Finding:** No. `object_id` is a deterministic task-local identifier derived from source SHA-256, layer path, depth-first index, parser layer ID and bounding box. `layer_id` is retained separately when available.

**Control:** Schema and UI label the distinction. V15.1 mapping must bind decisions to a source revision and preserve match evidence; it must not treat `object_id` as a cross-version permanent ID.

## 7. PSB and large-file challenge

**Challenge:** Does accepting `.psb` mean every PSB is supported at every size?

**Finding:** No. The adapter identifies PSD/PSB from the header and records extension/header mismatch. Upload and parser structural limits are explicit ceilings.

**Control:** Header-derived format, upload size limit, parser limits, worker timeout and worker output cap are reported.

**Residual risk:** The default 2 GiB upload cap is a product guard, not a claim that all PSB documents fit. A 20-file Windows compatibility corpus and large-file stress tests remain release gates.

## 8. UI evidence and progress challenge

**Challenge:** Does the progress indicator show actual upload progress, and does the result screen disclose integrity and typography limitations?

**Control:** Upload progress uses XMLHttpRequest upload byte events. The result screen displays task-copy SHA-256 verification, parser version, isolated-process status, text type, font names, mixed style-run count, bbox, visibility and lock state. The mobile table scrolls within its own container; the document viewport is checked for horizontal overflow.

**Residual risk:** Scan-stage progress remains an indeterminate/estimated status because the current parser worker does not stream per-layer progress events.

## 9. Release decision

V15.0 remains a **developer-preview read-only scanner**. It is not production-ready until:

1. Install and run on Windows 10/11 with Python 3.11+ and `psd-tools>=1.23`.
2. Scan at least 20 real PSD/PSB files and compare layer counts, text, font names, font sizes, bbox, text type, visibility and lock state with Photoshop.
3. Include mixed fonts, CJK, hidden/locked layers, deeply nested groups, paragraph/point text, vertical/warped text, missing fonts and large PSB cases.
4. Measure memory/runtime on large documents and verify worker timeout recovery.
5. Verify source files remain unchanged at the user workstation.

No translation mapping, Photoshop write, save/reopen, JPG/PNG export or automated visual approval is included.
