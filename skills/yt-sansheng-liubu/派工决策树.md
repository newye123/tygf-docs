# 派工决策树

一问一答，落到动作；任何一步走到「停车」或「上报」都立即停，不硬推。

## 树 0：这件事要不要派？

```
单点改动、判据自己能跑、无并发风险 → 不派（但要留可复跑判据）
判据需要"另一个人复核"才可信（发布/账务/门禁/对外口径）→ 派（门下另找一手）
写入面与他人现场重叠 → 必须派给独占槽，或换独立工作树
需要通宵/长时/多步骤 → 派 chat 会话（见树 2）
```

## 树 1：派给谁（复用还是新建）

```
读编制册
├─ 有匹配写入面且状态=空闲的槽 → 复用该 sessionId（首选）
├─ 匹配槽全部在飞
│   ├─ 任务不急 → 排队（登记"待派"，不改状态）
│   └─ 急 → 看存活槽数 <8 ? 新建入册 : 走树 4 超编处置
└─ 没有匹配写入面（新领域）→ 停车上报 Owner（先定编制，不临时塞进别人的面）
```

**为什么不默认新建**：平台在被委派轮次内拒绝 `create_chat_session`（实测），新建窗口不稳定；且"新建对话无限增长"正是要治的病。

## 树 2：派 chat 会话还是后台 Agent

```
预计 < 3 分钟、纯只读探针、可丢 → 后台 Agent（可被打断）
预计 > 3 分钟 / 会写文件 / 跨夜 / 需要回包 → chat 会话
```

理由：后台 Agent 会被"用户插一句话"连带杀死且**不发完成通知**，已因此死过两个执行手，现场只剩未提交改动。派 Agent 干重活 = 主动制造孤儿现场。

## 树 3：任务书出门前的自检（门下，30 秒）

```
七字段齐？（编号/目标/判据/基线/写入面/硬约束/交付物）
判据里有命令和期望退出码吗？
基线三问：哪棵树？哪个 SHA？开工前 porcelain 是否为空？
是否写了"禁用提问式挂起，歧义进回包『开放问题』"？
是否写了"交回包前必须提交或显式声明未提交"？
任一否 → 当场驳回补写，不派出（错的任务书比没任务书更贵）
```

## 树 4：超编处置

```
存活槽 = 8 且需新槽
├─ 有"已解任"可复用的老槽 → 起复该槽（同写入面优先）
├─ 有"空闲"槽 → 解任最老的空闲槽（记日期与原因），再新建
└─ 全在飞 → 停车上报：要么排队，要么 Owner 批准临时扩编（写明有效期）
```

解任 ≠ 删除：会话记录留着可查，只是不再派活。

## 树 5：收包后判定（考功 → 门下 → 记账）

```
回包文件存在？ 否 → 判挂起，走树 6
产物在授权写入面内？ 否 → 驳回（越界）
判据命令由复验手独立复跑，退出码符合期望？ 否 → 驳回（红就是红）
结论的每条论断有 file:line / 行号锚点？ 否 → 驳回（叙述不算证据）
产物已提交或已声明未提交并给可恢复路径？ 否 → 驳回（防孤儿现场）
全过 → 入账 + 槽位置"已解任"
```

## 树 6：现场异常（孤儿改动 / 基线漂移 / 同树撞车）

```
发现无主未提交改动 → 先保全：整份补丁存档 +（需要腾树时）带唯一标签的 stash，
                     不 drop、不 pop、把标签与补丁路径写进登记
                     → 再决定谁接手；禁止 rm/checkout/restore 直接清
发现两方同时写一棵树 → 立即停其中一方（后到者退），双方产物分别存档，
                     由 Owner 或门下判定合并顺序；不允许"边写边协调"
发现基线漂移（HEAD 已不是派工时 SHA）→ 整包作废重派，不"顺手 rebase 一下"
```

## 树 7：什么时候必须上报 Owner（只列四类，其余自己拍）

```
1) 不可逆或影响共享系统：部署到站、对外发布、改历史账务、删除他人现场
2) 触及凭据或客户数据
3) 需要改判据本身（放宽门禁/删断言/换验收标准）
4) 同一任务连续 4 轮仍不合格（制度失效，不是执行失效）
其余（表述取舍、实现路径、顺序调度）→ 总控直接拍，事后在回收文件写明"我拍了什么、为什么、怎么退回"
```
