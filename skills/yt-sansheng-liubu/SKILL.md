# 三省六部派工治理

## Overview

把"多个 AI 会话协同干活"当成一个官僚制度来治理：**拟令的人不能自己批准，批准的人不能自己动手，动手的人不能自己论功**。
目标只有一个——让"绿"这个字重新变得可信，并让会话数量与并发写冲突不再自然膨胀。

制度骨架（史实见 `调研_github与三省六部.md`，映射由本 skill 给出）：

| 机构 | 本项目角色 | 能做什么 | 绝对不能做 |
|---|---|---|---|
| 中书省（拟令） | **总控** | 写任务书、定判据、派工、编册 | **不动手**（不编辑、不跑门禁、不部署） |
| 门下省（封驳） | **独立复验手**（副总控/另一只手） | 核 `file:line`、复跑命令、**直接驳回重做** | 不提"建议"了事；不自己改代码 |
| 尚书省六部（执行） | **执行手**，按**写入面**分六槽 | 在授权写入面内改文件、提交、出产物 | 越槽写入；自证为绿 |
| 御史台（监察） | **只读复验 + 记账** | 读实况、巡检孤儿现场、**直报 Owner** | 任何写权 |
| 考功（绩效） | **退出码与产物** | 判定红/绿、记入账 | 接受"叙述性完成" |
| 将作监（临时） | 临时施工槽 | 一次性工事，完事即撤 | 转为常设编制 |

## 三条铁律（不可协商）

1. **拟令不自准**：任务书的判据与执行结果不能由同一只手判定。总控写了任务书，就必须由**另一只手**（或 Owner 之外的独立会话）复验收官。
2. **未复验不记账**：没有 `file:line` 或真实退出码支撑的"绿"，一律记为 `unverified`，**不得写进状态、发版说明或对外口径**。
3. **一槽一写者**：同一时刻，一棵树的一个写入面只允许一个写者。判"谁在写"只看 `git status --porcelain` 与文件 mtime 是否在分钟级变化——**不信任何自述、不信声明文档**。

## 六部分槽（按写入面，不按话题）

| 槽 | 写入面（授权范围） | 史实类比 |
|---|---|---|
| 户部 | 服务端与账务：计费、冻结、结算、迁移 | 掌计账钱谷 |
| 刑部 | 门禁与测试：`test:*`、守卫断言、preflight | 掌律令、驳正违失 |
| 工部 | 取证与度量：普查、度量表、读数工具 | 掌营造度量 |
| 兵部 | 发布与部署：打包、签名、预检、上站 | 掌驿传关梁 |
| 礼部 | 前端与文案：界面、话术、对外展示 | 掌辞令仪注 |
| 吏部 | 文档与站点交付：规范、记录、接力指针 | 掌簿书案卷 |

**同树并发必撞**（已实测发生：两个大脑同时改一棵候选树）。若两个任务必须写同一面：**串行**（后者等前者交回包）或**换树**（独立 worktree + 明确基线 SHA），不允许"边写边协调"。

## 派工流程（步骤 0 + 7 步，每步都有产物）

0. **读能力现状（总控开场第一动作，不占定时器）**：每轮开工先核 `总控/产品功能全景_<最新日期>.md` 页眉"核验时刻"的日期——**不是当日 ⇒ 先派一次吏部重核包，再派任何活**；重核是总控自己的开场动作，**不建 cron、不新建自治轮**。核完再找出与本任务相关的行，把**行号 + `file:line` + 状态码（T/P/N/U）**抄进任务书「能力现状」字段。写不出来 ⇒ **不许派工**，先派一次盘点（吏部槽）——制度病根就在这里：肯定式要证据、否定式随口讲，于是"已有能力"被反复当成"待新建"。
1. **查册**：读 `总控/官制.md` 取空闲槽（见 `官制模板.md` 的回收算法）。有空闲 → 复用；无 → 新建；超编 → 先解任最老的空闲槽。
2. **拟令**：写任务书（下方八字段），**一次写全**——追加通道不可靠（实测见"平台硬事实"）。
3. **门下自检**：任务书出门前，由复验手对照"基线三问"：哪棵树？哪个 SHA？是否他人现场？任一未钉死 → 当场驳回，不派。
4. **派出**：长活/跨夜派 chat 会话；只派**一次**、不追问、不等批复。
5. **交回包**：执行手写回包到 `总控/回收_<日期>/<编号>_回包.md`，含 ⓪结论 ≤5 行、①产物路径与行数、②真实退出码、③自决事项、④开放问题。
6. **门下复验**：另一只手独立复跑 + 核锚点（见"复验单七项"；第 7 项核的是**任务书自己**，判据错记总控不记执行手）。**驳回权是真的**：不通过就打回重做，不写"建议下次注意"。
7. **记账与解任**：考功按退出码入账（红就是红）；槽位置"已解任"，不再接活（会话不删，历史要可查）。

## 任务书八字段（缺任一项即视为不合格，门下应驳回）

```
编号：          例 FG-SKILL
目标：          一句话，可判定
判据：          逐条列出"看到什么算过"，必须含命令与期望退出码
基线：          树名 + HEAD SHA + 开工前 git status --porcelain 应为空的声明
能力现状：      本任务触碰的能力在全景表第 __ 行、file:line __、状态 T/P/N/U；
                写不出来 ⇒ 不许派工，先派一次盘点（吏部）
写入面：        允许改哪些路径；明写"不得碰"清单
硬约束：        不可逆动作、外部系统、凭据与客户数据边界
交付物：        文件路径与命名、回包位置与格式
```
另附两条**必须写进每份任务书**的操作条款：

- **禁用提问式挂起**（`AskUserQuestion` 之类）：worker 问了没人能答。需拍板的写进回包「开放问题」。
- **现场交接靠文件**：worker 看不到对话历史；一切上下文进任务书与回收文件，不靠"你知道的"。

**生效时刻分界（2026-09-23 11:00 拍板）**：该时刻**前**已派出的在飞包按七字段收包，**不得仅因缺「能力现状」而封驳**；该时刻**后**新派一律八字段。封驳**只认五类**（见"封驳与重派上限"），缺字段不在其列。

## 门下复验单（七项，全过才算绿）

1. **锚点**：结论里的每个论断都有 `file:line` 或日志/行号，且复验手**自己打开过那一行**。
2. **退出码**：门禁命令由复验手**独立复跑一次**，退出码原样入账（非零码被当 0 是历史假绿主因）。
3. **写入面**：`git status --porcelain` 与 `git show --stat` 只落在授权路径内；越界即驳。
4. **基线**：产物是否长在任务书声明的那个 SHA 上；基线错了整包作废（不"顺手改改"）。
5. **交付完整**：产物已提交，或回包**显式声明未提交**并给出可恢复路径（补丁/stash 唯一标签）。
6. **与全景表对齐**：结论与能力现状全景表冲突即驳（含"引用了却没实测"、"把 U/N 说成已上线"）；驳回时**必须同时要求吏部更新对应行**（附变更 SHA 与核验日期），否则同一误判会再来一次。
7. **任务书判据可跑吗（这一项记总控，不记执行手）**：复验手在派工前把任务书里每条判据**自己空跑一次**——脚本不存在、门数写错、期望退出码写错都算判据错。判据错时必须在回包**单开一节「总控判据错」**点名，附实测命令原式与真实退出码；**不得计入执行手的驳回理由**（执行手无权改判据，按错判据跑出的"红"不是他的失败）。本轮实测两例：`npm run test:binding-compiler` 根本不存在（`package.json` 里 0 命中，missing-script 被当成测试红）；"预检四道门"实为 **5 道**。

## 封驳与重派上限

封驳理由**只认这五类**（2026-09-23 定稿；此前一处"四类"表述系笔误，第 5 类为 Owner 亲手所加），其余一律"放行 + 记开放问题"，防止门下变成第二个执行者：

- **封驳只认五类**：基线错 / 写入面越界 / 退出码或锚点造假 / 判据未满足 / **与权威清单（能力现状全景表）冲突且未实测**。

重派轮次：**同槽连续 ≤3 轮**；第 4 轮换人（新会话）并升级表述，仍不合格即**停车上报 Owner**。挂死检测：超过约定时限无回包文件 → 判挂死，槽位回收，改派 chat 会话续做（现场以最近一次补丁/提交为准）。

## 考功纪律（禁止三种"凑绿"）

1. **禁止重试到绿**（同一判据反复跑到偶然通过再报）。
2. **禁止换棵树拿绿**（在别处验证通过却声称本树已修）。
3. **禁止删断言/放宽判据凑绿**（要放宽判据必须走门下+Owner 的显式批准，并留变更记录）。
红就是红；诚实的"部分绿 + 缺哪一路证据"比虚假的全绿有价值。

## 已实测平台硬事实（写制度前先承认物理约束）

1. `send_message_to_chat_session` 对**已是 worker 的会话**会被平台拒（委派任务不得再转发）⇒ **任务书必须一次写全**，不能指望追加澄清。
2. `create_chat_session` 从**被委派轮次**内调用也会被拒（不得嵌套建会话）⇒ "新建会话"的窗口不稳定，故优先**复用空闲槽**。
3. **后台 Agent 会被"用户插一句话"连带杀死且不发完成通知**（已死过两个执行手，现场只剩未提交改动）⇒ 长活、跨夜、多步骤的活**只派 chat 会话**，不派 Agent。
4. worker 会改写共享记忆目录 ⇒ **改共享文件前必重读**；判"谁在写一棵树"只看 porcelain + mtime。
5. 现场交接靠文件不靠聊天；未提交改动是最高危状态（会成为孤儿现场），所以交付纪律第 5 项优先于一切文字说明。

## 会话数量治理

- 常设编制 **≤8**：六部 + 御史 + 将作（临时）。
- **交回包即解任**：状态置 `已解任`，不再派活，避免挂着 `waiting-user` 的僵尸 worker。
- 会话**不删除**（历史要可查），但**逻辑退编**——这是"新建对话不能无限增长"的唯一可执行解法。
- 超编时先解任**最老的空闲槽**；确需扩编（如并行发布窗口）由 Owner 批准并写明有效期。

## 何时不用本 skill

单人单任务、无并发写、无需第二只手判定质量时，不必套全套流程——但**"未复验不记账"**一条仍然适用：自己跑出来的绿，最好留一条可复跑的判据给下一个人。
