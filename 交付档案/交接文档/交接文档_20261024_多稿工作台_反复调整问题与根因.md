## 三、今天实测查出来的真正卡点（这是重点，前面几轮都没暴露）

我今天用自动化浏览器＋真实测试账号在测试站走了一遍多稿流程。**页面本身是好的**：批量页能开、单/多稿切换正常、文件夹入口卡正常、矩阵格确实是带 aria-pressed 的按钮。**真正让"点了没反应"的，是本地助手授权链断了**——任何需要本机助手的动作（扫描、读文件夹、替换）都会失败，而失败提示要么不说人话、要么按钮按了没变化。

按严重度排：

### C1（P0）助手与工作台的设备绑定对不上：`ASSISTANT_INSTALL_BINDING_MISMATCH`

- 现象：批量页粘贴文件夹路径点「读取文件夹」→ 报「无法验证本次文件选择许可（ASSISTANT_INSTALL_BINDING_MISMATCH），请刷新工作台后重试」。
- 根因：我这台电脑的助手（3.7.24）在服务端绑定的是 Owner 的 installId；我用审计临时账号登录后，浏览器 localStorage 里的 `tygf.installId` 是另一个 UUID。助手收到请求→去服务端验票→服务端说"这个 installId 不是我绑定的那台"→ 拒。
- 这**不是产品 bug**，是"换账号但助手只认原来那台设备"的必然结果。但它揭示了一个真问题：**换账号/换浏览器后，助手绑定不会自动跟着走，用户会卡在一个看不懂的错误码上**（`ASSISTANT_INSTALL_BINDING_MISMATCH` 这种码不该直接给用户看）。

### C2（P0）助手向服务器验票超时：`VERIFY_TIMEOUT`，把所有本机操作都堵死

助手日志（`E:\软件\图译工坊本地助手\logs\assistant-events.log`）今天的真实记录：

```
[ticket] verify slow hop elapsedMs=5785 attempts=1
[ticket] verify slow hop elapsedMs=3790 attempts=1
POST /v1.5/preparation/read-table -> 403 code=VERIFY_TIMEOUT origin=https://test.tuyigf.com
[ticket] verify rejected reason=VERIFY_TIMEOUT elapsedMs=10007 transportCode=REQUEST_TIMEOUT
[authorization-check] reject code=VERIFY_TIMEOUT elapsedMs=10017 budgetMs=12000 budgetExhausted=true
```

- 助手单次验票超时阈值 = 10 秒，总预算 = 12 秒。今天服务端单跳延迟 3.7～5.8 秒，一两次就吃满预算。
- **后果**：验票失败 → 助手对工作台返回 403 → 工作台把"读取文件夹/扫描/替换"全部判为失败。Owner 侧看到的就是"点了没反应"或一句莫名其妙的超时提示。
- **这不是前端 bug，是测试站服务器慢＋验票超时太紧的组合**。之前几轮一直在改 UI，所以一直没暴露。

### C3（P0）助手回调地址配错：4 条 HTTP_403，回调打到了 `http://localhost:3000`

助手日志里有 4 条：

```
[assistant-authorization] server responded httpStatus=403 code=HTTP_403 callback=http://localhost:3000
```

- 助手拿着票去回调工作台确认，但地址填的是 `localhost:3000`（本机 dev 端口），而不是测试站 `test.tuyigf.com`。当然 403。
- 影响：即使验票不超时，回调这一步也会失败 → 授权链闭不了环。
- **需要修**：助手侧的回调服务器地址配置，或工作台下发配对信息时把正确的 origin 传下去。

### C4（P1）「重新授权」「重试」两个按钮按了看起来没反应

Owner 说"点了没反应"，我在批量页复现了两处按钮失效感：

- **「重新授权」**：横幅上确实有这个按钮，但它所在的"首次使用准备"横幅可以被用户关闭（`DISMISSED_KEY = tygf.assistantSetupGuide.dismissed.v1`）。横幅被关掉后，用户在整个页面上找不到任何"重新授权"入口 → 点了没反应＝根本没地方点。代码里 `assistant-setup-banner.tsx:91` 也承认"之前需要重新授权的情况仍需提示用户"，但 dismiss 之后没有别的兜底入口。
- **「重试」**：点了之后横幅从"授权尚未确认"跳回"正在检测…首次使用准备"，**看着像没反应**，因为 `checkAssistant()` 只做 `ping` + `authorization/check`，**不做 `pair`**。也就是说：重试只是重新问一次"你现在授权了吗"，答案当然还是"没有"——它不会自己去修复授权。按钮文案骗人。
- 代码证据：`local-assistant-client.ts:573` 的 `pairAssistantRequest()` 只在**全新激活**时被调用；已激活但绑定漂移时没有任何路径会调它。

### C5（P1）激活门与工作台反复打架，页面闪一下又回邀请码页

实测多次遇到：进工作台→加载→跳回"邀请码激活"→再点"进入工作台"→又进工作台。localStorage 里的 `tygf.activation` 会被清掉再重建。Owner 看到的就是"页面闪一下、进不去"。这块的 Account-First 采纳逻辑（`activation-gate.tsx` 的 `/api/invite/session`）在令牌/账号切换时状态不稳。

## 四、给下一个 AI 的环境接入手册（省得重新摸索，这些今天花了很久才打通）

1. **测试站有访问门**：直接访问 `test.tuyigf.com` 会 403。门令牌在服务器 nginx 配置里：`ssh tygf-server "grep tygf_test_token /etc/nginx/sites-enabled/tygf-test"`（令牌值不要写进任何文档/提交）。访问方式＝URL 后面加 `?key=<令牌>`。
2. **没有可用测试账号**怎么办：在测试站服务器上用 Prisma 直接造。
   - 造账号：`cd /var/www/tygf-test && set -a && . ./.env && set +a`，然后用 `PrismaClient` 建 `BetaUser`（status active）＋`EmailCredential`（scrypt 哈希，`scrypt$v2$16384$8$1$<salt>$<hash>` 格式）。今天用的密码是 `AuditOnlyA1!`。
   - 造邀请码：`InviteCode.codeHash` = `scrypt(code, INVITE_CODE_SECRET)` 的 hex，`codePreview` 填前两段＋掩码。
3. **登录后进工作台还需要激活**：`localStorage['tygf.activation']` 要有值，且 `anonymousInstallId` 要和服务端该账号的激活记录一致；同时调 `POST /api/invite/activate`（body: `{code, anonymousInstallId, appVersion}`）会种 `BETA_ACCESS_COOKIE`。**注意**：这套在自动化浏览器里很脆（见 C5），实操中我最后是"清掉 activation→刷新→重新种→再刷新"才稳定进入工作台。
4. **本地助手在本机跑着**（`E:\软件\图译工坊本地助手\`，端口 49152）。它在服务端绑定的是 **Owner 的 installId**，所以任何**非 Owner 账号**触发本机操作都会撞 `ASSISTANT_INSTALL_BINDING_MISMATCH`（见 C1）。**要端到端走通多稿流程，只能用 Owner 那个已绑定的账号**，或者先在服务端解绑/换绑。
5. **助手回执地址**：本机助手的回执配置是 `http://localhost:3000`（见 C3），对测试站无效。
6. **浏览器工具**：截图需要 tab 可见（`browser.tabs.focus` 后再截）；`evaluate` 里不能用 `setTimeout`；React 受控 input 要用原生 setter＋`_valueTracker` 绕过。
