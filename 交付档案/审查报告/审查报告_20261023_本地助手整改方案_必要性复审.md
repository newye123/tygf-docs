## 0. 一句话给 Owner

方案的方向是对的，但**最贵的那一件（P1-A 把对象发上去、服务端重算）按现在的写法根本跑不通**：字段会被服务端隐私白名单直接拒收，体积会顶穿 64 KB 的请求上限，服务端既没有对象清单也没有"哪一行对应哪个对象"的映射。它证明的只是"客户端自己跟自己一致"，不是"活真的干过"。

真正会让客户反复丢授权的，也不是方案里写的 ACL 一项，而是 **"读不到就拿默认配置覆盖" ＋ "托盘每 5 秒把引擎重新拉起"** 这对组合。这两件必须一起改，只改一件会更糟。

三分结论：

- **真必要 3 件**：身份核对（前置）、ACL 故障停损（可做得比方案便宜）、读不到绝不覆盖（含托盘闭锁）。
- **条件必要 4 件**：未签名不得冒充正式版的发布闸（必须排在热修之后）、回执墓碑（降级成 2 行）、最小证据闸（替代 P1-A 的主体）、本地 HTTP 卫生三件。
- **不必现在做 4 件**：全量对象上传、`DECRYPT_FAILED` 独立态、`C:\snapshot` 路径清理、MAJ-5 服务端重裁本体。

## 1. 判定：为什么是"打回"而不是"有条件放行"

方案的三条主线里，有两条按现写法会**直接制造新的生产故障**：

1. **P1-A** 一旦照做，新旧客户端会互相拒收。旧客户端不带 `objects`，新服务端按方案要拒；新客户端带 `objects`，旧服务端会按隐私白名单拒（`execution-batch.ts:2366`）。而本项目没有静默自动更新，升级等于换安装包——两个版本会长期并存，等于给存量客户发一张"回执永久失败"的通知。
2. **P0-C** 要求"证书没到之前生产发布保持失败闭合"（方案 `:146`）。现网的生产清单已经是 `UnsignedBeta`（`public/downloads/local-assistant-release.json`，publishedAt 2026-10-23T00:49:43Z）。照方案做，证书到位前**任何**生产发布都过不去，包括修 ACL 的 3.7.25。方案自己写了"证书到位时间不承诺"——等于给修复上了一把没有钥匙的锁。

这不是说方向错。ACL 按名字解析、读不到就覆盖、空证据能过结算闸，这三件都是真的。问题在于方案把"该修的问题"和"最贵的修法"绑在了一起，还把执行顺序倒过来了（先发布闸、后热修）。

所以判定是：**问题清单基本可信，执行顺序和实现方式要重写；改完 6 处再审一轮。**

## 3. 必要性三分：哪些是真的该动

这一节直接回答"是不是真有这个必要"。每一条都写清"不做会怎样"和"做了会引入什么"。

### 3.1 真必要（3 件）

#### ① P0.5 身份核对（前置，0 成本）

**为什么必要**：审计报告自报 `assistantBuildId=transport-hardening-20261011-r1`，这个 buildId 对应的是 **3.7.15**（git 历史 `b36773c5`），不是 3.7.24。也就是说，报告里"24 条回执、CORS、自启覆盖"这些行为结论，很可能是在 3.7.15 上取的。不先钉版本，后面所有判断都建在沙子上。

**不做会怎样**：拿旧引擎的行为给新引擎开药方。

**做了的风险**：无。一条 `/ping` 命令的事。

**具体判据**：客户机 `/ping` 的 `version` 与 `assistantBuildId` 必须和 `public/downloads/local-assistant-release.json` 逐字一致（3.7.24 / `in-app-folder-picker-20261023-r1`）。

**补充事实**：`persisted-state.js` 从 3.7.15 到 HEAD 没有任何 diff（`git diff --stat b36773c5 HEAD -- download/local-assistant/persisted-state.js` 输出为空），所以 BLK-1（ACL 按用户名解析）在 3.7.24 上**依然成立**，这条不用等重测。但 24 条回执、CORS 这两条必须重测。

#### ② P0-A：ACL 故障停损（建议改成更便宜的写法）

**为什么必要**：`persisted-state.js:18-26` 现在用 `process.env.USERNAME` 作为 ACL 授权目标，并且把 `/inheritance:r` 和 `/grant:r` 塞进同一条 `icacls` 调用。在"域账号 + 同名本地账号"的机器上，名字会解析到另一个 SID；`/inheritance:r` 又把继承权限全部切断 → 当前进程读不了自己刚写的文件。更糟的是，`restrictAclToCurrentUser` 只在**写盘成功后**调用（`persisted-state.js:75-76`），启动时不做修复——一旦锁坏，没有任何自愈路径。

**不做会怎样**：这类机器上，授权配置每次启动都读不到，用户每次都要重新授权；远程没法修，只能让用户手工跑 `icacls` 或重装。

**做了会引入什么**：方案的原版要新增 `whoami` 解析、PowerShell 兜底、SID 缓存、`icacls /findsid` 自检、负控 smoke……一套小型的身份子系统。而这套东西本身又带来两个新失败面：`whoami` 在非交互/受限环境取不到 SID；文件属主如果不是当前用户（例如安装时用管理员创建），属主的隐式 `WRITE_DAC` 也不成立，自愈照样失败。

**更便宜的反方案（建议采用）**：

- **停止写自定义 ACE**：配置在 `%LOCALAPPDATA%\Programs\图译工坊本地助手\.tygf_session`（`server.js:151`、`:257` ＋ `installer.iss:19`、`:31` `PrivilegesRequired=lowest`），这个目录本身只对当前用户、SYSTEM、Administrators 开放。自定义 ACE 挡不住管理员（他们能改 MachineGuid、也能改程序），对普通其他用户又是多余的——安全收益接近 0，故障面却是实打实的。
- **启动时做一次只读修复**：如果 `CONFIG_FILE` 存在但读不了，跑 `icacls <绝对路径> /reset`（超时 5 秒、捕获退出码），把继承权限恢复回来；修不好就进入 ③ 的"不覆盖 + 停"。
- 这样不需要 `whoami`、不需要 SID 缓存、不需要 `icacls` 输出解析，代码量大约是方案的三分之一，故障类被直接消掉而不是被绕开。

如果 Owner 坚持保留"防同机其他用户"的加固，再按方案的 SID 版做——但要在方案里写清"属主不是当前用户时自愈会失败"这个残留风险，不能写成"重启 3 次不回退"就完了。

#### ③ P0-B：读不到绝不覆盖（含托盘闭锁）

**为什么必要**：这是"授权反复丢"的真正放大器。现在 `loadConfig` 读失败时返回默认配置（`server.js:745-749`），`saveConfig` 再拿默认配置合并后写盘（`:766-773`）。写盘的轮转顺序是"先删旧 `.bak`，再把当前文件改名成 `.bak`"（`persisted-state.js:67-72`）——第二次写就会把上一份唯一的好备份也覆盖掉。而 `ensureMachineId` 在三个请求路径里都会触发 `saveConfig`（`:4793`、`:6241`、`:6750`，实现见 `:8134`），所以只要进程活着，任何一次请求都可能把 `assistantToken` 冲成空。

**不做会怎样**：一次 ACL 故障 → 默认配置 → 用户重新授权 → 下次启动再丢，循环；两次写之后连恢复的机会都没有。

**做了会引入什么**：如果只按方案做"不可读就退出"，托盘会在 5 秒后把引擎重新拉起（`TrayHost.cs:55-63`），变成重启风暴，比现在更难诊断。所以**退出与托盘闭锁必须同笔**。

**三处必须一起改**（方案只写了第一处）：

1. `readRecoverableHiddenState` 要能区分 `MISSING / UNREADABLE / CORRUPT / DECRYPT_FAILED`，现在它把所有异常都吞成 `null`（`persisted-state.js:103`）。
2. 闸要下沉到 `saveConfig`：读失败时 `saveConfig` 直接抛错，绝不写盘。只在 `start()` 拦是不够的（F-09）。
3. 托盘要记住"引擎在本次会话里已经因致命配置错误退出过"，停止自动拉起并显示明确状态（F-08）。

### 3.2 条件必要（4 件）

#### ④ P0-C：未签名不得冒充正式版（方向必要，机制必须改写）

**为什么必要**：现网就是 `UnsignedBeta`，下载页和清单没有把"未签名"这件事如实说清楚。用户看到 SmartScreen 警告会以为下载到了假货，这是真实的信任损失。

**为什么不能按原样做**：见 F-05。删 flag / 停写清单会让所有生产发布失败，包括马上要发的 ACL 热修。方案 `:146` 自己写了"证书到位时间不承诺"——那就等于无限期停发。

**建议的写法**：

- **保留**生产 manifest 与现有 `--allow-unsigned-beta`，但给它加两道约束：一是必须带 `--beta-reason` 和 `--beta-expires YYYY-MM-DD`（到期后 flag 自动失效）；二是发布记录里留调用参数（谁、何时、为什么）。
- **新增** beta 通道只是为了让测试包不污染生产清单，这件事本身对，可以照做，但**不阻断**生产路径。
- **下载页如实标注**"当前版本未签名"——这半件最便宜，可以立刻做，不需要等证书。
- 证书与 Inno 四签名位（setup / 内层引擎 / 托盘 / 卸载器）排在 ACL 热修**之后**。

#### ⑤ P0-D：回执墓碑（降级为 2 行）

**为什么不是"真必要"**：方案把它当成账务缺陷，但实际影响只是本地日志。`recoverPersistedAttemptReceipts` 里的 `unresolved` 只用于一条 `console.warn`（`server.js:4470-4472`），不上云、不进结算、不改任何状态。真正的后果是：**每成功一次，下次启动的假告警就多一条**，把真未知淹没。这是告警质量问题，不是钱的问题。

**为什么还是值得做**：修起来极便宜。ACK 成功后（`server.js:4381`、`:7731`）写一个标记文件，恢复时跳过即可。

**必须避开的坑**：不要写在 `removeAttemptReceiptArtifacts` 里（F-10），因为它在永久拒绝（`:4399`）和防御终态（`:4386`）时也会跑，会把"被拒收"记成"已结算"——那才是真的错账。

**比方案更便宜的做法**：不新开 `receipts-acked/` 目录、不做 30 天清理。直接复用 `receipts-pending/` 之外一个 `.acked` 后缀的空文件，或者更简单——ACK 成功后把 journal 回执一起删掉（云端已有存档，本地 journal 只是审计副本）。方案第 4 条"30 天清理时把墓碑与 journal 一起清"说明它自己也认为 journal 可以清，那就不必为它建第二套目录。

#### ⑥ 最小证据闸（替代 P1-A 的主体）

**为什么条件必要**：现在的收费闸只认"`verificationLevel === 'REOPEN_VERIFIED'` ＋ `objectEvidenceDigest` 是非空字符串"（`execution-batch.ts:1387-1398`）。`sha256("[]") = 4f53cda1…02b945` 是一个合法的非空字符串，能直接过闸。被改的客户端不需要伪造任何内容，发这个哈希加一行 VERIFIED 就能结算。这是真洞。

**最小修法（零客户端改动、零合同变更）**：

- 服务端加一条 `^[a-f0-9]{64}$` 形状校验（现在连长度和字符集都不看）。
- 当存在 `VERIFIED` 行时，拒绝 `sha256("[]")` 这个特定值。
- 两条都不改 `RECEIPT_KEYS`、不改请求体、不改客户端。

**它能挡住什么**：挡住"什么都不发、直接白拿"的最低成本路径。

**它挡不住什么**：挡不住"编 N 个对象、算一个自洽摘要"。所以**不能**把它写成"改不了结算"，只能写"抬高了最低成本"。真正的边界要等对象清单与行映射落地（见 ⑧）。

#### ⑦ P1-B：本地 HTTP 卫生（做，但别夸大）

**为什么条件必要**：`Vary: Origin` 是正确性（缓存串味），PNA 是面向未来 Chrome 的兼容，Host 白名单能挡 DNS rebinding 这一类。三件都便宜。

**为什么不能当 MAJ-1 的修复**：本机进程可以随手伪造 `Origin` 和 `Host`。Host 白名单只挡浏览器发起的 rebinding，挡不住本机程序。上一版审查已经确认：给浏览器发设备密钥、用 HMAC 签名在这条链上不可实现。所以 MAJ-1 只能**显式记为接受风险**，不能写成"已修复"。

**两个实现细节**：端口要从 `PORT` 取（F-03/N-03），不要把 49152 写死；`getAllowedOrigin` 的 `localhost:3000` 回退可以删，但删之前要确认 `isLocalDevServer` 在打包版恒为 false（方案 `:190` 已写，照做）。

### 3.3 不必现在做（4 件）

#### ⑧ P1-A 全量对象上传 ＋ 服务端重算

**为什么不做**：不是"不重要"，是"现在做不通"，而且它需要的前置条件方案一件都没写：

1. 白名单要改（F-01），而这是**隐私合同的变更**——按项目纪律要四层同步＋fixture＋Owner 签字，不是加一行。
2. 请求体上限要改（F-02），而方案自己提的 500 对象压测就已经 69,993 B > 65,536 B。
3. 服务端要有对象清单与行映射（F-03）。`ExecutionAttemptObjectResult` 这张表建了但 0 引用，说明这个能力从来没接上。
4. 要有双版本窗口（F-06）。没有静默升级，就得让新旧服务端/客户端互相宽容至少一个版本周期。
5. 方案 `:180` 写的"VERIFIED 行对应的对象不在 `objects` 里 → 该行降级"**无法实现**，因为行和对象之间没有映射（F-03）。

**结论**：把它拆成一张独立的 L 号单，先补对象清单表、行映射、双版本兼容，再谈上传。现在硬上，收益是"从白拿变成要编 100 行假数据"，代价是"存量客户回执全丢"。

#### ⑨ `DECRYPT_FAILED` 独立态

**为什么不做**：它只影响错误文案（"换了电脑"还是"文件坏了"），不影响处置——两种都不该覆盖，两种都要用户重新授权。多一个状态就多一条测试路径和一处分支。现有四态够用。

#### ⑩ `C:\snapshot\…` 路径字面量清理

**为什么不做**：`engine.log` 落盘前已经把盘符路径全部替换成 `[path]`（`server.js:172`），控制台不落盘。清理字面量只影响开发看日志的观感，不影响用户。随下次文案改动一起做即可。

#### ⑪ MAJ-5 服务端重裁本体

**为什么不做**：这是"服务端自己判断某一行到底算不算完成"的完整重裁链，L 号工程，而且需要服务端持有原文/译文摘要——这与现在的隐私合同直接冲突。P1-A 替代不了它，最小证据闸也替代不了它。先记成"已知边界"，不要塞进这一轮。

## 4. 必须改的 6 处（重审门）

按方案现在的写法，下面 6 处不改就不能执行：

1. **P1-A 降级**：主体改成"服务端最小形状闸"（64 位 hex ＋ 有 VERIFIED 行时拒绝 `sha256("[]")`）；全量对象上传另立 L 号单，并在这张单里写清白名单、体积上限、对象清单、行映射、双版本窗口五件前置。
2. **P0-B 的 CORRUPT 定义**：改成"当前与 `.bak` **都**失效"才算 CORRUPT；当前坏、`.bak` 好时走现有恢复路径（`persisted-state.js:89-105`），不得把好备份一起隔离。
3. **"不覆盖"闸下沉**：改在 `saveConfig`（`server.js:766-773`），覆盖 `ensureMachineId` 的三个请求路径（`:4793/:6241/:6750`）；只在 `start()` 拦不算完成。
4. **补托盘致命闭锁**：连续因配置错误退出即停止 5 秒重启（`TrayHost.cs:55-63`），托盘显示明确原因。否则"退出"比"覆盖"更难诊断。
5. **P0-C 不得阻断热修**：保留生产 manifest 与 `--allow-unsigned-beta`，加"原因＋到期日"约束；"未签名不得冒充正式版"先落在下载页文案与 beta 通道；证书排到 ACL 热修之后。
6. **P0-D 钉死写点**：只在 ACK 成功路径写 `{outcome:'acked'}`；永久拒绝与防御终态写成 `rejected` 并单独计数（`server.js:4381` vs `:4386/:4399`）。

附带三条低成本修正（不单列为门）：

- Host 白名单端口从 `PORT` 取（N-03）。
- `CONFIG_UNREADABLE` 的路径写进**独立的**诊断文件或托盘提示，不要指望 `engine.log`（N-02）。
- 方案里的 422 要落到路由层：现在 `recordLanguageAttemptReceipt` 的失败一律映射成 404/409（`receipt/route.ts:164`），没有 422 这条路。
