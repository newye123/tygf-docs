# 每日访客与运营数据：结论与方案（2026-10-20）

## 先给结论

你现在没有任何地方能看到「每天的访客」这个数。不是工具没选，是三条路各自断在不同环节：

一是官网前端一行统计代码都没埋。我把仓库全扫了一遍，Umami、Google Analytics、Plausible、微软 Clarity、51.la 这些一个都没有，连内容安全策略也只允许本站脚本，外部统计脚本现在插进去也会被浏览器拦掉。

二是服务器日志有原始记录，但去不了重。日志里每条访问的客户端 IP 现在全是 Cloudflare 的代理地址（因为没配"从代理头还原真实 IP"），所以按 IP 数访客会数出一个人；日志格式里也没有"是哪个站"这一项，官网和内测站混在同一卷里；更要紧的是访问口令会以明文进日志，这件事本身就是卡正式发布的老案子。

三是 Cloudflare 其实每天都在算访客数，只是我们没把它接出来看。我实测了生产站响应头，确认在 Cloudflare 后面；它自带分析接口，从今天起所有套餐（含免费）至少保留 30 天数据。

## 这对你意味着什么

「有多少人来过官网」这个问题，今天答案是零成本可查的，只是没人查过。站内从头到尾没有存过任何访客数，所以你不可能在后台看到历史曲线——不是曲线不好看，是根本没记过。

## 我按你要的方式先去 GitHub 逐个核了现成方案，结论是先都别装

Plausible 和 Matomo 判死：它们官方前置都要 2 GB 内存起（Matomo 另要 2 核），而生产机要求是 1 核 2G，Next.js 和 nginx 已经在上面跑了。装它们等于把整套统计压到独占一台小机，主站随时可能被挤死。

Umami 也暂缓，而且这里查出一件必须更正的事：仓库里那份待批的观测方案写着"Umami 单容器，复用一个 Postgres 库"。但生产库是 SQLite 单文件，全仓没有 Postgres——Umami 新版只支持 PostgreSQL，MySQL 和 SQLite 都不认。那句"复用"是事实错误，照它派工一定撞墙。

自建一张访客表我也否掉了：看着最省，实际会把访客写入并进生产主库（这个库刚出过写锁挡住入口的事），而且去重、反爬虫、数据保留期全要自己重造一遍——我们在"保留期"这件事上已经踩出过六种失效形态，不该再造一张有保留期承诺的表。

## 砍完剩下的最短路径

档一，今天就能做，零改动，一小时量级：你登 Cloudflare 控制台把时间范围拉到 30 天，就能看过来着多少访客。这个数站内没存过，我也没有你的凭据。或者给我一个只读的分析接口令牌（只放服务器 root 权限的环境文件，不进仓库），我写一个小脚本每天按域名拉一行访客数、浏览量、请求数，落进台账，每天早上发你一句人话：昨天官网多少访客、多少浏览，注册申请几条、激活几台。验收标准是同一段时间跑两次结果一致，没实测到的字段不许写进口径，脚本只输出聚合数字不打印 IP 和浏览器原文。

档二，本周，跟发布闸一起做：把日志那三件事补上（加"哪个站"和"耗时"两项、访问口令脱敏、从 Cloudflare 头里还原真实 IP）。这件事本来就已卡着正式发布，不该为统计单独立项。做完才有分站数据、真实访客去重、AI 爬虫抓取记录，以及一直测不出来的响应耗时。提醒一句：这个改动动的是全局配置，会同时影响生产站和测试站的日志格式，所以我没有自己上手，等你授权。

档三，等你拍合规再动：Cloudflare 自家的浏览器埋点能多给跳出率和停留时长，但代价是改一行安全策略、补一行第三方清单说明，而且它不记录网址参数，所以拿不到渠道来源标签，也不支持自定义事件。真要上 Umami，就得先把"生产机引入 Postgres"当一件独立立项来算备份、保留期和监控的账。

## 除了访客，运营其实还需要这几层（顺带查出现成的两个洞）

第一层是在场性：每天多少人来、从哪来、看哪一页。真缺。

第二层是获客归因：哪个渠道带来的是能用起来的人。两层都缺——申请表里根本没有"来源"和渠道标签这两个字段，落地页也不带参数。这条比选哪个统计工具值钱：即使明天有了访客数，也答不出"这人是从知乎还是小红书来的"。

第三层是激活漏斗：申请、发码、激活、下载助手、第一次跑通，逐日分渠道。这个有，但只是快照——事件数据九十天就清、后台看板又只读最近一千条，所以画不出历史曲线。

第四层是产品健康：首跑成功率（现在的第一指标）、批次失败和卡住、助手版本分布。已有，半手工。

第五层是留存回访：次日和七日回访。数据源在（登录会话表能算），只是没人按日落一行。

第六层是收入与成本：订单、成交额、客单、退款、套餐构成、积分消耗、AI 调用成本。已有，后台就有。

第七层是稳定性与数据防伪：错误率、慢请求、爬虫占比、同机多账号、"提交了站点地图不等于被收录"。半有，唯一卡住的是日志里没有耗时字段，所以时延一直测不了。

## 需要你拍两件事

一、把访问行为数据交给 Cloudflare 分析，算不算需要重新告知的"目的变更"？现有红线写的是"只自托管、不接任何第三方"，但那条红线当时没考虑一个事实：Cloudflare 早就登记在第三方处理方清单里了，请求本来就已经过它。你要是判"补一行用途说明就行"，档一今天能走；你要是判"行为数据一律不出服务器"，那唯一出路就是先解决数据库问题再上自建方案，代价按档三重算。
