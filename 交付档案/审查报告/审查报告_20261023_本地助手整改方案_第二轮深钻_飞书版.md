# 本地助手整改方案：第二轮深钻（飞书可读版）

结论先说

我按你说的"钻到最深处"又跑了一轮，只读，没改代码、没出包、没部署。这一轮的结论跟上一轮不在同一层：上一轮我说最贵的那件事（P1-A：让本地助手把逐对象证据传上去、服务端重算）"按现在的写法跑不通"；这一轮我钻到底之后，结论换成——**就算把它写通，它也挡不住它声称要挡的那件事**。

为什么？因为这套计费是"做完多少行就扣多少，剩下的退给你"。所以一个改过自己电脑上助手的付费客户，要白拿只需要**少报**：干了一百行，只上报一行为完成，就只付一行的钱，而文件照样在他自己机器上做出来了。而 P1-A 的六条拒收规则全是"证据不够就拒收"，防的是**多报**——多报对客户自己没好处，要多付钱。也就是说，这条链上真正有钱的那个口子，P1-A 一刀都碰不到。

这对你意味着什么：不要为了"防白拿"去做 P1-A。要防白拿，最便宜的做法在计价规则里，而且不用动客户端（下面第六节给了两件）。P1-A 不是没用，它的真实价值是防程序出 bug 造成"活干了、云端零交付"，还有防夸大申报（对客户不利那一侧）——这个价值值得留，但要按它实际能做到的事排期，别按方案里写的"最该先做的一条"。

一、这条账是怎么算的（四条读数，同一条链）

1. 实际扣多少，是按上报的完成行算出来的，差额退还。见 src/lib/server/execution-batch.ts 第 2058 到 2065 行。
2. 算出来大于零就走"按实际额扣款"，等于零就走"全额退款"。同文件第 2218 到 2227 行。
3. 哪一行算完成，是本地助手自己组装回执时决定的。见 download/local-assistant/v15-runner.js 第 1041 到 1085 行。
4. 交付件是在客户自己硬盘上产出的，跟上报了几行无关。

伪造"做过"要编数据，这个 P1-A 能挡；隐瞒"做过"只要闭嘴，这个 P1-A 挡不住。而且服务端压根没有可对照的信息——它连译文正文都不存（数据库定义文件里搜"译文正文"相关字段名，零命中）。要让服务端"看一眼成品"，就得把正文传上来，那直接顶穿我们现在对外的隐私承诺（execution-batch.ts 第 2326 到 2342 行明令禁止上传原文、译文、路径、图层名、对象正文）。

所以方案里那句"护城河不在藏，在即使读懂也改不了结算"方向是对的，但要限定清楚：**改不了结算动作**（只有服务端能写数据库），**但结算基数是客户端给的**。这句话不改写，后面每个会话都会以为 P1-A 做完就安全了。

二、身份核对那一步，比错了对象（这条最便宜，也最该马上改）

方案让客户把本机助手的版本号和构建号，去跟"已发布的安装包清单"逐字比对。但真正拦人的不是那份清单，是**跑着的那台网站自己编译进去的身份**（src/config/localAssistant.ts 第 12 到 17 行；拦截点在 execution-batch.ts 第 131 到 132 行，比对方式是构建号、报告合同号、脚本指纹四项逐字相等，版本号只设下限）。

后果：如果网站部署在甲提交、安装包是从乙提交发布的，客户本机跟清单能对上（P0.5 判绿），但一进批次就被拒，报"构建身份不一致，请升级"——这是用户看得见的硬失败。

好消息是站点自己就有个现成的公开只读接口能取到"这台网站期望的助手版本和构建号"：直接访问 /api/runtime-provenance 就行，不用登录。所以判据改成：客户机的一条 /ping 输出，等于客户浏览器所连那台站点的 /api/runtime-provenance 里的期望值。一分钟的事，而且对不上就说明是发布不同步，先修发布再谈别的。

三、发布闸按现写法会把热修一起堵死（比上一轮说的更严重）

上一轮我说它挡生产发布。这一轮查清了：它**挡一切新安装包，包括测试站**。三个理由叠在一起——身份检查这道门对所有目标无条件跑（scripts/release-preflight.cjs 第 154 到 193 行）；发布脚本禁止同名换二进制（scripts/publish-local-assistant.cjs 第 79 到 91 行）；而部署文档记录的受控内测发布，用的正是那个"允许未签名测试版"的开关（deploy/部署三步走.md 第 52 行）。

所以"先立发布闸、后修配置权限"这个顺序不是建议调整，是硬约束：不改顺序，就没有能出厂的热修。

另外方案提的"beta 隔离目录"落地即空转，两处原因：下载页的读取器固定去找安装包同目录那份名为 local-assistant-release.json 的清单，方案写的是另一个文件名，所以 beta 包在页面上永远显示"不可用"（src/lib/server/local-assistant-release.ts 第 44 行）；而且 beta 助手带着新构建号，会被第二节那道身份闸直接拒。要真隔离，至少还得同时改这两处。

四、"读不到就退出"这条路，目前没有出口

方案要求配置读不到就退出、不改文件。方向对，但产品里已经没有任何自助恢复手段了：重置接口早就停用（返回 410，server.js 第 8060 到 8066 行）；卸载器明确保留会话文件，重装也清不掉（installer.iss 第 82 到 84 行）；托盘每 5 秒无条件把引擎重新拉起、不记致命错误（TrayHost.cs 第 55 到 63 行、117 到 132 行）；而方案说"打印路径和建议"——日志落盘前会把所有绝对路径替换成 [path]（server.js 第 172 行），并且普通输出根本不进日志文件（只有警告和错误进，第 195 到 206 行）。

合起来就是：一旦触发，用户既看不到该删哪个文件，也没有按钮可点，只会看到"助手连不上"，而进程在后台每 5 秒起一次。所以这条改动必须自带一句离线恢复指令，明确到删哪个文件、用什么命令。

还有一条本轮新发现的诱导链：每一次 HTTP 响应（包括被拒的 403、404）都会读一次配置（server.js 第 2606 到 2628 行、4486 到 4496 行）。配置瞬时读失败不会直接写坏文件，但会把"默认配置"呈现给浏览器——配置接口报"未配置"、激活状态归零，工作台于是引导用户"重新授权"，而重新授权走的正是那条会写盘的路。所以"读不到绝不覆盖"这道闸必须下沉到配置写入函数本身，只在启动时拦不算完成。

五、回执体积与"30 天清理"这两处，我把数字算死了

体积：按真实对象标识的形状算（obj_ 加 32 位十六进制、图层号是正整数、摘要是 64 位十六进制），**五百个对象单独就已经 79,513 字节**，还没加行结果；三百对象加三百行再加诊断尾巴是 101,814 字节。服务端请求体上限是 65,536 字节，超了直接拒收，连解析都进不去。方案自己提的"先按 500 对象压测一次"，第一次压测就会撞墙。

上一轮我报的数字是 69,993 字节，那是用估的标识长度算的，本轮按真实形状重算，更大。

清理：方案说"30 天清理时把墓碑标记和日志一起清"。但助手里**没有这个执行体**——启动时唯一的清理是学习记录的过期清理（server.js 第 8169 到 8174 行），日志目录文件里搜删除、清理、保留期，零命中。

这件事顺带暴露一个更值得处理的隐私面：日志区里躺着明文。回执派生输入文件保存了整份执行清单，里面有原文和译文正文（清单字段定义见 download/local-assistant/execution-manifest.js 第 158 行、174 行）；本地回执文件保存了设计稿在本机的绝对路径。两者都走同一条不加密、也不做权限收紧的写盘路径（server.js 第 4147 到 4158 行）——权限收紧只覆盖会话配置文件。也就是说方案的 P0-A 护不到这些文件。

六、如果认同第一节的判断，本轮真正该做的两件（都不动客户端）

1. 批次保底：结算时实扣额取"报价乘一个下限比例"和"按上报算出的值"里较大的那个；整批一行都没成的情况不受影响（仍全额退）。作用是把少报的收益从百分之百压到下限比例以下。比例该定多少归你或运营定，我不替你编数。
2. 少报要付解释成本：完成率低于阈值才允许退款，而且必须逐行给出失败原因——这条通道现成就在（回执行白名单里已经包含原因码字段）。服务端再按设备统计"低完成率批次的占比"，超常的进人工对账（现在已有人工复核这种结算形态，直接挂）。

这两条把"改客户端"从零成本自我折扣，变成"要编一套逐行失败理由、还要过异常检测"。它不是密码学意义上的保证，是抬高成本——在"用户完全控制自己电脑"这个前提下，这是能诚实做到的上限。方案里威胁模型那一节应该照这个口径改写，别写成"服务端重算所以改不了结算"。

七、重审门（第二轮版）

上一轮六条门，保留四条原文不动，替换和新增如下：

1. P1-A 从本轮剔除，另立一张单，目标重写为"防 bug 造成零交付、防夸大申报"，不再写"防白拿"；本轮先做第六节两件。
2. 身份核对的判据换对象：比本机 /ping 与客户所连站点的 /api/runtime-provenance，不比出厂清单。
3. 发布闸加两条前置：beta 通道必须同时改清单文件名解析与身份闸的取值来源，否则不许动那个开关；任何发布闸改动的验收，必须包含"测试站还能出包"这条正向断言。
4. 回执墓碑加前置：日志区明文的保留期和清理执行体先定，并明确豁免已经点名的历史样本（方案同节第 4 条要清理、第 5 条要不删，这两条现在互相打架）。
5. 配置权限那一条要写清范围："只护会话文件"，日志区明文面另立一条处置，不许在验收里含混成"配置与状态文件已收紧"。
6. "读不到绝不覆盖"必须自带离线恢复指令，明确到删哪个文件、用什么命令。

八、我上一轮说错、这轮更正的三条

1. 我说审计客户端自报的那个构建号对应 3.7.15。本轮用 git 追了一遍：它从 3.7.15 一路用到 3.7.22，到 3.7.22 升 3.7.23 那笔才换掉。"就是 3.7.15"这个精确说法收回，只能写"落在 3.7.15 到 3.7.22 之间，确切版本必须本机取一次"。方向不变：审计客户端不是 3.7.23/3.7.24，行为类结论仍要重取。
2. 我说超体积的回执会每 5 分钟无限重试。错：批次 72 小时后转终态，服务端返回"批次已结算"，这属于永久拒绝，于是本地出队删件。正确后果要这样写：活干完了，证据最多重试 72 小时，然后被**静默丢掉**，批次按未完成结算退款。这比无限重试更糟也更真实——它不吵着人来查，它自己把证据销毁了。
3. 我建议 P1-A 要有"新旧版本互相宽容一个版本周期"的窗口。本轮判死：窗口要按客户端自报版本放行，而版本号和构建号是客户端自己填的、常量还明文躺在出厂包里（要防的那个东西正好是判据的来源）。窗口只能建在"服务端已知的该设备最近一次配对版本"上，而那个值只在配对时更新，会滞后。

九、还没解决的三件事，和这轮也没看到的角落

未决：
1. 少报在现网的真实规模数不出来——需要"完成率不到百分之百、但本机确实有交付件"的批次分布，云端记不记得到这一层，未核实。
2. 干净 Windows 上那个配置目录的真实继承权限：本机测到的是当前用户加系统加管理员，另外还挂着一个沙箱组的继承只读；缺一台没装过沙箱类软件的机器的原始输出。
3. 各客户机上日志区明文的实际留存天数和体积：只读了代码，没在任何客户机上看过目录。

这轮也没做的：没上客户机、没跑安装器、没做权限故障注入、没跑类型检查和测试套件、没实测浏览器私有网络预检、没向证书机构询价、没核实生产下载页当前怎么描述"未签名"；新增两项——没实测超限回执的真机行为（只读代码加算字节），没实测那个身份接口在测试站和生产站的真实返回（只读源码）。第八节"少报"那条结论是代码路径级的，不是现网观测级的：我没有、也不该在真机上做一次少报实验，那等于自造一次计费异常。
