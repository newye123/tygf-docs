打开网站这么慢，到底卡在哪一层

慢的不是网站，是你到网站之间那段网线。请求从广州被路由到美国洛杉矶，再跨洋回源到新加坡的服务器，绕地球一圈半；这一段实测一半的包会丢，所以页面经常传一半就断。服务器本身 16 毫秒就能吐完首页。

01现场：真浏览器里的 263 秒

先看现象，再看原因。用真实浏览器打开 https://tuyigf.com/，读它自己的性能时间线：

1.46s首页 HTML 拿到首字节
这一段其实不慢
134s8 个 JS 文件同时卡住
才等到第一个字节
263s整批资源拖到 4 分 24 秒
取数时仍未完成
0domInteractive / DCL / load
页面从未真正加载完成

8 个文件同时卡住、同时恢复——它们都在第 11.4 秒发起请求，都在第 134.3 秒拿到首字节。这是 HTTP/2 队头阻塞的标准指纹：所有文件共用一条连接，只要有一个包丢了，整条连接上的所有文件一起等，直到重传成功才集体放行。配合下一层实测的 50% 丢包，这个 134 秒就是这么来的。

这对你意味着：你感觉到的「打开这么慢」，不是首页 HTML 慢（它 1.46 秒就到了），而是页面卡在 JS 上，转圈转了几分钟。网站渲染不出来，看起来就像「网站挂了」。

02先排除掉错误答案

对抗式审查第一步是证伪。三个「看起来像根因」的嫌疑人都被实测否掉了。

被排除的

  • 服务器太慢？ 服务器自己访问自己：16 毫秒吐完 98KB。
  • Cloudflare 配置错？ 新加坡服务器访问同一域名：TLS 38ms、全程 99ms——就近调度正常。
  • 页面太大？ 今天已做字体分片，14.13 MiB → 446,865 B，已解决一大半。

真正的对照

同一个 Cloudflare IP 104.21.11.101，同一时刻，不同出发点：

  • 新加坡服务器 ping：8 发 8 收，0% 丢包，2.076 毫秒
  • 你的网络 ping：12 发 6 收，50% 丢包，299 毫秒

差 144 倍延迟 + 半数丢包。问题不在 Cloudflare，不在网站，在「广州 → 边缘节点」这段路由。

03第 1 层：到边缘的链路掉一半的包（占大头）

落点CF-RAY 响应头

4 次请求全部落在 LAX（洛杉矶）。对照新加坡服务器访问同一域名，3 次全部落在 SIN（新加坡）——说明 Cloudflare 就近调度本身正常，是中国出海流量被运营商路由到了美西。

成功率20 次连测

建 TCP 连接：15 成功 / 5 失败（p50 = 234ms）。完整下载首页：14 次拿全 / 6 次只拿到一半。传输速度 1.4 – 16 KB/s。

真浏览器Chromium 实测

直接打开 https://tuyigf.com/ 报 ERR_TIMED_OUT，页面根本没渲染出来。这就是你「打开这么慢」的现场。

协议h1 / h2 各 5 次

HTTP/1.1 成功 3 次，HTTP/2 成功 0 次——高丢包下多路复用反而更糟：一个包丢，整条流都卡住。HTTP/3 未测（本机 curl 不支持）。

为什么是洛杉矶？ 这不是我们能配的。Cloudflare 官方社区确认：中国大陆出海流量走哪个节点，主要由运营商的路由决定，「很多流量被送到 LAX」是已知现象。Cloudflare 在大陆没有普通版节点，要国内节点必须 Enterprise 企业版 + 中国网络附加包 + ICP 备案。

04第 2 层：首页每次都跨洋回源——绕了两趟太平洋

首页被声明为强制动态渲染（src/app/(zh)/page.tsx:12 export const dynamic = 'force-dynamic'），因为它要在服务端读 cookie 注入登录态（:35）、合并功能开关（:38）、判断编辑态（:42）。副作用是响应头带 no-store + cf-cache-status: DYNAMIC，Cloudflare 永远不缓存，每次都回源。

源站在新加坡、边缘在洛杉矶 → 每次回源都是跨太平洋。

07优化方案（请拍一个）

A

改代码，我现在就能做（治标）

A1 让未登录访客的首页可被边缘缓存（现在读 cookie 导致永不缓存）→ 省掉每次 0.7–18 秒的跨洋回源。唯一红线：必须严格区分带/不带 cookie 的请求，否则登录态可能被缓存泄漏。
A2 字体头 max-age=0 → immutable，不再每次回源校验。
A3 合并 3 个 CSS、收紧 15 个 JS 分片，23 次往返降下来——50% 丢包下失败概率显著下降。
A4 关 HTTP/3：第三方称国内部分网络干扰 QUIC，未核实（本机 curl 不支持 h3，需真浏览器验证）。

天花板：即使 100% 命中边缘，你到洛杉矶那 50% 丢包还在。A 能去掉「白等几秒回源」，不能让网站从打不开变成秒开。

B

换网络路径（治本，要拍 + 可能有成本）

B1 Cloudflare 中国网络：国内有真实节点、几十毫秒延迟；企业版 + 中国网络附加包 + ICP 备案，贵。
B2 换/加一层国内 CDN（阿里云、腾讯云）：国内 <50ms；需 ICP 备案 + 改 DNS。
B3 优选 Cloudflare IP：低成本、可能立竿见影；但不稳——IP 会被墙、会变，要长期维护。
B4 源站从新加坡迁到香港：回源从跨洋变近距离；迁移工作量 + 确认新加坡机器其它用途。

C

先补齐测量（建议先做，再拍 B）

C1 多点位复测——我只有广州联通一个点，你在电信/移动、或让外地朋友各测一次，就能分清是全国性还是联通局部。
C2 开 Cloudflare Browser Insights（免费），拿真实用户数据代替我这台机器的样本。
C3 给 nginx 日志加耗时字段——实测确认当前日志是默认格式，没有 $request_time，无法统计真实用户平均等多久。

我的建议：A 立刻做（没风险，纯赚），同时做 C1（你换个网络测一次只要两分钟），拿到结果再拍 B。

08残留与缺口（如实）

  • 只有一个测点：广州联通。所有网络结论都基于这一台机器，样本单点，不能代表所有用户。
  • 「更慢」的时间对比待确认：没有同条件历史基线，只有 CHANGELOG 文字记录。
  • HTTP/3 未测：本机 curl 报 the installed libcurl version does not support this。响应头 alt-svc: h3=":443" 说明站点支持 h3，效果未知。
  • 没动任何生产配置：Cloudflare 规则、nginx、源站位置全部未改；A 方案的代码改动也还没做，等你拍。
  • 真浏览器取证受限：本机浏览器打开站点报 ERR_TIMED_OUT，拿不到加载瀑布图——这本身就是最直接的证据。
  • 今天的字体分片（main 分支 df93c257）已生效，5 个分片实测全部可达，共 406,956 字节，与方案数字逐位一致。
