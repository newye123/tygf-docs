## 结论（VERDICT：打回，但不是打回你的判断，是打回"我们已经有学习系统"这个说法）

你的判断**基本成立**，但根因和你猜的不是一回事，而且有两处要先更正：

1. **上传链路已经通了，今天还在写。** 测试站库里现在有 16 条学习信号，其中 9 条是 `manifest_bound`（这是 10-07 那笔修断链的补丁才有的状态），落在 10-21 15:54 到 10-22 08:36——也就是**今天早上还在落库**。所以"信号传不上去"这个说法已经过期，谁再说它断在上传，是旧账。
2. **真正没跑起来的是"学"这一半，而且是三处结构性缺口，不是调度忘了开。** 采集侧把用户动作收上来了，但它收的是"用户点了哪个按钮"，**没有收"用户最终把译文定成什么"**。聚合器算建议时唯一的目标值就是这个最终选择——所以它现在**一条候选规则都写不出来**。库里候选规则 0 行、规则版本 0 行、规则部署 0 行，三个 0 不是运气，是必然。

一句话讲清这件事：**这台机器现在只做"记录"，还没做"学习"；而记录的东西不足以学出任何东西。**

## 已证实的缺陷（8 条，按重要度）

### F-1 采集端不带"最终选择"，聚合端遇到空最终选择直接跳过 —— 学习闭环断在这里（Important）

- 聚合器用 `finalCode`（用户最终选定的那个码/那条译文）作为唯一建议目标：`src/lib/learning/candidate-aggregator.ts:209` 只在 `row.finalCode` 非空时才计数，`:262` 把桶内最高频 `finalCode` 当作建议内容。
- 跑批脚本更硬：`scripts/aggregate-learning-candidates.mjs:120` 写的是 `if (!recommendation.finalCode) continue` —— **最终选择为空，这一组直接不写库**。
- 而客户端五个采集点一个都不带它：`src/components/workbench/workbench-view.tsx:1356`（排除图层）、`:1385`（一键排除缺译）、`:2768`（确认原文绑定）、`:3705`（应用智能检测建议），传的都是 `actionCode` + `contextFeatures`；`src/lib/workbench/learning-signal-client.ts:96` 是 `finalCode: input.finalCode ?? null`，即**参数存在但没人填**。
- 实测收口：我在全 `src/` 搜 `finalCode`，`src/components/**` 命中 **0 处**（所有命中都在 lib/learning 内部和 API 路由里）；测试站库 16 条信号的 `finalCode` **16/16 全空**。

后果：不管聚合跑多少次、样本攒到多少条，`LearningCandidateRule` 恒为 0。这条不修，其他都是白做。

### F-2 聚合脚本没有任何调度器 —— 就算 F-1 修好也没人跑（Important）

- 唯一的入口是 `package.json:146` 的 `test:learning-aggregate`，它把 `--dry-run` **写死在脚本命令里**，天生不写库。
- `--apply` 这条路径在仓库里没有任何调用者：全仓搜 `aggregate-learning-candidates` 只命中 package.json、历史文档和台账。
- 部署机实读：`systemctl list-timers --all` 列出的 tygf 单元里，学习相关的只有清理（`tygf-test-learning-cleanup.timer` 每 12h、`tygf-learning-cleanup.timer`），**没有任何聚合跑批单元**。清理 timer 是干"到期删除"的，不是干"学"的。

后果：信号在服务库里躺到 180 天保留期满被删掉，期间没有任何一次聚合。这是"整套系统没跑起来"最直接的那一刀。

### F-3 学习成果没有下游 —— 规则即使生出来也不进产品（Important）

- 除管理端 API 外，全仓没有任何代码读规则部署表：搜 `LearningRuleDeployment` 在非 admin 路径下命中 **0 处**。
- 两个本应承担"规则解析/隐私削减"的模块是孤岛：按引用者计数实测 `src/lib/learning/rule-resolver.ts` 与 `src/lib/learning/privacy-reducer.ts` 在 `src/` 内的 **importer = 0**。
- 给用户下发学习成果的那个接口 `/api/workbench/learning/rule-pack/status` 在前端**没有任何调用者**（全 src 搜 `rule-pack` 只命中一个版本常量 `src/lib/learning/rule-version.ts:7`）。

要分清两件事：**"不自动改写生产结果"是 Owner 定的红线**（`src/lib/learning/feature-flags.ts:46-48` 硬编码 false，这是设计，不算缺陷）；但"把学习成果告诉用户、给用户看"这条也没有接线——这一半是真缺口。

### F-4 所谓"每个用户单独的学习系统"：服务端按人分了，界面上一个人都看不到（Important）

- 分组键确实支持按人：`src/lib/learning/candidate-aggregator.ts:160` 对 personal 作用域返回 `user:${betaUserId}`，四个作用域里 `personal` 排在第一位（`:310`）。
- 但用户维度数据的唯一读者是**管理端**：`src/app/api/admin/learning/users/[id]/route.ts:24-26` 和 `:67-69`（读个人排版偏好档案）。
- 用户侧组件里跟学习有关的只有两个静默采集点。搜 `src/components/` 下含 `learning` 的文件，用户可见的是 `execute-step.tsx` 与 `workbench-view.tsx`，两者都只是"悄悄上报"，**没有任何一处告诉用户"我们学到了你什么、对你有什么用"**。
- 同意开关也不给用户：`src/app/api/workbench/learning/consent/route.ts:5` 明写"POST 不再提供：用户侧不允许自助关闭"。

后果：现在的事实是"我们在按人收集"，而不是"每个人有一套为自己学的系统"。这两句话对外不能混着讲。

### F-5 同意门把 34/38 个账号永久关在外面，而且用户自己开不了（Important）

- 门是 fail-closed：`src/lib/learning/consent-gate.ts:10-14` 无记录即拒绝，写库路由在事务里二次复核（`src/app/api/workbench/learning/signals/route.ts:67-69`），拒绝时返 403。
