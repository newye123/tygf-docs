二、它到底怎么"走一遍官网"

capture --help 的全部参数：URL、输出目录、--skip-assets、--skip-vision、--max-screenshots、--timeout、--capture-budget、--json，以及视频下载模式的 --video/--index/--video-url/--list〔A〕。

没有 cookie、登录、点击、输入、等待选择器、脚本注入这一类的任何参数。所以：

  • 只能抓公开页面；
  • 滚动过程逐屏截图（scroll-000.png…，相邻约 30% 重叠）；
  • full-page.png 是滚动结束后把 sticky/fixed 转成 static 再拍的整页 1x 大图（页面高于 16384 px 时跳过）〔B，references/film.md〕；
  • 官方文档自己写明：用 HTML 重建页面会偏离真实布局；要展示站点原样就用它的截图，只重建会动的那部分〔B〕。
所以"然后剪辑"要换个理解：不是拖着剪一段录像，而是用截下来的真实像素 + HTML/CSS/GSAP 在时间轴上重新编排，最后逐帧渲成 MP4。镜头里的"点击""输入"要靠动画演出来——这正是我们现有 animatic 已经在做的事。

四、对我们意味着什么

能做不能做
① 官网真实像素进片：第 1 镜右侧那张"图层/译文表"目前是自绘示意，capture 能直接给真实截图，更经得起"这是不是真的"。
② 设计有据可依：品牌色、可变字体 100–900、板块数、CTA 文案一次抓全。
③ 你能自己拖时间轴：preview 起本地 Studio（3002）。		 ① 产品内真实操作演示：登录后的执行界面抓不到（与既有硬约束一致：产品内执行入口要云端票据、真机跑批要 Owner 登录）。
② 录屏式的点击过程：它没有录制交互的能力，镜头里的"点击"只能靠动画演。
一个必须提前说的坑：HyperFrames 的模板和文档默认从 cdn.jsdelivr.net 加载 GSAP（CLI 包内 23 处命中，dist/docs/gsap.md:8）〔A〕。国内网络下这会卡住或渲出没有动画的片。我们现有渲染器不依赖外网（纯 CSS + window.seek），这是它当下的真实优势；要用 HyperFrames 就得先把 GSAP 本地化。

五、该不该换现有的渲染链

建议：不整体迁移，做三件局部接入。

选项代价收益判断
整体迁到 HyperFrames现有 11 镜分镜要改写进它的契约（data-start/data-duration、禁 Date.now()、字体必须本地 @font-face、动画走 GSAP 时间轴）+ GSAP 本地化 + 多一层 CLI 依赖5 进程渲染、lint/check/snapshot/inspect 审片工具链、可拖 Studio、官网一键抓暂不迁
只借 capture 抓素材很低（一条命令，约 1 分钟）官网真实截图 + token + 文案做
借 snapshot 思路补审片低逐帧快照复核，比肉眼抽帧稳做
9:16 拆条时用 preview 当时间轴低你能直接拖可做

唯一值得整体迁移的触发条件：你希望"自己拖时间轴改片"变成常态，而不是每次让我改 HTML 再重渲。

六、覆盖缺口（未核实，别当结论引用）

· HyperFrames 桌面 App（hyperframes open）在 Windows 上能不能装：未核实。实测可用的是浏览器 Studio。
· 只抓了 tuyigf.com 一个站，SPA / 超长页 / 登录页的边界未验（后者按参数判断不可能）。
· 渲染对比用的是 --quality draft，没和我们的 CRF 19 做同档对比。
· capture 的 AI 图像描述未开（无 key 情况下跑通），所以"资产语义描述"这一项没验。
· 没验 preview Studio 的实际交互手感（时间轴拖动、元素选中），只确认命令与端口存在。
· 第三方 7 步 skill 只读了 SKILL.md 与 step-1，其余 6 步未逐篇读。
