# 灰度与生产隔离对抗式审查（初版方案纠偏）

- 日期：2026-10-14
- 基线：worktrees/develop @ 756978c，只读实测，未改任何文件、未碰两站（补正 2026-10-15 22:40：基线/指针更正见文末「补正」节；本句为当日历史基线，不回改）
- 审查对象：本会话初版灰度方案（Unleash + OpenFeature + PostgreSQL + Sentry + WebSocket 全栈）
- 结论一句话：初版 P0 推翻一半。Unleash 全栈是重复建设；真风险不在流量分发，在「配置随代码发布」与「实时处理缺地基」。

## 一、判定

初版方案方向对（灰度=应用层特性开关+用户分群），但选型错了。本仓库已有一条完整的 DB 可配置开关链路——默认形状、运营台覆盖、Owner 鉴权、审计日志、客户端 hook 全部现成。在它旁边再部署一套 Unleash，等于给同一个事实建两本账，是本仓库 #137 双账本病的重演。

对抗审查还挖出一个初版完全没看到的头号漏洞：灰度默认值写死在 src/config/featureFlags.ts 里，随代码部署。哪天有人把新旗标默认值误设为 true，生产站下次部署那一刻灰度直接归零——全量用户一起进。这才是「不影响生产用户」真正的命门，不是流量分发问题。

## 二、五路对抗核对（全部实测 file:line）

**路一 · 重复建设（推翻初版选型）**。既有链路四件套：默认形状与二十余个开关在 src/config/featureFlags.ts:6-62（支付族默认 false）；DB 合并与防注入在 src/lib/server/feature-flags-store.ts:27-41（SiteSetting key=featureFlagsV1，sanitizeAgainst 按默认形状清洗，禁任意 JSON 注入）；运营台 API 在 src/app/api/admin/feature-flags/route.ts:18,24 requireOwnerDb 与 :45,57,67 writeAuditLog（鉴权+审计已有，初版「需补审计」不成立）；客户端 hook 在 src/lib/workbench/use-feature-flags.ts:27-41。裁决：不装 Unleash，缺的只有分群和 TTL，不是缺平台。

**路二 · 版本闸先例（推翻硬闸写法）**。develop AI_MEMORY/ISSUES.md:1152 实录：测试站升 3.6.15 后，已激活的 3.6.14 用户被版本门槛一刀切，全流程卡死；当时结论「canary 空白名单=放行」与版本门槛矛盾。初版「绑定 minAssistantVersion，旧版自动落回」重演此坑。修正：旗标对旧版=功能隐藏（软落回旧流程），版本门槛只拦「用户显式开新功能」，永不拦既有流程。

**路三 · 杀开关时延（推翻「秒级」话术）**。use-feature-flags.ts:8-12 是模块级 cached，永不失效——今天关旗标只对「刷新过页面」的会话生效。且 in-flight PS 执行是分钟级，旗标只能断新进入。修正为验收「最坏 30s」：hook 加 30s TTL + visibilitychange 重取。

**路四 · 实时处理地基（推翻监控重工业）**。地基是坏的：#143 源站 :80 对公网开放、cf-connecting-ip 可伪造（develop AI_MEMORY/ISSUES.md:131；#138 为同账 :179）→ #138 限流不敢开；#120 access.log 无 $host 与 $request_time → 按站归因不可能；记忆纪律「零回看零基线」→「错误率<0.1%」无基线可比。Sentry + WebSocket + Grafana 全套在这个地基上是浪费。修正：可观测降级为「查得到」——复用执行 evidence 结构化落库，运营台加只读查询；Sentry 推迟，将来接必须复用 FORBIDDEN_LOCAL_FIELD_NAMES 脱敏先例（learning-evidence.js:33），否则客户素材路径外泄。

**路五 · 消费面错位（初版落点是摆设）**。photoshop-step.tsx:33,202 用的是静态 featureFlags import——运营台动态覆盖根本到不了这个组件。动态 hook 消费方实测只有 4 个文件：execute-step、workbench-view、settings-panel、pack/page。字体功能恰好要挂 photoshop-step，不改消费方式，开关做了也是摆设。

## 三、上轮没说、这轮必须说的三点

1. 分群评估必须在服务端。Unleash Proxy（初版推荐的）和任何「把白名单下发给客户端自己判断」的方案，都会把全部白名单用户 ID 泄漏给每个浏览器。正确形态：服务端 isFeatureEnabledForUser(flag, userId)，客户端只拿「对我开没开」这一个布尔。这也是不用 Unleash 的又一理由。
2. 10% 随机放量在内测基数下是噪音。内测是十位数用户（量级，待确认），10% 只有 2-5 人，统计无意义，只制造偶发不可复现的客服负担。改为显式名单 + 阶段扩名单。
3. 审计不用新建。运营台开关已有 requireOwnerDb + writeAuditLog（route.ts:4,5,18,45）。新分群管理沿用同一 route 模式，零新面。

## 四、修正后方案 P0′（约 1 天，全部在既有链路上）

1. featureFlags 形状加 typographyCustomizationEnabled: false 与 typographyBetaUserIds: string[]，默认必须 false。落点 featureFlags.ts:6-62。零 DB 迁移（避开 #129 迁移门）；admin API route.ts:60-68 的 flags 字段路径原样可用。
2. 服务端分群判定 isFeatureEnabledForUser(flag, userId)，约 40 行：全局开关 AND 用户在名单（名单空=仅 Owner/测试账号）。新文件 src/lib/server/feature-flag-gating.ts。
3. photoshop-step 改动态消费：SSR 时调第 2 条，props 下发。静态 import 留给官网板块。
4. 杀开关修真：use-feature-flags.ts:8 加 30s TTL + visibilitychange 重取。验收话术「最坏 30s」。
5. 助手端本轮不动（字体能力若为纯服务端计算）。确需助手感知时走既有 /config（download/local-assistant/server.js:4372-4386）加字段，按助手版本纪律单独立项——那是另一个任务书。
6. 可观测降级为「查得到」：复用执行 evidence 结构化落库，运营台加只读「灰度用户执行结果」查询。
7. Unleash/OpenFeature 推迟。复议触发条件写死：旗标超过 8 个，或需要 A/B 百分比分桶，或出现同部署多环境。在此之前不预付成本。

## 五、验收（P0′）

1. 生产站不部署新默认值时行为逐字节不变。
2. 测试站 Owner 加进名单 → 字体面板出现。
3. 换一个不在名单的账号 → 全旧流程。
4. 运营台关总开关 → 所有会话最坏 30s 内面板消失。
5. 触及 execute-step 消费链时跑 npm run test:batch-row-contract 与 test:trust-chain，必须绿。

## 六、开源候选裁决（推迟备查）

- Unleash：Node SDK 成熟、分群策略全、10s Proxy 热刷——但需要 PostgreSQL，本项目 SQLite 单机不匹配。不装。
- GoFeatureFlag：Go 单二进制、无 DB、OpenFeature 兼容——若将来复议，首选。
- Flipt：Go 单二进制、SQLite 默认。备选。
- OpenFeature：CNCF 标准规范，Provider 可换，长期方向。
- Argo Rollouts / Flagger / Istio：K8s 专属，本项目无 K8s，永不适用。

## 七、「不影响生产用户」的三条风险排序

1. 配置随代码发布（部署即生效）。铁律：新旗标默认 false；生产开启必须是运营台的独立动作（SiteSetting 覆盖），永不随代码部署生效。
2. 灰度用户拿到坏输出。字体缺失静默替换是 #66 家族已实证机制（develop AI_MEMORY/ISSUES.md:641-648）。字体灰度必须捆绑 readback/coverage 门禁，否则明知有坑还放人进去。
3. 「实时处理生产问题」缺地基。#143 → #138 → #120 一串前置没修；源站加固不落地，任何「实时」都是口号。源站加固比灰度系统本身更优先。

## 八、治理红线（接续执行者必读）

生产站与测试站是两套部署+两套独立 SQLite，SiteSetting 互不可见——流量层面「不影响生产」天然成立，别再为此加网络层方案。生产部署需 Owner 单点授权（O1 生产链 pending），本任务不动生产。支付 flag 保持 false。助手行为变更必须走版本纪律，P0′ 第 5 条明确不动助手。跨文件引用写路径:行号指针，不抄原文。CURRENT_STATUS.md 单写者不改。
