灰度与生产隔离对抗式审查

对本会话初版灰度方案（Unleash + OpenFeature + PostgreSQL + Sentry + WebSocket 全栈）的五路对抗核验。基线 develop@756978c，全程只读，未改任何文件、未碰两站。

五路并行 初版 P0 推翻一半 修正方案 P0′ 约 1 天 未部署、未提交

01判定

结论

初版方向对——灰度=应用层特性开关+用户分群；选型错了——本仓库已有一条完整的 DB 可配置开关链路，再部署一套 Unleash 等于给同一个事实建两本账（#137 双账本病的重演）。

保留的

  • 白名单分群 + 阶段扩名单：替代无意义的 10% 随机放量（内测十位数基数下 10% 只有 2-5 人）。
  • 版本闸方向：但必须改写——ISSUES.md:1152 实录证明硬闸一刀切会卡死已激活用户，改为「旗标对旧版=功能隐藏」的软落回。
  • 杀开关 + 可观测：保留方向，落点改为既有 hook 加 TTL + evidence 落库查询，不引监控重工业。

推翻的

  • Unleash + PG + OpenFeature 全栈：重复建设。既有链路四件套全部实测存在（详见 §02）。
  • 「秒级杀开关」话术：现有 hook 模块级缓存永不失效，in-flight PS 执行是分钟级，最多承诺「最坏 30s」。
  • Sentry + WebSocket + Grafana：地基是坏的（#143 > #138 > #120 一串前置未修），先加固源站再谈实时。
初版漏掉的头号漏洞

配置随代码发布：灰度默认值写死在 src/config/featureFlags.ts，随部署上线。默认值误设 true → 生产站下次部署那一刻灰度直接归零、全量用户一起进。铁律：新旗标默认 false；生产开启必须是运营台独立动作（SiteSetting 覆盖），永不随代码部署生效。这才是「不影响生产用户」真正的命门——不是流量分发问题。

推翻选型 路一 · 重复建设 featureFlags.ts:6-62 / feature-flags-store.ts:27-41 / route.ts:18,24,45 / use-feature-flags.ts:27-41

既有链路四件套：默认形状与二十余开关（支付族默认 false）；SiteSetting key=featureFlagsV1 合并 + sanitizeAgainst 防注入；运营台 API requireOwnerDb + writeAuditLog（鉴权+审计已有，初版「需补审计」不成立）；客户端 hook。裁决：不装 Unleash——缺的只有分群和 TTL，不是缺平台。

推翻写法 路二 · 版本闸先例 AI_MEMORY/ISSUES.md:1152

实录：测试站升 3.6.15 后，已激活的 3.6.14 用户被版本门槛一刀切，全流程卡死；当时结论「canary 空白名单=放行」与版本门槛矛盾。初版 minAssistantVersion 硬闸重演此坑。修正：旗标对旧版=功能隐藏（软落回），版本门槛只拦「显式开新功能」，永不拦既有流程。

推翻话术 路三 · 杀开关时延 use-feature-flags.ts:8-12

模块级 cached 永不失效——今天关旗标只对「刷新过页面」的会话生效；in-flight PS 执行分钟级，旗标只断新进入。修正：hook 加 30s TTL + visibilitychange 重取，验收话术「最坏 30s」。

推翻重工业 路四 · 实时处理地基 ISSUES.md:179（#138）前置 #143；#120

#143 源站 :80 对公网开放、cf-connecting-ip 可伪造 → #138 限流不敢开；#120 access.log 无 $host 与 $request_time → 按站归因不可能；「零回看零基线」→「错误率<0.1%」无基线可比。修正：可观测降级为「查得到」——复用执行 evidence 落库 + 运营台只读查询；Sentry 接时必须复用 FORBIDDEN_LOCAL_FIELD_NAMES 脱敏先例（learning-evidence.js:33）。

推翻落点 路五 · 消费面错位 photoshop-step.tsx:33,202

用的是静态 featureFlags import——运营台动态覆盖到不了这个组件。动态 hook 消费方实测仅 4 文件：execute-step、workbench-view、settings-panel、pack/page。字体功能恰好要挂 photoshop-step，不改消费方式开关就是摆设。

03上轮没说、这轮必须说的三点

  • 分群评估必须在服务端。Unleash Proxy（初版推荐）与任何「白名单下发客户端自判」的方案，都会把全部白名单用户 ID 泄漏给每个浏览器。正确形态：服务端 isFeatureEnabledForUser(flag, userId)，客户端只拿「对我开没开」一个布尔。这也是不用 Unleash 的又一理由。
  • 10% 随机放量在内测基数下是噪音。内测十位数用户（量级，待确认），10% 只有 2-5 人，统计无意义，只制造偶发不可复现的客服负担。改为显式名单 + 阶段扩名单。
  • 审计不用新建。运营台开关已有 requireOwnerDb + writeAuditLog（route.ts:4,5,18,45）。新分群管理沿用同一 route 模式，零新面。

05验收（P0′）

07「不影响生产用户」三条风险排序

  • 配置随代码发布（部署即生效）——头号命门。新旗标默认 false；生产开启必须是运营台独立动作。
  • 灰度用户拿到坏输出——字体缺失静默替换是 #66 家族已实证机制（ISSUES.md:641-648）。字体灰度必须捆绑 readback/coverage 门禁，否则明知有坑还放人进去。
  • 「实时处理生产问题」缺地基——#143 → #138 → #120 一串前置未修；源站加固不落地，任何「实时」都是口号。源站加固比灰度系统本身更优先。

08最后一句

这套灰度不需要引入任何新平台——缺的只是既有开关链上的三块补丁：分群、TTL、消费面。「不影响生产」天然成立在双站双库架构里，真正的命门是默认值随代码发布，和源站还没加固就谈实时。
