01判定

结论

这份文档不是那种「看着很实、其实站不住」的产物——它不吹。
但它把半截证据当成了已完成的证明，而那个「半截」恰好是唯一决定成败的一步。

可以立刻用的

  • 读侧解析：57 份真实客户件、3525 个文字图层、不变量零违反。这一侧完全不依赖 Photoshop，直接解掉「扫描 PSD 总扫不到」。
  • 三条硬不变量：以 EngineData 的 /Text 为基准量，而非描述符 Txt 。这是全文最值钱的部分。
  • 字体规则：PS 按文字里的脚本切分样式 run 再逐脚本挑字体；原字体渲染不了目标语言时才补；文件里写的字体名不等于本机装了那个字体。

不能当写入规范用的

  • 「增量恒为偶数」：漏了 XMP 的 UTF-8 奇数增量。作者自己的代码里已写好补丁，文档没写。本件恰好是偶数，是运气不是性质。
  • 「签名必须落在 4 的倍数上」：那是长度补齐的结果，不是位置公理。照此实现会在别的文件上补错对齐。
  • 「7 份副本跨 2 种编码」：实为 3 类（UTF-8 两处、UTF-16BE 四处、遗留字段一类）。

03四处错数

差错不是数据臆造，而是比对口径与解码方式错误留下的产物：数字看起来有零有整，却复现不出文档自己描述的那个口径。

为什么第一条最重

「200 层有 140 层不一致」是全文唯一支撑「Photoshop 自己不维护 Pascal 名字段一致性」这一结论的量化证据。方向没错（不一致确实来自 31 字节截断），但数字错了近九倍，任何照它复测的人都会得到不同结果，结论将失去自称的数据支撑。

另有一处两路撞车：格式论断路据单层样本判日文层的 Pascal 名是 Shift-JIS，数字核验路据 140 个名字判全件单一 GBK。那一层的名字是纯假名串，而 GBK 与 Shift-JIS 在假名区码位重叠，单层样本区分不了两种假说。按现有证据偏后者。

04三处结构性打回

§01

产品结论的后半句「打开 + 保存就能当渲染器」被实跑推翻

证伪

本栏当日下午更正过一次，这里把更正本身也记下。本栏原判「§01 那句『PS 画布显示的是文件里存的图层像素，不是从描述符实时渲染』被 Adobe 官方帮助文档证伪」，并据此推出「PS 一打开就会重渲染，画布本就该显示新文字」。用 PS 2021 实跑后事实相反：机制句是对的，原判是纸面推断压过了实测，已撤回。

实测三步：① 打开产物导出画布 ＝ 源文英文；② 从 PS 里另存副本、重新打开、再导出 ＝ 仍是英文；③ 对每个文字层做一次非破坏性重写（contents = contents，55/55）后再导出 ＝ 日文，且版式与客户真产物完全一致。⇒ PS 打开时用文件里存的图层像素，不按描述符重渲染；保存也不触发；必须真的碰到那一层，它才重画那一层。

⇒ 所以 §01 的产品结论要劈成两半看：「把 PS 从流水线里拿掉」走不通——成立；「把 PS 降级成无脑渲染器，只需打开 + 保存」——不成立。要刷新像素就得逐层触碰，助手侧那一步省不掉。实测记录见 tmp/psb5857/判读清单-JP-第3轮-结果.md。

§08

封面数字盖住了最大的洞

需标注

封面写着「七项验证全绿」。七项逐项复算确实全绿——但七项全部是机器自检，没有一项在 Photoshop 里看过画布或换行。其中「ag-psd 独立回读」一项是真的，强度边界也写得准确（它排除的是「我的读和写犯了同一个错」）；问题在于它不能排除「我对 PS 渲染行为的理解错了」，而实跑证明这恰恰是最要命的一条：文档里「只需打开 + 保存就能让 PS 当渲染器」那半句是错的，七项自检没有一项能发现。正文其他节没有守住同样的限定。

§09

缺了最关键的那一条

缺项

「已知缺口」列了六条，唯独没有「PS 打开后画布是否正确」。它列的是「保存再打开的往返」——而「往返」预设了第一次打开就是对的。这一条应当排在第一位。

归因错的另一处

§03 把「某些文本图层需要更新后才能用于基于矢量的输出」这条提示，归因到「改了 Txt2 文字却没改它的 run 数组」。该提示的已文档化触发条件是字体版本不一致、字体缺失、旧版文字引擎——与 run 数组无关。而真正对应「文字数据自相矛盾」的是另一条提示（「发生错误导致无法读取此文档中的某些文字图层，所以已将这些文字图层栅格化」）。文档把两条不同的 PS 提示混为一谈，接手的人会照错误方向排查，而真因恰好是 §06 自己在讲的主题，两节没有接上。

05Photoshop 真机观测史

这条路线的 PS 端观测只发生过两次，两次看到的都是失败；两次的修复都没有再进过 PS。

第 1 轮失败

用 PS 打开产物：画布全是源文英文。定位到 EngineData 里有两个 /RunLengthArray——只重算了段落 run、留着样式 run 原值，求和与文字长度不符，PS 不报错、不弹窗，静默丢弃新文字。

修复：样式 run 按比例重分配、用最大余数法保证求和精确、元素个数按源件保留。

第 2 轮部分成功

画布显示日文了（样式 run 那次修复是对的）。但 PS 弹「已将这些文字图层栅格化」，被栅格化的层退回显示文件里存的旧像素，表象是「有些文字没替换成功」。中招 3 层，全是减行的层。由此挖出第三条硬不变量。

修复：段落样式对象数与段落 run 元素数、按行切开的段数三者相等。同层内所有段落样式对象实测完全相同，增删即复制同一个对象。

字体版（当前最好的产物）从未进过 PS

七项机器验证全绿，含「含假名的层不再引用纯拉丁字体 39/39」。但这份产物没有任何一次人工判读记录——第三条不变量的修复与字体规则，都还没有在画布上被看见过。

三轮判读清单

等长替换实验的判读清单：五个记录栏全空。变长改写第 1 轮清单：七个记录栏全空。第 2 轮清单：两个文件各三栏，全空。唯一的 PS 端结论是靠第 2 轮清单正文里一句回述反推出来的（「图层名、双击进文字编辑这两项第 1 轮就是对的」）。这条路线的真机证据，目前只活在对话记录里。

08顺带查明，不影响判定

  • 2 GiB 硬墙。最大的真实客户件读不进来——Node 的 Buffer 上限，与堆大小无关。而生产服务器是 2 核 2G，所以读侧能力也只能跑在用户机器上，上不了服务器。
  • Txt 可能是陈旧值。实测有 4 个图层的 Txt 是 226 字的模板占位文本，而 EngineData 的 /Text 是空文字。扫描必须以 EngineData 为准；目前的改写器信 Txt ，靠 run 比对告警兜底。
  • 安全声明有一条不成立。文档称「源件每次操作后用 md5 复核」——三个脚本里没有任何 md5 或哈希实现，七项验证只校验产物、从不重读源件。md5 只出现在人工判读记录里。这是把「人工事后做过一次」写成了「工具的安全设计」。
  • 版本漂移。正式依赖锁定的第三方解析库是 31.0.2，实验目录装的是 31.0.3。
  • 泄漏面已核。报告本身干净（无绝对路径、无凭据、无人名）。敏感内容（真实译文、客户与译者姓名、绝对路径、客户素材）全部落在被 gitignore 覆盖的临时目录内，未入库。
