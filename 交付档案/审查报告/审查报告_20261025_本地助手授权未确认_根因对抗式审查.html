01先排除掉错误答案

屏幕上是两句话打架：「本地助手已连接」和「当前授权尚未确认」。先证明助手本身没问题。

助手侧：健康

  • /ping 返回 200，版本 3.7.27，activationStatus=active，有效期到 11-03。
  • 测试站授权槽：安装号 3d1550e7，有效期到 11-08，bindings=3。
  • 所以 10-25 上午补的配对并没有白做——授权数据是对的。

浏览器侧：请求发不出去

  • 同一浏览器、同一请求，只多一个 x-tygf-install-id 头，就从「成功」变成 TypeError: Failed to fetch。
  • 助手日志里查不到 Owner 点浏览器的那几次——请求在浏览器里就被挡了。
  • 能通的只有 GET /ping：简单请求，不带自定义头，不需要预检。

02证据链（可复跑）

根因server.js:2686

修复前助手的放行头只有 Content-Type, x-tygf-ticket。浏览器发请求前先问一句「我能带 x-tygf-install-id 吗」，助手回「不行」，于是请求根本没发出去。

引入点6c15cc4c · 2026-10-24 20:06

3.7.25「多绑定」给每个助手请求都加了 x-tygf-install-id（local-assistant-client.ts:408-411，在 :279 无条件注入），但那笔提交没有同步 CORS 放行表。

浏览器对照同机 · 同请求 · 只差一个头

A（不带该头）→ 成功 HTTP 403，可读，121 ms。B / C（带上该头）→ 浏览器拒绝，TypeError: Failed to fetch，31 / 35 ms。复跑两次都一样。

受控 mock排除探针失灵

两个本地 mock，唯一差别就是放行表里有没有这个头：不含 → 浏览器拒绝；含 → HTTP 200 且服务端确认 sawInstallId=true。

03为什么「一直修不好」

四个环扣在一起，任何单环修复都会被下一环带回原点。

验证通道选错了

所有「已修好」的终验都走 Node / curl 直连。Node 没有 CORS，浏览器才有。唯一会失败的通道，恰好是唯一没被用来验收的通道。

10-25 10:1x 的终验 authorized:true, bindings:3 就是脚本验的（TASK_LOG:63）。

界面把「连不上」说成「授权失效」

ASSISTANT_UNREACHABLE 不在网络类码表里，横幅于是走第三分支，显示「授权尚未确认」并给出「重新授权」按钮——而这条路走的是同一个被拦的请求。

assistant-setup-banner.tsx:157-165 · error-messages.ts:263-271

按钮本身也不是真配对

横幅上的「重新授权 / 重新连接」绑的是 checkAssistant()（只重查、不配对）。10-25 10:1x 已登记为「假按钮 / C4 未修」。

assistant-setup-banner.tsx:240 · :256 · TASK_LOG:62

门禁不覆盖 CORS

现有门只比对 prepare 载荷字段、只对 isAllowedOrigin 做源码正则；没有任何门检查「客户端发什么头 / 助手允什么头」。所以 3.7.25 加头、CORS 没跟，全套测试照样绿。

04影响面

从 3.7.25 起，任何已激活的浏览器都用不了工作台里需要助手的动作：选文件夹、预扫描、准备、执行、配对、诊断、排障上传。只有 GET /ping 能通——正好是截图里「已连接但什么都做不了」的样子。

容易误判

未激活、或本地没有安装号的浏览器不受影响。这也是为什么有些自测看起来是正常的——它不是同一个通道。
