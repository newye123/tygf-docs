## §4 改造后的方案：三层运营台，全部扩现有 `/admin`，不新建站点

**先改问法**：把"每个访客从哪来"改成"**流量按来源／内容分组的日趋势** ＋ **注册用户从头到尾的真实旅程**"。前者零合规成本，后者是我们独有的优势数据（已登录、已告知、已有 16 个事件）。

### 第一层 · 流量总览（今天就能做，零合规成本，数据已在手）

在 `admin-sidebar-data.ts:36-70` 加一项 owner-only 只读板，读我今天已经落盘的 `AI_MEMORY/traffic-daily.jsonl`（一天一行：访客／浏览／请求）＋ 按月去重快照。展示：日／周／月访客趋势、国家分布 Top、入口页 Top、请求/浏览比（当噪声看）。

- **为什么合规干净**：全部是 zone 级聚合计数，不落 IP、不落 UA、不落日志原文（沿用 `scripts/site-traffic-daily.mjs:9-11` 的既有纪律）；匿名化聚合后不再是个人信息 ⇒ R-3 的 (a)(b)(c) 三项义务都不触发。
- **顺手修 R-7**：把 `stats/route.ts` 的"取最近 1000 条再按日聚合"改成按日 `groupBy`，趋势才是真的。
- 工作量：一个下午（判例件 :128 原话就是"约一个下午的量，不是新站"）。

### 第二层 · 来源与着陆（本周，依赖已授权未执行的日志改动）

来源站这一维**不靠 CF，靠我们自己的服务器日志**——nginx 里本来就有 Referer。档二那份改动（`deploy/nginx/tygf-ops-logging.conf` ＋ `apply-ops-logging.sh`，今日已备好并带自检门）落地后，写一个**按日聚合**的日志分析器，产出：来源站排行、着陆页排行、各来源的会话页数分布、**停留时长估算**（同一客户端在 30 分钟窗口内的首末请求时间差）。

- **口径必须钉死**：停留时长是"估算"，误差来自单页跳出（无第二次请求 ⇒ 记 0）与长轮询接口；要准值得上浏览器埋点（第三层）。
- **合规**：只做聚合、不落个体轨迹 ⇒ 不触发 R-3。一旦要"看某一个人的序列"，立刻触发，见 §5 的代价清单。
- 这一层同时回答 Owner 最关心的"**知乎／小红书到底有没有带来人**"——不需要付费、不需要新处理方。

### 第三层 · 用户旅程（真价值，合规干净，建议优先）

补三个漏斗事件（`signup_submitted`／`email_verified`／`logged_in`）进 `funnel-event-contract.ts:9-14` 白名单并接 `auth/*` 调用点，就把"**从注册到首次跑通到付费**"串成一条完整序列——按人、按设备、带 `runId`，且对象是**已登录已告知的用户**，不碰匿名访客那条红线。

板子上给四个数：注册→激活→首跑→付费的逐级转化与流失率；各步的中位耗时；卡死在哪一步最多（这个我们已经有 `NEVER_DISPATCHED` 等终态码可接）；分渠道的转化差（等第二层的来源接上后自动出）。

**为什么这条最值钱**：匿名访客告诉你"有人来过"，这条告诉你"**谁真的用起来了、在哪一步放弃**"。你要决定做什么功能，靠的是后者。

### 第四层 · 关键词（唯一可行形态，且我们已经具备条件）

搜索词**只能按词聚合、不能按人关联**。可用来源是 **Google Search Console**——我们的域名已用 DNS 方式验证过（sc-domain），接它的 API 就能拿：展示次数、点击、平均排名、查询词列表，按日趋势。百度侧同形态（站长平台），现行回传口径未核实（U-3）。

产出形态：一张"哪些词带来曝光／点击"的表 ＋ 与入口页对照。**明确标注：无法回答"某个人搜了什么"，这是行业事实（R-1），不是我们的缺陷。**

### 明确不做

按个体拼接匿名访客的来源＋关键词＋停留＋页面序列；给未注册访客打指纹或写 cookie 做画像；新建第二个带口令门的公网面（R-2）。

## §5 更正（推翻我自己此前两句说法）

1. **原说法**（今日 13:2x 交付件）："跳失率、停留时长、**来源渠道**一个都没有。"
   **反证**：来源渠道并非"没有源"——自有 nginx 日志一直记着 `$http_referer`（`deploy/nginx/security-logging.patch.md` 还专门警告它是第二泄漏面），CF adaptive 表也有该字段（只是本 zone 无权限，R-4）。
   **新结论**：准确说法是"**有源未接**"——数据在日志里，缺的是采集与聚合，而这正是档二那份改动顺带交付的东西。这个区别直接改变了 §4 第二层的可行性判断。
2. **原说法**（今日 11:2x 交付件 §3）："CF 分析保留 ≥30 天。"
   **反证**：本会话实测接口可取 `2026-07-12 → 2026-10-20` 共 **101 天**（`tmp/unique-total.mjs` 输出）。
   **新结论**：控制台展示与 API 可查窗口不是一回事；我按 30 天设计窗口保守了，历史深度实际是 101 天。
3. **若 Owner 坚持要"个体级轨迹"**，代价清单（必须全做完才准接采集，依 LEGAL-1:65 判据）：修订 `privacy/page.tsx` 第二节收集清单（中英双语同步）→ 更新《第三方处理方清单》自有服务器行的目的与信息种类 → 按 `:150-151` **提前 30 天**公告 → 新增 cookie／首次访问告知层（站内现在**没有** banner，子代理实测 0 命中）→ 新表配 `retentionExpiresAt` ＋删除执行体（现承诺"使用与事件指标最长 90 天"，`:105`）→ 过 `npm run test:legal-pages-drift`。**这一串不是"加个面板"，是一次对外承诺变更。**
