## 0. 一句话给 Owner

这份报告值得看，但不能照单执行。

它抓到了一个真问题：**会话文件的 ACL 是按“用户名”去授权的，不是按“当前进程的身份”**。在“域账号 + 同名本地账号”的机器上，它可能把文件锁给一个没在运行的账号，助手读不回自己的凭据，配对和上报全线停摆。这个结论我已在源码里逐行确认，**必须修**。

但它有三条判断是错的或过期的，还有一条更严重的放大器它没看见：

- 它说回执 journal“没有 fsync、没有重放”——**源码里有**。真正的问题是另一个：回执 ACK 之后，清理逻辑把重放所需的输入删了，却把 journal 回执永久留着；下次启动就把每一个**已经成功送达**的尝试重新数成“状态未知”。报告看到的 24 条，主要是这个误报，不是 24 笔卡住的钱。
- 它说 ticket 与会话的绑定关系“未知”——**源码里是一次性、短时、强绑定**：HMAC 签名、5 分钟（批次票 60 分钟）、nonce 只能消费一次、绑定 install / activation / job / attempt / origin。这一条不需要再做实验。
- 它说“生产构建信任 localhost:3000”——**那是响应头的回退值，不是放行条件**。真正让 localhost 被信任的，是配置读不到之后被默认值顶掉，而默认值恰好是 `http://localhost:3000`。也就是说，这是 ACL 故障的下游症状，不是独立的 CORS 设计缺陷。
- 它没看见的放大器：**配置读不到时，程序不是停下来，而是拿默认配置把会话文件覆盖掉；覆盖之前，还先把上一份好备份删了。** 结果就是：用户不是“这次要重新授权”，而是**每次启动都可能把最后的凭据和备份一起弄丢**。

还有一件必须先核对的事：报告自称测的是 3.7.24，但它写出的 `assistantBuildId` 是 `transport-hardening-20261011-r1`——这是 3.7.15～3.7.19 的身份，不是 3.7.24 的。官方 3.7.24 的身份是 `in-app-folder-picker-20261023-r1`，三处出厂文件逐字一致。**它审的很可能不是当前出厂件**。先花 5 分钟在客户机跑一条 `/ping`，再决定哪些行为结论能用；否则会把旧版行为当成新版缺陷来修。

**我的建议**：先做 P0.5 身份核对（5 分钟，阻塞其余），再做 P0 的三件（ACL 按进程 SID、读不到不覆盖、未签名发布闸），然后修回执误报和证据校验。签名证书采购是外部周期，代码闸本周能落，**证书到位的时间我不承诺**。

### 2.1 对 F-01 再补一句

报告说“每次升级复发”。从源码看，更准确的说法是：**只要发生一次“写盘时名字解析命中错账号”，之后每次启动都会读不到；升级只是让用户更容易注意到它**。修复不能只改名字解析，还要有启动自愈，否则已经锁坏的机器升级后仍然读不到。

### 2.2 对 F-03 的边界

代码签名能解决的是：分发环节被重打包、企业 EDR/SmartScreen 不信任、用户无法区分“厂商发的”和“别人改的”。它**不能**阻止本机管理员改程序。报告把“签名 + 服务端签名清单”写成能防本机篡改，口径要收窄；真正能提高本机证据可信度的是 §4 的 P1-A（服务端重算摘要），不是签名。

### P0-A 会话 ACL 改为“进程 token SID + 启动自愈”（鉴权面，2 人复核）

改 `download/local-assistant/persisted-state.js`：

1. 新增 `currentUserSid()`：
   - 用**绝对路径** `%SystemRoot%\System32\whoami.exe`，参数 `['/user','/fo','csv','/nh']`，`timeout: 5000`，解析第二个 CSV 字段；校验 `^S-1-\d+(-\d+)*$`。
   - 失败再试 PowerShell `([Security.Principal.WindowsIdentity]::GetCurrent()).User.Value`（timeout 8000）。
   - 两者都失败：返回 `null`，**跳过 ACL 收紧**，记 `ACL_SID_UNAVAILABLE`；**绝对不再用 `process.env.USERNAME` 做 ACL 目标**。
   - 进程内缓存 SID（像 MachineGuid 一样只取一次）。
2. 重写 `restrictAclToCurrentUser(filePath)`：
   - 用绝对路径 `icacls.exe`，参数 `[filePath, '/grant:r', '*' + sid + ':F']`，`timeout: 5000`，捕获 stdout/stderr 和退出码。
   - 检查输出里没有 `Failed processing`；否则记 `ACL_GRANT_FAILED rc=… stderr=…` 并返回 false。
   - 授权成功且回读确认 SID 在 ACL 里之后，才单独执行 `/inheritance:r`；失败只记 `ACL_INHERITANCE_FAILED`，不阻断写盘。
   - 不再把 `/inheritance:r` 和 `/grant:r` 放在同一条命令里“一次成功或失败”；先授权、再收继承，任何一步失败都不会把当前用户锁在外面。
3. 启动自愈：在 `loadConfig()` **之前**，对 `CONFIG_FILE` 和 `.bak` 各跑一次 `restrictAclToCurrentUser`。文件是当前用户创建的（owner 有 WRITE_DAC），即使读被拒也能补回 ACE；补不回就进入 P0-B 的“不可读就停”。
4. `setHidden` 同样改用绝对路径 `attrib.exe`，`timeout: 5000`，失败记退出码；隐藏属性失败不阻断写盘。
5. 测试：
   - 扩展 `scripts/smoke-local-assistant-state-persistence.mjs`：Windows 上创建临时文件，调用新函数，`icacls <file> /findsid <当前 SID>` 必须命中；静态断言源码里不再出现 `process.env.USERNAME` 作为 ACL 目标。
   - 新增负控：对一个**一次性临时副本**应用一个假 SID，断言函数返回 false 且记了错误码；临时目录整目录丢弃，不碰真实会话文件。
   - 手工 A/B：在“域账号 + 同名本地账号”的机器上启动 → `/pair` 成功 → 连续重启 3 次仍成功 → `icacls .tygf_session /findsid <token SID>` 每次命中。

**验收**：`whoami /user` 的 SID 与 `icacls .tygf_session /findsid <SID>` 命中同值；`/pair` 200；重启 3 次不回退。

### P0-B 读不到会话文件时，绝不覆盖；备份先立后破

改 `download/local-assistant/server.js` 与 `persisted-state.js`：

1. `loadConfig` 改成能返回状态：`OK | MISSING | UNREADABLE | CORRUPT`。
   - `MISSING`：两个文件都不存在。
   - `UNREADABLE`：文件存在，但 `readFileSync` 抛 `EACCES/EPERM/EBUSY` 等。
   - `CORRUPT`：读到了，但 `decodeState` / `JSON.parse` / 校验失败。
2. 启动逻辑：
   - `UNREADABLE`：先跑 P0-A 自愈并重读；仍不可读 → 打印 `CONFIG_UNREADABLE`（含路径、当前 SID、建议），**退出，不调用 `ensureMachineId` / `saveConfig`**，不改任何文件。
   - `CORRUPT`：把当前文件和 `.bak` 一起改名成 `.corrupt-<时间戳>` 保留证据，再按首次启动处理；记 `CONFIG_QUARANTINED`。绝不静默删除。
   - `MISSING`：按首次启动处理。
3. `writeHiddenStateFile` 的轮转顺序改成“新备份先落盘，再替换旧备份”：
   - 写 temp + fsync + 校验（保留现有）。
   - 当前文件可读且有效：复制到 `${backup}.new` → fsync → 原子改名为 `.bak`（旧 `.bak` 只在这之后才被替换）。
   - 当前文件存在但不可读：**中止**，记 `STATE_CURRENT_UNREADABLE`，不删任何东西。
   - 当前文件存在但无效：复制到 `${file}.corrupt-<时间戳>`，**保持 `.bak` 不动**。
   - 最后才 `rename(temp, file)`；失败只删 temp，不动当前与备份。
   - 删除现在这行 `removeFile(backupPath)` → `renameSync(filePath, backupPath)` 的“先删后换”。
4. 测试：
   - 扩展 smoke：当前文件有效 → 写新值 → `.bak` 等于上一版；当前文件损坏 → 写新值 → `.bak` 仍是上一份**有效**版本，且出现 `.corrupt-*`；把当前路径做成目录（模拟读失败）→ 写盘必须失败且 `.bak` 哈希不变。

### P0-D 回执恢复误报：ACK 后留一个“已结算”标记

改 `download/local-assistant/server.js`：

1. `removeAttemptReceiptArtifacts(attemptId)` 在删除 pending / inputs 之前，写 `${attemptId}.acked.json`（`{ackedAt, receiptEventId}`），放在 `RECEIPTS_PENDING_DIR` 或 journal 同级；journal 回执继续保留作审计。

### P1-A 服务端重算证据摘要（MAJ-5 的可落地部分）

改 `src/lib/server/execution-batch.ts` 与回执载荷：

1. 云端回执带上逐对象证据（至少 `objectId / layerId / actualTextDigest`），不要只发一个摘要字符串；`v15-runner.js` 的 `buildCloudReceiptPayload` 已经有 `receipt.objects`，把它纳入云端载荷（控制体积，可按对象哈希列表）。

## 6. 不做清单

- **不重写 journal 为两阶段提交**：现有 fsync + 原子改名 + 重放已经够用；真问题是 ACK 后的误报（F-04）。重写风险大于收益。
- **不做“浏览器持有 device secret + 每请求 HMAC”**：浏览器无法对同机进程保守秘密；这会把“本地进程可伪造 Origin”换成“本地进程可读浏览器存储/内存”，还会破坏现有配对与一次性票链路。要加客户端身份，应该用 OS 用户边界 + 一次性票据 + 服务端绑定。
- **不做 bytecode / 加壳 / 反调试**：报告 §3 已用实测说明收益低、代价高，且会伤自家可诊断性；§2 与 §3 矛盾时按 §3。
- **不删除中文错误文案**：用户和支持需要它；只移除泄漏构建路径的字面量。
- **不在未确认客户机 buildId 前，按报告的 3.7.24 行为结论改代码**：先做 P0.5。
- **不自动删、不自动重投那 24 条**：先分类（已结算误报 / 待重放 / 真未知），再出数据修复工单；删了就没证据了。
- **不拆客户过渡件**：客户机上的启动器/看门狗先留着；等 ACL 修复在**那台机器**上连续重启验证通过，再用 `tygf-assistant-patch.ps1 -Uninstall` 一次性拆除并留回滚。修复前拆，等于把客户再推下去一次。
- **不在自启值上做“存在即不覆盖”**：报告 §5 的值名与 MIN-1 的“覆盖”说法对不上（U-03）；先取升级前后注册表快照，再决定改不改安装器。盲目改成“存在即不覆盖”会让升级后的路径更新失效。
