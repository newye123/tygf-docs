# 对抗式审查：2026-10-21 PHP 两个严重漏洞，与我们收到的处置方案

VERDICT: 打回（处置方案按原文执行会留下未修补的 PHP 5.6）｜我方主机：不受影响
范围: php.net 官方通告 `2026-10-21-5` ＋ tygf-server 只读实测（2026-10-22 10:15–10:19 +0800）｜Round 1/3
改动: 0 个文件（只读审查，未安装、未编译、未改 nginx）｜风险档 High（漏洞本体）／我方暴露面 无

## 一、先回答：我们的服务器不用 PHP

在生产/测试同机的那台服务器（SSH 别名 `tygf-server`）上做了只读实测：

- `command -v php` → 无输出；`dpkg -l | grep -i php` → 无 PHP 包；`systemctl list-units --all | grep -Ei 'php|apache|httpd'` → 无相关服务。
- `ps` 里没有 php/php-fpm/php-cgi 进程；监听端口只有 22、80、443、3000、3001、本地 DNS（53）和一个本地端口 20241，**没有 9000**（php-fpm 默认端口）。
- `nginx -T` 全量配置里没有生效的 `fastcgi_pass`；唯一命中 `php` 的是一行注释 `# auth_http localhost/auth.php;`（nginx 自带示例）。
- `/etc/nginx/sites-enabled/` 的 5 个站点全部 `proxy_pass` 到 `127.0.0.1:3000` 或 `:3001`——就是生产/测试两个 Next.js 进程。
- `/var/www` 三层内 `*.php` 文件数 = 0；`/etc/php`、`/usr/bin/php*` 均不存在；常见目录（/usr、/usr/local、/opt、/var/www）5 层内也找不到 `php`、`php-fpm*`、`php-cgi`、`lsphp*` 可执行文件。

**结论：两站都是 Node/Next.js 由 nginx 反代，没有 PHP 运行时，这个漏洞在我们的服务器上没有攻击面。** 不需要升级、不需要编译、不需要改 nginx。

顺带排除一个常见误判：`/etc/nginx/fastcgi_params`、`fastcgi.conf`、`sites-available/default` 里出现 `php` 字样，是 nginx 安装包自带的模板/注释；`sites-enabled` 没有启用它们，不能据此判"在用 PHP"。

## 二、漏洞本身：真的，而且严重

- php.net 官方 2026-10-21 通告（锚点 `2026-10-21-5`）标题为 "Security advisory: Critical remote code execution vulnerabilities, update now"，明确说两个漏洞可让**未认证**请求远程执行代码。
  - CVE-2026-109618：内存耗尽（OOM）处理中断时，请求数据只初始化了一半，清理阶段把无效数据当有效数据用。
  - CVE-2026-109619：请求私有状态在底层内存释放后仍被同一 worker 的后续请求复用（stale state）。
- 官方修复版本：**PHP 8.5.12、8.4.27、8.3.36、8.2.35**。官方额外为 **7.4、8.0、8.1** 提供了最小源码 backport。
- 官方原话：所有处理 Web 请求的 PHP 形态都受影响，包括 PHP-FPM、Apache mod_php、php-cgi、FrankenPHP、LiteSpeed；mod_php 风险最高，可在应用代码运行前触发。
- NVD 已收录两条：CVSS 4.0 均为 9.2（Critical），CVSS 3.1 均为 9.8（Critical），发布时间 2026-10-21 14:17 UTC。
- GitHub `php/php-src` 确实存在三个 backport 分支：`PHP-7.4-CVE-2026-109618-109619`、`PHP-8.0-...`、`PHP-8.1-...`；7.4 分支头提交 `712e60f` 的说明明确写了两条 GHSA/CVE。

来源见文末。

## 三、处置方案的对抗式审查

### F-1　Important｜PHP 5.x 给的链接是"未修补的原始源码包"，不是修复版

转来的方案写：PHP 5.x 用 `https://packages.sury.org/php/pool/main/p/php5.6/php5.6_5.6.40.orig.tar.xz`。

这是 Debian 打包体系里的 **orig tarball（上游原始源码）**，不是带补丁的版本。实测：

- 它与官方 2019 年的 `php-5.6.40.tar.xz` **逐字节相同**：两者都是 12,472,236 B，SHA-256 都是 `1369a51e…56d1c`，`cmp` 返回 0。
- 它的 `Last-Modified` 是 **2019-01-11 14:04:49 GMT**，不可能包含 2026-10-21 的补丁。
- 同一个目录里真正的修复版是 `php5.6_5.6.40-104+0~20261021.134+ubuntu24.04~1.gbp7401dd`：`.dsc` 同时列出 orig 与 `debian.tar.xz`，后者含补丁 `0261-Avoid-state-corruption-via-bailout.patch`，补丁头明确写 `Fix GHSA-w8hw-w9fx-j79w (CVE-2026-109618)` 和 `Fix GHSA-6wmf-4rv5-p3rp (CVE-2026-109619)`；changelog 也写明 "Backported from 8.2.35"。

**失效场景：** 按转来的链接下载 orig.tar.xz、`./configure && make`，得到的仍是有洞的 PHP 5.6.40；服务看起来"升级过了"，实际没有任何修复。这是本次审查里最危险的一条。

**正确做法：** 用 `.dsc` 走 `apt-get source` / `dpkg-buildpackage`（会同时取 orig 和 debian 补丁），或者更推荐：5.6 早已 EOL，迁到受支持版本。

### F-2　Important｜"PHP 7.x" 的范围写大了，官方只修了 7.4

方案写"PHP 7.x 需要使用官方发布的修复版源代码编译"。实测 GitHub refs：`PHP-7.4-CVE-2026-109618-109619` 存在；`PHP-7.0-CVE`、`7.1-CVE`、`7.2-CVE`、`7.3-CVE` 查询结果全部为空。

**失效场景：** 跑 7.2/7.3 的人照着"7.x 有修复版"去找，找不到；或者误以为自己的 7.2 已被覆盖。

**正确做法：** 7.4 用官方 backport；7.0–7.3 只能升级到受支持版本，或找 LTS 厂商的 backport。

### F-3　Medium｜"PHP 8.x 需要从源代码编译"不是官方要求，且风险更高

官方通告的更新顺序是：**优先用发行版/LTS 厂商的更新包**；源码下载也在官方下载页，但没有说"必须自己编译"。在 Ubuntu 24.04 上，包管理器能给你可回滚、可审计的升级；自己编译会引入工具链、依赖版本和后续补丁跟踪的问题。

另外，"最新 8.x"应锁定为四个明确版本：8.5.12 / 8.4.27 / 8.3.36 / 8.2.35。8.0/8.1 属于 EOL 分支，只有最小 backport，不是"升到最新 8.x 就自动安全"。

### F-4　Nit｜"获得所有权限、对服务器和数据库做任意操作"是夸大

RCE 的权限上限是 **PHP 工作进程的运行用户**；能不能读数据库，取决于该进程拿到的数据库凭据和数据库授权。风险依然很高（CVSS 3.1 9.8），但"所有权限"会让人误判爆炸半径，进而做出错误决策（例如以为只有装 PHP 的机器才需要查 DB 凭据）。

### F-5　排除性结论｜我方主机不受影响（不是缺陷，是实测结果）

见第一节。没有 PHP 运行时，两个 CVE 都无法触发；不需要采取任何"升级/编译"动作。

## 四、现在实际要做什么

1. **这台服务器：零动作。** 不装 PHP、不编译、不改 nginx；继续按现有 Node/Next.js 方式运行。
2. **如果还有别的服务器、托管面板或老项目**：在每一台上先跑一条只读探针，确认到底有没有 PHP（命令见下），再决定是否修补。
3. **如果探到 5.6**：不要用 orig.tar.xz；用 sury 的 `.dsc` 源包，或直接迁移。5.6 已 EOL 多年，打补丁只是止血。
4. **如果探到 7.0–7.3**：官方没有 backport，升级是唯一完整解。
5. **如果探到 8.x**：优先发行版包到指定修复版；没有包再源码编译，并记录下载来源与校验值。

只读探针（在任何 Linux 主机上跑，不写盘）：

```bash
command -v php; dpkg -l 2>/dev/null | grep -i php; \
systemctl list-units --type=service --all 2>/dev/null | grep -Ei 'php|apache|httpd'; \
ps -eo pid,comm,args | grep -i '[p]hp'; \
ss -ltnp 2>/dev/null | grep -E ':9000|:9001'; \
sudo -n nginx -T 2>/dev/null | grep -nE 'fastcgi_pass|include .*fastcgi'
```

如果第一条有 `/usr/bin/php` 或第二条有 `php-fpm`，才算"这台在用 PHP"；再看 `php -v` 决定分支。

## 五、覆盖缺口与未决

- **只实测了 `tygf-server` 这一台**（生产与测试同机）。没有其它服务器的清单，不能替别的机器下结论；如果 Owner 还有别的 VPS、宝塔面板、虚拟主机，需要逐台跑上面的探针。
- 未检查 Owner 个人电脑或其它项目目录是否装 PHP（与"服务器"问题无关）。
- 未做外部端口扫描或漏洞利用验证（不在授权范围内，也没有必要）。
- 未验证 sury 二进制 `.deb` 安装后的实际版本（我们不需要安装）；只验证了源码包确实带补丁。
- "我们有没有别的机器跑 PHP"＝**未核实**；"这台机器没有 PHP"＝已实测。
