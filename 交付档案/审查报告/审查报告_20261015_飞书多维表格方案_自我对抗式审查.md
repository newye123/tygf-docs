## 一、被实测推翻或需修正的假设（3 条）

### 1. 「从 TASK_LOG 读条目、约百行脚本」——**严重低估**

方案步 3 写：「输入：`AI_MEMORY/TASK_LOG.md`（条目）+ git 状态……约百行」。

实测 `AI_MEMORY/TASK_LOG.md`：

| 项 | 实测 |
|---|---|
| 总条目数 | **209** |
| 含「- **目标**」 | 31（14.8%） |
| 含「- **测试结果**」 | 52（24.9%） |
| 含「- **下一步**」 | **7（3.3%）** |

⇒ TASK_LOG 是**自由格式**：字段名不统一，而且**绝大多数条目根本没有这些结构字段**（「下一步」只有 7 条有）。指望写个脚本把这 209 条异构文本解析成结构化行，**不是百行的活，而且格式会继续漂移**——今天我刚写的两条新条目格式就与旧条目不同。

**修正**：**不解析历史**。改为——

> AI 会话在收尾时**直接产出一行结构化记录**（追加到 `AI_MEMORY/ledger.jsonl`），脚本只做 **JSONL → 飞书表格** 的搬运。这样脚本确实只有几十行，且格式由写入方保证。历史 209 条**不回溯**（需要时人工补）。

### 2. 「CLI 装好可复用 connector 授权」——**实测基本否定**

方案把这条列为「待确认 1」。实测后应**升级为「基本确定需要重新登录」**：

- WorkBuddy 的 connector 凭据存在 `~/.workbuddy-ai/connectors/<userId>/`；
- 该目录 `README-DO-NOT-DELETE.txt` 自述：「本目录包含 **WorkBuddy 连接器**（QQ 邮箱 / 腾讯文档 / 微云等）的本地凭据」；
- `connector-states.v3.json` 的 `connectors` 键实测为 `["github","feishu"]`，加密方案含 `scheme/kdf/salt`，密钥是本目录的 `.master.key`。

⇒ connector 的授权由 **WorkBuddy 自己加密管理**，与 `lark-cli` 的 auth 是**两套独立存储**。CLI 装好后**需要重新 `auth login` 扫码**。

**修正**：步 1 的描述与耗时都要改（10 分钟 → 15–20 分钟）。

### 3. 「约半天」——**低估**

拆解实际工作量：装 CLI（含 Windows/权限/版本排错）＋ 建表（要试模板、对字段）＋ 脚本（原先按非结构化解析估，现改为 JSONL 后回落）＋ 改 `AGENTS.md` ＋ 验证与降级。

**修正**：**1–2 天**，且第一版应接受「半自动」（先手工触发，稳定后再接自动）。

## 二、内部矛盾（1 条，最要紧）

### 「单向投影、git 为准」与表格里的「状态」列**互相打架**

方案问 2 裁决「单向投影，git 为准」，问 3 又说「只放需要您决策 + 跨会话可见的」，字段表里还有一列「状态」。

但您要的正是「**哪些做没做到什么地步**」——**您很可能想在表格里直接改状态**。这正是多维表格的价值所在。一旦人工改状态：

- 表格就从「只读投影」变成了「写入源」，「git 为准」失效；
- 且与下一次投影**互相覆盖**（投影按 git 写回，会抹掉您的手改）。

**必须二选一，并写进方案**：

| 选项 | 做法 | 代价 |
|---|---|---|
| **甲（纯投影）** | 状态列只读；改状态必须回 git（改 TASK_LOG / ledger） | 安全、无歧义；但您不能直接改 |
| **乙（双写 + 冲突规则）** | 允许表格改状态，约定「表格状态优先，投影不回写状态列」 | 顺手；但表格与 git 分歧时无法自动判定谁对 |

**我的建议：甲 + 一个例外**——单独加一列「**Owner 批注**」（自由文本，**只由您在表格里写，投影永不覆盖**）。这样既保留您的输入通道，又不破坏「git 为准」。

## 三、遗漏（4 条）

### 4. 权限面变化没提示（安全，重要）

`lark-cli` 的授权身份是 **user**（插件配置 `statusMatchJson.identity = "user"`），不是 bot。而 connector 带 **28 个** `lark-*` skill，其中包含 `lark-mail`、`lark-drive`、`lark-doc`、`lark-calendar`。

⇒ 装完 CLI 并扫码后，**本机任何能执行命令的 AI 会话，都能读写您的飞书邮件、云盘、文档、日历**。

这是**实质的权限边界扩大**，而原方案只说了「凭据不进仓库」，**完全没提这一层**。

**缓解建议**：① 至少要让您知道（本条即是）；② 可考虑「用时登录、用完 `auth logout`」；③ 评估能否改用 `--as bot`（代价：bot 建的表您可能看不到，需另做分享）。

### 5. 飞书自动化 workflow 被我一刀切掉（过度收缩）

原方案问 8 写「本方案**不做**仪表盘、不做甘特图、不做自动化 workflow」。

但「**状态变成『等您定』时，自动推一条到飞书群**」恰恰是您最需要的功能——**您就不用天天打开表格看**。我把它连同仪表盘一起砍掉，属于过度收缩。

**修正**：P0 保留**一条**最简自动化（`状态 = 等您定` → 推群），其余不做。

### 6. BaseApp（应用模式）没提

`lark-base` skill 明确：BaseApp（AppMode）通过 Page 和组件组织 Base 数据，是**应用界面**，不是 Base 的别名。它可能比「裸表格」更贴合「打开就能看」。

**修正**：步 2 增加一步——**评估 BaseApp 形态**再决定用裸表还是应用。

### 7. 任务 ID 从哪来没定义

方案说「用稳定键（如 `T-20261015-01`）」，但**没写谁生成、怎么保证唯一**。多会话并行时，两方可能生成同一个 ID。

**修正**：定义生成规则（日期 + 会话槽 + 序号），脚本里做去重校验。
