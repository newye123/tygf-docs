# 对抗式审查｜"除了多稿工作台，其他都可以全部推生产"——部分成立，三处不成立

日期：2026-10-27 15:4x
被审命题（Owner 原话）：「其实除了多个设计稿工作台不能推到生产之外，其他的都可以全部推了，现在就卡在多个设计稿工作台」
方法：只读实测（git 差集 / 生产库只读 SQL / 源码读到强制点 / 同一道门两点比对）。基线 `origin/develop@97abb21d`、生产 `origin/main@80eb4263`、测试站现役 `3ae696f2`。

VERDICT: **有条件成立**——"卡在多稿"这一句**对**（唯一红的门就在多稿线上）；但"其他都可以全部推"**不成立**，有三处非多稿的拦路，其中一处会**直接拒掉现网用户的扫描与执行**。

## 1. 先给他对的那一半（有证据）

| 检查 | 结果 |
|---|---|
| 出包门禁 | 13 道绿（含 `test:contracts` 约 354s、`test:trust-chain` 61s、`assistant-script-distribution` 74s、`partial-index-guard` 78s），**唯一红的**是 `fold-no-report-loss` |
| 红点位置 | `src/components/workbench/step1-stage-view.tsx:1782` 缺「折叠不得删报」出口声明 ⇒ **多稿/批量台线** |
| 定责比对 | 同一道门在 `3ae696f2` → `ok 折叠点=21 R1=0 rc=0`；在 `97abb21d` → `FAIL R1=1 rc=1` |

⇒ "现在就卡在多个设计稿工作台"这句，**在门禁这一层站得住**。

## 2. 不成立之一：助手版本门会拒掉现网用户（硬，且与多稿无关）

源码读到的强制点：`src/lib/server/assistant-execution-contract.ts:69-72`
```
if (compareAssistantVersions(identityCard.assistantVersion, localAssistantVersion) < 0) {
  ... '本地助手版本 X 低于要求的 Y。请升级到 Y 并完全重启助手后重新扫描。'  // ASSISTANT_VERSION_MISMATCH
```
另有 `src/app/api/local-assistant/scripts/distribute/route.ts:101` → `SCRIPT_VERSION_TOO_OLD` **403**。

实测版本要求与仓库内安装包：
| | 网页要求的助手版本 | 仓库里最高安装包 |
|---|---|---|
| `origin/main`（生产） | **3.7.15** | 3.7.15 |
| `origin/develop`（要推的） | **3.7.28** | 3.7.28（25/27/28 都在） |

**推 develop 网页到生产 ⇒ 现网所有装着旧助手的人，扫描与执行会被硬拒**，直到他们自己下载安装 3.7.28 并"完全重启助手"。安装包确实随包能拿到，但**升级动作发生在客户机器上，不是我们推一下就完**。这条与多稿无关。

- **未核实**：现网用户实际装的是哪几档。`BetaFunnelEvent.appVersion` 1868 行**全是 "0.1"**（取不到真值），所以"多少人会被挡"现在算不出来。

## 3. 不成立之二：生产库缺一张表，推上去官网表单 100% 报错（非多稿）

差集实测（develop 声明 68 张表 vs 生产库 67 张）：
```
comm -23 models.txt prod-tables.txt  →  ApplicationAttribution   ← 只差这一张
```
- 生产库**没有 `_prisma_migrations` 表**（实测 `no such table`）⇒ 生产迁移是"历史机制"手工追平的，工具看不出该补哪些。
- `beta-applications/route.ts:249` 无条件 `tx.applicationAttribution.create()` ⇒ 本地已复现：**每次提交都 500**。
- 生产部署脚本 `deploy/deploy-release.sh` 里 `approved_migrations` 与 `migrate` **两条 grep 全空** ⇒ 部署不会自动补表；漂移门对生产恒 **rc=2「不算通过」**。

⇒ 这是**一条命令能补**的加表动作（纯新增、不改数据），但**必须有人显式做**。它属于官网/归因线，不属于多稿。

## 4. 不成立之三：技术上不存在"只推非多稿"的干净拆法

命题隐含"能把多稿单独摘出去"。实测多稿线与其余改动**高度纠缠**（242 笔里各文件被改次数）：
| 文件 | 被改次数 |
|---|---|
| `workbench-view.tsx` | **41** |
| `step1-stage-view.tsx` | 12 |
| `stage-folder-gate.tsx` | 6 |
| `coverage-matrix.tsx` | 3 |

要"推其余、不推多稿"就得做提交级手术（cherry-pick 或反向剔除），而同一批文件上交错改动几乎必然冲突，且**冲突解完就是一棵新树——所有门的绿证全部作废，得整轮重跑**。

## 5. 还有一条他没提的：生产有 2 笔 develop 没有（双向合流，非快进）

`git rev-list --count origin/develop..origin/main` = **2**：`df93c257`（首页字体分片 14.13 MiB→406,956 B）、`80eb4263`（分片给 CF 1 小时边缘缓存）。
**其中 `df93c257` 动的正是 `home-view.tsx`**——我这次也改了这个文件 ⇒ 推生产第一步是双向合流并处理冲突，不是单向快进。这也不是多稿问题。

## 6. 所以真实图景

"卡在多稿"只说对了**门禁那一层的一道红**。要真推生产，非多稿的前置还有三条：**助手版本随发决定、生产库补一张表、把 main 独有 2 笔合回来**；而"只推非多稿"这个拆法本身不成立。

## 7. 建议（给拍板用，不是放行）

- **推荐：不要试图拆半推。** 三条非多稿前置 + 多稿那一句声明，总量比"做提交手术 + 重跑全部门"小得多，风险也低得多。
- 若要把生产发布排上：**① 先合 main 那 2 笔**（`home-view.tsx` 冲突，合完我的官网验证重跑）；**② 生产库补 `ApplicationAttribution`**（一条加表命令，纯新增）；**③ 定助手随发 3.7.28 并提前公告老用户**"不升级就无法扫描"——这条是唯一会伤到客户的，必须先有说法再发；**④ 多稿线补声明** ⇒ 门全绿 ⇒ 出包 → 测试站验 → 才谈生产。
- **②③④ 之间没有依赖，可以并行**；① 是硬前置。
