## §01 判定

**你的问题不是"支线开得多"，是"开了不关"。**

实测：84 个本地分支里，**40 条已经合并进 develop 却还挂着**，34 条是历史 `codex/*` 一次性支线；worktrees 目录下 130 个子目录里约 45 个是没人管的孤儿。同时 5 件交付件产出后没发出去、今早的生产发版没挂号。

公开实践里对这件事有现成结论，而且几乎每家都说同一句：**先限制"同时在办"的数量，再谈别的。** Personal Kanban 的原话正好命中你的处境——"too many things are started, not enough are finished"（开始得太多，完成得太少）。

## §03 别人怎么做（GitHub 上可查到的四类做法）

### 做法一：限制在办数量（WIP limit）——最直接对应你的问题

- **Personal Kanban**（Jim Benson / Tonianne DeMaria）只有两条规则：**可视化你的工作** ＋ **限制在办数量**。官方原话："Agree how much can be in 'Doing' at once so people can focus, finish, and learn, instead of juggling too much, finishing too little, and drowning in half-done work." 出处：<https://personalkanban.com/>
- **Atlassian 的 WIP 限值说明**：同时办太多会让人直接过载。出处：<https://www.atlassian.com/agile/kanban/wip-limits>
- **GitHub Projects 原生支持**：看板列可以设 WIP 上限，超了给警告；官方建议"别让看板变成垃圾场，不再相关的 issue 要归档或关掉"。
- 业界口号：**"Stop starting, start finishing"**（别再开新的，先把旧的做完）。

### 做法二：干脆不要 backlog——Shape Up 的"赌注制"

Basecamp 的 Shape Up（免费在线书 <https://basecamp.com/shapeup>）核心是三条：

1. **时间固定、范围浮动**：先定"这事值多少时间"（appetite），再决定在这么长时间里做到什么版本。原话对照："Estimates start with a design and end with a number. Appetites start with a number and end with a design."
2. **没有 backlog**：这一轮没选上的提议**不自动结转**，想做要重新提一次。这就避免了"越攒越多、没人敢删"的坟场。
3. **断路器（circuit breaker）**：到期没做完**默认不延期**，项目直接砍掉——要接着做必须重新拍一次，不能靠惯性拖。

配套还有 **6 周干 + 2 周冷却**：冷却期不排新活，只修 bug、清尾、想下一轮。作者的理由很直白——没有冷却期，疲劳和小毛病会一直堆。

### 做法三：分支短命、合完就删（trunk-based / GitHub Flow）

- **Trunk-Based Development**（Paul Hammant，站点 <https://trunkbaseddevelopment.com/>，源仓库在 GitHub：<https://github.com/paul-hammant/tbd>）：主干一条，**抵制建长期分支**，每人至少每 24 小时往主干合一次；确实需要长周期的变更，用 **feature flag** 或 **branch by abstraction**，而不是开一条活三个月的分支。发布分支"发完就删"。
- **GitHub 官方 GitHub Flow**（<https://docs.github.com/en/get-started/using-github/github-flow>）：开分支 → 改 → 提 PR → 合 → **删掉分支**。官方给的两条理由对你特别对症：
  - "Make a separate branch for each set of unrelated changes… **if there is a delay in one set of changes, your other changes aren't also delayed**."（别把不相关的事塞一条分支，否则一件卡住全部卡住）
  - "After you merge your pull request, **delete your branch**. This indicates that the work on the branch is complete and **prevents you or others from accidentally using old branches**."（合完就删，标记完成，防止误用旧分支）

### 做法四：把"完成"定义清楚——只有"已合并 + 已验证"才算完

- 一个真实开源仓库的治理文档把状态分成：Done / In progress / Design / Not started / Experimental / **Deferred（暂缓）** / **Rejected（不做，保留理由）**，并明确写了一句对你最有用的话：**"只把 PR 已合并称为 Done，不要把'有人提出'或'代码已开分支'当作完成。"** 出处：<https://github.com/askdkc/dsh-cli/blob/04ee532f649a508ec22a9ede413f25e8eae3a1e5/docs/community-management.md>
- 另一份 GitHub 上的路线图方法文档主张默认用 **Now / Next / Later** 三档，且明确区分："roadmap 是一组赌注，backlog 是可能工作的库存"；Later 保持不确定、写清非目标。出处：<https://github.com/stylusnexus/agent-plugins/blob/main/plugins/product-strategy/skills/pm-roadmap/SKILL.md>

### 附加：Owner 自己的精力边界

GitHub 官方 Open Source Guides 里有一篇专门讲维护者过载（<https://opensource.guide/maintaining-balance-for-open-source-maintainers/>），把"**Not saying 'no'**"（不会说不）列为过载的首要成因之一，并建议把"我做什么、不做什么"写进 README，作为挡需求的凭据。原话："You can't say yes to every request."

## §04 哪些能搬、哪些不能搬（对抗式审查）

| 做法 | 能不能直接搬 | 理由 |
|---|---|---|
| WIP 限值（限在办数量） | ✅ **能，且最该先做** | 不依赖工具、不依赖团队规模，一个人就能执行；你已有类似规则（三账 ≤30KB/周、每周新签任务书 ≤7）但**宽到没约束力**，且实测已停写 8 天 |
| 合完即删分支 | ✅ **能** | 40 条已合并分支零风险可关；GitHub 官方原话就是"标记完成 + 防止误用旧分支" |
| 没有 backlog / 不自动结转 | ✅ **能，但要你定** | 你现在的事实是"每条线都自动结转、永远挂着"；改成"没做完下轮重新拍"需要你接受"有些线会主动砍掉" |
| 断路器（到期默认不延期） | ⚠️ **改一半能用** | Shape Up 假设有团队和固定周期；你是单人 + 随时插生产问题。可以改成"每条线给一个到期日，到期没完就降级为 Deferred，不占当前名额" |
| 6 周干 + 2 周冷却 | ⚠️ **改成一周粒度** | 单人做不了 6 周节奏。等价物＝**每周留 1 天不接新线，只收尾** |
| Trunk-Based Development（直接合主干） | ❌ **现在不能照搬** | TBD 的前提是 CI 硬门禁（提交后自动验证没破坏构建）。本项目实测 `test:seo-consistency` 与 `test:admin-security` **都不在发布门内**，直接对主干高频提交会放大风险 |
| 删分支 / 删 worktree 目录 | ⛔ **不是我的决定** | 按项目红线与 SOUL 约定：删分支、删文件是你的决定。我只出清单和建议，不代拍 |

## §05 处置建议

### 第一步（今天就能做完，零风险，只需你点头删）

1. **关账 40 条已合并分支**：它们的内容已经在 develop 里，删掉不丢任何代码。
2. **清 45 个孤儿 worktree 目录**：git 已不认它们，占空间、也占你的注意力。清单我出，删除动作等你批。
3. **给剩下的 43 条未合并分支打标签**：分成"还要（≤3 条）／暂缓 Deferred／不做 Rejected（留理由）"三类。34 条历史 `codex/*` 大概率直接进 Deferred。

### 第二步（设闸，这周定）

4. **把在办上限从 7 条压到 2 条**：同一时间只允许 2 条活跃线（1 条产品 + 1 条应急）。超了就必须先关掉一条才能开新的。这是全部建议里唯一真正治本的一条。
5. **改"完成"的定义**：只有"已合并 + 已验证 + 已登记"才算完成。**"开了分支"不算、"报告写完了"不算、"发出去了"才算。** 你现在的 5 件产出没发出、今早发版没挂号，就是这条定义缺失的直接后果。
6. **加一条到期规则**：每条线开工时写一个到期日；到期没完 → 自动降级为暂缓，**不占在办名额**，想接着做就重新拍一次。

### 第三步（每周一次，5 分钟）

7. **每周留一天"冷却"**：不接新线，只做收尾（把做完的登记、把发出的确认、把没做的降级）。

### 要你定的三件

| # | 决定 | 说明 |
|---|---|---|
| D1 | 40 条已合并分支 + 45 个孤儿目录，删不删 | 删是你的决定；我只出清单，不动手 |
| D2 | 在办上限定 2 条还是 3 条 | 建议 2；你现在是 7 条上限但实测无约束力 |
| D3 | 未做完的线是否接受"到期自动降级" | 这条会真的砍掉一些线，需要你同意 |
