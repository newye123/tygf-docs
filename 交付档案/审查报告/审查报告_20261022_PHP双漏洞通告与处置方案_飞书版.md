# PHP 两个洞是真的，我们的服务器没事；但转来的 5.x 修复链接会把人带进坑

## 先说结论

两个漏洞真实存在，不是谣言：PHP 官方在 10 月 21 日发了紧急通告，NVD 给出的严重级是 9.8（满分 10）。攻击者不用账号，发一个特制请求就可能远程执行代码。

但我们的生产/测试服务器没有装 PHP。两站都是 Next.js 应用，由 nginx 转发到本机的 3000/3001 端口，机器上没有 php 命令、没有 php 软件包、没有 php 进程、也没有 9000 端口（php-fpm 的默认端口）。所以这个漏洞在我们这台机器上没有攻击面，不需要升级、不需要编译、也不需要改 nginx。

需要立刻纠正的是转来的处置方案：PHP 5.x 那一条给的链接是未修补的原始源码包，照着编译会得到一个仍然有洞的 PHP 5.6.40，而且会让人以为已经修好了。

## 我们的服务器实测到了什么

在这台服务器上做了只读检查，没有安装或修改任何东西。查 php 命令，没有；查系统软件包，没有 PHP；查服务，没有 php、apache、httpd；查进程，没有 php 或 php-fpm；查监听端口，只有 22、80、443、3000、3001、本地 DNS 和一个本地端口，没有 9000；查 nginx 全量配置，没有生效的 fastcgi_pass；查网站目录，三层以内没有 .php 文件。

另外提醒一个容易误判的点：nginx 安装包里自带 fastcgi_params、fastcgi.conf，以及一个默认站点配置，里面会出现 php 字样，但那些是模板和注释，我们的站点配置没有启用它们。看到这些文件就判断“在用 PHP”是假阳性。

## 漏洞本身确认

官方通告标题是“严重远程代码执行漏洞，立即更新”。两条编号分别是 CVE-2026-109618 和 CVE-2026-109619：一条是内存耗尽处理时数据只初始化了一半，清理阶段误用；另一条是请求状态在内存释放后还活着，被同一个工作进程的下一个请求复用。

修复版本是 PHP 8.5.12、8.4.27、8.3.36、8.2.35。官方另外给 7.4、8.0、8.1 三个老分支提供了最小补丁。NVD 两条都是 CVSS 3.1 9.8、CVSS 4.0 9.2，属于最高一档。

## 处置方案里必须改的三处

第一处最危险：PHP 5.x 给的链接是 php5.6_5.6.40.orig.tar.xz。这是 Debian 打包体系里的“上游原始源码”，不是修复版。我把它和官方 2019 年的 php-5.6.40.tar.xz 都下载下来比对，两个文件都是 12,472,236 字节，SHA-256 完全一样，逐字节比较也返回相同，最后修改时间停在 2019 年 1 月。真正的修复在同一个目录下的 debian.tar.xz 里，补丁名叫 0261-Avoid-state-corruption-via-bailout.patch，补丁开头明确写着修复这两个 CVE。所以正确做法是用 .dsc 源包走 apt-get source 或 dpkg-buildpackage，不能只编译 orig.tar.xz；更推荐的是把 5.6 迁到受支持的版本，它已经停止维护很多年了。

第二处：方案说 PHP 7.x 有官方修复版，实际只有 7.4 有。我查了官方仓库的分支，7.4 的 CVE 分支存在，7.0、7.1、7.2、7.3 都没有。跑这几个版本的人只能升级，或者找长期支持厂商的补丁。

第三处：方案说 PHP 8.x 必须从源代码编译。官方并没有这个要求，优先推荐发行版或长期支持厂商的更新包。自己编译会引入工具链、依赖和后续补丁跟踪的问题，生产上也不如包管理器好回滚。版本要锁定到 8.5.12、8.4.27、8.3.36、8.2.35 这四个，不要笼统说“最新 8.x”。

还有一句表述要修正：“拿到所有权限、对服务器和数据库任意操作”是夸大。远程执行代码的权限上限是 PHP 工作进程的运行用户，能不能读数据库取决于这个进程拿到的数据库凭据和授权。风险仍然很高，但不该用“所有权限”来判断影响范围。

## 现在实际要做什么

这台服务器：零动作，不装 PHP、不编译、不改 nginx。

如果还有别的服务器、宝塔面板或老项目，逐台确认有没有 PHP 再处理。探针很简单：查 php 命令、查 php 软件包、查 php/apache 服务、查 php 进程、查 9000 端口、查 nginx 里有没有生效的 fastcgi_pass。第一条或第二条有命中，才算这台机器在用 PHP。

如果确实有 5.6：不要用 orig.tar.xz，用 sury 的 .dsc 源包，或者迁移。如果确实有 7.0 到 7.3：官方没有补丁，升级是唯一完整解。如果确实有 8.x：优先用发行版包升到前面那四个版本。

## 这次没查到哪

我只实测了这一台服务器，没有其它机器的清单，不能替别的机器下结论。我没有做外部端口扫描或漏洞利用验证。我也没有实际安装 sury 的二进制包，只验证了源码包里确实带补丁。所以准确的说法是：“这台机器没有 PHP”是已实测；“我们所有机器都没有 PHP”还未核实。
