# 审查报告：免 PS 引擎"接线"六面对抗式审查（2026-10-17 第三轮）

**判词：接线的真正风险不是行号搬家，是扫描引擎与执行引擎的身份没有绑死。** `layer_id` 是各自引擎内部的层号空间，把 PS 扫出来的层号喂给免 PS 引擎，指的可能不是同一层；而现有前置检查挡不住"同一段原文出现在多层"这一形——那种情况下比对通过、读回通过、回执全绿，**真正该翻的那层被静默漏掉**。这一轮我在隔离树补了第一道 fail-closed 防线并跑绿，同时把另外五面的结论钉死。

本轮实测全部在 `worktrees/pc-port-20261017`（基线 develop `338da1d`）；未推、未部署、未碰两站，旗标默认关。

## 面 1（阻断级，已补第一道防线）跨引擎层号歧义

三条实测证据：

- `download/local-assistant/execution-manifest.js:158` 允许的执行字段只有四键 `expected_source / layer_id / object_id / target_text`——**没有任何扫描引擎标记**；`:165` 还强制 `layer_id` 为正整数、`:166` 查重。也就是说 manifest 无法回答"这批层号是谁扫出来的"。
- 执行器按整数层号直通编辑（Phase 0 钉 S1 实测：字符串写法被数值强转成错误层），这是两套引擎共同的用法约束。而 10-14 五路审查实测 **PS `Layer.Id` 在遍历期确定性串号**（`paramId=14207 realId=12075`，`AI_MEMORY/TASK_LOG.md:752`），10-14 可行性评估同样写明"跨引擎只认 ledgerEntryId"（`AI_MEMORY/TASK_LOG.md:767`）。⇒ 同一个整数在 PS COM 空间与 PC 树空间里不是同一个对象这件事，有实测先例。
- 现有前置检查（`OBJECT_MISSING / OBJECT_NOT_TEXT / SOURCE_STALE`）能挡住大多数错指，**挡不住同原文多层**：错指到文本相同的兄弟层，比对通过、重开读回也通过，该翻的那层没翻，回执全绿。

本轮动作（已实现并跑绿）：执行器在编辑前做一次"原文命中层数 vs 投喂替换条数"清点，**命中数大于投喂数就整批拒执行**；错误码复用既有 `SOURCE_STALE`（原因见下面面 6），真相写进 `details` 的 `SOURCE_TEXT_AMBIGUOUS`。实测：`dup-ambiguous`（同原文两层只给一条替换）被拒、`dup-paired`（给满两条）放行，`smoke-pc-executor` **17/17 rc=0**。

**这不等于彻底解决。** 彻底解＝manifest 增"扫描引擎"标记 + 跨引擎一律拒执行，那是合同变更（四层同步 + fixture），要单独一班车。本轮做的是把最容易静默出错的那条形变成硬失败。

## 面 2（重）接线点比方案 v2 说的少，但扫描闸不在执行链里

develop 实测：`runV15Execution(` 只有两个调用点（`server.js:5590` 本地、`:6711` 云批次），`launchExecutor:` 在 `:5606` 与 `:6746`；组件检查 `:5482`，握手在 `:5490` 一带（`handshakeFresh` 有 30 秒缓存）。而预扫描 PS 闸 `:4582`、就绪扫描 `:5243` **属于扫描链，不在执行链**。⇒ 别把扫描兜底和执行接线混在一次改里；混改会让"哪条门放行哪条门拦"说不清，正是这类改动最容易留后门的地方。

## 面 3（重）白名单判定面本轮不做，且必须写明"给别人用之前"是硬前置

v1.5 的 B1 是在助手本地判 `manifest.install_id ∈ cfg.pcExecutorBetaUsers`（`server.js:435/:3372/:4118`）＝用户改本机 JSON 就能自开，按既定判据（只能靠自觉＝无效）**不能当灰度管控**。develop 有服务端先例 `src/lib/server/feature-flags-store.ts:184`。本轮只在代码里保留默认关；F 段只放您那台笔记本，属可控单人验证，**任何对外放开前服务端判定必须先落地**。

## 面 4（中）新码与中文映射

develop 有 `test:contracts` 里的 `smoke-batch-error-zh-mapping`。接线时若引入 `PHOTOCRAFT_EXECUTOR_MISSING` / `PHOTOCRAFT_TIMEOUT`（v1.5 已建两码），必须同笔补中文映射，否则前端显示英文原句；而 `PC_EXE_SHA_UNPINNED`、`PC_EXE_VERSION_*` 这类只进 `details`，不进用户句子。

## 面 5（中）`existingPsExe()` 被当引擎校验器用（语义雷）

v1.5 判引擎存在性写的是 `existingPsExe(cfg.pcExePath)`。实测 `server.js:408-414` 这函数只做"路径存在且是文件"，不校验是不是真的 Photoshop.exe ⇒ 功能上今天没坏，但这是**语义借用法**：将来给 PS 加真实名校验，或者有人往里加 COM 探测，引擎路径会被连带影响。接线时换中性名 `bundledEnginePresent()`，并把"引擎文件存在性"与"PS 存在性"分成两个函数。

## 面 6（中）为什么新防线复用旧码——以及它的代价

`v15-runner.js:36` 把终止码闭集成五码集合，`:208` 是 `issueCode = TERMINAL_CODES.has(result.code) ? result.code : 'EXECUTOR_FAILED'`。⇒ 任何新增码在上报时被**折成通用码**，等于新增码即静默降级。所以本轮刻意复用 `SOURCE_STALE`、把差异只写进 `details`。代价要说白：用户看到的句子与"原文真的变了"相同，不够准；要准就得扩 `TERMINAL_CODES` + 服务端报价/结算/回执/前端四层同步 + fixture，那是一整班车，不该塞进这条免 PS 线里顺手做。
