03别人怎么做（GitHub 上可查到的四类做法）

做法一

限制在办数量（WIP limit）——最直接对应你的问题

  • Personal Kanban（Jim Benson / Tonianne DeMaria）只有两条规则：可视化你的工作 ＋ 限制在办数量。原话："Agree how much can be in 'Doing' at once so people can focus, finish, and learn, instead of juggling too much, finishing too little, and drowning in half-done work."　personalkanban.com
  • Atlassian WIP 限值说明：同时办太多会直接过载。　atlassian.com/agile/kanban/wip-limits
  • GitHub Projects 原生支持看板列 WIP 上限，超了给警告；官方建议"别让看板变成垃圾场，不再相关的 issue 要归档或关掉"。
  • 业界口号："Stop starting, start finishing"。
做法二

干脆不要 backlog —— Shape Up 的"赌注制"

Basecamp 的 Shape Up（免费在线书 basecamp.com/shapeup）三条核心：

  • 时间固定、范围浮动：先定"这事值多少时间"（appetite），再决定这么长时间里做到什么版本。原话对照："Estimates start with a design and end with a number. Appetites start with a number and end with a design."
  • 没有 backlog：这一轮没选上的提议不自动结转，想做要重新提一次——避免"越攒越多、没人敢删"的坟场。
  • 断路器：到期没做完默认不延期，项目直接砍掉；要接着做必须重新拍一次，不能靠惯性拖。
  • 配套 6 周干 ＋ 2 周冷却：冷却期不排新活，只修 bug、清尾。理由很直白——没有冷却期，疲劳和小毛病会一直堆。
做法三

分支短命、合完就删

  • Trunk-Based Development（Paul Hammant，trunkbaseddevelopment.com，源仓库 github.com/paul-hammant/tbd）：主干一条，抵制建长期分支，每人至少每 24 小时往主干合一次；需要长周期的变更用 feature flag 或 branch by abstraction，而不是开一条活三个月的分支。发布分支"发完就删"。
  • GitHub 官方 GitHub Flow（docs.github.com）：开分支 → 改 → 提 PR → 合 → 删掉分支。两条原话对你特别对症：
    ① "Make a separate branch for each set of unrelated changes… if there is a delay in one set of changes, your other changes aren't also delayed."
    ② "After you merge your pull request, delete your branch. This indicates that the work on the branch is complete and prevents you or others from accidentally using old branches."
做法四

把"完成"定义清楚——只有"已合并 ＋ 已验证"才算完

  • 一个真实开源仓库的治理文档把状态分为 Done / In progress / Design / Not started / Experimental / Deferred / Rejected（不做，保留理由），并写明："只把 PR 已合并称为 Done，不要把'有人提出'或'代码已开分支'当作完成。"　github.com/askdkc/dsh-cli
  • 另一份 GitHub 上的路线图方法文档主张默认用 Now / Next / Later 三档，且明确区分"roadmap 是一组赌注，backlog 是可能工作的库存"，Later 保持不确定、写清非目标。　github.com/stylusnexus/agent-plugins
附加

Owner 自己的精力边界

GitHub 官方 Open Source Guides 有一篇专讲维护者过载（opensource.guide），把"Not saying 'no'"（不会说不）列为过载的首要成因之一，建议把"我做什么、不做什么"写进 README 当作挡需求的凭据。原话："You can't say yes to every request."
