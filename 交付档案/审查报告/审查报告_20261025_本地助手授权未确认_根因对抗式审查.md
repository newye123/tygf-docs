# 本地助手「授权尚未确认」到底卡在哪

**承接**：Owner 报「本地助手已连接，但当前授权尚未确认」＋同一屏下方「无法连接本地助手（http://127.0.0.1:49152）」。10-25 10:1x 已按「浏览器身份没和新助手握过手」处置过一轮（`AI_MEMORY/TASK_LOG.md:60-64`，替浏览器身份补配对、bindings:3、脚本终验 `authorized:true`），现象仍在。

**方法**：基线 `worktrees/develop` `dbc434ff`（2026-10-25 13:51）。只读取证 + 真实浏览器对照实验 + 受控 mock 对照；不改任何授权判定、计费判定、执行判定。

**一句话结论**：不是授权问题。浏览器在 **CORS 预检**阶段就把请求拦下了——助手只放行 `Content-Type, x-tygf-ticket`，而客户端从 **3.7.25** 起每个请求都带 `x-tygf-install-id`。请求从未到达助手，所以助手侧一切正常、日志一片干净；所有基于「助手日志/脚本直连」的排查都会得出「助手没问题」，于是每一轮都回到授权层，永远修不到这里。

## 一、证据链（全部实测，可复跑）

### 1. 助手活着，且它认为授权是有效的

```
GET http://127.0.0.1:49152/ping → 200
{"alive":true,"version":"3.7.27","assistantBuildId":"verify-lease-20261025-r1",
 "activationRequired":false,"activationStatus":"active",
 "activationExpiresAt":"2026-11-03T06:30:24.047Z", ...}
```

本机授权槽（解密 `.tygf_session` 后只读非密字段）：

```
https://test.tuyigf.com   installId=3d1550e7  expiresAt=2026-11-08T02:09:36Z  bindings=3
https://tuyigf.com        expiresAt=2026-10-27T09:57:03Z
http://localhost:3000     expiresAt=2026-11-03T06:30:24Z
```

即：**授权数据是对的**（测试站槽还有 14 天、绑了 3 个身份），`/ping` 也如实报告 active。问题不在授权。

### 2. 客户端从 3.7.25 起给每个助手请求都加了一个头

- `src/lib/workbench/local-assistant-client.ts:408-411` 定义 `assistantInstallIdHeaders()` → `x-tygf-install-id`
- `src/lib/workbench/local-assistant-client.ts:279` 在 `fetchLocal()` 里**无条件注入**（18 个调用点），另有 6 处显式注入（`:615 :903 :1748 :1814 :1835 :2063 :2194 :2269 :2508`）
- 引入这笔头的提交：`6c15cc4c`（2026-10-24 20:06，「多绑定——同站点多账号授权槽按安装号选择」，3.7.25）

### 3. 助手只放行两个头

修复前 `download/local-assistant/server.js:2686`（补齐后该行在 `:2690`）：

```js
'Access-Control-Allow-Headers': 'Content-Type, x-tygf-ticket',
```

`x-tygf-install-id` 不在表里 ⇒ 浏览器预检不通过 ⇒ `fetch` 直接抛 `TypeError`，请求**根本没发出去**。

### 4. 真实浏览器对照（同一台机器、同一个请求、只差一个头）

页面来源 `http://127.0.0.1:3000`，目标 `http://127.0.0.1:49152`：

| 组 | 请求头 | 结果 |
|---|---|---|
| A 对照 | `Content-Type` + `x-tygf-ticket` | **成功 HTTP 403**（可读，`code=ASSISTANT_TOKEN_MISSING`，121 ms） |
| B 实验 | 再加 `x-tygf-install-id` | **浏览器拒绝**：`TypeError: Failed to fetch`（31 ms） |
| C 复跑 B | 同上 | **浏览器拒绝**：`TypeError: Failed to fetch`（35 ms） |

### 5. 受控 mock 对照（排除"探针失灵"）

两个本地 mock，唯一差别是 `Access-Control-Allow-Headers` 里有没有这个头：

```
A 允许头不含 x-tygf-install-id (49998): 浏览器拒绝 TypeError: Failed to fetch
B 允许头含 x-tygf-install-id (49999): 成功 HTTP 200 {"ok":true,"mock":49999,"sawInstallId":true}
```

### 6. 修复后同一份代码在同一浏览器里通了

把补丁打到 `server.js` 副本、起在 49318：

```
现役 3.7.27 (49152):        浏览器拒绝 TypeError: Failed to fetch
打过补丁的同一份代码 (49318): 成功 HTTP 403 {"ok":false,"valid":false,"code":"HTTP_404",...}
```

（403/HTTP_404 是隔离副本没有云端验票端点，与本次判定无关；关键是**请求真的到了、响应真的被浏览器读到了**。）

### 7. 助手日志里没有任何一条浏览器请求

- `logs/engine.log` 尾部只有回执投递告警（`ECONNREFUSED` ×4），没有一条授权/验票记录
- `logs/assistant-events.log` 最近的 `POST /v1.5/authorization/check` 全部落在脚本作业时段（00:46–03:44 UTC），**Owner 点浏览器的那几次一条都没有**

这解释了为什么「查助手日志 → 一切正常」：请求在浏览器里就被拦掉了，助手没有机会留痕。

## 二、为什么这个现象"一直修不好"（元层原因）

1. **验证通道选错了**。所有"已修好"的终验都走 Node/curl 直连（`TASK_LOG.md:63` 的 `authorized:true, bindings:3` 就是脚本验的）。Node 没有 CORS，浏览器才有。**唯一会失败的通道，恰好是唯一没被用来验收的通道。**
2. **界面把"连不上"说成"授权失效"**。`ASSISTANT_UNREACHABLE` 不在网络类码表里（`src/lib/workbench/error-messages.ts:263-271`），于是横幅走第三分支（`src/components/workbench/assistant-setup-banner.tsx:157-165`），显示"授权尚未确认"并给出**「重新授权」**按钮——而这条路走的是同一个被拦的请求，点多少次都一样。
3. **按钮本身也不是真配对**。`assistant-setup-banner.tsx:240 / :256` 绑的是 `checkAssistant()`（只重查、不配对），10-25 10:1x 已登记为「假按钮 / C4 未修」（`TASK_LOG.md:62`）。
4. **门禁不覆盖 CORS**。`scripts/verify-client-assistant-contract.cjs` 只比对 prepare 载荷字段；`scripts/smoke-assistant-origin-ticket.mjs` 只做 `isAllowedOrigin` 的源码正则；**没有任何门检查"客户端发什么头 / 助手允什么头"**。所以 3.7.25 加头、CORS 没跟，全套测试照样绿。

## 三、影响面

- 从 3.7.25（10-24 20:06）起，**任何已激活的浏览器**都无法使用工作台里需要助手的动作：选文件夹、预扫描、准备、执行、配对、诊断、排障上传。只有 `GET /ping`（简单请求、不带自定义头）能通——正好对应截图里"已连接但什么都做不了"。
- 未激活/无 `anonymousInstallId` 的浏览器不受影响（这也是一部分自测看起来正常的原因）。

## 五、残留检验点（如实）

1. **修复还没到你机器上**。改的是 `server.js`，必须打成新助手安装包（建议 3.7.28）并安装一次才生效。**当前树里仍是 3.7.27 + 行为已变，这不是可发布态**：发版前必须把版本链五处（server.js / report-renderer / installer.iss / 助手 package.json / server-setup）一起升到 3.7.28 并实编安装包。本轮没有做，也没有 push / 部署 / 装包。
2. **云端验票往返偏慢**：一次真实验票探针 `elapsedMs=9001`（预算 30 s），历史上有 `VERIFY_TIMEOUT`（`engine.log` 03:44 UTC，10 010 ms）。CORS 修好之后这条慢链路会重新暴露在用户路径上，属既有风险（ISSUES #142），不是本次引入。
3. **4 条历史回执仍投不出去**：`pendingReceipts.count=4`，`lastErrorCode=ECONNREFUSED`，最老 3 789 807 秒（约 43.8 天）。根因是助手 `serverUrl=http://localhost:3000` 而云端不在本机——与本问题同源于"本机地址误配"，但属另一笔账。
4. **`/ping` 的 active 是 localhost:3000 槽**，不是测试站槽。两个槽都在有效期内，不构成故障，但排查时容易看错。

## 六、覆盖缺口

- 没有在 Owner 那台机器的**真实登录态 + 真实站点**下复验（需要你的会话）；本机用"同源语义 + 同浏览器 + 同请求"的对照替代，结论强度足够，但严格意义上不是现场。
- 没有验证 Chrome 版本相关的本地网络访问（LNA）授权提示——`/ping` 能通说明你的浏览器没有拦本地网络访问，所以不构成干扰项。
- 没有审 3.7.26 / 3.7.27 的其他改动（本次只追这一条链路）。
