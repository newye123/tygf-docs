日期：2026-10-27 16:5x（各钟点以每条日志原式为准） 被审对象：交付档案/执行方案/执行方案_20261027_发版不再砸客户_讲人话定稿.md 里 Owner 16:3x 追加令带进来的第 3 批（D6 改口） 审查方式：不是纸上过一遍。在 tmp/selfexit/ 里造了一对假托盘＋假引擎和一份复用同一段安装脚本逻辑的测试安装器，真跑了 8 个 case，包括"故意把要拦的东西放出去，看它拦不拦得住"。 结论：方案的方向成立，但我第一版的实现形状是错的，已经被实测打回并改掉；改完的四条安全性质逐条有日志。

01一、先说被打回的那一条（这是这轮最有价值的产出）

我方案里第 3 批第 1 步原本打算这么写：新增一个 图译工坊本地助手.exe --exit，它去杀引擎、把退出标志置真、自己退出，安装器调它就行。

实测证明这样做不成立。

日志 log-T1.txt 原文（16:49 那次）：

```

[selfexit] --- 自关开始（SELF_CLOSE=1）---

[selfexit] --exit 返回码 = 0

[selfexit] 互斥体 15 秒未释放 ⇒ 走旧版兜底强杀

[selfexit] taskkill 托盘 返回码 = 0

[selfexit] taskkill 引擎 返回码 = 0

[selfexit] 兜底后互斥体已释放

```

--exit 很高兴地返回 0，可是那个正在跑的托盘根本没退出。原因很朴素：exiting 是一个进程内的变量，--exit 是另一个进程，它改不到别人的变量；那个托盘的 5 秒定时器还在，引擎被杀了又拉起来。要不是我这条链后面还留了"互斥体没释放就兜底"，装到一半就会因为文件被占而失败——也就是说，我差点交一个"只在兜底那一步才碰巧能用"的方案。

根因写成人话："叫它自己退出"必须是"正在跑的那个进程"自己执行的，不能由别人替它退出。

改法（已验过）：--exit 只做三件事——判断忙不忙、把一个命名事件点着、然后等托盘的互斥体消失。正在跑的托盘在自己的循环里看到事件点着，就执行它本来那条干净退出路径（停定时器 → 杀引擎 → 释放互斥体 → 退出）。改完的日志 log-T4b.txt（16:55）：

```

[selfexit] --exit 返回码 = 0

[selfexit] 托盘互斥体已释放

...

Dest filename: ...\app\fake-engine.exe

Dest filename: ...\app\fake-tray.exe

[selfexit] 收尾：已拉起托盘

```

1.1 秒释放、没走兜底、文件真被覆盖、装完自动起来。方向对，实现形状换了。

02二、第二条差点写错的判据：忙不忙不能看 errorCode

我本想用"有没有错误码"来判"能不能关"。在本机那个正在跑的真助手上做了一次只读请求（没动任何进程）：

```

HTTP 200 bytes 438

busy= false phase= "idle" errorCode= "PHOTOSHOP_COM_UNAVAILABLE" lastJob= null

```

errorCode 在明明空闲的时候也是非空的（这台机器没开 Photoshop 的 COM）。如果拿它当"忙"，所有没装／没开 Photoshop 的客户机都会永远装不上新版。 判据只认一个字段：busy === true（该字段由 download/local-assistant/server.js:2650 的 publicQueueStatus 公开）。

04四、顺手挖出来的一条老老虎（今天就存在，与客户点不点"退出"有关）

托盘菜单"退出本地助手"今天走 TrayHost.cs:277 的 ExitAssistant()，它不看忙不忙，直接 process.Kill()（:146）。跑批的时候点它，会打断 Photoshop 执行；助手自己的代码写着打断之后落下恢复锁，server.js:2380 那句原文是「检测到未完成 Photoshop 执行或恢复标记；请先人工核实现场，不会自动重试」，:2575 是「恢复确认前不会接收新任务」。

也就是说：客户今天手动退出，就可能把自己的助手锁成不能用，而且没有任何提示。第 3 批把忙判断放进这条路径本身，这个老洞跟着一起堵。
