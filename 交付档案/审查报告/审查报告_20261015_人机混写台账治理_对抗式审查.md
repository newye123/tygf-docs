## §01 判定

**「锁」锁不住你，「恢复」会吃掉你的意思，能用的只有「协议」。**

- 你是这张多维表格的**所有者**。飞书官方文档原话：所有者/管理员「默认拥有最高权限……权限不可修改」，对全部行和列都有新增、编辑和删除权。⇒ **任何「把机器列锁成只读」的平台手段，对你本人天然无效**，只能防将来进场的协作者。
- 反过来，「手改了就用机器值盖回去」（Jira 官方 KB 的做法）有两个已知毛病：**意图丢失**（你改「已交付」是想拍板，不是噪音）＋**人不被告知**（Jira KB 自己承认「被回改的用户可能不知道发生了什么，甚至会以为系统坏了」）。
- 六家公开实践里活得最久的做法（IssueOps、Renovate）走的是第三条：**机器把归属讲清楚、给人一个明确写入口、覆盖前先对账、必要时先问人**。
- 我们已有一半（「Owner 批注」列 + 回读闸）；缺的另一半是「投影前对账、不静默覆盖」——一个**约半天**的 P0 小改造（§05）。

## §02 现状机制 与 一个真实漏洞（本机实测）

| 机制 | 位置 | 关键行为 |
|---|---|---|
| 单向投影 | `scripts/sync-task-ledger.mjs:13,92-105` | 只写 8 个机器列，**永不触碰「Owner 批注」**；payload 整列无条件生成 |
| 幂等比对 | `scripts/sync-task-ledger.mjs:72-86,144-165` | 拉飞书现状**只用于「任务ID → record_id」映射**——不做格值对账；命中即整行覆盖 |
| 回读闸 | `scripts/feishu-readback.mjs:124-154` × `scripts/control-plane.sh:39-59` | 漂移/新批注/多余行/缺行/**重复行**五类告警（重复行＝当夜事故后新增，见文末后记）；**只在每日日检里跑** |

**漏洞（本次审查最要紧一条）**：幂等比对不比对格值、覆盖又是整行无条件——**若你在表上手动改了机器列，而当天我们先跑了一次投影（还没跑到日检），你的改动会被静默覆盖**，回读闸永远看不见它。窗口最长 24 小时。

旁证（反面）：20:23 那次 OPS-GH 漂移被回读抓到，是因为它先于投影存在。**回读能看见「不一致」，但分不清「你手改的」还是「我们还没投影的」**——所以它只能当日检兜底，不能直接拿去卡投影；这就是 P0 要对账的原因。

## §03 别人怎么处理（6 家，全部当日一手资料）

| # | 对象 | 做法 | 对我们的裁决意义 |
|---|---|---|---|
| 1 | **IssueOps**（github.com/issue-ops；github/command） | 人用 issue 表单下结构化请求、用评论下命令；机器 parse→validate→打 label 状态机 | 其解析器自述「只要内容没被人大改就能可靠解析」——**反证自由手写会打碎机器管道**，所以要给人**结构化通道+尽早校验** |
| 2 | **Renovate**（22.7k★，mend.io） | 机器拥有 PR（描述/标签/提交）；人一旦自己动过分支，bot 检测「最后提交者不是自己」即**冻结不动**，要求人显式勾选 rebase 才覆盖，并警告 "custom changes will be lost"（discussion #22076）；正式交互=checkbox/标签/`rebase!` 标题（docs/updating-rebasing） | **别静默覆盖**；机器覆盖前必须有人的显式动作 + 风险警告 |
| 3 | **GitHub Projects V2** | 官方访问控制只有项目级 Read/Write/Admin 三种角色（当日文档实测），**没有字段级权限**；社区通行玩法=「仓库为准，label 单向同步到字段」 | 连 GitHub 都不做「字段锁」；行业答案是**单向投影+对账** |
| 4 | **Jira** | 「只允许某组人改指定字段」的官方需求（JRACLOUD-62157）挂了多年未做；官方 KB 替代方案=Automation「检测手改→改回原值」（{{fieldChange.fromString}}），**并强制建议配通知** | 「恢复」可做，但**必须配通报**；否则人会以为系统坏了（KB 原话） |
| 5 | **Airtable** | 有真字段级编辑权限（Team 版起）；官方推荐用法原话：「保护一个驱动工作流的字段（比如触发自动化的勾选框），**同时让页面其余部分可编辑**」 | 若将来要上锁，这就是对标形态（飞书高级权限有同款） |
| 6 | **飞书多维表格·高级权限**（一手帮助文档） | 字段级「可阅读/可新增/可编辑」确实存在；**但「所有者」「管理员」权限不可修改、对全部行列可增删改** | **平台锁=「防协作者」，不是「防你」**——直接判决：锁不能当主方案 |

## §05 协议 v1：以后就这么管

**一句话**：批注=你说的；机器列=我说的；你手改机器列=**你说的算（我记账）**；改 ID/删行=我不动、先问你。

| 你动了什么 | 发生什么 |
|---|---|
| 「Owner 批注」写任何字 | **永不覆盖**；最近一次日检/同步我会读到、落实，并在推送里回你 |
| 状态/标题/负责人/下一步/到期日/出处 手改 | 视为**你的命令**：采纳 + 记进台账（来源注明「飞书手改」）+ 下次报告点名；有歧义按字面采纳并请你复核 |
| 任务ID 手改 | 身份列=恢复原值 + 告警（防两账串行） |
| 更新时间 手改 | 机器戳=恢复（它不是给人改的） |
| 新增整行 | 新任务请求：内容齐→进账「等您定」；空行→告警等你处置 |
| 删行 | 不生效（下次投影会补回来）；要停任务请在批注写「不做/删掉」 |

**节奏**：任何投影前先对账（P0）；每天早晨日检回读；想更快→直接对话（最快通道）。

**P0 落地（约半天，等你一句话）**：`sync-task-ledger.sh` 加「投影前对账闸」——

- 每格三值比对：台账值 **L** / 飞书现值 **F** / 上次投影快照值 **P**（新增 `--state-out` 落 `tmp/readback/last-projected.ndjson`）；
- 分类：L=F 无碍；**L≠F 且 F=P ＝你在表上改的**（拦下）；L≠F 且 L=P ＝正常待投影（放行）；两边都动＝冲突（拦下）；
- 拦下的行默认**不动**（其余照常投影）；`--force`＝全量覆盖（你说了算的显式口子）；
- 验证：2 个合成夹具 + 真表空跑。

**P1**：机器列加字段描述「机器列，勿手改；要改请写 Owner 批注」；清空行。
**P2（多人时代）**：开高级权限+自定义角色（机器列=可阅读、批注列=可编辑）——防的是协作者，不是你。

## §06 未核实 / 边界

1. 批注去重是刻意的（`feishu-readback.mjs:116-120`，同 taskId+同文本只报一次）——若你把同一句话再写一遍当催办，可能不报；**换句话写**即可。
2. 秒级竞态：对账快照的那一刻你正在键入，可能读到中间态（飞书并发写有 Write conflict 1254291，官方建议加延迟/重试）。
3. 「所有者锁不住」出自飞书帮助中心 2026 年版文档；产品规则可能变。
4. `lark-cli +advperm-enable / +role-create` 已核实存在（help 原文：需管理器、仅支持 custom_role）；其角色 JSON 的字段级 `field_perm` **未构造实测**（开放平台 API 文档已确认该参数存在）。
5. GitHub Projects「无字段级权限」依据=当日官方访问控制文档只列项目级角色；未穷举第三方插件。
