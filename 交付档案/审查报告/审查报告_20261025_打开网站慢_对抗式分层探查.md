# 审查报告_20261025_打开网站慢_对抗式分层探查

## 结论先说

慢的不是网站本身，是**你到网站之间那段网线**。

你的请求从广州出发，被路由到**美国洛杉矶**的机房，再从洛杉矶跨洋回源到**新加坡**的服务器，再原路回广州——绕地球一圈半。这一段实测**一半的包会丢**，所以页面经常传一半就卡死：20 次里 6 次拿不完页面，真浏览器直接报超时打不开。

**这对你意味着：** 网站代码和服务器都没问题（服务器本地吐完 98KB 只要 16 毫秒），改代码只能省掉几秒的「绕路回源」，**真正的几倍差距在换一条网络路径**——这需要你拍一个方向（下面方案 B）。今天刚上线的字体分片（14MB → 407KB）已经把最大的一块解决了，剩下的慢主要就是这段链路。

一句话：**能改的我都列出来了（方案 A），但 A 只能治标；要治本必须动网络路径（方案 B）。**

## 现场：真浏览器里的 263 秒

先看现象再看原因。用真实浏览器打开 `https://tuyigf.com/`，读它的性能时间线：

- 首页 HTML 本身 **1.46 秒**就拿到了首字节——不算慢；
- 但页面里的 JS 一直下不完：**8 个 JS 文件同时在第 11.4 秒发起请求，同时等到第 134.3 秒才拿到第一个字节**，整批文件拖到 **第 263.5 秒（4 分 24 秒）**；
- 到我取数那一刻，页面状态还停在 `loading`，`domInteractive`、`DOMContentLoaded`、`loadEvent` **全是 0**——**页面从头到尾没有真正加载完成过**；
- 一共 23 个资源、已传 251,966 字节（还差得远，全部要 1.34 MB）。

**8 个文件同时卡住、同时恢复**——这是 HTTP/2 队头阻塞的标准指纹：所有文件共用一条连接，只要有一个包丢了，整条连接上的所有文件一起等，直到重传成功才集体放行。配合第 1 层实测的 50% 丢包，这个 134 秒就是这么来的。

**这对你意味着：** 你感觉到的「打开这么慢」，不是首页 HTML 慢（它 1.46 秒就到了），而是**页面卡在 JS 上，转圈转了几分钟**。网站渲染不出来，看起来就像「网站挂了」。

## 探查方法：先排除错误答案

对抗式审查的第一步是证伪。下面三个「看起来像根因」的东西，都被实测排除了：

| 嫌疑人 | 实测结果 | 结论 |
|---|---|---|
| 服务器太慢 | 服务器自己访问自己：**16 毫秒**吐完 98KB | ❌ 排除 |
| Cloudflare 配置错了 | 新加坡服务器访问同一域名：TLS 38ms、首字节 98ms、全程 99ms | ❌ 排除（CF 就近调度正常） |
| 页面太大 | 今天已做字体分片，整页 14.13 MiB → 446,865 B | ⚠️ 已解决一大半，但仍有 1.34 MB |

**真正的问题藏在一个对照里**：同一个 Cloudflare IP（`104.21.11.101`），

- 从**新加坡服务器** ping：8 发 8 收，**0% 丢包，平均 2.076 毫秒**
- 从**你的网络（广州联通）** ping：12 发 6 收，**50% 丢包，平均 299 毫秒**

同一个 IP、同一时刻、不同的出发点，差了 144 倍延迟 + 半数包丢失。问题不在 Cloudflare，也不在网站，在「广州 → Cloudflare 边缘节点」这段路由。

## 三层根因（按影响大小排）

### 第 1 层：到 Cloudflare 边缘的链路——掉包一半（占大头）

**证据（全部本机实测）：**

- 你的网络位置：广州，中国联通，AS17623（`ipinfo.io` 返回 `163.125.214.150 / Guangzhou / AS17623 China Unicom Shenzen network`）
- Cloudflare 边缘落点：**洛杉矶（LAX）**。4 次响应头 `CF-RAY` 后缀全是 `-LAX`
- 丢包：ping `104.21.11.101`，发 12 收 6，**50% loss**，RTT 最小 272 / 平均 299 / 最大 312 毫秒
- 连接成功率：连续 20 次建 TCP，**15 成功、5 失败**（建连 p50 = 234 毫秒）
- 传输成功率：连续 20 次下载首页，**14 次拿全、6 次只拿到一半**（25 秒超时）
- 传输速度：**1.4 – 16 KB/s**（正常应是几百 KB/s）
- 真实浏览器打开 `https://tuyigf.com/` → **`ERR_TIMED_OUT`**，直接打不开
- 协议对比（各 5 次）：HTTP/1.1 成功 3 次、**HTTP/2 成功 0 次**——高丢包下多路复用反而更糟（一个包丢，整条流卡住）

**为什么落在洛杉矶而不是香港？** 这不是我们能配的——Cloudflare 官方社区确认：中国大陆出海流量走哪个节点，主要由你的运营商（电信/联通/移动）的路由决定，「很多流量被送到 LAX」是已知现象（`community.cloudflare.com` 官方员工 sjr，2024-08-22）。Cloudflare 在中国大陆没有普通版节点，要国内节点必须 Enterprise 企业版 + 中国网络附加包 + ICP 备案。

### 第 2 层：首页每次都跨国回源——绕了两趟太平洋

**证据：**

- 首页声明为强制动态渲染：`src/app/(zh)/page.tsx:12` `export const dynamic = 'force-dynamic'`
- 原因是它要服务端读 cookie 注入登录态（`page.tsx:35`）、合并功能开关（`:38`）、判断编辑态（`:42`）
- 结果：响应头 `Cache-Control: private, no-cache, no-store, max-age=0, must-revalidate` + `cf-cache-status: DYNAMIC` → **Cloudflare 每次都必须回源，永远不缓存**
- 服务器在**新加坡**（`ipinfo.io`：Singapore, Tencent AS132203），而边缘在**洛杉矶** → 每次回源是 LAX ↔ SIN 跨太平洋

**回源到底多贵**（把 TLS 握手扣掉，只算纯首字节等待，HIT = 边缘命中不回源，ORIG = 回源，交错采样 6 组）：

| 组 | 边缘命中 | 回源 | 回源多花 |
|---|---|---|---|
| 1 | 1.903s | 1.791s | -0.112s |
| 2 | 0.326s | 0.960s | +0.634s |
| 3 | 0.710s | 0.687s | -0.023s |
| 4 | 1.322s | 7.032s | **+5.71s** |
| 5 | 0.319s | 1.933s | **+1.614s** |
| 6 | 1.524s | 20.007s | **+18.48s（超时）** |

中位多花 0.7–1.6 秒，长尾 5.7 秒，最坏直接超时。

**对照**：新加坡服务器访问自己的网站（边缘 SIN，同城回源）只要 **99 毫秒**。同一份代码、同一个 Cloudflare 账号，差 100 倍——差的就是「边缘在哪」和「回源跨不跨洋」。

### 第 3 层：页面要下 1.34 MB、23 个文件

**证据（从源站直连取的稳定结构，不经 Cloudflare）：**

| 类型 | 个数 | 字节 |
|---|---|---|
| JS | 15 | 760,613 |
| CSS | 3 | 173,944 |
| 字体 | 5 | 406,956 |
| **合计** | **23** | **1,341,513** |

首页 HTML 文本 98,126 字节，含 18 个 `<script>`、14 个 `<link>`，预载 1 个脚本 + 5 个字体分片。

**换算成你的体感**：

- 在实测的 15 KB/s 下：1.34 MB ≈ **89.4 秒**
- 即使链路正常到 150 KB/s：也要 **8.9 秒**

字体那 407 KB 是今天刚优化的（原来整包 14.13 MiB）。如果没做那次分片，同样的链路要 **16 分钟**。

**顺带发现一个可改点**：字体在源站的缓存头是 `Cache-Control: public, max-age=0`（立即过期），导致 Cloudflare 每次都要回头源校验（响应状态 `REVALIDATED`）。JS 的头是对的（`max-age=604800, public, immutable`），字体应该同样处理。

## 优化方案（请拍一个）

### 方案 A：改代码，我能直接做（治标，省 1–18 秒的回源）

| # | 动作 | 收益 | 风险 |
|---|---|---|---|
| A1 | 让**未登录访客**的首页可被边缘缓存（现在读 cookie 导致永不缓存） | 省掉每次 0.7–18 秒的跨洋回源 | 必须严格区分带 cookie / 不带 cookie 的请求，否则登录态可能被缓存泄漏——这是唯一红线 |
| A2 | 字体缓存头从 `max-age=0` 改成 `immutable` | 字体不再每次回源校验 | 无（文件名不变内容不变） |
| A3 | 合并 3 个 CSS、收紧 15 个 JS 分片的加载顺序 | 23 次往返降下来，在 50% 丢包下失败概率显著下降 | 需回归测试，不能弄坏首屏 |
| A4 | 关掉 HTTP/3（QUIC） | 第三方报告称国内部分网络干扰 QUIC | **未核实**——我的 curl 不支持 h3，无法实测，需要真浏览器验证才能做 |

**A 的天花板要说清楚**：即使首页 100% 命中边缘，你到洛杉矶那段 50% 丢包还在。A 能把「白等几秒回源」去掉，但**不能让网站从打不开变成秒开**。

### 方案 B：换网络路径（治本，需要你拍 + 可能有成本）

| # | 做法 | 效果 | 代价 |
|---|---|---|---|
| B1 | Cloudflare 中国网络（Enterprise 版 + 中国网络附加包 + ICP 备案） | 国内有真实节点，延迟降到几十毫秒 | 贵（企业版按需报价），且需要 ICP 备案 |
| B2 | 换/加一层国内 CDN（阿里云、腾讯云） | 国内访问 <50ms | 需要 ICP 备案；要改 DNS |
| B3 | 优选 Cloudflare IP（把域名解析到延迟更低的 Cloudflare 任播 IP） | 低成本，可能立竿见影 | 不稳定：IP 会被墙、会变，要长期维护 |
| B4 | 源站从新加坡迁到香港 | 回源从跨洋变成近距离 | 迁移工作量 + 新加坡服务器的其它用途要确认 |

**B3 是「先试试看」的低成本选项**，B1/B2 是「一次到位」的贵选项。

### 方案 C：先把测量补齐（我建议先做，再拍 B）

1. **多点位复测**——我只有广州联通这一个点，不能代表所有用户。你在电信/移动网络、或让外地朋友各测一次，就能知道是全国性还是联通局部问题。
2. **开 Cloudflare Browser Insights**（免费功能）——拿真实用户的数据，而不是我这台机器的样本。
3. **给 nginx 日志加耗时字段**——现在日志里没有 `$request_time`，无法统计真实用户平均等多久（`/var/log/nginx/access.log` 当前是默认格式，实测确认）。

## 残留与缺口（如实）

- **只有一个测点**：广州联通。所有网络结论都基于这一台机器，样本单点。
- **「更慢」的时间对比是待确认**：没有同条件历史基线，只有文字记录。
- **HTTP/3 未测**：本机 curl 不支持 `--http3-only`（实测报错 `the installed libcurl version does not support this`）。虽然响应头 `alt-svc: h3=":443"` 显示站点支持 h3，但效果未知。

- **真浏览器取证受限**：本机浏览器打开站点报 `ERR_TIMED_OUT`，拿不到真实加载瀑布图——这本身就是最直接的证据。
- 今天上线的字体分片（`main` 分支 `df93c257`）已生效，5 个字体分片实测全部可达，共 406,956 字节，与方案数字逐位一致。
