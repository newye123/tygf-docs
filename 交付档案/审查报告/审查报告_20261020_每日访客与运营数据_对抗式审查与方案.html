结论

07建议动作：三档，按代价排

  1. 档一 · 今天，0 改动，约 1 小时可验收。你自己在 CF 控制台把时间范围拉到 30 天看一眼（今天唯一零成本能看到的一类访客读数——站内从没存过它，我无凭据）。或者给我一个只读 Analytics Token（只进服务器 root-only 环境文件，禁进仓库），我做 scripts/site-traffic-daily.mjs：按 hostname 拉每日 uniques / pageViews / requests 落一行到账本，并每天早上推飞书一句人话——「昨天官网 X 个访客、Y 次浏览，申请 N 条，激活 M 台」。验收：同窗两次幂等；没实测到的字段不写进口径；脚本只出聚合计数，不打印 IP/UA 原文。
  2. 档二 · 本周，与发布闸同一批。nginx 日志三件事：格式加 $host 与 $request_time、?key= 类参数脱敏（含 Referer 第二泄漏面）、set_real_ip_from CF 段＋real_ip_header CF-Connecting-IP。这件事本来就已卡正式发布，不该为统计单独立项；做完才有分站、真实 IP（UV 才成立）、AI 爬虫事实源、可测时延。判据：单行测得 host 非空、key 值为 REDACTED、出现非 CF 网段 IP，nginx -t rc=0 且两站首页都过。注意该补丁动 http 块会同时影响两站日志 ⇒ 需你授权。
  3. 档三 · 等你拍过合规再动。CF Web Analytics beacon（CSP 加一行放行、Next.js 客户端路由要手动补 track()、拿不到 UTM、暂不支持自定义事件）；Umami 若要上，先把"生产引入 Postgres"当独立立项（备份/保留期/监控/内存），并更正草案那句"复用 Postgres"。Plausible / Matomo / 自建 PageView 表本方案判死，不建议再排期。
