登录态 UI 一致性 · 对抗式审查与执行方案（2026-10-21）

结论先说

你报的两个问题都真实存在，而且是同一个病根：登录这件事只活在"工作台"这一个页面里，官网首页的导航是写死的静态文字，谁登录都显示"登录"。另外还查出一件更严重的事——后台给用户填的运营备注，现在被直接当成用户名显示给用户本人。

严重程度分两级：

一是 P0（隐私泄漏）。运营在后台给某人填一句内部备注，比如"王先生 / 已付尾款"，这句话会直接出现在这个人的工作台账号菜单里；而且他在浏览器开发者工具的网络面板里也能读到原始值。不需要任何越权，只要他是登录用户就能看到。

二是 P1（体验断裂）。用户登录后回到官网，导航上还是写着"登录"，界面上完全看不出他已经登录过。

这次的性质是只读审查：没有改任何业务代码，没有部署，没有提交，只出了判定、证据和执行方案。

证据（都有出处）

- 工作台账号菜单优先用 me.name 当显示名：worktrees/develop/src/components/workbench/user-account-menu.tsx 第 77 到 81 行。同一文件第 4 行的注释还写着"展示当前登录邮箱"，跟代码自相矛盾。
- /api/auth/me 这个接口把 name、betaUserId、sessionId 一起返回给浏览器：src/app/api/auth/me/route.ts 第 21、23、26 行。登录成功的响应里也带 name：src/app/api/auth/login/route.ts 第 118 行。
- name 这个字段的来源是申请表单里的姓名或邀请码归属，不是用户自己填的资料：src/lib/server/beta-users.ts 第 73 行。
- 后台台面自己就把它标成运营字段：src/components/admin/installs-credits-panel.tsx 第 452 行写"这里的备注名用于运营识别"，第 457 行的表单标签是"姓名 / 运营备注名"。
- 首页导航无条件渲染"登录"：src/components/site/home-view.tsx 第 135 行；首页分支没有任何会话注入：src/components/site/app-shell.tsx 第 37 到 39 行。
- 首页本身是 force-dynamic（src/app/(zh)/page.tsx 第 10 行），也就是说服务端本来就能读到会话，具备做首屏直出的条件；生产实测首页响应头是 private, no-cache, no-store，共享缓存不会把一个人的首页发给另一个人。
- 顺带查出四条同类问题：同一个 /api/auth/me 被四个地方各自请求（account-gate 第 29 行、user-account-menu 第 37 行、设备会话页第 170 行、登录页第 77 行），一次打开打四个包；登录页"前往工作台"按钮实际落到营销首页（src/app/(zh)/auth/login/page.tsx 第 55、195 行，工作台是 hash 路由 #workbench）；退出登录一律跳登录页丢上下文；非首页的 SiteHeader 干脆没有账号入口（src/components/site/site-header.tsx 第 88 到 101 行）。
- 现行身份契约测试本次实跑通过：npm run test:identity-account-gate，输出 A6 account gate contract PASS。行号基线是 develop 分支的 670f7cb。

对抗式审查里最要紧的四条

一、首页做服务端直出注入会不会把一个人的页面缓存给另一个人？当前不会，因为页面是动态渲染加私有不缓存。但这是"配置碰巧对"，不是结构保证，所以执行时必须补一条测试把它锁死，否则将来有人改成静态化就会串号。

二、把三个字段裁掉会不会打坏现有的调用方？全仓搜过，接口只有上面那四个消费者，逐个读了源码：betaUserId 和 sessionId 在浏览器端一次都没被用过，name 只有账号菜单这一处在用，而那处正是要改的。裁剪安全。

三、首屏直出之后客户端又去请求一次，会不会闪一下或者水合报错？会有这种风险，所以方案要求首帧身份只认服务端下发的值，客户端不再首屏请求，后续变化由一个统一的状态提供者推送。

四、账号被停用和"网络连不上"是不是会被当成"没登录"？不能混。停用的号保留头像加一个琥珀点，菜单里写明原因，不让用户反复登录一个已经停用的号；网络问题保留上一次已知状态加重试，不能回落成"登录"。

外部方案对照（不凭空设计）

借的是这些成熟项目的做法，不引新依赖：Next.js 官方 App Router 认证指南（cookie 会话 + 服务端读会话渲染账号态）、Auth.js 的 useSession 三态（loading / 已登录 / 未登录，不把"未知"当"未登录"）、Clerk 的 Show 与 UserButton（未登录渲染占位，登录渲染头像菜单，同一位置互斥）、shadcn/ui 的 DropdownMenu 加 Avatar（项目现在用的就是这套 radix 组件）、Supabase 的 onAuthStateChange 配 BroadcastChannel（跨标签页广播会话变化）、Stack Overflow 79865034（刷新时先闪一下"登录"，解法是服务端直出或骨架）、OWASP API3:2023 过度数据暴露（响应只回客户端该看到的字段）。另外项目 2026-08-18 就定过不引入 Clerk / Auth.js / Supabase，保留自建身份体系，这次只借模式不换依赖。

执行方案

P0 三条。一，裁剪身份接口：/api/auth/me 只回 email、emailVerified、accountStatus，登录响应去掉 name，前端类型同步收窄，并在 §7.4 那条注释旁补一句"name 属运营字段不得下发"。二，账号菜单改成显示邮箱，不再读 name，头像首字母也取邮箱。三，首页服务端读会话，把身份摘要作为 props 下发：未登录照旧显示"登录"，可用就渲染和工作台同款的账号菜单，停用就渲染头像加琥珀点；菜单组件按需加载，不给营销首页加首屏负担。

P1 四条。抽一个统一的会话状态提供者，消掉四次重复请求；未知态渲染 34 像素圆形骨架，和头像同尺寸，不闪也不跳；用 BroadcastChannel 广播登录登出，跨标签页同步；停用和不可达分开呈现，沿用 AccountGate 现有口径，不放松任何鉴权。

P2 三条。"前往工作台"改成直接进工作台视图；退出登录后回原处并给提示，不再一律跳登录页；SiteHeader 接入同一个账号入口。

需要你拍板的一项（属产品行为变更，我没擅自动）：登录后首页要不要隐藏"申请试跑"按钮、改成"进入工作台"。

验收

命令：npx tsc --noEmit、npm run lint、npm run test:auth、npm run test:identity-account-gate、npm run test:identity-logout-device-semantics，另外必须新建一个 smoke 脚本，断言 me 接口的响应里不含那三个字段、首页输出在登录态与未登录态各自正确、裁剪后两个前端组件仍能取到 email。现在没有任何测试守着这条线，这是本次必须补的。

人工场景六条：登录后打开首页看到头像且刷新不闪；后台改备注后用户端不变且网络响应里没有 name 字段；停用账号看到琥珀点和原因说明而不是反复要求登录；未登录仍然显示"登录"且行为不变；一个标签页登出其他标签页同步变回"登录"；登录页点"前往工作台"直接落在工作台。

风险与回滚

裁字段是破坏性变更，风险是存在未登记的消费者会白屏——已经全仓搜过确认没有，回滚就是还原字段，单个提交可逆。首页直出只多一次服务端 cookie 解析，页面本来就是动态渲染，不新增渲染模式。状态提供者引入水合不一致的风险靠首帧单源来消，验收时看控制台有没有 hydration 警告。停用态保留头像可能误导，所以必须有琥珀点和文字说明，受保护操作照旧由 AccountGate 拦截。

同类问题建议单独立项，别混进这次：BetaUser.name 一个字段同时承担"用户姓名"和"运营备注"两种语义，正解是拆成用户自有的 name 和运营用的 adminNote，属数据库变更要单独评审；英文站 home-view-en.tsx 也用同一套导航样式，首页登录态方案要一并考虑，否则只修一半。

配套的交互模拟件在 交付档案/执行方案/模拟_20261021_登录态UI_修复前后.html，可以切换未登录、已登录、首屏加载、账号停用、会话过期五种状态，左边现状右边建议方案，后台备注输入框实时联动，能直接看到"左边泄漏、右边不跟随"的效果。
