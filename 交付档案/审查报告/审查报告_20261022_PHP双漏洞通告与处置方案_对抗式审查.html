PHP 的两个洞是真的，但我们的服务器没有 PHP；转来的 5.x 修复链接是坑

两件事分开说：第一，tygf-server 上没有 PHP 运行时，生产/测试两站都是 Next.js 走 nginx 反代，这个漏洞在我们这台机器上没有攻击面。第二，转来的处置方案里，PHP 5.x 给的是未修补的原始源码包，照做会得到一个"看起来升了、其实仍有洞"的 PHP 5.6.40。

VERDICT：处置方案打回 ｜ 我方主机不受影响

一句话：漏洞真实且严重（NVD CVSS 3.1 9.8），但我们的服务器不用 PHP，零动作；方案本身要改两处——5.x 的链接必须换成带 debian.tar.xz 的源包，7.x 只能写 7.4（7.0–7.3 官方没修）。

01我们的服务器用 PHP 吗：不用

实测排除（全部只读）：没有 php 可执行文件、没有 dpkg PHP 包、没有 php/apache/httpd 服务、没有 PHP 进程、没有 9000 端口；nginx -T 全量配置里没有生效的 fastcgi_pass；/var/www 三层内 *.php 数量为 0。
检查结果说明
PHP 二进制 / 包无command -v php 空；dpkg -l | grep -i php 空；/etc/php、/usr/bin/php* 不存在
服务 / 进程无systemd 无 php/apache/httpd；ps 无 php/php-fpm/php-cgi
监听端口22 / 80 / 443 / 3000 / 3001 / 53 / 20241没有 9000（php-fpm 默认口）
nginx 后端全部 Nodesites-enabled 五个站点都 proxy_pass 到 127.0.0.1:3000 或 :3001
Web 目录 PHP 文件count=0/var/www 深度 3 内无 .php
别被文件名字骗了：/etc/nginx/fastcgi_params、fastcgi.conf、sites-available/default 里出现 php 字样，是 nginx 安装包自带的模板/注释；sites-enabled 没有启用它们。看到这些文件就判"在用 PHP"是假阳性。

02漏洞本身：真的，而且严重

php.net 官方通告标题是 "Security advisory: Critical remote code execution vulnerabilities, update now"，明确写的是未认证远程代码执行。两条 CVE：

  • CVE-2026-109618：OOM 处理中断 PHP 时，请求内部数据只初始化了一半；清理阶段把无效数据当有效数据用。
  • CVE-2026-109619：请求私有状态在底层内存释放后仍存活，同一 worker 的后续请求会用到过期状态。

官方修复版本：8.5.12 / 8.4.27 / 8.3.36 / 8.2.35；另外为 7.4 / 8.0 / 8.1 提供最小源码 backport。NVD 两条均为 CVSS 4.0 9.2、CVSS 3.1 9.8（Critical）。

03处置方案的对抗式审查

F-1Important照做会留洞

PHP 5.x 的链接给错了。方案指向 php5.6_5.6.40.orig.tar.xz，这是 Debian 打包体系里的"上游原始源码"，不是修复版。实测它与官方 2019 年的 php-5.6.40.tar.xz 逐字节相同：同为 12,472,236 B，SHA-256 同为 1369a51e…56d1c，cmp 返回 0；Last-Modified 是 2019-01-11。

真正的修复在同一目录的 php5.6_5.6.40-104+0~20261021.134+…debian.tar.xz：补丁 0261-Avoid-state-corruption-via-bailout.patch 头两行明确 Fix 两个 GHSA/CVE。`.dsc` 同时列出 orig 与 debian 两个包。要用 .dsc 走 apt-get source / dpkg-buildpackage，不能只编译 orig。

失效场景：照原链接编译 → 得到 2019 年的、仍有洞的 5.6.40 → 以为已修复。这是本次最危险的一条。

F-2Important范围写大

"PHP 7.x 有官方修复版"只对 7.4 成立。实测 GitHub refs：PHP-7.4-CVE-2026-109618-109619 存在；7.0、7.1、7.2、7.3 的 CVE 分支查询全部为空。

正确写法：7.4 用官方 backport；7.0–7.3 只能升级到受支持版本，或找 LTS 厂商。

F-3Medium方案风险

"8.x 必须从源代码编译"不是官方要求。官方优先让用发行版/LTS 厂商的更新包；源码只适合没有包的情况。生产上自己编译会引入工具链、依赖和后续补丁跟踪问题，且不如包管理器可回滚。应锁定四个明确版本，不是笼统"最新 8.x"。

F-4Nit表述

"获得所有权限、对数据库任意操作"是夸大。RCE 的权限上限是 PHP 工作进程的运行用户；能否读数据库取决于该进程拿到的凭据与数据库授权。风险仍然很高，但别用"所有权限"判断爆炸半径。

F-5排除性结论我方无暴露

本机没有 PHP，两个 CVE 都无法触发。不需要升级、编译或改 nginx。

04现在实际要做什么

  1. 这台服务器：零动作。不装 PHP、不编译、不改 nginx。
  2. 如果还有别的服务器 / 托管面板 / 老项目：逐台跑只读探针，先确认有没有 PHP，再决定修补。
  3. 如果探到 5.6：不要用 orig.tar.xz；用 sury 的 .dsc 源包，或直接迁移。5.6 已 EOL 多年，打补丁只是止血。
  4. 如果探到 7.0–7.3：官方没有 backport，升级是唯一完整解。
  5. 如果探到 8.x：优先发行版包到 8.5.12 / 8.4.27 / 8.3.36 / 8.2.35；没有包再源码编译，并记录来源与校验值。
只读探针（任何 Linux 主机都能跑）：
command -v php; dpkg -l 2>/dev/null | grep -i php; systemctl list-units --all 2>/dev/null | grep -Ei 'php|apache|httpd'; ps -eo pid,comm,args | grep -i '[p]hp'; ss -ltnp 2>/dev/null | grep -E ':9000|:9001'; sudo -n nginx -T 2>/dev/null | grep -nE 'fastcgi_pass|include .*fastcgi'
