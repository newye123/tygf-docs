用四把混沌压力刀往「全盘靠 GitHub 打通」这个念头上一砍，真假立判：

### 1. 哪些数据用 GitHub 打通是真香？（`Survived: YES`）

- **第一类：自研与通用 Skills 库（如 `yt-adversarial-review`、`yt-uiux`、`yt-sansheng-liubu`、`yt-zongkong-round`）**
  - **为什么成立**：Skills 是纯方法论与确定性脚本，变更频率低、体积小（几十 KB）、跨电脑/跨工具都需要复用。照抄本机已有的 `ljg-push` 模式，建一个独立的 `yt-skills` GitHub 仓（公开版脱敏，或私有仓自用），换电脑 `git clone` 一下就能把全套大脑带走。
- **第二类：业务代码与测试站/生产站部署（已落地的「GitHub 三段轨」）**
  - **为什么成立**：本机 → `origin/develop` → 测试站拉取验证 → `origin/main` → 生产站拉取，配合 `release-preflight.cjs` 的 `merge-base --is-ancestor` 硬门禁，已经彻底解决了「本机、测试站、生产站代码不一致」的问题。

### 2. 哪些数据用 GitHub 打通会当场翻车？（`Survived: NO`，四把刀实证）

- **刀 1 · 跨接缝探针（Cross-Seam）：同机多 AI 工具「不互通」的病根根本不在 GitHub**
  - 你的 OpenCode、Qoder、CodeBuddy 全部跑在**同一台电脑的同一个硬盘**上。它们之所以互相不知道对方干了什么，是因为 Skills 分裂在 `C:\Users\ivan\.agents`、`.qoder-cn` 和 `F:\...\.qoder` 三个目录，且 `AGENTS.md` 指向了 44 天前的 `v1.5-trust-chain` 旧目录。
  - 如果同机通信非要绕道 GitHub，A 会话改完必须 `commit + push`，B 会话开机如果少跑一次 `git pull` 照样读到旧账——**把原本 0 毫秒的同盘读取，变成了依赖网络和人工拉取的脆弱链路**。
- **刀 2 · 重放与并发探针（Replay & Concurrency）：高频账本走 Git 必出 Merge Conflict 锁死全盘**
  - 本项目常有多个会话同时往 `TASK_LOG.md` 第 1 行置顶插入、往 `ledger.jsonl` 最后 1 行追加。
  - Git 对「两路同时改同一文件同一位置」的唯一反应就是报错 `CONFLICT (content)` 并在文件里塞进 `<<<<<<< HEAD`。一旦出现冲突标记，`sync-task-ledger.mjs` 等自动化脚本会当场解析失败停摆。
  - **正确解法**：高频任务状态继续走现有的**「本机原子追加 + 飞书多维表 `L/F/P` 三值对账闸」**，不要拿 Git merge 当多 Agent 的并发数据库用。
- **刀 3 · 隐蔽检测（Subtlety / 脱敏红线）：容器根直接绑 GitHub 极易泄漏 9 类敏感信息**
  - `AI_MEMORY/ISSUES.md`（526 KB）、`TASK_LOG.md`（1.65 MB）和 `交付档案/`（985 份文件）里记满了 3 个月排障时的服务器路径 `/var/www/...`、真实客户素材目录名（如 `5857`）、本机路径 `C:\Users\ivan` 等。
  - 在没有把「9 类敏感面阳性对照脱敏扫描」挂进 Git `pre-push` 钩子之前，把容器根直接推上 GitHub 存在极高的合规与泄密风险。
- **刀 4 · 规模跳变（Scale Shift）：治理档案绝不能混进业务代码仓 `newye123/tygf.git`**
  - 985 份 HTML/MD 交付件加上 MB 级记忆账本一旦混进业务仓，每次测试站/生产站出包部署都要拖着几百兆的文档跑。即便将来要给容器根做异地 Git 备份，也必须用**完全独立的私有仓库**，与业务代码仓物理隔离。
