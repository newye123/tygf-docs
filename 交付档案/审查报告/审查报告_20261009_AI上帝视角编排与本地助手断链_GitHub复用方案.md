## 0. 一句话结论

本次首先不是“Photoshop 跑完却没保存”，而是**同一执行时窗内本地助手收到 13 次批次请求、0 次接受，所有请求都在 Photoshop 启动前被授权、manifest、脚本或证据门拒绝；输出目录又在这些门之前被提前创建，所以最终留下 0 文件空目录**。页面把客户端估算的 528 积分显示成“已冻结约”，不能据此判定云端已经扣款、已释放或仍冻结；必须先按执行号做服务端只读对账。

更深层的问题仍然是：**每一段都有自己的状态、重试和回执，但错误分类、冻结前预检、未知态恢复、设备解绑和全局观察没有形成同一份合同**。这使一个系统性故障被前端当成“单语言失败”，其余语言继续提交，第二轮再尝试未完成语言，最终把一个故障放大成半天等待、13 次拒绝和难以理解的积分状态。

项目治理侧的“总控 AI / 执行 AI”目前主要存在于 Markdown DAG、交接文档、任务书和人工授权里；产品侧的“扫描 → 检查 → 冻结 → Photoshop 执行 → 回执 → 结算”主要由浏览器函数、本地助手内存状态、SQLite/文件 journal、轮询与若干 outbox 推进。两条链都能局部工作，但彼此不订阅同一份事件账本，也没有共同的运行实例视图，所以用户感受到的是“扫描是扫描、本地助手是本地助手、AI 是 AI”。

**推荐结论：先完成 P0 事故对账和现有链路收口——冻结前统一预检、系统性错误停批、未知态禁止盲重跑、可见目录延迟发布、权威积分状态回显、设备容量开关与统一解绑事务。Temporal、OpenTelemetry、UXP 作为 P2 独立 PoC；它们不能替代本次验票、账务和本机执行合同，也不能作为本次修复的前置条件。**

### 1.2 仍然断开的部分

#### 断点 A：文档 DAG 不是运行时编排器

`全量执行交接文档_v1.1_20261009_执行结果与续办.md:3` 定义了 `S0→D0→I0-I4→...`，但下一个 AI 仍需“读文档 → 跑探针 → 等 Owner 拍板”（`:135-157`）。它没有机器可查询的 workflow instance、step lease、事件历史、超时或自动恢复。只要换会话、漏读交接、回包不合流，控制面就再次断掉。

上午审查已经出现过同型事故：`签发 → 隔离树施工 → 回包 → 停在隔离树 → 无人合流 → HANDOFF 零命中`，证据见 `建议文档_20261009_全项目对抗式审查_问题清单与处置建议.md:14,57-59`。今天人工合流成功证明团队能救火，不证明机制已经不会复发。

#### 断点 B：浏览器实际上承担了产品编排器职责

`local-assistant-client.ts` 依次做身份确认、冻结、prepare、authorize、run，并用最长 40 分钟循环轮询完成状态（`worktrees/develop/src/lib/workbench/local-assistant-client.ts:1169-1315,1877-1947`）。浏览器关闭、刷新、标签页冻结或网络断开时，“谁继续推进、谁判断当前真状态”没有统一答案。

前端可以是命令发起者和状态展示者，但不应是长事务的唯一协调者。

#### 断点 C：扫描态与 prepare 清单仍依赖进程内状态

- 扫描使用单个全局 `preparationScanState`，见 `worktrees/develop/download/local-assistant/server.js:1926`；同一助手同时只能有一个扫描，重启后该状态本身不构成全局可查询历史。
- prepare 后的不可变执行清单放在 `executionManifestCache = new Map()`，见 `server.js:1849-1852,6026-6036`；TTL 到期或进程重启后必须重走 prepare。
- 本地确实有 journal/outbox 补强执行后的恢复，但“扫描前、prepare 后、execute 前”仍是另一套生命周期。

这不是说 Map 本身错误，而是**全局流程不能把 Map 660唯一事实源**。

#### 断点 D：多个补偿循环各自正确，整体状态仍可能不一致

本地助手有 report retry、receipt retry、扫描 watchdog、readiness heartbeat、执行 heartbeat；服务端另有冻结、cancel、finish/reconcile。每段都有重试，但没有一份统一事件历史回答：

- 这次执行现在卡在哪一步？
- 哪一步已经发生且不可重复？
- 当前等待用户、本地助手、云端还是人工复核？
- 哪个超时是业务终态，哪个只是观察端超时？

于是只能靠错误码、日志和人工对账重建事实。

#### 断点 E：学习链默认静默，无法成为“上帝视角”的可靠输入

`learning-evidence-client.ts:6,52-61` 明确将浏览器上报做成 fire-and-forget 且失败静默。这对“不影响用户主流程”是合理降级，对“全局 AI 判断系统是否真的在学习”却是盲区。正确做法不是阻断用户，而是把失败作为可观测事件进入控制平面。

#### 断点 F：项目 AI 与产品运行链没有共同主键

当前项目治理围绕任务书、worktree、commit、回包和 Owner 原话；产品运行围绕 `scanId/jobId/attemptId/batchId`。两边没有共同的 `correlationId` 或事件订阅关系。因此项目 AI 不能自动回答：“某次客户失败对应哪个版本、哪个助手 build、哪个已知问题、哪个修复提交、是否已经部署并真机复验？”

## 1A. 本地助手能力释放专项审查

### 1A.1 审查结论：不是能力少，而是发现、诊断、修复和执行没有成为一条用户可见链

本地助手专项评分：**58/100（能力资产较多，接线和产品化不足）**。当前助手已经包含 Photoshop 发现、真实 JSX 握手、扫描、preparation cache、字体覆盖、布局几何、working copy、执行 journal、失败快照、report outbox、支持包和学习证据等模块；但用户主要只看到“已连接/未连接”和执行按钮，设备能力没有形成统一面板，失败后也没有沿着“发现 → 验证 → 诊断 → 可修复性判断 → 显式修复 → 再握手”推进。

| 能力层 | 已有证据 | 当前断点 |
|---|---|---|
| Photoshop 路径发现 | 运行进程、App Paths、COM LocalServer32、标准 Program Files 扫描，见 `worktrees/develop/download/local-assistant/server.js:424-670` | 目录兜底只扫标准安装根和 2019–2027；未运行且放在任意解压目录时不会命中 |
| 自动化可用性 | `/diagnostic` 做真实 COM + JSX round trip，前端调用见 `worktrees/develop/src/lib/workbench/local-assistant-client.ts:682-737` | “找到 exe”与“可以自动化”没有被清楚分成两种状态 |
| COM 修复 | `Fix-Photoshop-COM.ps1` 会找运行实例、备份注册表、只写已验证 CLSID，见 `worktrees/develop/download/local-assistant/diagnostics/Fix-Photoshop-COM.ps1:1-24,206-309` | 目前更像隐藏的运维工具；没有接成用户可理解、需确认、可回滚的助手流程 |
| 执行与恢复 | journal、working copy、failure snapshot、outbox、receipt 已存在 | 没有汇总成一次运行的设备侧时间线，也没有统一上报给总控 workflow |
| 配置入口 | `/config` 可为 PSD 任务根目录提供 ticket-bound 选择 | API 只允许 `localPsdPath`，其他字段会拒绝，见 `server.js:4382-4435`；错误文案却让用户“在助手配置指定 Photoshop.exe”（`:1319-1323`），形成死路 |

### 1A.2 “解压版 PS 没检测到”不能只当成一个 bug

现有文档曾明确把绿色版/破解版本列为不支持，要求正式安装且 COM 可用，见 `worktrees/develop/docs/上线部署清单.md:90`、`worktrees/develop/docs/本地引擎对接说明.md:118`。因此现在要支持“解压目录中的 PS”，属于**支持边界变更**，必须把“非标准路径的正版/可信程序”与“被修改、来源不明的程序”分开，不能把任意 exe 自动加入可信执行链。

结合现有实现，用户现场至少有以下待真机取证的可能性，不能在没有日志时武断归因：

1. Photoshop 未运行，且位于非标准目录：运行进程、注册表、Program Files 三路都可能落空。
2. 可执行文件被改名：当前运行态探测使用 `Get-Process -Name Photoshop`，见 `server.js:455-473`。
3. 助手与 Photoshop 权限级别不同，导致进程路径或 COM 调用不可见。
4. 能找到 exe，但便携包没有注册 `Photoshop.Application` COM class；现有 JSX 执行最终仍通过 `GetObject/CreateObject`，见 `server.js:1044-1205`，所以“多扫几个目录”也不能让它自动化。
5. COM class 存在但默认 ProgID 或 LocalServer32 指向旧版本：这类才是现有安全修复脚本可以处理的范围。

必须把二元的 `photoshopDetected` 改成可解释状态机：

```text
PROCESS_NOT_FOUND
  → PROCESS_FOUND_PATH_KNOWN
      → COM_REGISTERED_MATCH → JSX_HANDSHAKE_READY
      → COM_REGISTERED_MISMATCH → REPAIR_CONFIRMATION_REQUIRED
      → COM_MISSING_REPAIRABLE → REPAIR_CONFIRMATION_REQUIRED
      → COM_MISSING_UNREPAIRABLE → UXP_BRIDGE_REQUIRED_OR_UNSUPPORTED
  → UXP_BRIDGE_AVAILABLE → JSX_HANDSHAKE_READY
```

其中 `PROCESS_FOUND_PATH_KNOWN` 只能证明程序位置；只有真实 round trip 成功才可进入 `JSX_HANDSHAKE_READY`。这条门不能因“检测到了 Photoshop.exe”而放宽。

### 1A.3 建议的本地助手完整闭环

1. **自动发现**：保留现有运行进程、App Paths、COM 和标准目录四路；补充有界的进程枚举，不再只依赖固定进程名。
2. **用户选择兜底**：由本地助手弹出原生文件选择器选 `Photoshop.exe`，使用短期 ticket；网页不得直接提交任意绝对路径。
3. **候选验证**：检查文件存在、PE 版本信息的 `OriginalFilename/ProductName`、签名者与实际运行映像；来源或签名异常时只显示风险，不静默启动、不进入付费执行。
4. **本地保存、云端脱敏**：`psExePath` 只保存在本机；云端事件只接收状态、版本、路径哈希/安全摘要，不接收完整本地路径。
5. **真实握手**：无论自动发现还是手选，都运行现有 COM + JSX round trip，不能以进程存在代替可执行性。
6. **只读诊断**：把版本冲突、权限不一致、默认 ProgID、LocalServer32、真实 COM probe 变成结构化诊断结果。
7. **显式修复**：只有发现已验证的 Adobe Application CLSID 时，才允许用户明确确认后以管理员权限修复；修复前备份、修复后复验、失败可回滚。禁止静默提权和猜 CLSID。现有脚本在找不到可信 CLSID 时本来就会停止（`Fix-Photoshop-COM.ps1:268-283`），这个 fail-closed 设计应保留。
8. **第二自动化通道**：对“能运行但没有 COM class”的 Photoshop，做 UXP 插件桥接 PoC；若目标版本不能加载受信 UXP 插件，则明确标为不支持，不循环提示重装或重试。
9. **能力快照上报**：助手产生 `DeviceCapabilitySnapshot`，包括发现方式、PS 版本、COM/UXP 状态、握手结果、权限模式、助手 build 和诊断码；总控 workflow 据此排队、解释和阻断，不上传 PSD 内容。

### 1A.4 对抗式边界

- 不承诺“所有解压版都能支持”：缺失 COM 的包只有 UXP 桥接或不支持两条路。
- 不把“能启动”写成“能执行”：真正标准仍是无副作用的自动化握手。
- 不自动扫描整块磁盘：先运行进程和注册表，再用户选择，避免慢、误报和隐私越界。
- 不因用户选择就信任任意 exe：否则本地助手会变成云端可触发的任意程序启动器。
- 不自动修注册表：需要明确确认、管理员边界、备份和复验。
- 不让诊断/修复绕过 activation-bound 执行授权；设备探测可以本地进行，真实 PSD 写入仍走原有授权链。

## 2. 对抗式质询：如果现在自称“已经串起来”，会在哪些场景露馅

| 场景 | 当前最可能结果 | 合格控制平面应给出的答案 |
|---|---|---|
| 冻结积分后浏览器被关掉 | 前端轮询消失；靠服务端、本地 outbox 和后续人工核对拼事实 | workflow 仍存活，明确停在 `WAIT_LOCAL_EXECUTION` 或 `WAIT_RECEIPT`，重新打开页面可继续查询 |
| prepare 成功后助手重启 | 内存 manifest 丢失，重走 prepare；若调用端误判可能重复提交 | workflow 记录 prepare 版本与失效原因，只允许重新 prepare，不重复冻结/执行 |
| 本地执行完成但回执上传失败 | outbox 会重试，但 Web/治理 AI 未必即时知道 | 同一 workflow 显示 `LOCAL_DONE / CLOUD_RECEIPT_PENDING`，告警但不重跑 Photoshop |
| 两个 PSD 几乎同时扫描 | 单全局扫描态返回 409；用户只看到“忙” | 每个 workflow 独立排队，设备能力决定并发度，队列位置和 owner 可查询 |
| 隔离 worktree 已交回包但未合流 | 文档里“已完成”，主线里没有 | 项目 workflow 停在 `DELIVERED_NOT_MERGED`，超过期限自动提醒责任人 |
| AI 读取到旧 HANDOFF/CURRENT_STATUS | 给出过期结论，甚至重复派活 | AI 查询事件账本和 GitHub 当前 SHA；Markdown 只作解释层，不作运行态唯一事实源 |
| AI 得到高权限工具后误判 | 可能直接部署、改积分或处理历史 pending | AI 只能提议；R/E/P 等动作必须持 Owner 审批信号与短期、定目标 capability token |

## 3. GitHub 开源项目怎么处理这类问题

### 3.1 Temporal：最适合作为确定性控制平面

[Temporal Server](https://github.com/temporalio/temporal) 与 [TypeScript SDK](https://github.com/temporalio/sdk-typescript) 都是 MIT。它把 Client、Server、Worker 分开：Server 保存 Event History 和任务状态，Worker 轮询队列执行代码；进程或机器失败后可以从事件历史恢复。官方 [TypeScript samples](https://github.com/temporalio/samples-typescript) 已包含 human approval、signals/queries、saga、worker-specific task queues、worker versioning 等可直接改造的样例；[Web UI](https://docs.temporal.io/web-ui) 可查看每个 workflow 的历史、pending activity、worker、关系和元数据。

对本项目最有价值的不是“更多重试”，而是四件事：

1. 每个翻译任务有唯一、耐久的 workflow instance；
2. 用户审批、助手回执、人工复核用 Signal/Update 进入同一事件历史；
3. 冻结、结算、取消用幂等 Activity 和 Saga 补偿，而不是散落在调用端；
4. 项目 AI 用 Query 读取现状，不从多份 Markdown 猜现状。

**重要适配边界**：Temporal TypeScript Worker 依赖 Node 原生能力和 Core SDK；当前本地助手是 CJS + `pkg` 单文件打包（`worktrees/develop/download/local-assistant/package.json:5-11`）。因此 P2 PoC **不要把 Temporal Worker 塞进本地助手 exe**。Temporal 只跑在独立协调/观察面，本地助手继续使用现有 HTTP + 签名回执；PoC 通过前不接管冻结、Photoshop 写入或结算。

### 3.2 OpenTelemetry：解决“每段都有日志、全链看不见”

[OpenTelemetry JavaScript](https://github.com/open-telemetry/opentelemetry-js) 是 vendor-neutral 的 trace/metrics/logs 框架。它不能替代工作流状态，但适合统一 `workflowId / scanId / jobId / attemptId / assistantBuildId / commitSha` 的 trace attributes，让网页、云端 API、本地助手和结算服务在同一条 trace 上可查。

建议 P1 只加手工 span，不先追求全自动埋点：`scan.requested`、`scan.completed`、`review.approved`、`credits.reserved`、`local.execute.accepted`、`receipt.persisted`、`settlement.finalized`。

### 3.3 MCP：适合作为 AI 工具接口，不是状态机

[MCP TypeScript SDK](https://github.com/modelcontextprotocol/typescript-sdk) 是官方 Tier 1 SDK，可把工具、资源和提示以统一协议暴露给 AI。适合把以下只读能力交给“上帝视角 AI”：

- `get_project_snapshot`
- `get_workflow_status`
- `list_orphan_worktrees`
- `get_release_provenance`
- `explain_failed_attempt`

但 MCP 规范本身明确要求宿主实现用户同意、访问控制和工具安全；协议不会替你提供业务级审批与耐久执行。也就是说：**MCP 是插头，不是总控柜**。任何部署、积分、真实 Photoshop 写入工具都必须在宿主侧做 capability gate，不能因为“接成 MCP”就自动授权。

### 3.4 OpenHands：可复用在 repo 扫描/代码执行，不应接管客户任务

[OpenHands](https://github.com/OpenHands/OpenHands) 与 [Software Agent SDK](https://github.com/OpenHands/software-agent-sdk) 是 MIT。其仓库边界把“什么时候运行、webhook、run history、dispatch”交给 Automation Service，把“agent/tool/workspace/events”交给 Agent Server/SDK；这个职责切分与本项目非常相关。

可复用方式：用 OpenHands SDK 做隔离的 repo 扫描、补丁候选、测试执行和回包生成；由 Temporal 的 `ProjectDeliveryWorkflow` 调度并记录结果。不要让 OpenHands 直接碰积分、生产、客户 PSD 或本地 Photoshop。

由于当前已有 Codex/多会话执行体系，OpenHands 不是 P0 必装项。先把统一状态和事件做出来，再用一张相同任务比较“现有 Codex 执行器 vs OpenHands SDK”的回包完整度、隔离性和成本。

### 3.5 LangGraph.js：适合 AI 决策图，但暂不进入 P0

[LangGraph](https://github.com/langchain-ai/langgraph) / [LangGraph.js](https://github.com/langchain-ai/langgraphjs) 是 MIT，提供 durable execution、checkpoint 和 human-in-the-loop。它适合“AI 如何计划、反思、调用工具”的有状态图。

但本项目现在缺的是跨层一致的状态合同与可核对事件历史，不是缺一个更复杂的 LLM 推理图。P2 同时引入 Temporal 和 LangGraph 会产生“两套 checkpoint、两套恢复语义、谁是真相”的新问题。建议以后只把 LangGraph 放进一个 Temporal Activity 内，负责可重放边界之外的 AI 推理；其输出是**建议**，由 workflow 和 Owner 决定是否执行。

### 3.6 明确排除或降级的候选

| 候选 | 结论 | 原因 |
|---|---|---|
| Restate | 不作为“纯开源优先”首选 | 核心当前是 BUSL-1.1，许可证正文明确“not an Open Source license”；技术形状优秀但不符合本次筛选口径 |
| n8n | 不采用为核心控制平面 | Sustainable Use License，不是标准 OSI 开源许可；更适合内部集成自动化，也不适合承担积分/Photoshop 长事务真相 |
| Inngest | 备选，不优先 | TypeScript 体验好，但自托管/组件许可证与产品边界需逐件复核；Temporal 的 MIT 全栈与事件历史更清晰 |
| BullMQ | 仅作短任务队列，不作总控 | 能解决 Redis 队列、锁和 stalled job，不能自然表达跨小时审批、版本化 workflow、全局事件历史与 Saga |
| “一个万能 Agent + shell 权限” | 明确禁止 | 把不确定推理、执行权限和业务真相绑在一起，正好违反当前 activation-bound、fail-closed 和分层授权红线 |

### 3.7 Adobe UXP：复用官方桌面桥，补足无 COM 场景

[Adobe Photoshop UXP 官方 samples](https://github.com/AdobeDocs/uxp-photoshop-plugin-samples) 采用 MIT，已经提供两类与本项目高度贴合的样例：`desktop-helper-sample` 演示 Electron 桌面 helper 与 UXP 插件通过 socket.io 通信，`io-websocket-example` 演示 Photoshop 内 WebSocket client/server；仓库还包含文件 I/O、DOM 和 BatchPlay 示例。这里最值得复用的不是 UI，而是**“本地守护进程 ↔ UXP 插件 ↔ Photoshop”**的桥接形状。

建议做一个隔离 PoC：本地助手继续负责 activation、任务绑定、manifest、journal、outbox 和回执；UXP 插件只接收已授权、带 digest 的最小命令，在 Photoshop 内执行受限动作并回传结果。这样可以为没有 COM 注册但能加载 UXP 插件的安装形态提供第二通道，又不需要把业务授权逻辑复制进插件。

[CORE-Automate-WSS/photoshop-mcp](https://github.com/CORE-Automate-WSS/photoshop-mcp) 也是 MIT，已经走通 `Node MCP server → WebSocket → UXP plugin → Photoshop DOM/batchPlay`。它适合作为代码阅读和快速原型参考，不适合直接成为生产依赖：项目规模和采用度尚小，而且它解决的是 MCP 调用桥，不包含图译工坊的 activation、计费、任务绑定、回执和恢复语义。

进程发现方面，[microsoft/vscode-windows-process-tree](https://github.com/microsoft/vscode-windows-process-tree) 能提供 Windows 原生进程树，但它是 native Node addon；当前助手是 CJS + `pkg` 单文件产物，所以必须先做打包兼容性 spike，不能直接塞进生产包。[ps-list](https://github.com/sindresorhus/ps-list) 在 Windows 返回的信息不足以可靠取得可执行路径，不应为“少写几行 PowerShell”而引入。

### 4.1 “上帝视角 AI”真正应该做什么

- 读：查询所有 workflow、Git SHA、助手 build、部署 provenance、未合流回包、验收缺口。
- 解释：把事件历史翻译成“现在卡在哪里、为什么、下一步需要谁”。
- 提议：生成下一步命令或任务卡，但不自授权限。
- 守门：发现事件缺口、版本漂移、重复冻结风险时建议停机。
- 复盘：将已结束 workflow 聚合成问题模式和 benchmark。

它**不应该**直接成为计费服务、本地助手的隐形超级用户、Git 合并者和部署者。真正的“上帝视角”是全知可查，不是全权可写。

### 4.2 两条 workflow 必须分开

不要把“开发项目治理”和“客户翻译执行”塞进同一个状态机：

- `ProjectDeliveryWorkflow` 管 repo/worktree/任务书/回包/合流/部署/验收。
- `TranslationRunWorkflow` 管 PSD 扫描/审核/冻结/执行/回执/结算。

两者只通过版本 provenance 关联：客户运行记录 `commitSha + assistantVersion + assistantBuildId + contractVersion`；项目 workflow 可以反查哪些真实运行使用了某个版本。这样既能串联，又不会让项目 AI 获得客户数据或积分权限。

### 4.3 统一事件信封

建议所有环节至少统一这些字段：

```json
{
  "eventId": "uuid",
  "workflowId": "translation:<batch-or-run-id>",
  "correlationId": "stable-end-to-end-id",
  "causationId": "previous-event-id",
  "subjectType": "scan|attempt|batch|project_task|release",
  "subjectId": "domain-id",
  "eventType": "scan.completed",
  "actor": "web|cloud|local_assistant|owner|project_agent",
  "idempotencyKey": "stable-retry-key",
  "evidenceRefs": ["digest-or-safe-reference"],
  "occurredAt": "RFC3339",
  "provenance": {
    "commitSha": "...",
    "assistantVersion": "...",
    "assistantBuildId": "...",
    "contractVersion": "..."
  }
}
```

事件里只放摘要、digest 和安全引用；PSD 路径、正文、密钥与客户内容不进入云端事件历史。

## 5. 不推倒重做的迁移路径

### Phase P0：先收口现有链路

先完成第 11—17 节的事故只读对账、冻结前预检、错误分类、未知态恢复、延迟发布、权威积分 UI、设备策略、测试与真实 Windows/Photoshop 验收。P0 未通过，不启动下述架构接管。

### Phase P2-0：ADR + 最小小样（2–3 天，零业务接管）

1. 在独立目录启动 Temporal dev server + Web UI。
2. 写一个 `TranslationRunWorkflow` 骨架，只包含：`scan requested → wait signal → review approval → wait receipt → complete`。
3. 用假 activity 和 fixture 验证：进程重启、浏览器关闭、重复 signal、超时、人工 reject。
4. 形成 ADR：Temporal 只做控制面；现有数据库仍是业务数据源；本地助手不嵌 Temporal Worker。

**通过门**：同一 workflow 在服务重启后仍可继续；重复 signal 不产生第二次业务效果；UI 能回答“卡在哪一步”。

### Phase P2-1：Shadow 观测（约 1 周，不改变现有结果）

1. 现有路径每到关键节点，额外发一条去标识事件到 shadow workflow。
2. 加 OpenTelemetry correlation attributes。
3. 每日对账现有数据库/日志/outbox 与 Temporal history，差异只告警，不自动修复。

**通过门**：连续真实试点中，shadow history 能 1:1 重建状态；任何缺事件都可定位到发送方，不影响主流程。

### Phase P2-2：先接管扫描与人工审核（1–2 周）

1. workflow 发签名扫描命令；本地助手仍执行现有 `/v1.5/preparation/scan`。
2. 扫描进度/结果通过 gateway 变成 signal。
3. 浏览器只 Query 状态和发送用户审批，不再自己持有整条长循环。
4. 不接计费、不接 Photoshop 写入。

**通过门**：关闭浏览器后扫描继续；重新打开能恢复；两份 PSD 有独立 workflow；助手忙时显示队列/owner，而不是只有 409。

### Phase P2-2A：释放本地助手设备能力（与 Phase P2-2 并行，不碰计费）

1. 先交付结构化 `DeviceCapabilitySnapshot` 和状态机，把路径发现与自动化握手拆开显示。
2. 加入 ticket-bound 的 Photoshop.exe 本地选择、候选验证和本地持久化；补齐错误文案与真实配置入口。
3. 把现有只读诊断接入 UI；将 COM 修复做成显式、备份、可回滚的高级动作。
4. 用三类受控 fixture/真机做矩阵：标准安装、非标准目录但 COM 可用、无 COM 但 UXP 可加载。来源不明或被修改的包只记录兼容性证据，不作为发布验收基准。
5. 基于 Adobe 官方 `desktop-helper-sample` / `io-websocket-example` 做 UXP 桥 PoC；只实现无副作用 `ping/version/document metadata`，暂不写入 PSD。

**通过门**：每种失败都落到唯一、可操作状态；选择任意非 Photoshop exe 会被拒绝；无 COM 时不会谎报 ready；UXP PoC 不持有计费或云端凭据；完整路径不出本机。

### Phase P2-3：接管执行、回执与结算（1–2 周以上，另开合同窗口）

1. 把冻结、execute authorization、receipt、settlement 逐步改成 workflow activities/signals。
2. 复用现有 `attemptId + manifestDigest`、journal、outbox、receipt，不改 binding 语义。
3. 对每个 activity 定义明确的 idempotency key、retryable/non-retryable 分类和 Saga 补偿。
4. 双轨对账通过前，旧状态机仍是裁决源；切换必须单独授权。

**通过门**：重复请求不重复冻结/结算；本地执行完成但云端暂不可达时绝不重跑 Photoshop；未知态保持冻结并要求核查；历史 pending 不自动处理。

### Phase P2-4：接入项目治理 AI

1. GitHub webhook / 本地只读 repo scanner 产生 `RepoSnapshot`。
2. 把“派单、回包、合流、验证、部署、验收”建成 `ProjectDeliveryWorkflow`。
3. 先让 AI 只 Query + 提议；Owner 批准后才 Signal。
4. 用同一任务 A/B 比较现有 Codex 执行器与 OpenHands SDK，不先替换现有工具。

**通过门**：任何“已交未合”“已合未部署”“已部署未真机验收”都成为可查询状态，不能再靠翻回收目录发现。

## 6. 旧“不引入 Temporal”结论如何处理

`worktrees/develop/docs/plans/20261008_图译工坊_扫描与执行超时链修复_对抗审查执行方案.md:343-349` 曾明确不引入 BullMQ/Redis/Temporal，理由是与 SQLite + 自研状态机不匹配、局部迁移成本过高。

本轮不否定那张单：它的 scope 是修扫描/执行超时链，直接换引擎确实会扩大风险；借鉴心跳和 deadline 是正确的最小修法。

但今天的问题已经不是单个超时，而是同时出现：

- 浏览器长事务编排；
- 本地助手多套 in-memory / journal / outbox；
- 云端冻结/结算与本地回执对账；
- 项目任务回包与合流断链；
- AI 跨会话靠 Markdown 恢复状态。

这已经具备了“耐久控制平面小样值得做”的条件。**结论不是立刻迁移，而是用 2–3 天 PoC 取得是否迁移的证据。** 如果 PoC 不能在不动业务语义的前提下证明恢复、幂等和可观察性收益，就停止，不把架构潮流当任务。

## 7. 决策与优先级

### 推荐采用

| 优先级 | 项目 | 用途 | 采用方式 |
|---|---|---|---|
| P0 | 现有执行链事故收口 | 528 积分权威对账、冻结前预检、系统性停批、未知态恢复、延迟发布输出目录 | 直接扩展既有批次、journal、outbox 与结算合同 |
| P0 | 本地 Execution Preflight Snapshot | 统一激活、组件完整性、Origin 验票、PS 握手、输出可写、待投回执状态 | 复用现有 `/ping` 与组件检查，冻结前和提交前各校验一次 |
| P1 | OpenTelemetry JS | 跨 Web/API/助手/结算关联 | 先手工 span + correlation attributes |
| P2 | Temporal Server + TypeScript SDK + UI | 耐久协调、观察、人工审批 | 独立 PoC 后 shadow；不嵌助手 exe，不作为账务或 Photoshop 事实源 |
| P1 | Adobe UXP 官方 samples | 为无 COM 但可加载插件的 PS 提供第二自动化通道 | 复用 desktop-helper/WebSocket 形状，先做无副作用 PoC |
| P1 | MCP TypeScript SDK | 给上帝视角 AI 暴露标准化只读工具 | 默认只读；写工具必须 capability gate |
| P2 | OpenHands Software Agent SDK | repo 扫描、补丁候选、隔离执行 | 与现有 Codex A/B，不碰客户运行链 |
| P3 | LangGraph.js | 复杂 AI 计划与 HITL | 只作 Temporal activity 内部推理，不作事实源 |

### 现在不要做

1. 不重写 `binding-core`、scanner、v15 runner、journal、outbox、receipt。
2. 不把 Temporal Worker 强塞进 `pkg` 助手。
3. 不让 AI 直接处理积分、历史 pending、生产部署或真实 Photoshop 写入。
4. 不把 Markdown 全删掉；它继续做解释、审计和人读交接，但运行态真相转到 workflow/event history。
5. 不在 Phase P2-0 同时装 Temporal、LangGraph、OpenHands、MCP 全家桶。
6. 不把“支持非标准路径”扩大成“信任所有破解/修改版 Photoshop”。

## 8. 最小验收清单

- [ ] 任一运行都有唯一 `workflowId`，可从 `scanId/jobId/attemptId` 反查。
- [ ] 浏览器关闭 30 分钟后重新打开，状态不丢、不重复执行。
- [ ] 助手在 prepare 后重启，只能安全 re-prepare，不重复冻结或 Photoshop 写入。
- [ ] 本地完成、云端回执失败时显示双态，不自动重跑。
- [ ] 重复 signal/webhook/receipt 只产生一次业务效果。
- [ ] Owner reject/approve 有事件、时间、目标、有效期和授权层级。
- [ ] AI 默认只能 Query；任何写动作都有 capability token 和审计事件。
- [ ] Temporal history、业务 DB、助手 outbox 三方可自动对账。
- [ ] Photoshop 发现状态与自动化 ready 状态分开；进程存在不等于通过 JSX/UXP 握手。
- [ ] 非标准目录可通过本地 ticket 文件选择；任意 exe、路径注入和云端绝对路径提交均被拒绝。
- [ ] COM 不匹配可诊断；修复必须显式确认、备份、复验和可回滚；无可信 CLSID 时 fail closed。
- [ ] UXP 桥仅执行已绑定 manifest 的允许动作；插件不保存积分、activation 或云端密钥。
- [ ] 真实 Windows/Photoshop 验收仍单列，不用 PoC/smoke 冒充。

## 9. 最终建议

建议先签一张 P0 合同修复任务，把本次执行号、冻结状态、13 次拒绝、空目录、重试资格和设备绑定统一到可验收的状态机；通过自动化、测试站和真实 Windows/Photoshop 验收后，再签 Temporal 与 UXP 两张互不绑架的 P2 PoC。目标不是“引入某个新框架”，而是先让既有链路在失败时停得住、说得清、能恢复、账对得上。

1. 它能否让浏览器退出后仍准确恢复扫描/审批/回执状态？
2. 它能否复用现有 `scanId/jobId/attemptId/manifestDigest`，而不是再造一套业务身份？
3. 它能否在不把 PSD/正文上传云端、不放宽 activation-bound 授权、不改变积分语义的前提下工作？
4. 非标准目录中的可信 Photoshop 能否经“本地选择 → 验证 → 真实握手”安全进入 ready？
5. COM 缺失时，系统能否明确区分“可修复”“仅 UXP 可用”“不支持”，而不是笼统报未检测到？
6. UXP 桥能否在不复制授权/计费逻辑、不持有云端密钥的前提下完成无副作用 round trip？

控制平面三问全过，再进 shadow；本地助手三问全过，才进入真实 PSD 只读试点。任一 PoC 不过，就保留现有实现，只带回已验证有效的事件信封、状态拆分、诊断或安全边界。

## 12. 一次收口的目标合同

### 12.1 两段式执行

```text
无计费预检
  → 报价
  → 服务端冻结
  → 冻结后短 TTL 再预检
  → 为全部语言绑定/续签 manifest ticket
  → 本地助手明确 accept
  → Photoshop 串行执行
  → staging 产物校验与 readback
  → 原子发布可见目录
  → 可信回执
  → 服务端结算或释放
```

`ExecutionPreflightSnapshot` 必须包含：账号资格、activation、机器绑定世代、助手版本、脚本分发 phase/integrity、Origin 验票可达性、manifest ticket TTL、Photoshop 进程与真实握手、执行锁、pending receipt 阻断策略、源文件可读和目标目录可写。快照由服务端签名，TTL 要短；浏览器不能自行把失败项改成通过。

冻结前失败：不创建 reservation、不建可见输出目录。冻结后提交前失败：不进入 Photoshop，立即走权威释放或 `UNKNOWN_RECONCILE`。执行已 accept 后：关闭页面、助手重启或网络断开都不得产生第二个 Photoshop 执行。

### 12.2 重试分类

| 类别 | 例子 | 批次动作 | 自动重试 |
|---|---|---|---|
| 全局系统性 | activation/组件/脚本/Origin/manifest 基础设施失败 | 立即停批 | 否；修复后重新预检 |
| 单语言确定失败 | 输入文件或该语言 manifest 可验证无效 | 记录该语言失败，可按合同继续 | 仅显式新操作 |
| 未知结果 | `VERIFY_TIMEOUT`、响应丢失、助手断连 | 进入对账 | 否 |
| 已接受执行中 | Photoshop 或助手暂时失联 | 保持执行锁与冻结 | 只恢复观察/回执，不重跑 PS |
| 终态回执失败 | 本地已完成、服务端收据暂不可达 | outbox 重放同一回执 | 是，但只重放回执 |

删除“统一第二轮重跑未完成语言”的默认行为。重试资格应是显式枚举，不是“没成功就再来一次”。现有 `src/lib/server/execution-batch.ts:2032-2052,2058,2220-2238` 的未开始零计费、终态失败不计费、缺回执待核与成功结算规则继续作为账务底座，不另造第二套账。

### 12.3 产物发布

助手把工作文件写到隐藏的 `_staging/{executionId}/{language}`，journal 记录写前意图、文件摘要、readback 和发布状态。只有第一份已验证产物存在时才创建/原子 rename 到用户可见的最终目录；预检拒绝不得留下新的最终目录。已有用户目录只做只读清单，不自动删除。

页面要显示每语言的 `预检 / 已冻结 / 已接受 / Photoshop 中 / 已保存待回执 / 已结算 / 已释放 / 待人工核对`，并显示服务端回读的冻结、扣除和释放数额；“正在提交”不能覆盖整个半小时，也不能继续显示客户端估算数为权威余额。

## 13. 激活码、解绑与内测多机：统一方案

### 13.1 产品语义

激活码只用于建立内测账号资格；以后登录、重装、解绑和换电脑由账号与设备管理完成。**关闭单机数量限制不等于关闭激活校验**：执行仍必须 fail-closed 校验账号资格、activation 未撤销/未过期、助手机器身份、绑定世代和签名 token。

服务端新增集中策略：

- `OFF`：内测环境不限制机器数量，但仍建真实绑定、计数、审计和世代；建议本轮内测默认。
- `AUDIT`：不拦截超额，但记录若按生产策略会拒绝的事件；用于回收数据。
- `ENFORCED`：按服务端 `maxDevices` 严格 CAS 抢槽；未来生产默认。

配置缺失、值非法或生产环境误配为 `OFF` 时保持 `ENFORCED`，不得静默放宽。浏览器无权提交或覆盖此模式。

### 13.2 必须同时修的绑定缺口

1. `pair/route.ts:101-107` 的 `maxMachines:1` 改为服务端策略解析；旧 `redeem/route.ts:125-133` 与 pair 统一走同一事务/CAS，消除事务外容量检查。
2. 四条解绑路径统一为 `releaseAssistantBinding`：用户 activation revoke、devices revoke、管理员 install release、管理员 user release 都使用同一权威事务。
3. 区分“释放一台助手绑定”和“撤销整个账号安装激活”；运行中或 `UNKNOWN` attempt 禁止释放，且活跃批次检查必须与 CAS 同事务。
4. CAS 成功数决定是否减 `activatedCount/boundCount`，避免双击或并发重复减计数；操作使用 `operationId` 幂等，审计与业务事务同提交。
5. 恢复被撤销 activation 时重新抢槽或采用明确的账号资格策略，修复“撤销 A → B 占槽 → 恢复 A”越限。
6. redemption 增加授权世代或 token `jti`；token 验证同时校验当前世代，防止解绑后同机重绑令旧 token 复活。
7. 助手持久机器 ID 与浏览器 `anonymousInstallId` 建可审计映射；不把清缓存后产生的新浏览器 UUID 当作新物理电脑。

### 13.3 GitHub 可复用而非整仓替换

- [quteam/license-manager](https://github.com/quteam/license-manager)（MIT）最接近当前 TypeScript 自托管形态，可复用“同机幂等激活、受控解绑、冷却/审计、稳定错误码”合同；它的默认设备数、冷却时间和到期策略不能照搬。
- [Keygen machine activation example](https://github.com/keygen-sh/example-python-machine-activation)（MIT 示例）适合参考“license 资格”和“machine 实例”分离及指纹校验；不引入其托管依赖作为本轮前置。
- [OpenLicensd](https://github.com/alvarorg14/openlicensd)（Apache-2.0）可参考自托管 API/后台边界，但整套较重。
- [Keygate](https://github.com/tabloy/keygate) 为 AGPL，仅作概念参考，不复制代码进入闭源产品。

映射关系：`License Key → InviteCode/BetaUser`、`Device → AssistantCodeRedemption`、`activate → pair`、`verify → assistant authorization`、`unbind → releaseAssistantBinding`、`max activations → 服务端设备策略`。

## 14. 长任务与断线恢复的 GitHub 复用结论

1. [BullMQ](https://github.com/taskforcesh/bullmq)（MIT）的 stalled job、幂等 job 与 retry pattern 可借鉴到云端非 Photoshop 队列，但不能把 Redis 队列当财务账本，也不能让 worker 重跑未知状态的本地 Photoshop。
2. [Graphile Worker](https://github.com/graphile/worker) 和 [pg-boss](https://github.com/timgit/pg-boss)（MIT）适合在 PostgreSQL 附近承载 outbox/后台任务；本轮先扩展现有 outbox，避免同时引入新基础设施。
3. [pg-transactional-outbox](https://github.com/Zehelein/pg-transactional-outbox)（MIT）可参考事务内写事件、事务外投递；当前项目应把账务事实留在业务数据库。
4. [p-queue](https://github.com/sindresorhus/p-queue)、[p-retry](https://github.com/sindresorhus/p-retry) 和 [write-file-atomic](https://github.com/npm/write-file-atomic) 可分别复用串行调度、白名单重试和原子 journal 写入模式。
5. Temporal 继续保留为 P2。Activity 可能被执行多次且默认可自动重试，因此冻结、Photoshop 写入和结算不能直接放入默认 Activity。Temporal 只能先作耐久协调/观察层；服务端数据库是财务事实源，本地 journal + 产物 + 签名回执是 Photoshop 事实证据。
6. Adobe UXP 继续保留为 P2 无副作用 PoC，只解决无 COM 设备通道，不解决这次发生在 Photoshop 启动前的验票、manifest 与结算问题。

## 15. 数据迁移、回滚与安全边界

### 15.1 上线前只读盘点

导出脱敏计数：活跃 activation、`activatedCount`、redemption、`boundCount`、孤儿关系、一个 installId 多机器、同账号多 installId、活跃/未知 attempt。不得导出激活码、token、客户 PSD 或翻译文本。

### 15.2 迁移顺序

1. additive schema：绑定世代、操作幂等键、设备策略审计、preflight snapshot、staging 发布状态。
2. 服务端双读校验旧关系和新关系；不在运行时猜测性重置计数。
3. 新助手写持久机器 ID 与世代，服务端持久化后读回确认。
4. 浏览器只采纳助手/服务端规范身份；旧 ID 保留映射和审计。
5. 无活跃/未知任务且 machine→activation 唯一的对象自动迁移；歧义对象进入待核队列。

### 15.3 回滚

回滚设备开关只阻止新增超额绑定，不自动踢出已合法绑定机器，不撤销执行中任务。新增字段、旧 ID 映射和审计不删除。token 世代生效后，不允许回退到会接受已撤销旧 token 的授权实现。助手变化必须同时重建 embedded runtime、安装包、SHA 与发布回执。
