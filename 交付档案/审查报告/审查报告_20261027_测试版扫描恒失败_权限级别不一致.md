# 测试版「扫描总是不成功」根因定位：本地助手被装成了管理员身份

对象：Owner 机器上的本地助手（3.7.28）／测试站扫描链路
取证时刻：2026-10-27 16:0x–16:12（本机实测）
结论状态：根因已定，代码侧防复发已改完并跑过门禁；机器恢复只差一次点击

---

## 一、一句话结论

不是设计文件的问题，也不是 Photoshop 版本的问题。

**本地助手当前是以「管理员身份」运行的，而 Photoshop 是以「普通身份」运行的。**
Windows 有一条硬规矩：管理员权限的程序不能去控制普通权限的程序。所以助手每次想去驱动 Photoshop 都被告知「不存在」，它按设计重试十轮、每轮约一分钟，最后报一个看不懂的错——这就是你看到的「扫描总是不成功」。

时间也能对上：**助手是 2026-10-25 17:44:35 由新安装包「装完立即启动」那一步拉起来的**，它继承了安装程序的提权身份；在这之前的 10-23 扫描全部正常。

---

## 二、这对你意味着什么

1. **扫描能力本身没坏。** 同一个时刻、同一台机器、同一份 Photoshop，我用普通权限跑一条探针，一秒就连上了（见证据三）。
2. **今天的失败会「卡 12 分钟再报错」**，因为旧版助手不知道这两种权限不能互控，只会傻等重试。
3. **旧版报的错还会把人带偏**：它把这种情况说成「Photoshop 没注册」，建议重装 Photoshop；另有分支会建议「以管理员身份运行修复工具」——那正好是把问题钉死的方向。这两处已经改掉。
4. **这不是测试站独有的问题。** 任何用户只要助手是被提权安装、又被安装包自动拉起来，都会一模一样地失败。

---

## 三、证据（三组，均为本机实测）

### 证据一：三个进程的权限级别

用 Windows 令牌接口直接读完整性级别（12288＝管理员级，8192＝普通级）：

| 进程 | PID | 管理员 | 完整性级别 |
|---|---|---|---|
| 图译工坊引擎 | 23568 | 是 | 12288 |
| 图译工坊本地助手 | 53524 | 是 | 12288 |
| Photoshop | 25136 | 否 | 8192 |

### 证据二：这个管理员身份是怎么来的

| 事实 | 读数 |
|---|---|
| 助手进程启动时间 | 2026-10-25 17:44:35 |
| 引擎进程启动时间 | 2026-10-25 17:44:36 |
| 安装目录 bin／licenses／diagnostics | 2026-10-25 17:44:33 |
| unins000.dat（安装数据库） | 2026-10-25 17:44:34 |
| Photoshop 启动时间 | 2026-10-25 08:14:13（早于安装，普通身份） |

安装程序在 17:44:33–34 落完文件，助手在 17:44:35 起来 ⇒ **它就是安装脚本 `[Run]` 段「装完立即启动」拉起的那个进程**，因此拿到了和安装程序一样的权限。助手自身的清单是「按调用者身份运行」，不会自己提权；提权只可能来自父进程。

### 证据三：同一分钟，普通权限能连上，管理员权限连不上

- 普通权限（我的命令行，8192）：2026-10-27 16:12:18 跑 COM 探针 →
  `GETOBJECT_OK` / `VERSION_OK: 22.0.0`，退出码 0。
- 管理员权限（现役助手进程内）：`POST /diagnostic` 走同一条 COM 路径 →
  等满 60 秒后返回 `503 PHOTOSHOP_COM_UNAVAILABLE`。
- 浏览器侧看到的失败，与上面「管理员连不上」完全一致（见证据四）。

同机、同账号、同 Photoshop，唯一差别就是权限级别 ⇒ 根因确定。

### 证据四：失败史

`engine.log` 里扫描结果：

| 时间（UTC） | 结果 | 耗时 |
|---|---|---|
| 2026-10-23T23:28:49 | 成功（prepared） | 17.6 秒 |
| 2026-10-25T13:35:44 | 失败 PHOTOSHOP_COM_UNAVAILABLE | 759,186 ms（12.7 分） |
| 2026-10-26T12:12:08 | 失败 | 771,326 ms（12.9 分） |
| 2026-10-26T15:19:43 | 失败 | 762,775 ms（12.7 分） |
| 2026-10-26T23:33:44 | 失败 | 766,509 ms（12.8 分） |
| 2026-10-27T01:31:17 | 失败 | 711,859 ms（11.9 分） |
| 2026-10-27T06:18:11 | 失败 | 709,486 ms（11.8 分） |

6 次全失败，全部落在 10-25 17:44 那次安装之后；失败一次约 12 分钟，是因为扫描脚本的重试阶梯是「十轮 × 每轮两次 COM 尝试」，每次 COM 尝试在跨权限时会一直等到系统超时。

## 四、根因链（为什么会这样）

1. 安装程序以管理员身份运行（安装包本身声明的是「最低权限」，说明这次它是被提权启动的——大概率是照着旧报错文案里「以管理员身份运行修复工具」的做法，右键用了「以管理员身份运行」）。
2. 安装脚本最后一步「装完立即启动助手」直接把助手拉起来，**子进程继承父进程的提权身份**。
3. 助手再拉起引擎，引擎同样是管理员身份。
4. 引擎通过脚本去创建 Photoshop 的 COM 对象 → Windows 拒绝（高权限不能控低权限）→ 脚本只拿到一个笼统的 `429 ActiveX 部件不能创建对象`。
5. 旧版逻辑把 429 当成「没注册」并重试十轮 → 12 分钟后失败，界面给出一条指错方向的建议。

## 五、已经改好的（代码侧，防复发）

| 改动 | 位置 | 作用 |
|---|---|---|
| 助手能判断自己是不是管理员 | `download/local-assistant/server.js:524-538` | 用系统 whoami 读完整性级别，结果缓存，一次开销 |
| 扫描前秒级判掉这种组合 | `server.js:5715-5718`、`5740-5746` | 助手是管理员且近期没有握手成功 ⇒ 立刻 422，不再起 12 分钟的重试 |
| 失败原因单独成码 | `scan-error-code.cjs:44-51` | 新增 `PHOTOSHOP_PRIVILEGE_MISMATCH`，云端能数出「卡在权限」这一档 |
| 429 归类改对 | `server.js:1697-1725`、`3579-3587` | 管理员身份下的 429 不再冒充「没注册」，也不再建议去跑管理员修复工具 |
| 云端/浏览器白名单 | `src/lib/server/funnel-event-contract.ts:151`、`src/lib/workbench/batch-error-policy.ts:252` | 新码不会被折叠成泛化码；前端本来就把助手码原样上报（`design-file-card.tsx:510`） |
| `/ping` 增加自述字段 | `server.js:4897` | 排障时一眼看到助手是不是管理员 |
| 门禁 | `scripts/smoke-preparation-failure-observation.mjs` | 42 条断言（含 6 行真值表、文案方向、路由接线、归类顺序、两处白名单），全 Pass；`node server.js --self-test-errors` 通过 |

用户会看到的新文案（旧版没有这段）：

> 本地助手当前以「管理员身份」运行，Photoshop 以普通权限运行，两者权限级别不一致，Windows 拒绝控制。请完全退出本地助手（右下角托盘图标右键 → 退出），再从开始菜单正常启动（不要选「以管理员身份运行」），然后重新扫描。

一句设计上的保险：如果这台机器上 Photoshop 本来就是管理员启动的（两边同级），这条守卫会在「最近 10 分钟内成功握过手」时自动放行，不会误伤。

## 六、还没做的（需要你拍）

1. **把修复做成新版安装包**：本机没有 Inno Setup（装包编译器），develop 树还有别的会话在改（不能清树）。所以这一版修复现在只在代码里，出包要换台构建机 + 代码签名 + 走 GitHub 三段轨。
2. **安装脚本的根治性改动**（候选，未改）：在「装完立即启动」那一行加上「以原用户身份启动」，这样即使安装程序被提权，自动拉起的助手仍是普通身份。之所以没直接改：本机没有编译器，改完无法编译验证，不验证就写进去属于「坏判据比没有判据更坏」。建议随下一版出包时在构建机上改并实机验一次。
3. 顺带记一笔：以前把「以管理员身份运行」当修 COM 的推荐做法，是这次事故的诱因之一。新文案已经把方向反过来，但**下载页/帮助文档里如果还有类似指引，也该一起改**（未核查具体文案，标「待确认」）。

## 七、现在要做的一件事（A 还是 B）

**A：现在就恢复这台机器的扫描（一次操作，立刻生效）**

- 如果屏幕上还有那个 Windows 的「是否允许此应用对你的设备进行更改」提示：点「是」。
  那个提示是我起的，它只做一件事——把管理员身份的助手和引擎关掉，再用普通身份重新拉起（脚本在 `%TEMP%\tygf-deelevate.ps1`，执行结果会写到 `%TEMP%\tygf-deelevate-result.txt`，可回查）。
- 如果提示已经消失：右键右下角托盘图标 →「退出本地助手」，然后从开始菜单（或桌面快捷方式）正常双击启动。
- 恢复后我会用探针复验：两个进程的完整性级别应变回 8192，`/diagnostic` 应返回 200 与 `PHOTOSHOP_READY`。

**B：同时把修复做成新版安装包给所有用户（需要构建机）**

- 效果：新用户即使安装时用了管理员身份，助手也会在扫描前秒级给出正确指引；装到已出问题的机器上同样能立刻说清原因。
- 代价：要一台有 Inno Setup + 签名证书的机器，走 GitHub 三段轨（先推 GitHub → 测试站验 → 通过后再上生产），生产上线需要你点头。

两台事不冲突。A 解决你眼前的扫描，B 解决别人以后踩同一个坑。
