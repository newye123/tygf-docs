# 以后您在飞书表上直接动手，我怎么接

（2026-10-15 夜 · 人机混写台账治理 · 调研已查完 GitHub，对抗式审查已做完）

**一、解决什么问题**

您问「以后对这种（您在飞书表上直接动手）要怎么管理」。我把 GitHub 上一手资料查了六家（IssueOps、Renovate、GitHub Projects、Jira、Airtable、飞书高级权限官方文档），又逐行读了咱们自己的投影脚本和回读闸。结论先说：不是把表锁死，而是「机器列讲清楚归属、您的手改当命令、覆盖前先对账」。

同时抓到一个真实漏洞：如果您手动改了机器列，而我们当天先跑了一次投影、还没跑到日检，您的改动会被静默覆盖——回读闸永远看不见它，窗口最长 24 小时。这个洞要补。

**二、还有什么问题**

飞书官方文档明说：所有者/管理员「权限不可修改」、对全部行列都能改——所以「把机器列锁成只读」这类平台手段锁不住您本人，只能防以后来帮忙的协作者。Jira 官方的替代做法是「手改就盖回去」，官方自己也承认「被回改的人不会知道、甚至以为系统坏了」——会吃掉您的意思。

**三、接下来怎么办**

已拟好「协议 v1」，一张裁决表就说完：批注列（您写任何字，永不覆盖，我读到就落实）；状态/标题/负责人/下一步/到期日/出处 您手改＝您的命令，我采纳、记账、报告里点名；任务ID 手改＝恢复+告警；新增整行＝新任务请求；空行＝告警等您处置；删行不生效（要停任务请写批注）。

配套一个约半天的 P0 小改造：投影前先对账——「您改的」和「我们待投影的」用上次投影快照精确区分，可疑行拦下不动、其余照常投影，全程打表；覆盖所有行需显式加 `--force`（您说了算的口子）。

您回一个「行」，我就实施 P0。另外顺提：飞书里那条全空行（reczz28NgK1sMIo0）、42 个孤儿目录（≈18GB）、4 条带改动的分支，也还等您一句话处置。
