# 工作计划搬进飞书多维表格：能不能做

## 解决了什么问题

去 GitHub 查了，也把您这台机器摸了一遍。结论：**能做，而且飞书官方就支持**——官方有个开源的命令行工具（MIT 协议），装上之后 AI 就能直接往多维表格里写行。您想要的那个场景（「新增一行：标题、负责人、截止、状态」）就是官方示例里的第一条。

但这台机器上**现在还没装**这个工具，这是第一步。

## 还有什么问题

1. **最大的坑：它会变成第四本没人写的账。** 前面那三本账为什么停了 8 天？因为靠人写。飞书表格如果也靠人手动填，会一样烂掉。所以必须让 AI 自动写，而不是让谁去填。
2. **得先定谁是「真相」。** 如果表格是唯一真相，那飞书一挂，项目就失忆了。我的建议：**以代码库和任务日志为准，表格只是给人看的窗口**。这样「表格没更新」不算事故，「代码里有但表格没有」才算。
3. **不能什么都往里塞。** 把四本账、18 个交付目录、58 份任务书全搬进去，等于把乱从电脑搬到云端，还是没人看。只放两样：等您决定的、需要跨会话知道谁在做什么的。控制在 20–40 行。
4. **要防重复行。** 现在多个会话同时干活，都往里写会写重。得用固定的任务编号，先查后写。
5. **写失败不能拖住干活。** 飞书会限流、会超时。失败就登记一下继续，绝不能让表格变成开工的前提。
6. 顺便发现个反面教材：GitHub 上有个把飞书表格当数据库的项目，README 里**把密钥明文写着**。我们不会这么干。

## 接下来怎么办

1. **先装官方工具**（一条命令，需要您扫一次码）。装完确认能读能写。
2. **建一张表**，7 列就够：任务编号、标题、状态、负责人、下一步、出处、更新时间。可以先用飞书官方模板改。
3. **写个同步脚本**：从任务日志和代码提交里读，自动推到表格。先出预览，确认了再写。
4. **接进收尾流程**：以后每次干完活顺手推一次，不用您操心。
5. **验证标准只有一条**：您打开表格，能不能一眼看出「谁领了什么、做到哪了」。看不出就是失败，撤掉。

**最后一件事**：您这个想法，正好补上了今早那个 A/B 选择的第三条路。我建议 **B 和 C 一起做**——B 管「账有人写」（以代码为准），C 管「账有人看」（飞书表格）。只做 C 会重演没人写的坑；只做 B 您还是得翻文件。
