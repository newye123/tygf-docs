网页侧那块面板是真上线了（测试站跑 d8f507c）：按语言的页签、字体族/样式/字距/行距四个输入框、一行 CSS 预览、顶部黄条明说"执行时不会被应用"。写回侧是真的一行都没有：助手里搜 v1.5/fonts 端点，命中 0（退出码 1）；薄执行器整个文件搜 font，命中 0，它只有第 114 行那一句写文字内容。现有的 36 条排版测试我跑了，全过，但那 36 条全是"形状校验和源码里有没有那句文案"，一条都没碰到 Photoshop。台账上 FONT-CUSTOM 那行还写着"前置＝P0 spike"，这个前置今天闭了。

GitHub 上别人怎么做的，能不能复用

能抄形状的有三件，能装进产品的零件。

PhotoshopAPI（BSD 授权，384 星）把 run 级的字距、行距、假粗体都做出来了还带读回单测，我拿它当字段名和单位口径的权威参照，但它没有 Node 绑定，不装。ag-psd（MIT）确实能写引擎数据里的字距行距，可作者自己承认实现不完整：改了文字层不重绘位图，打开必弹"更新文字图层"；竖排文字层能造出连 Photoshop 都打不开的文件；字体清单那张表还是个 TODO；有 issue 实测它建出来的文字层包围盒 0×0、在 PS 里看不见。所以我们只在离线取证上用 ag-psd，绝不用它当写回主链路。comic-translate（Apache 授权）里有一段"读 name 表第 6 项拿 PostScript 名 + 判假粗体"的解析逻辑可以照形状写，但它同一文件里另一个做法正是我们明令禁止的：字段不支持就静默跳过，失败还自己拼 -Bold、-Italic 造一个不存在的字体名。

字体枚举这条路上，npm 最主流的 font-list 反而是坑：它在 Windows 上取的是 WPF 的族名（不是 PS 要的 PostScript 名），中文系统上还优先返回本地化名"微软雅黑"，而且每个族只取第一张脸，Bold 和 Italic 根本拿不到。font-manager 的方向是对的（走 DirectWrite 拿 PostScript 名），但 2019 年就停更、要自己编译原生模块。正解是我们自己已经有的一半：助手扫字体目录，用 fontkit 读 name 表第 6 项，一次返回族名、样式名、PostScript 名三列（.ttc 集合字体必须走 fonts 数组，否则字段直接 undefined）。浏览器的 queryLocalFonts 只在 Chrome/Edge 桌面版有、要点权限，只能当助手掉线时的降级，不能当权威源。

产品形态上，业界跟我们想的不一样：Android 系统按文种绑了 149 条字体，只给"紧凑/疏朗"两档，从来不暴露行距数字；Google Slides 只给三档自动适配、缩放比例明确是只读；InDesign 缩放完把字号显示成"20 pt (40)"，数字是结果不是输入。更要紧的一条：Canva 的翻译功能压根不让你选字体，只有三个勾选，其中一个默认就是"缩小字号以适应页面"；DeepL 文档翻译只承诺"保持原版面"。也就是说，我们现在这四个输入框比这两家头部竞品都重。

Photoshop 22 实测的七条结论

一，字体能写，但只认 PostScript 脸名。你这台机器上 PS 报出 1605 张脸，只有 1319 个不同的显示名；"Noto Sans SC"一个名字底下挂着 Thin、Light、DemiLight、Regular、Medium、Bold、Black 七张脸。喂显示名进去，Photoshop 不报错，自己给你换一张：写 Arial 读回来是 MyriadPro-Regular，写 Noto Sans SC 读回来是 AdobeHeitiStd-Regular，写一个本机没有的名字读回来还是 MyriadPro-Regular。这就是静默降级最典型的形态，只有"读回比对"能抓住它。

二，字距（tracking）是四个字段里唯一没坑的。写 500 读回 500，图层宽从 122 变成 242；写 -100 变 98。我用间隙数乘千分之 em 乘字号自己复算过，两点都逐位对上，口径就是 1/1000 em，而且能改之前就算出会不会顶破原稿行宽。

三，行距能落，但差一步——这一步让我下午差点把这个字段砍了。只写 leading 的时候，赋值返回"接受"，读回来抛"文本设置为自动行距"，三行高一动不动（55→55）；先把 useAutoLeading 置为 false 再写 60pt，读回 60 pt，层高 55→133。保留自动的话走 autoLeadingAmount（300 档 55→85）。关自动之后重写文字内容或者换字体，行距都还在。ActionDescriptor 那三种写法我今天全部抛错，那条路没跑通，也不再需要。

四，顺手钉死一条闭式：层高 = (行数−1)×行距 + 单行高。六个独立数据点逐位对上（12pt 单行高 13；自动 175%→55、写 60→133、300%→85、写 24→61、写 50 三行 113 四行 163）。这就是 #75"渲染行数"一直算不准的正解——行距现在有可靠读法了，不用再拿字号乘 1.2 猜。

五，多脚本混排层（一行里既有假名又有拉丁）Photoshop 会自己按脚本换脸：用 Arial 写日文，读回来变成 KozGoPr6N-Regular。DOM 上没有 run 的概念（textStyleRange 属性在 PS 22 根本不存在），要按 run 控制必须走 ActionManager，业界都是这么做的，这条我今天没验。

六，缺字形预检只能靠 fontkit 的逐码点查（它只看 cmap），拿宽度或排版结果反推必然假绿——缺字时它静默给你 .notdef、宽度还非零。告知文案要做成两态："这台电脑没装这个字体"和"字体在，但这些字它没有"。

七，TextItem 上真能用的旋钮就这么几个：内容、字体、字号、颜色、位置、字距、基线偏移、假粗体、假斜体、对齐、自动字距、warpStyle、以及行距那三件套。orientation、vertical、autoLeading、textStyleRange 都不存在。language 读的时候抛"内部错误"，原因未核实。

对抗式审查，第一刀砍我自己

砍自己那条：我下午一度写"行距在 PS 22 上写了不变，建议这个字段撤掉"，是错的。真因是我没先关自动行距。病根是把"我没试对"读成了"它不行"。以后凡是想下"这个不行"的结论，必须先把相关开关位穷举一遍。

砍现状代码四条：一，面板存的"字体族+样式"和 PS 认的 PostScript 脸名根本不是一套东西，照现在的字段接下去必然静默换脸，这条推翻了 10-14 方案的字段设计，得降到脸级单值。二，假保存（真缺陷）：只填行距不填字体名时，校验整份拒绝、落盘函数直接 return、localStorage 字节一字未变，可界面照样回显"已保存到本机浏览器 15:12"，我写探针实测到 returnValue=undefined、bytes_unchanged=true 两条回显，已登记 #157。三，"有未保存改动"那枚徽标判的是"有没有值"，存完照样亮（这条是读码判的，界面实跑没做，标待确认）。四，前瞻性的坑：面板里有一条分支文案写"执行时将按此定制写回译文层"，哪天助手把字体清单端点做了但执行器还没接排版，这句话当场变成新的谎——验收判据要写成端点和执行器同车发，不许分批发。

隐私面守住：字体清单是机器画像（本机 1605 条），试验期只留本机；学习证据那边本来就把 fontName、fullFontName 列为禁字段，端点响应不许上云。
