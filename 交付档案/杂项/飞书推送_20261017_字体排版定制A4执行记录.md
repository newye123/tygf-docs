# 执行记录 · 用户自定义字体排版（2026-10-17 20:2x，A2–A4 与 W3 已执行完）

一句话：面板上设的每个排版值，在 Photoshop 里要么真变成那样，要么明确告诉你"这条没生效、为什么"——不许静默换脸、不许静默不生效、不许静默忽略。这一轮把这条链从"校验器"推到"真机读回"，四笔本地提交，未推、未部署。

## 解决了什么

一、助手侧排版校验器（A2，86 条断言）。只放行实测能写且不改行数的字段：字体脸名、字距、行距、字距方式、假粗、假斜。锁死 15 项会打穿行数判据与取证法的字段（合成器、点转段落、noBreak、字号、框宽框高、大小写、删除线、下划线、语言、方向等）。拼错的字段名一律当场拒，不再静默忽略——那和"假保存"是同族问题，把没做成的事洗成成功。全默认归一为"不发"，执行器走零写入路径。

二、转递链（A3，42 条断言）。三条执行入口各设一道 400 闸：旧 execute、execute/prepare→run、batch/execute。校验值随 attempt 缓存透传，最后写成执行信封里与清单同级的兄弟字段。

这里方案被实测改形两次，值得记一下：我原来说"排版走信封旁路"是含糊的说法。实测清单的键集是精确校验的（execution-manifest.js:28），而算摘要的函数自己先跑这道校验（:181）——带排版键的清单连摘要都算不出来，派发当场就死。所以后果不是"静默改口径"，是硬失败；旁路是唯一不动四层合同的路，实测也证实四层合同一字未动。第二个改形：原来设计"按语言一份排版"，在执行侧根本解析不出来（语种码只存在于清单的 locale 和各 attempt），改成每个 attempt 携带一份已定语言的排版值，助手侧零路由，还少了"表里没这个语言"这类新失败态。

三、执行器应用（A4，1.1.0 升到 1.2.0）＋真机验证。写完译文并核过后，按 face → 字距方式 → 行距 → 字距 → 假粗假斜 的顺序应用，逐字段读回比对，不一致就记码随结果留痕：FONT_UNAVAILABLE、FONT_FALLBACK_APPLIED、LEADING_NOT_APPLIED、TYPOGRAPHY_INVALID。排版是偏好，文本替换才是承诺——字段没吃进不推翻本次交付，但必须留痕，不静默。

四、面板与客户端改读能力位（W3）。这一条是本轮对自己前一轮交付的对抗审查里挖出来的真洞：面板判断"写回可用"原来只看字体清单读没读到，从不读助手报的 typographyApplyReady，客户端甚至把这个字段整条丢了。等 A1 的字体端点随新包上线，界面那句"执行时将按此定制写回"就是谎。现在能力位接进了客户端和面板，并给"清单读到了但写回没开"单独写了文案。

## 真机读数（本机 Photoshop 22.0.0，走生产同通道 DoJavaScriptFile；探针是从出厂执行器里按标记原样抽出来的代码，不是另写一份等价的）

- 合法档（ArialMT＋字距 500＋固定行距 30 磅＋OPTICAL＋假粗）：读回全部相等，零留痕
- 显示名 Arial：PS 换成 MyriadPro-Regular，正确报"已换脸"（这正是要抓的那件事）
- 不存在的脸名：PS 同样静默替换且不抛错，也报"已换脸"（说明"字体不可用"这个分支只能作防御，不能指望 PS 报错）
- 百分比行距 250＋字距 −100＋假斜：读回相等，零留痕
- 未设排版：零写入、零留痕
- 非法行距档位：当场拒，报 LEADING_NOT_APPLIED

这一跑抓到我自己两处"假绿"：① 脸名读回我写成 item.font.name，而 PS 22 里 textItem.font 读回来就是字符串，取 .name 得 undefined，后果是每一次成功写回都会被误报成换脸；② 行距读回用 String() 拿到的是 "30 pt"，Number("30 pt") 是 NaN，而 NaN 参与的比较恒为 false，等于"没吃进"和"吃进了"读起来一模一样——这条断言原本是假的。两处都已改，并各配一道能变红的负控。

另外澄清一条机器事实：PS 22 没有原生 JSON（typeof JSON 是 undefined，JSON.parse 直接抛"引用错误: JSON 未定义"），生产链的结果序列化靠助手 wrapper 注入的那段 polyfill。我新加的排版留痕是嵌套数组，所以把那段 polyfill 原样抽出来在真机上序列化一遍、回 node 侧解析比对，确认逐字段同形，不算"想当然能用"。
