飞书补一条（第七轮收尾时我又出了一次事，2026-10-17 20:0x）

我把要写进长期记忆的一段话，塞进了双引号包住的命令串里，而那段话里有反引号。bash 在双引号里照样会把反引号中间的东西当命令执行——于是我那句话里的三条 git 命令真的跑了：一条 push、一条 pull、一条 worktree remove。

结果是三条全失败，而且我逐条复核过没有留下任何影响：这个外层仓库根本没有配远端（列远端是空输出），所以那条 push 发不出去；pull 报"当前分支没有跟踪信息"，工作树没动；worktree remove 只打了用法说明。又核了业务仓的远端分支，还是我刚推的那一枚提交，没有多出任何分支引用。

但我要说清楚一件事：这次没出事是运气，不是设计。恰好这个仓库没配远端、恰好那个分支没有跟踪信息，才让误跑的命令都撞在拒绝上。换个目录、换个分支，那一条 push 就可能真的把别人的提交推上去。所以我没有"没事就好"过去，而是立案了 ISSUES 第 166 条，把三条命令的真实失败原式和复核读数都写进去。

实际造成的损害只有一处：我想追加的那段记忆正文被替换成了空洞文本（读出来是"实测 推送前 、推送后"这种缺字句）。已经按正确方式重写并核对：先写成文件，再让程序读文件写盘；项目记忆那份文件从 12,699 字符变 13,378 字符，空洞匹配 0 处、正确锚点 1 处。

规则这次落到动作形态上，不再靠我记着：只要要写的文本里有反引号（或任何可能被 shell 展开的字符），一律先用写文件工具落成 .txt，再用追加或读文件的方式进目标；命令行引号里永远不出现反引号。同一口锅这一天咬了我两次——前面刚因为"按文件而不是按代码块暂存"把别人的半笔推上去，紧接着又栽在引号上，所以判据得是"用什么工具落笔"，不是"我记得要小心"。

第七轮的交付没有受影响：origin/develop 仍是 b39f6f7（两份 llms 文件补平＋四处精度化＋llms.txt 补上名称澄清句，都没部署）；方案、操卡、报告与台账都在位。台账追加这一条事故记录时，我第一次用的时间戳写成了"20:1x"，被投影脚本按非法日期拒了（这是同一类老坑复现），已改成真实分钟重发成功（create=1，拦下的仍只有您手改的那条 ZHIHU-COPY）。
