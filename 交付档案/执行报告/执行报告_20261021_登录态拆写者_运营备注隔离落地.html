01结论

VERDICT：泄漏闭环，用户昵称与首页登录态按约定未做

病根不是"少一个字段"，是一个字段两个写者：BetaUser.name 既是用户自报姓名，又被后台当"运营备注名"写。运营要抢这一格，是因为所有后台用户资料载荷都过隐私守卫 assertSafeUserProfile，而守卫把 adminNote 列为禁键——守卫是对的，缺的是给运营备注一个合规位置。这次补位置，没动守卫。

04没做什么（及为什么）

  1. 用户可自设昵称——Owner 定调"先只拆写者"。将来若做，建议新增 displayName 而非让用户直接改 name（历史行的 name 里存的正是运营备注，用户"第一次改名"等于"擦掉备注"，语义混乱；新字段可零数据迁移）。且按 Owner 第二问"昵称还要给运营在后台认人用"：认人锚点必须是邮箱 + BetaUser.id + 申请单自报姓名，不能是任何用户可写内容——否则改个名就换了身份。
  2. 问题 B（登录后首页仍显示"登录"）——本轮范围外（需首页服务端注入会话摘要 + 统一会话 Provider + 骨架 + 跨标签同步，即审查报告 P0-3 + P1）。用户端目前仍会看到"登录"按钮。
  3. 存量脏数据——库里已有若干行的 name 存着运营备注。无法自动区分"用户真名"与"运营备注"，需人工/一次性脚本点名清理，本轮未连生产库、未做。
  4. 两个新 smoke 的 npm 入口——package.json 当前有别手在飞改动，本轮不碰；直接命令见报告 §7。
  5. 未推远端、未部署测试站/生产。
