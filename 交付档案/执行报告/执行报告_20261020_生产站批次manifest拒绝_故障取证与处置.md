# 生产站故障取证：批次在 manifest 阶段被本机助手拒绝（2026-10-20 17:34—18:05）

## 一句话结论

生产站本身没有挂。是**一位真实内测用户的两份译文表**里，「记录编号」这类行标识进入了助手不接受的字符形态，助手在构建执行清单（manifest）阶段直接拒绝，Photoshop 从未启动；批次因此悬挂在 RUNNING，界面上"取消""完成"都被 409 拒回，看起来就是"用不了"。用户 17:37 换了一份表（3 语 × 20 行）后**同一台机器成功跑完并交付**（17:46:44 replacement_done ES），两笔失败批次的预占积分已由回收器在 17:49:02 / 17:59:02 自动释放，当前 0 积分冻住。

这是 2026-09-14「事故3」的复发（同一 stage、同一 code），差别是这次终于拿到了助手侧的内层原因码。

## 根因链（到代码行为止）

1. 用户译文表若有「记录编号」列，浏览器把它直接当成清单里的行标识：`src/components/workbench/execute-step.tsx:401` `rowId: row.recordId || String(index + 1)`；该列在导入时**只校验唯一性、不校验字符集**：`src/lib/workbench/csv.ts:646`（列定位）、`:751-753`（取值 trim）、`:765-770`（仅查重）。
2. 助手侧清单校验器对 id 的形状有白名单：`download/local-assistant/execution-manifest.js:9` `ID = /^[A-Za-z0-9][A-Za-z0-9._:-]{0,127}$/`，命中即抛 `MANIFEST_FRAGMENT_ROWS_INVALID`：同文件 `:168`。中文、空格、全角括号、以 `-`/`_`/`.` 开头、超 128 字符的记录编号都会踩雷。
3. 清单构建失败＝attempt 从未被本机接受（`state=DISPATCHING`、`acceptedAt=NULL`），服务端只能靠派发窗口收口：`src/lib/server/execution-batch.ts:955/971`（每语 3 分钟预算，5 语＝15 分钟）、`:1636-1660`（窗口用尽→`ATTEMPT_ABANDONED_NEVER_DISPATCHED`）。
4. 界面在这个窗口内既不能取消也不能完成（409），用户主观感受＝"点了没反应、卡住"。

## 账务与影响面

- 失败两批：各 70 单位预占，均已 `released`（回收器 17:49/17:59 两拍），**没有多扣、没有悬挂冻结**。
- 成功一批：60 单位 `committed`，是真实交付的应扣额。
- 受影响范围：今日生产只有这一位用户产生批次（3 笔），其余为官网/助手心跳流量；生产与测试站的 Web 面均 `200`，`/api/runtime-provenance` = BOUND `6ff5c3c1414f`、期望助手 3.7.15。

## 顺带查出来的三处"下次还会瞎"的缺口

1. **排障快照通道在生产是坏的**：`support-bundles` 返回 503 `SUPPORT_BUNDLE_STORAGE_UNAVAILABLE`，而 `/var/www/tygf/support-bundles` 自 09-17 建目录以来**一个文件都没有**；路由把异常整个吞掉不记日志（`src/app/api/local-assistant/support-bundles/route.ts:68-70`），所以具体抛的是什么错，盘上无从取证。这正是 09-14 事故3 拖了五周才拿到内层码的同一根病灶。
2. **助手回传的诊断条目被服务端丢弃**：今日 23 条 `ATTEMPT_DIAGNOSTICS_INVALID`，落库成功的条目里 `code` 是 `TUESDAY_`、`2026_10_20T09`、`_` 这种 PS 日志串——助手把日志文本写进了 code 字段，解析器按白名单判非法。PS 阶段的现场基本收不到。
3. **两站共用一份 nginx access.log 且 log_format 没有 `$host`**（`/etc/nginx/nginx.conf:40`）：按路径统计出来的 403/409/503 无法判定属于生产还是测试站，本次全部结论改走"生产库 + tygf.service journal"取证。

## 待办（分两类）

需要 Owner 点头才动的：

- 修法 A（推荐，改动面最小）：在导入与执行前按助手同一白名单校验「记录编号」，不合规就指名哪一行、哪一列，而不是等助手在 manifest 阶段整体拒绝。属于校验与文案，不碰计费/回执合同。
- 修法 B（合同变更）：清单构建时把任意 `recordId` 规范成安全 token（`frag-<hash>`）并在浏览器/助手 evidence/服务端报价/结算闸四层保留映射——按纪律要同步四层＋`smoke-batch-row-contract` fixture，成本明显高于 A。
- 缺口 1 的修复要不要现在做（把 catch 改成带错误码的 warn＋给目录写权限自证），以及缺口 3 的 nginx 改法（加 `$host`，需 reload 生产 nginx）。
