## 二、系统 Node 20 → 22.23.4（收口 ISSUES #235）

### 为什么走这条路

上午查清的那件事：这台机器上有个**已停止维护的 Node 20**，而且真在执行东西——PM2 管理进程，和测试站那枚每 10 分钟的对账任务（13 个业务单元里唯一写死它的那枚）。两条修法：改那枚单元指向我们的运行时，或者**把系统 Node 升到同一个版本**。

选后者，理由都是实测的：`/usr/lib/node_modules` 里**原生模块 0 个**（`find … -name '*.node'` 计数 0）⇒ 换解释器不用重装任何依赖；NodeSource 官方源里就有 `22.23.4-1nodesource1`，与业务运行时**同版本、同 ABI 127**；而且**一行 unit 配置都不用改**。

### 过程里我自己摔的两跤（都留在证据里）

1. **13:18:55 第一次跑**：脚本以 ubuntu 身份执行，而日志目录是 root 700 ⇒ 写日志被拒 ⇒ 脚本以为"apt update 失败"，**自动把源文件还原了**。盘上什么都没变（node 仍 `v20.20.2`、源仍是 `node_20.x`）。这一跤反而证明**自动回滚那条链是真能跑的**。
2. **13:20:09 第二次跑**：五项健康门**全绿**（node v22.23.4、npm 10.9.9、pm2 7.0.3、两站本机 200、PM2 三应用 online），但我把返回值极性写反了——shell 里 **0 才是通过**，我用 1 表示通过 ⇒ 门误判成失败，脚本按预案**把刚升好的 Node 又降回 20.20.2**。升级被我自己的 bug 回滚了一次。
3. 改对极性后，**先跑负控**（13:24:34）：在 v20 上这道门必须红。实测只有版本那条红、其余四条绿、整体返回非零 ⇒ 门确实能红，不是摆设。
4. **13:24:48 第三次跑：`RESULT=PASS`。**

### 读数（13:26:06 实测）

- 包：`nodejs 22.23.4-1nodesource1`；系统 `node v22.23.4`／`npm 10.9.9`／ABI 127；业务 `node v22.23.4`（实指 `/opt/tygf-node-v22.23.4/bin/node`）
- 两站：本机 3000／3001 都 **200 ＋ BOUND**；公网 `tuyigf.com/` 与 `/download` 都 **200**
- PM2 守护进程：pid 41446，`exe=/usr/bin/node`（这个路径现在就是 22.23.4），13:24:59 起；三应用 online
- 红单元：**还是 1 枚**，就是存量那枚对账任务
- 那枚对账任务在升级后（13:30:01）报的还是同一句 `403 INVALID_RESPONSE` ⇒ **运行时切换没改变它的失效形状**，它是另一件事（#236）

### 残留（如实）

机器上现在有**两个 Node 安装通道**：NodeSource 的 apt 包，和我们自己的 tarball 目录。版本此刻一致，但**通道不一致——以后只升一个就会重新漂移**。建议下一步二选一：业务也收到 apt 通道，或把那枚单元指到 tarball 路径。本轮不做（又一次生产改动，且方向该您认）。

### 回滚

源文件备份在 `/var/backups/tygf-security-20261022/nodesource.sources.bak`；`cp` 回去 → `apt-get update` → `apt-get install nodejs=20.20.2-1nodesource1` → 重启 `pm2-ubuntu`。**这条链今天实测跑通过两次**（就是那两次误回滚）。

## 三、运行时安全探针：把"看新闻才排查"换成"跑一条命令"

新增三个文件（都在容器根 `scripts/`，未提交——这个仓库没有 remote）：

- `scripts/security-runtime-probe.sh` —— 主入口：`bash scripts/security-runtime-probe.sh`（网络受限时加 `--offline`）
- `scripts/security-runtime-latest.mjs` —— 解析 nodejs.org 官方发行索引，认它的安全版标记
- `scripts/security-runtime-baseline.json` —— **唯一判据来源**：最低版本、ABI、必须放开的安全源、自动重启必须 false、磁盘下限、红单元基线

它查九件事：业务与系统运行时版本、ABI 是否还是 127、**待装安全包数（按 `noble-security` 这个源数，不拿"全部待装"糊过去）**、自动更新是否真的还允许安全源、自动重启是否关着、红单元数对不对基线、磁盘可用率、以及**官方那条版本线有没有更新版**（是安全版就判红，非安全版只提醒）。

退出码分三档，故意把"坏"和"红"分开：**0 全绿／1 有 FAIL／2 探针自己跑不动**——坏掉的探针绝不能被读成"安全"。

**实测**：

- 13:33:42 全绿：`FAIL=0 WARN=1`（那条 WARN 是 `tmux` 被 Ubuntu 官方灰度推送，非安全项）；官方索引这一条给出 `已是官方 22.x 最新（v22.23.4，2026-10-20，security）`
- 负控 13:35：把基线临时抬到 `22.99.0` ⇒ **`FAIL=2`、rc=1**（两条版本判据都红），随后按备份还原、**哈希一致**（`cc47c4003bd6cac2`）

两个坑已经写进代码注释，免得下家重踩：本机 `curl nodejs.org` 取不到（实测 `http=000`），**索引必须在服务器上取**（服务器 0.05 秒 335 KB）；把解析脚本塞进 ssh heredoc 里的 `node -e` 会被解析器咬（实测 `SyntaxError: missing ) after argument list`），所以独立成一个文件。

**有一件故意没做**：没把它接进每日控制面或服务器 cron——那是别人的写面（`scripts/control-plane.sh` 与服务器定时单元）。要接就加一行，等您点头。

## 四、边界与遗留

1. **磁盘还有 6G 级可换空间，但都带代价**（npm 缓存 3.9G 换部署变慢、状态目录 1.6G 需先验证、swap 6G 是内存兜底）。要更多空间就按第一节那张"有意没动"清单逐条拍。
2. **双安装通道漂移风险仍在**（第二节末）。
3. 探针**只覆盖这一台服务器**（主机名写在基线里，多机要扩），而且**不做漏洞级比对**——它判"版本是否 ≥ 基线、官方是否发了安全版"，不判"某个 CVE 是否走到我们的调用路径上"。
4. 测试站那枚 403（#236）**未修**，本轮所有改动都没改变它的失效形状。
5. 本轮没跑业务全链路（不占 PS 与积分）、没做入侵痕迹排查、没推远端、没碰数据库与支付开关。
