# 流量板的长期方案：能在我这边做完的都做完了，只剩服务器上三条命令

## 你说"按长期方案来"，我做了什么

把"每天自动去 Cloudflare 取一次官网访问数"这件常态化的事，做成了仓库里的正式部件：一个每天跑一次的定时器定义（早上 8:20，机器停过机也会补跑一次），接进仓库既有的那套定时器安装脚本，测试站一条命令就能装上。

**但真正落到服务器上执行，我这个会话做不到**——到不了服务器这件事前面已经说过（四条路都被本机权限层挡住，我没试第五条）。所以我把剩下的动作写成三条命令，投进了总控的待投递队列（22:35:12 落盘），请派一只到得了测试站的手执行。

## 做的时候发现一件必须提前告诉你的事

面板要读的那个数据文件，按仓库规则**不会随发布包发出去**（发布打包时整目录排除了我们的内部账本目录，那条规则在 `.gitattributes:7`）。这意味着：如果不在服务器上显式指定"数据文件放哪"，就算定时器天天正常跑，面板也会永远显示空的。

所以那三条命令里的第二条不是可选项，是必需的：把数据文件位置指到服务器的状态目录（这个目录是发布时不会被删的那一个）。

## 三条命令分别是什么，以及为什么这么设计

第一条，在服务器上建一个只有 root 能读的文件，把 Cloudflare 的只读令牌放进去。令牌的值不会出现在仓库、文档或任何提交里。

第二条，把数据文件位置写进应用的正式环境文件，指到状态目录。

第三条，跑仓库既有的定时器安装脚本装上它。这个脚本我加了"前置拦截"：令牌文件不存在、权限不是只有 root 能读、两项值有任一为空、数据文件位置没指到状态目录——这四种情况**任何一种都拒绝安装**。因为仓库里有过一次教训：定时器装上了但路径写错，连红七周没人发现，那阵子承诺的数据清理其实一直没跑。装完它还会当场跑一次，并核对数据文件真的落了盘，红就直接报出来，不允许带着"应该能跑"收工。
