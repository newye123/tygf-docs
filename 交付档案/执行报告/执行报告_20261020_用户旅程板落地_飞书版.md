# 用户旅程板落地：注册到付费一条链，零新增采集（2026-10-20 18:4x）

## 做了什么

后台运营台再加一个页签，叫"用户旅程"，只有 owner 能看。它把六步串成一条漏斗：提交内测申请 → 开通账号 → 首次登录 → 激活设备 → 首次成功跑通 → 首笔付费到账。每一步给三个数：多少人走到这、相对上一步转化多少、从上一步到这步中位花多久。

**关键是：这一步一个新埋点都没加。** 上一轮我说过"要补三个事件才能串旅程"，那是错的——动手前把表结构又读了一遍，这些时间戳早就在各张表里了，纯只读关联就能拼出来。所以零新增采集、不动数据库结构、不动隐私政策、不碰登录注册代码。

## 中途差点踩的一个大坑，值得你知道

这个产品里有**两套"用户标识"**：行为数据（跑批、漏斗事件）记的是账号 id，订单数据记的是另一个计费主体 id。用错任何一把，那一步会**稳定显示 0 个人**，而且不报错——看起来就像"没人付费"或"没人用"。

我用本地真库当场验了：行为表按账号 id 关联命中 3 条、按计费 id 关联命中 0；订单表正好反过来，按计费 id 命中 5、按账号 id 命中 0。两套键在代码里分开处理了，并且写进自检——**以后谁"顺手统一成一把键"，自检会立刻红给他看**。

还有一件：这个库里的日期存的是整数毫秒，不是日期字符串。我第一版交叉核对用字符串比较，结果 SQL 侧全 0，差点把"核对方法错了"当成"面板没数"。改成按毫秒比之后，面板数与 SQL 数逐步对上（账号 8 对 8、登录 2 对 2、跑通 1 对 1）。

## 另一个设计修正

漏斗原来是"每步各按自己的时间过滤"，这会出现"账号是三个月前创建的、但最近登录过"的人只算在登录步——漏斗不单调，转化率能算出百分之一百二。改成**先按账号创建时间圈定同期群，再看这群人走到哪**，这才是能看的漏斗。

## 验收（真跑的）

类型检查零错误；七个改动文件 lint 零告警；后台安全契约门通过（新接口已登记进两份清单，漏登记那道门就红）；旅程自检 **15 条全过**，其中包含"错键必须得 0"和"SQL 侧必须有非零样本"两条防假绿的断言；直接调用接口做运行时探针，无身份时回 403 拒绝。

## 一个副作用，如实报

中途我传数据库路径的方式在 Windows 下不合法，导致程序连到一个"存在但没有这些表"的库。我查了工作区的库目录和 git 未跟踪列表，**没有多出任何数据库文件**，没留下东西；修法是让自检脚本自己算绝对路径，不再靠命令行传。

## 数据现状说明

本地开发库里这几步是有数的（8 个账号、2 个登录过、1 个跑通、0 笔已到账订单）。**生产库我没有读权限**，所以这个板子在你真实后台上的第一屏，同样要等部署之后才有真数——我不会拿本地开发库的数冒充生产情况。

## 还差什么

第三层现在能告诉你"多少人卡在激活、多少人没跑通第一次"，但**还不能告诉你"哪个渠道来的人更容易跑通"**——那要等第二层（服务器日志取来源）做完，两边一合就有答案了。这也是我催那件事的原因。
