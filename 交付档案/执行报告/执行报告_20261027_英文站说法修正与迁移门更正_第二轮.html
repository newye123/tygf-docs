043. 更正我自己：F-11 那颗雷比我说得窄，而且门已经有了

我上一轮写的是「下一次发版如果不带 prisma migrate deploy，官网申请会 100% 提交失败」，并建议「加一道自动检查：代码里有新表但没建表脚本，就不许出包」。本轮实测后要改口：

  1. 对测试站不成立。 那条迁移已经在测试站发布脚本的批准名单里：deploy/deploy-test-release.sh:500 有 20261024120000_application_attribution，还带 sha256 与预期表名/索引名。测试站发布会自动应用，不会漏。
  2. 仓库里早就有那道门，我不该再造。 scripts/check-migration-drift.mjs（页眉写明病根＝2026-10-10 cebb737 那次"部署脚本不认识新迁移目录 ⇒ 静默跳过"事故），npm 入口 test:migration-drift。它的自测本轮跑了一遍，7 例全绿（含 4 条负控：多一个未批准迁移必须 rc=1、--baseline 指向不存在目录必须 rc=2 不得静默退回、production 无名单必须 rc=2 不算通过、未知 target 必须 rc=2）。
  3. 对生产成立，但机制不是"没有门"，而是"门拒绝盖章"。 deploy/deploy-release.sh 里 approved_migrations 与 migrate 两条 grep 全为空 ⇒ 生产部署脚本根本不跑迁移；而 node scripts/check-migration-drift.mjs --target production 实测 rc=2，原文：no approved-migration ledger rows found ... manual review required, this is not a pass。
  4. 今天真正爆的现场是本机开发库：develop 的开发库从没跑过 migrate deploy，所以本地测表单必 500（我本轮用隔离库 tmp/en-check.db 全量应用后 rc=0 才验通）。这是环境问题，不是发布缺陷。

所以动作改成这一条（不需要写代码）：生产发布清单里显式加一步——「生产库的 prisma migrate deploy 是独立人工动作；check-migration-drift --target production 恒回 rc=2，必须有人核对并签字，不得因为部署脚本退出码 0 就认为迁移已应用」。这条我落进本报告的 §5 待办，不新造门。
