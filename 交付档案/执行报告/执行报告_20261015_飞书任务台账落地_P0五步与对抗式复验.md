## 三、对抗式复验：推翻的 4 条既有判断

这一节是本件的核心。四条都是**实测推翻了先前记录或方案假设**，不实测就会写错代码。

### 3.1 「`lark-base` 写入走异步链路，写成功但立刻读不到」——**本次不成立**

- 既有记录（`.workbuddy-ai/memory/MEMORY.md`）：写入异步、验收要留缓冲。
- 实测：`+record-upsert` 返回后**立刻** `+record-search` 即读到该记录（`reczz28NcEwjow7U`），datetime 已正确落为 `2026-10-15T16:35:00.000+08:00`。
- **结论**：至少 record create 是同步可见的。既有结论不适用于本操作，故未按「留缓冲」设计验收。**但保留缓冲仍是稳妥做法**——一次成功不足以断言永远同步。

### 3.2 `--domain base` 会裁剪实际授权集——**不成立**

- 方案里的「最小权限」建议：用 `--domain base` 只申请 base 域。
- 实测：`auth login --domain base` 后，`auth status` 的 scope 是**全量 22 个域**（含 `mail:*`、`im:*`、`calendar:*`、`okr:*`、`vc:*`、`drive:*`、`docs:*`）。
- **结论**：`--domain` 只影响 CLI 侧提示，**不裁剪实际授权集**（授权集由开放平台 app 注册决定）。**这是权限面大于预期的既有事实，如实登记**，不粉饰。

### 3.3 node 进程内可以 spawn 子进程——**不成立**（这条决定了整个架构）

- 原方案设想：mjs 脚本内 `execFileSync('lark-cli', ...)` 直接调 CLI。
- 实测 **4/4 全失败**：`shell:true` → `spawnSync cmd.exe EBUSY`；直接 `.cmd` → `EINVAL`（Node 安全策略拒绝）；`bash -lc` → `spawnSync bash EBUSY`；直接 spawn 原生 `lark-cli.exe` → 仍 `EBUSY`。
- 对照：**Bash 工具直接执行 lark-cli 全部成功**（含中文参数）。
- 反证：`scripts/send-feishu-report.mjs` 发飞书用的是 `fetch`（HTTP），唯一 spawn（取环境变量的 `powershell`）**包在 try/catch 里**——即该脚本从未真正依赖 spawn 成功。
- **结论**：本沙箱下 **node 进程内 spawn 被拦**。故架构改为 **mjs 只做纯变换（不 spawn）+ bash 负责执行 lark-cli**。

### 3.4 `+record-upsert` 可按业务键自动 upsert——**不成立**

- 命令原文：**"It does not auto-upsert by business key."**（无 `--record-id` 即新建，有才更新）
- **结论**：「主键幂等禁 append」**不能靠命令自身**，必须由脚本先拉现状、按「任务ID」比对后再决定 create/update。已如此实现。

**另修两处自己埋的坑**（未等出错先修）：

- **路径坑**：`mktemp -d` 在 git bash 返回 MSYS 路径（`/tmp/...`），node 不认 ⇒ `existsSync` 为假 ⇒ **静默空跑**（正是 MEMORY 里记的「假 0」类陷阱）。已加 `to_win()`（`cygpath -w`）转换。
- **重复坑**：ledger 是 append-only，同一 `taskId` 会有多行历史；而现状映射是同步前拉的，重复 taskId 会被判成两次 create ⇒ **飞书出现重复记录**。已加去重（取最后一条），并以追加 `TASK-LEDGER` 新状态行实测：`deduped:1 / create:0 / update:15`，记录数仍 15、无重复。
