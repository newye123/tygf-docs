04对抗式复验：推翻的 4 条

本节是核心。四条都是实测推翻了先前记录或方案假设——不实测就会写错代码。

①「写入走异步链路，写成功但立刻读不到」

不成立

既有记录说写入异步、验收要留缓冲。实测：+record-upsert 返回后立刻 +record-search 即读到该记录，datetime 已正确落为 2026-10-15T16:35:00.000+08:00。至少 record create 是同步可见的。

但保留缓冲仍是稳妥做法——一次成功不足以断言永远同步。

② --domain base 会裁剪实际授权集

不成立

方案里的「最小权限」建议是用 --domain base 只申请 base 域。实测授权后 scope 是全量 22 个域（含 mail:*、im:*、calendar:*、okr:*、vc:*、drive:*、docs:*）。

--domain 只影响 CLI 侧提示，不裁剪实际授权集（授权集由开放平台 app 注册决定）。权限面大于预期，如实登记，不粉饰。

③ node 进程内可以 spawn 子进程

不成立

原方案设想 mjs 内 execFileSync('lark-cli', ...)。实测 4/4 全失败：shell:true → spawnSync cmd.exe EBUSY；直接 .cmd → EINVAL（Node 安全策略）；bash -lc → spawnSync bash EBUSY；直接 spawn 原生 exe → 仍 EBUSY。而 Bash 直接执行 lark-cli 全部成功。

反证：send-feishu-report.mjs 发飞书用 fetch，唯一 spawn（取环境变量）包在 try/catch 里——它从未真正依赖 spawn 成功。架构因此改为：mjs 只做纯变换 ＋ bash 负责执行 CLI。

④ +record-upsert 可按业务键自动 upsert

不成立

命令原文：“It does not auto-upsert by business key.”（无 --record-id 即新建，有才更新）。

「主键幂等禁 append」不能靠命令自身，必须脚本先拉现状、按「任务ID」比对再决定 create/update。已如此实现。

另修两处自己埋的坑（未等出错先修）

路径坑：mktemp -d 在 git bash 返回 MSYS 路径（/tmp/...），node 不认 ⇒ existsSync 为假 ⇒ 静默空跑。已加 to_win()（cygpath -w）转换。

重复坑：ledger 是 append-only，同一 taskId 会有多行历史；而现状映射是同步前拉的，重复 taskId 会被判成两次 create ⇒ 飞书出现重复记录。已加去重（取最后一条）。
