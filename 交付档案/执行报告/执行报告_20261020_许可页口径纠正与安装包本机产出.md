## 一、开源许可页：不写 Learning Machines LLC，不违规

我之前写"要同时写明两个署名主体"，是把一条我自己的建议写成了法律义务。对抗式复核许可原文后站不住：

- MIT 的义务句原文只有一句："The above copyright notice and this permission notice shall be included in all copies or substantial portions of the Software"（见入库的 `download/local-assistant/build/vendor/photocraft/licenses/LICENSE-MIT:12-13`）。
- 随包的 NOTICE 写的著作权主体是 "ArtCraft Team and the PhotoCraft contributors"（同目录 `NOTICE:2`）。
- MIT 和 Apache-2.0 都没有任何条款要求把 exe 右键属性里那行公司名复制到许可页——那是 Windows 的版本资源元数据，不是许可声明。

**必须随包和必须上许可页的**是这些：上游软件名 PhotoCraft、许可名 MIT OR Apache-2.0、版权行原文、NOTICE、两只 OFL 字体与 SCOWL 词表的保留声明、上游地址，以及"我们分发的是它的副本"这一事实。公司名不在其内。

顺带把那行公司名的来路查清了（不再是需要"核实"的谜）：它就是上游自己的构建脚本写进去的——我们的 fork 里 `apps/photocraft-cli/build.rs:22` 逐行 `set("CompanyName", "Learning Machines LLC")`、`set("ProductName", "PhotoCraft")`、`set("OriginalFilename", "photocraft-cli.exe")`。

补一层实证（浅克隆源码后现查，台账已记 `AI_MEMORY/ISSUES.md` #198 补证段）：上游发行文档 `docs/releasing.md:127-129` 自己写明两只 exe 的资源 "set ProductName to PhotoCraft, CompanyName to Learning Machines LLC and the same copyright line"；Linux 元数据把 `<developer><name>` 定为 Learning Machines LLC（`packaging/linux/ai.storyteller.photocraft.metainfo.xml.in:11`）、`nfpm.yaml:16` 是 `vendor:`、Windows WiX `photocraft.wxs:21` 是 `Manufacturer=`，苹果证书名也是 "Developer ID Application: Learning Machines LLC"。⇒ 两个名字同属一个项目：**LLC 是上游的发行主体，ArtCraft Team 是版权声明里的团队／品牌名**。所以许可页提不提 LLC 都是"加分项"而非义务，但若要提，现在有了可引的出处，不用写"待核实"。

## 二、这个更重要的纠正：出包不需要别的机器

我先后两次上报"本机没有 NSIS，出不了 setup.exe，需要你指定一台出包机"。**工具我认错了**：本项目的安装脚本是 Inno Setup 的 `.iss`（`installer.iss:2-3` 第一行就写"用 Inno Setup 6+ 编译"），而我按 NSIS 的 `makensis` 去找，找不到就下了结论。实际上这台机器一直装着 Inno Setup 6（`%LOCALAPPDATA%\Programs\Inno Setup 6\ISCC.exe`）。

于是我当场把包装出来了，全部是真跑读数：

- 打包全链在隔离构树走完：配置校验 rc=0、助手 exe 用 pkg 打出 38,631,757 B、四条自检 rc=0（其中冻结证据自检回显 `version=3.7.16 / assistantBuildId=bundled-engine-20261020-r1 / frozenEvidenceContract=true`）、引擎与许可 staging rc=0、托盘编译 rc=0。
- **安装包编译 rc=0，耗时 42.844 秒**：`tygf-engine-setup-3.7.16.exe`，37,172,332 B，SHA-256 以 `7c663d1c` 开头。
- 编译器日志逐条列出实际压进去的 20 个文件，包括 `bin\photocraft-cli-0.7.0.exe`、`bin\engine.sha256`（出厂钉值）和 `licenses\` 八件——不是"脚本里写了"，是"确实在包里"。

交付位置：`tmp/setup-3.7.16-内测\`（安装包 + 自跑的 tools + 说明 + 和值清单，和值复算 0 处不符）。

用法就三步，都在说明.txt 里：装 → 跑一条**只读演练**（`--bundled --dry-run`，看它能不能认出刚装进去的内置引擎）→ 你自己去掉 `--dry-run` 真开。最后这步我不替你做：它改的是那台机器的助手会话文件。

要提醒的两点：这仍是**内测件**（3.7.16 的身份只在构树本地打过，没走发布登记、没有御史复验、未签名）；里面的引擎还是上游未修改的副本，保留人家原名和资源。

## 三、编译器还替我抓出一个真错

昨天入库的安装脚本里，`dist\bin\*` 那行用了 `createallsubdirs` 却没带 `recursesubdirs`，Inno Setup 直接在 [Files] 段中止（`Error on line 54 … Compile aborted`，该行现为 `installer.iss:54`）。只在文本层验过、没真跑编译器＝漏验。已修，并把这条规则钉进门里（提交 `dce444f`，22:36:45；判据在 `scripts/smoke-pc-bundled-engine.mjs:216`）：新增形状判据"用了 createallsubdirs 就必须带 recursesubdirs"，负控实测坏写法被抓 1 条、正确写法不误报 0 条；那枚新门复跑 15/15、退出码 0。

## 五、有一件我必须自报：我误起了一个助手进程

我在构包脚本里多塞了一条 `--version` 探针，想读打包 exe 的版本。但那个 exe **没有实现 --version**，于是它直接走了助手启动路径（回显"正在本机运行…已检测到 Photoshop…等待授权"），把我的调用挂到 300 秒超时，最后由工具按 PID 收掉。逐条核对后果：

- 它在构树目录里新建了一份**自己的**会话文件（721 B，未授权），我已删除。
- **你那份便携助手的会话文件没被碰过**（643 B，时间戳仍是 10-19 19:40）。
- 现在 49152 端口没有监听、也没有助手进程在跑。我不能证明此前有没有你的实例在听（如果端口被占，我起的这个会立刻报错退出，而不是挂满 300 秒）。
- 按红线我没有替你重启助手。**你需要自己重开一次**：托盘或双击「启动引擎.bat」。

规矩也沉进台账了：未验证过的旗标，先读源码分支再执行——"看着无害"的 --version 恰恰是启动开关。
