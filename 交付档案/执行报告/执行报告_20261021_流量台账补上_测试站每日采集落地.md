# 流量台账补上：测试站每日采集已落地（2026-10-21 20:5x）

## 为什么之前是空的（实测，不是猜）

面板读数的逻辑是：去一个固定路径找台账文件，找到就画图，找不到就显示这句话。服务器现场实测，三条前置一条都没满足：

- `/etc/tygf-site-traffic.env`（放 CF 只读 Analytics 令牌与 zone id 的那枚文件）—— 不存在；
- `/var/www/tygf-test/.env` 里 `TYGF_TRAFFIC_LEDGER`（台账放哪）与 `TYGF_TRAFFIC_HOST`（本站主机名）两个键 —— 一个都没有；
- `tygf-test-site-traffic.timer`（每日采集任务）—— 没装。

读侧和写侧靠 `TYGF_TRAFFIC_LEDGER` 这一个键同源：缺了它，面板会退回去读「应用目录下的 AI_MEMORY/traffic-daily.jsonl」，而发布包里根本没有 AI_MEMORY 目录（那目录在打包时被整目录排除），所以永远空态。这条不是推测，是代码与服务器两边对上的。

## 我在服务器上做了什么（四步，每步都有实测读数）

**第一步：放令牌文件。** `/etc/tygf-site-traffic.env`，权限 0600、属主 root:root、121 字节，里面是 `CF_ANALYTICS_API_TOKEN` 与 `CF_ZONE_ID` 两行。令牌和 zone id 取自上一轮运营数据线留在本机的 Cloudflare 只读 Analytics token（53 字节），本轮实测仍然有效（GraphQL 能看到 2 个 zone，zone tag 与上一轮真实拉取一致）。**令牌值只落在服务器和本机 tmp 目录里，没有进仓库、没有进文档、没有进任何提交。**中转副本装完即删。

**第二步：把台账路径与本站主机名写进应用配置。** 照发布脚本里既有的写法（deploy-test-release.sh 的 set_env_key），在 `/var/www/tygf-test/.env` 写两行：

```
TYGF_TRAFFIC_LEDGER=/var/www/tygf-test-state/traffic/traffic-daily.jsonl
TYGF_TRAFFIC_HOST=test.tuyigf.com
```

这里有个坑值得记一下：台账路径**必须落在状态目录的 traffic 子目录下**，不是状态目录根。原因是 systemd 单元只把 `.../traffic` 这一个子目录放进可写清单（ProtectSystem=strict，其余路径只读），写在根上会被只读拦下、单元天天红。上一轮派工件里写的路径少了这一层，按现装的安装闸门会被直接拒装——本轮按闸门口径落。

**第三步：装每日采集任务。** `sudo -n bash deploy/install-test-timers.sh tygf-test-site-traffic`。这个脚本自带一整套前置校验（令牌文件在不在、权限是不是 0600、两个键有没有非空、台账路径有没有落在允许写的子目录里），任一不满足就拒装；装完会**当场冒烟跑一次**再排程，冒烟不过就不排程——避免留下"天天红的僵尸单元"。本轮冒烟通过：台账 12 行，末行日期 2026-10-20。任务已启用，下次 2026-10-22 08:20（时区写死 Asia/Shanghai），停机漏掉的会补跑。

**第四步：重启 web 进程让新配置生效。** 应用是用 `node --env-file=.env` 启动的，环境变量只在进程启动那一刻读，所以改完 .env 必须重启一次（pm2 `tygf-test`，pid 3388031 → 3409692）。重启前查过在飞批次：只有 EXPIRED／QUOTED／SETTLED／STALLED，没有 RUNNING，不会切断谁正在跑的活。

## 期间挖出来的一个真 bug（已修）

第一次装的时候直接死在 `check-unit-paths.sh: Permission denied`。根因不在服务器，在**发布包**：打包走的是 `git archive`，而 git 根本不记录可执行位，所以发布出去的 `deploy/*.sh` 全是 0644；而安装脚本那一行是**直接执行**这个 .sh 的，于是安装 fail-closed 中止 —— 这就是"看起来该装的都装了、面板却一直空态"的机械原因。

要注意：**现场 chmod +x 只是临时补丁，下一次发布会把它带回来**（包每次重出、.sh 每次 0644）。所以我改了码：改成用 `bash` 显式调用（跟全仓一律 `bash xxx.sh` 的写法一致，不依赖文件模式），并在 timer 的离线自测里补了两条回归断言。

红绿都实测过（在服务器上真 Linux 跑）：修好的版本 16 条断言全过（rc=0）；**把发布包里那份旧版原样放回去，新断言当场判红（rc=1）**，证明这条断言真能抓住这个坑。提交：develop `2e55efa`（2 个文件，14 增 1 删，未 push）。另外 `test:site-traffic` 与 `test:admin-traffic` 两个流量门也都 rc=0。

顺带一个我自己踩的坑：`grep -E` 里没转义的 `$` 是行尾锚点，所以第一版断言模式永远匹配不到、会写出"永远绿"的假断言。改成 `\$` 后才真正判红。

## 生产站怎么挂（等你一句话）

前置与测试站完全一样，只是路径与主机名不同：

1. 令牌文件共用现在这枚（已在服务器上，0600 root:root，不用再动）；
