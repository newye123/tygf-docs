# 站点流量线：对抗式审核与加固（2026-10-22）

## 一句话

昨天两站挂上以后，我没有停在"能出数"就收工。今天早上把这条线当被审对象过了一遍，找到 5 个真缺口——其中 2 个是"门本身就是坏的"——逐条封掉，又加了三道"以后不会再犯"的闸。另外有一件事必须等时间：今早 8:22 和 8:26 两拍到底会不会自己跑。8:26 之后拿到硬证据：**两枚都自己跑了**。

## 我审出了什么（都是实测，不是推测）

**第一，面板空态给的补救指令是测试站专用。** 那一段原文是"在服务器上装每日采集：sudo -n bash deploy/install-test-timers.sh tygf-test-site-traffic"，生产站照抄就会装错地方（生产那枚命令不一样，而且缺一个确认参数会被直接拒）。同一段还写着"手工补一次跑 npm run ops:site-traffic"——这在服务器上根本不成立：令牌在只有 root 能读的文件里，npm 根本读不到它。已改成按环境分站给命令，单次补跑给 systemctl。

**第二，那道自测门本身是坏的。** 它有两条断言依赖"服务器上还没有令牌文件"这个前提——而那枚文件现在就在（这是它的本来用途）。结果就是：昨天在测试站服务器上实跑，这道门直接红两条。门不能只在没装过采集的机器上绿。已改成自测走沙箱路径，并补了两条真断言（令牌文件到位就放行、权限不是 0600 就拒装）。**同一台机器，昨天红两条，今天 19 条全绿。**

**第三，台账陈旧了没人看得出来。** 面板只显示"哪几天到哪一天"。采集任务哪天静默停了（令牌过期、边缘接口抖动、机器没开机），旧数字照样显示得像"最近就是这样"。已加：面板显示"最后抓取"时刻，距离上次抓取超过两天就红字提示"数字可能停在旧值，别当现状用"。

**第四，两站是同一份数据的两个副本，会漂移。** 两站采的是同一个 Cloudflare 区域、同一组主机名，数据内容本来就一样，却各存一份。边缘数据会事后修订，两站各抽各的版本，于是同一天在两块运营台上可能显示不同的数——这是真会发生的，不是理论风险。已加一个巡检脚本：同一天逐值比对，并按两站各自的排程区分"今天还没轮到"和"真漏采"，避免误报。

**第五，发布包里的脚本没有可执行位，这一类没人管。** 昨天装采集时第一次就死在 `check-unit-paths.sh: Permission denied`。根因不在服务器：打包走的是 git archive，git 根本不记录可执行位，所以仓库里 9 个 shell 脚本全是 644，发布出去还是 644，任何"直接执行脚本"的地方都会 Permission denied。已做两件事：把 9 个脚本在 git 里的模式改成可执行（实测发布包出来就是 755），以及在出包卫生门加两道断言——索引里的脚本必须带可执行位、最终压缩包里的脚本也必须带。以后有人新增脚本忘了改模式，出包就被拦下。

顺带扫了同类缺陷：全仓 1081 个文件里，"grep 模式中未转义的美元号"这种会写出永远绿的假断言的写法，精确扫描命中 0 处；粗扫出的 9 处全是 shell 变量展开，属误报。另外把"直接执行 .sh"的地方逐条核过，除了昨天修的那一处，其余都已经是 bash 调用——这一类在仓库里已经闭合。

## 硬证据：今早两拍自己跑起来了

测试站 8:22:29 由定时器自动触发，拉到 10-21 的数，追加 3 行，正常退出。生产站 8:26:48 同一次，同窗口同数，追加 3 行，正常退出。两站台账现在各 15 行，覆盖 10-17 到 10-21，每天 3 行；漂移巡检逐值比对结果一致（退出码 0）。

这里也有一个我自己的教训要记：早上 8:16 我看到日志里没有今天的记录，差点报"没跑"——其实那是今天的排程还没到（定时器显示下一次触发是 8:22:26）。把时间窗当故障这种误报，只发生在我自己的排查里，没有进交付结论。

## 一件我没做、也不该替他做的

测试站发版我没做。原因是出包被 clean-tree 门挡住了——develop 工作树里有另一窗口正在改的东西，他还中途提交了一笔（v13 多稿工作台）。就算能出包，发版会把他半途的工作一起送上共享测试站，那不是我该替他做的决定。

所以现在的状态是：**服务器侧是好的**（两枚定时器在跑、两份台账有数、今天早上各自跑成功），**代码与门都已提交**（develop f800028，连同昨天的 2e55efa），但面板上的"最后抓取／陈旧提示"和分站补救指令**还没上线**。他收工或你点头，随时可以出包发测试站。

生产发布面同理：两笔提交都还没进任何发布包，生产发布目录里那个脚本的可执行位目前还是现场补的位，下次发布会被换掉——根治要等这两笔进生产包。
