## 1. 最值得改的六件事
1. 演示用固定样例与真实无副作用计算，不把计时动画当执行。真实 Photoshop 结果作为另一种证据单独展示。
2. 演示隔离要查三层：代码是否发起危险请求、浏览器是否阻止、服务端是否收到或写入。Mock 只能帮助测试交互，不能证明产品自己隔离了网络。
3. 内容回滚不能仅指定目标旧版本，还应核对“现在这一版是不是我要撤的那一版”，防止误撤别人刚发布的内容。
4. 先准备一套可追溯真实样例，再围绕它写承诺和做演示。完整录屏可后置，但事实证据不能全部拖到第三批。
5. 匿名试用采用受限临时身份和原子额度，不采用“没登录就放行”。本轮仍不开放真实匿名执行。
6. SEO 优先抓取、内容价值与可见事实一致；不把 llms.txt 或结构化数据数量当增长目标。

## 3. 大家如何做，我们该学哪一层
### 3.1 WordPress Playground：零门槛的关键是独立运行环境
WordPress Playground 将 PHP/WordPress 放进浏览器 WebAssembly 环境，并用 Blueprint 描述安装与运行步骤。这是实际运行相应引擎，不是播放进度条。可借鉴的是“固定输入、可重复环境、明确能力”，不是把它的零安装能力外推到 Photoshop。[项目](https://github.com/WordPress/wordpress-playground)、[官方说明](https://developer.wordpress.org/playground/)。

反证更重要：该项目 2025-06-24 合并 #2296，默认启用网络；官方说明可以单独关闭。因此“在浏览器沙盒中运行”不等于“离线或绝无外部副作用”。[已合并变更](https://github.com/WordPress/wordpress-playground/pull/2296)、[网络行为说明](https://make.wordpress.org/playground/2025/06/27/wordpress-playground-now-connects-with-the-internet-by-default/)。

对图译工坊的裁决：网页可真实计算固定样例的匹配/歧义，前提是复用的函数不含授权或网络副作用；不能模拟 Photoshop 运行却叫真实执行。要承诺真实本机执行，必须走真实安装授权与引擎。无需为演示移植 Photoshop 或引入整套 WASM 平台。

### 3.2 Supabase：匿名仍有身份，不是绕过身份
Supabase Auth 的 anonymous.go 在事务里创建用户并签发令牌。官方还提醒匿名身份使用 authenticated 角色，要区分匿名标记，补防滥用与清理策略。借鉴身份生命周期，不迁移我们的认证栈。[源码](https://github.com/supabase/auth/blob/master/internal/api/anonymous.go)、[匿名认证说明](https://supabase.com/docs/guides/auth/auth-anonymous)。

本地真实任务要求授权解析、安装 ID 与 activationId：src/app/api/local-assistant/attempt/route.ts:30、34、145。匿名方案若只给前端一个 guest=true，就没有回答执行归属、过期、恢复、撤销和结算问题。

裁决：未来真实匿名试用应是独立受限身份，明确权限集合、到期与任务归属。额度控制需服务端原子预留，设备 ID、IP 或验证码各自只能提供部分防滥用能力，不能声称“每人永远只能一次”。清浏览器数据后是否还能恢复任务也必须明确。

Stripe 的幂等机制按请求键与参数重用结果，可借鉴重复提交约束；但它是 HTTP 操作语义，不能证明 Photoshop 外部副作用恰好一次，也不能把“超时未回”自动当作没执行。[官方幂等说明](https://docs.stripe.com/api/idempotent_requests)。

### 3.3 Sanity：补丁要知道自己基于哪一版
Sanity client 的 BasePatch.ifRevisionId 把预期修订号放入补丁，官方事务说明强调客户端“先读再写”的竞争需要乐观锁；事务本身不能表达操作者脑中的旧基线。[客户端源码](https://github.com/sanity-io/client/blob/main/src/data/patch.ts)、[事务与乐观锁](https://www.sanity.io/docs/content-lake/transactions)。

本地已做得正确的部分：建草稿事务内重新核 ACTIVE（site-settings.ts:621），发布核基准修订与摘要（:698），数据库迁移还有每环境一个 ACTIVE 的唯一约束（prisma/migrations/20260901153000_content_studio_v1/migration.sql，现有守卫 scripts/smoke-content-studio-v1.mjs:30）。不应推翻这些现成机制。

更深的边界在回滚：它接收目标版本、管理员、理由；没有调用方预期的当前发布 ID（site-settings.ts:713）。这不是认证绕过，而是部署自动化可能缺少“不要撤掉别人刚发布内容”的条件，详见第 5 节。

### 3.4 Playwright / MSW：测试拦截器会改变你正在观察的系统
Playwright 明确区分页请求与 Service Worker 请求的观测/拦截；源码的 worker 请求使用 BrowserContext 拦截器。不能只装 page.route 就宣称捕获全部浏览器网络。[网络文档](https://playwright.dev/docs/network)、[Service Worker 文档](https://playwright.dev/docs/service-workers)、[实际源码](https://github.com/microsoft/playwright/blob/main/packages/playwright-core/src/server/chromium/crServiceWorker.ts)。

MSW 的历史讨论 #943 提醒：即便模拟层抛异常，测试也可能吞掉异常继续通过。它只能作为失败形态的佐证，不作为当前 MSW 版本缺陷结论。[历史讨论](https://github.com/mswjs/msw/discussions/943)。

裁决：交互 mock 测试与真实网络边界验收分开；禁止用 mock 的成功响应证明真实处理链可用。错误日志不是失败断言，页面显示“成功”也不是副作用证据。

### 3.5 Stryker / SLSA：验“测试能抓错”与“产物来自哪里”是两件事
Stryker 区分变异被杀死、存活、未覆盖、编译/运行异常等结果。我们应对关键判断做小范围定向破坏，不追求一个全仓高分；语法被破坏导致无法启动，不能冒充业务断言抓住了错误。[变异结果定义](https://stryker-mutator.io/docs/mutation-testing-elements/mutant-states-and-metrics/)。

SLSA 的产物核验重在构建来源、签名与期望参数。可借鉴样例包/安装包的来源清单，但哈希和来源正确仍不等于 PSD 文字与视觉正确。[产物核验](https://slsa.dev/spec/v1.2/verifying-artifacts)。

裁决：证据至少分三种：产物身份、处理正确性、设计师视觉验收。不能因为 SHA 一致就给出“零漏改”。本项目不必为了这次官网修订先建设完整供应链平台。

### 3.6 Adobe：文字类型和实际渲染决定换行，不是字符串长度
Adobe 区分点文字与段落文字：点文字的行由人工换行控制，段落文字在边界框内自动流动；UXP 文档也区分这两种类型及转换方法。[文字类型](https://helpx.adobe.com/photoshop/desktop/text-typography/type-layers-creation/create-point-type-and-paragraph-type.html)、[TextItem API](https://developer.adobe.com/photoshop/uxp/2022/ps-reference/classes/textitem)。

不能把现代 UXP API 的可用性外推到本项目所有 Photoshop 版本或现有 JSX 执行器。更不能因为转换成文本框能折行，就假设转换不改变原稿布局、混合字体与渲染。

本地已有更精细的 wrap-planner：src/lib/workbench/wrap-planner.ts:1–4 明示纯规划器、暂不接线；:318 要求调用方提供度量表。当前绑定路径则在 binding-core.ts:1157、1254、1302 调 structuralTargetText，:1772 进入既有结构换行。两个层次可以同时存在：规划代码已实现，不代表实际任务消费了它。

裁决：撤回“需要从零新建自动换行”的潜在误读；未来工作是核清已有规划器、真实字体度量、冻结计划和执行写回之间的缺口。宣传只认已经接通并有运行证据的路径。

### 3.7 Google：把可见内容做好，别把文件堆砌当增长
Google 官方明确说 Google Search 不使用 llms.txt 改善可见性或排名；AI 搜索仍依赖正常抓取、索引和内容质量，结构化数据应与可见内容一致。这只适用于 Google，不能外推所有 AI 服务。[官方 AI 搜索指南](https://developers.google.com/search/docs/fundamentals/ai-optimization-guide)、[AI 功能与网站](https://developers.google.com/search/docs/appearance/ai-features)。

裁决：现有 llms 文本有错就修，但停止把新增它当增长里程碑；先检查索引资格、页面可读性、真实成果及内链。搜索结果没出现某页，不足以证明未收录；需要 Search Console 等站点证据，本轮未取得。

## 4. 实验一：同一缺陷，三种“看起来成功”的结果
证据与复跑脚本：交付档案/调研报告/证据_20261026_外部实践深探/network-counterexample.cjs；结果 network-counterexample.json。
命令：node 交付档案/调研报告/证据_20261026_外部实践深探/network-counterexample.cjs，真实退出码 0。只启临时本地 HTTP 服务，finally 关闭浏览器与端口。

四个场景：
- 正常基线：点击仅改变演示状态。应用尝试 0，浏览器网络请求 0，假服务端命中 0，界面完成。
- 有缺陷但被 mock：按钮尝试发 POST，测试给假成功。应用尝试 1，浏览器请求 1，服务端命中 0，界面完成。
- 同一缺陷撤掉 mock：应用尝试 1，浏览器请求 1，服务端命中 1，界面仍完成。
- 同一缺陷加产品侧 CSP 限制：应用尝试 1，浏览器策略违规 1，可见网络请求 0，服务端命中 0；因为应用吞掉异常，界面仍完成。

第 2、3 个场景证明：测试自己挡住请求，不能证明应用不会发请求。
第 4 个场景证明：零网络请求可能因为策略已经阻断；需要检查策略违规与应用错误，不能只盯 Network 数量。策略起效是好事，但页面还在假报成功仍是缺陷。
本实验没有 Service Worker，因此并未实测所有 SW 边界；SW 结论来自官方文档与源码，应在最终产品采用 SW 时另测。

### Finding N1 [CRITICAL / CONFIRMED] 上版 V8 需要升级为三层验收
问题：上版方案:127 只写“捕获浏览器网络，证明不触发”，没有要求区分 mock、违规尝试和真实服务端副作用。

影响：演示回归成真实请求时，mock 测试仍可通过；沿用全站策略也不能给演示提供独立的本机访问限制。

防回归：交互测试允许 mock；边界测试关闭 mock，用隔离假后端计数，同时统计禁止请求尝试、CSP 违规、真实命中及数据库/队列副作用。坏样例先证明测量能抓到，再运行正常样例；正常样例三个层面均符合约束。

MDN 列明 connect-src 管 fetch、XHR、WebSocket、EventSource、sendBeacon 等，不覆盖所有资源类型。还应按演示资产检查图片、脚本、表单与 frame 的相应约束，不能只拦 fetch。[CSP 范围](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/connect-src)。

## 5. 实验二：回滚目标正确，仍可能撤错一次发布

场景 A：操作者以为当前是 B，实际也是 B；请求回滚到 A → B 退役，A 生效。

## 6. 再钻一层：根因不是“测试写得少”
### IS / IS-NOT 对照
- IS：坏演示 UI 成功；IS-NOT：正常演示也成功。二者差异藏在副作用，不在 UI。
- IS：mock 状态服务端 0 命中；IS-NOT：同代码不 mock 时 1 命中。差异是测试拦截器，不能归因成产品隔离有效。
- IS：发布会核草稿基准；IS-NOT：回滚没有操作者预期的 ACTIVE 参数。事务内操作不等于意图不会过期。
- IS：有 wrap-planner 源码；IS-NOT：当前 src 调用检索只找到其定义，实际绑定走 structuralTargetText。模块存在不等于功能已接入。

为什么会重复出现“全绿但没完成”？
第一层：把可见完成状态当作实际结果。
第二层：测量与被测对象共享同一假设，例如测试给假成功，然后验证页面显示成功。
第三层：没有明确区分各证据能证明的范围：源代码存在、运行进入、外部副作用、保存后的产物、视觉正确性。
可操作的根因：验收合同缺少“谁产生结果、谁独立观察、故意破坏哪一步必须失败”。不是要求 AI 再认真一点，而是让成功必须经过不同观察点。
反向验证：单看截图无法区分四个网络场景；加入请求尝试和服务端计数后可区分；再加策略违规可解释第 4 场景。因此新观察点确实补上了原判据的信息缺口。
