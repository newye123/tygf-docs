# 调研报告 · 对抗式审查怎么钻得更深：全网公开做法与可抄的五件事

日期：2026-10-26
调研范围：GitHub 仓库与 skill 原文、LLM 红队框架、相关论文、中文实践文章
取证方式：读原文（curl/raw）、GitHub API 取星数快照、Web 检索
明确没做：Reddit / Twitter / 小红书（本机后端未配，见 §6 覆盖缺口）；论文只读到摘要与二手转述，未逐篇读全文

## 0. 一句话

公开实践里，"钻得深"几乎都不是靠"让模型更努力地想"，而是靠**把审查拆成几道互相独立的关卡，并且每道关卡的产出都能被机器复核**：审查者不写代码、验证者不是审查者、结论绑住被测物的指纹、每条意见必须过"先找反例"、历史漏网变成下次的攻击用例。我们自己的 skill 已经踩到了其中大部分思想，缺的是**机械化**——规则还写在脑子里、裁决还不是结构化数据、批准还没有绑方案指纹。

这对你意味着什么：同样的模型、同样的时间，只把流程改成"审查／验证分人 + 意见结构化 + 结论绑哈希"，就能把"看起来审过了"变成"审过哪一版、哪条被证伪、哪条还缺证据"可查。下面五件事都能在一到两天内落地，且都不需要换模型。

## 1. 我查到的六个做法（按"对深度的贡献"排序）

### 1.1 审查者必须换人，最好换厂

三个独立实现，说法不同、约束相同：

- **read-frog 的 adversarial-review** 写死了硬约束：「reviewers MUST run via the opposite model's CLI… Do NOT use subagents, the Agent tool, or any internal delegation mechanism as reviewers — those run on *your own* model, which defeats the purpose.」（`.agents/skills/adversarial-review/SKILL.md`）
- **claudex-loop**（3,231★）把"另一个厂"写进工作流：Claude 写代码则 Codex 评审，Codex 写则 Claude 评审；审查者用只读沙箱，关掉插件与 MCP；最后由"另一厂"在**全新会话**里做终检，且**协调者自己动手改的代码必须再检一次**。
- **lobehub deep-review** 的原则第 2 条：「an agent that just wrote the code is grading its own homework and will pass it」；验证模板里再钉一句：「Review and verify must never share an agent.」

我们的现状：母语是子代理分面取证 + 主审证伪，**已经是两个人**，但仍是同模型、同会话环境。我们自己的 skill 里已有方向性数据（Claude 审 Codex +18.1pp、Codex 审 Claude −8.6pp），却没把它落成"必须换厂"的硬闸。

### 1.2 把审查规则写成可执行清单，并明确写"什么不算问题"

lobehub deep-review 把审查拆成 14 个维度文件（`logic` / `business-logic` / `new-feature` / `reuse-architecture` / `performance` / `release-risk` / `security` / `compatibility` / `ux` / `observability` / `workflow` / `skill-freshness` / `code-style` / `ai-coding-bad-habits`），每个文件四段固定结构：

- **Quick checklist**：能逐条打勾的具体攻击面（例：文本解析器要枚举"空载荷 / 只有标记 / 分隔符出现在正文里 / 截断输入"；发现一处 `indexOf` 脆弱，就要把同函数里每个 `indexOf`/`lastIndexOf`/正则都过一遍）
- **How to check**：先写"对抗输入清单"，再逐条读码，不许想到哪查到哪
- **Violations**：什么算违规（必须给具体输入/状态序列）
- **Not violations**：什么不算（上游已保证的状态不要求防御式编程；声明为临时的代码按寿命判，不要求可配置）

还有一张**剪枝表**：哪些维度在什么 diff 上不适用、一句话理由。以及一条反直觉校准：**文档修改如果改的是给 agent 看的指令（AGENTS.md、prompt、skill），它就不是文档，按代码审**——"prose 里带着控制流和契约"。

我们现在的"切面"是按对象临时定的（见 skill 里的四行表），没有沉淀成可版本化的规则文件。深度差异主要来自这里：同一个审查者，给不给 checklist 结果完全不同。

### 1.3 意见必须过"独立验证"关，且裁决是机器可读的

deep-review 的验证模板规定每一条意见都走同一套十步，其中三条最狠：

1. **先找反例**：「Look for the counterexample first: an upstream guarantee, early return, framework behavior, or existing validation that prevents the scenario.」
2. **区分新引入与存量**：改动行 = introduced，旧代码 = exposed_legacy；存量问题要给出**具体的触发前后对比**，给不出就降级为"旁观者"，只有明显的 P0 生产故障才留。
3. **校准到代码库现状**：如果这个写法在库里到处都是、这次没让它更坏，就不是 finding（理由前缀 `over-scrutiny:`）。

裁决是固定 schema 的三态：`confirmed` / `false_positive` / `need_more_context`，confirmed 还必须给 `evidence`（file:line 原文）、`can_auto_fix`、`blocks_release`，并允许验证者用 `severity_override` / `nature_override` / `exposure_override` / `likelihood_override` 改判。之后还有一道**去重**：只有"一处具体修复能同时解决两条"才算同根，同主题同位置都不算。

我们的现状：主审的三分处置（采信 / 改判 / 未决）思路一致，但是自由文本，没有 schema，也没有"修复能否同时解决"这个同根判据。

### 1.4 结论要绑住被测物的指纹，改了就失效

claudex-loop 的批准机制：runner 校验"成功的 CLI 回合 + 结构化评审"，空输出或会话启动事件不算通过；**批准记录方案路径与 SHA256，方案一改批准即失效**；终检记录"构建前 commit + 被检改动的指纹（含已暂存与未跟踪文件）"。

我们的现状：审批绑 commit 已有，但**方案文本没有指纹**。这正是这一轮的问题：施工图在被审期间被另一只手改过（P0 已开工），批准针对的是哪一版文字，事后说不清。

### 1.5 反方角色固定成三镜头，过半数存活才采信

fable-harness（204★）的多方抗辩：给出重大结论前同时派三个独立子代理——**skeptic**（找逻辑漏洞）、**red-team**（找安全与失效风险）、**simplifier**（找过度工程），"三个镜头里要过半数存活，结论才算采信"。

read-frog 按 diff 规模配镜头数：<50 行 1 个（Skeptic），50–200 行或 3–5 文件 2 个（+Architect），200+ 行或 5+ 文件 3 个（+Minimalist），每个镜头独占一种视角、不许混着用。

我们的现状：分面表按对象定，路数不固定——这是优点（贴合对象），但缺"simplifier"这类**专门盯过度工程**的镜头，而 Anthropic 又明确警告过找茬式审查会诱发过度工程。

### 1.6 把"找茬"变成"证伪"：负控、变异测试、攻击库回归

这一层是公开实践里最接近"钻到底"的部分：

- **负控**（我们已有）：任何"修好了"都要故意弄红一次。
- **变异测试**（我们没有）：往代码里注入小缺陷（`<` 改 `<=`、去掉 `+1`），看测试能否杀死——杀不死的变异体就是测试的真实盲区。中文实践文章给的数字是"AI 生成单测变异分数 34–52%，人工 78–85%"，**来源是二手文章，标 C 级，只能当线索**；但"覆盖率只回答跑没跑过、变异分数才回答抓不抓得住"这个区分是结构性成立的。
- **攻击库 + 成功率指标**（我们没有）：promptfoo（26,422★）的红队把攻击策略分成静态 / 动态 / 多轮三类，用攻击成功率（ASR）衡量，并把历史失败沉淀成回归集；NVIDIA garak（9,699★）、Microsoft PyRIT（4,687★）同理。翻成我们的话：**每次漏网的缺陷，都应该变成一条可重放的负控**。我们的 `REVIEW-EVALS.md` 有台账，但没有重放入口。

## 2. 四条"别抄错"的反面证据

1. **没有外部信号的自我纠错基本无效。** Huang et al.《Large Language Models Cannot Self-Correct Reasoning Yet》(ICLR 2024)：内在自我纠错在推理任务上常无提升、甚至下降。近期一篇把反思重新定义为"受限再生成"的工作说得更直白：没有新信息输入时，迭代只是在重采样。**所以"再想想"不是深度，加一道独立验证才是。**
2. **强制"每人至少报一条"会逼出捏造。** 我 skill 里记的实测：为凑数给出的 hedge 会被判捏造（3/5 条）。claudex-loop 也写明：「Zero findings is valid; a large number of findings is not a quality score.」
3. **找茬式审查诱发过度工程。** Anthropic 的警告被多处引用：被要求找茬的审查者即使没问题也会报东西，追着每条改会催生多余抽象、防御性代码、为不可能发生的情况写测试。deep-review 用 "Not violations" 段和 `over-scrutiny:` 前缀来对抗这一点。
4. **裁判偏差是结构性的。** MT-Bench（Zheng et al., arXiv 2306.05685）列了位置/冗长/自我增强三类偏差，缓解手段是交换顺序、多裁判投票、剥离长度与风格信号。对审查的含义：**"先看到谁"会影响判决**，所以对比两个方案时要换顺序各判一次；报告长度与 findings 数量都不能当质量。

## 3. 五件可以直接抄进我们 skill 的事（按代价排序）

**A. 方案审查绑指纹（半天）**
审完方案后记录 `sha256(方案文件)`；任何后续编辑让批准失效，必须重审改动段。判据可复跑：改一个字 → 批准状态必须变成"失效"。
顺带把"被审版本"写进报告页首（本轮就吃了这个亏：P0 已开工，报告审的是哪一版文字说不清）。

**B. 审查者与验证者分人，裁决结构化（一到两天）**
- 验证子代理只吃"意见清单 + 范围"，不吃审查者的推理过程；它只能回三态 + 证据 + 缺失项。
- 意见 JSON 字段：`id / verdict / evidence / blocks_release / can_auto_fix / overrides`；`false_positive` 必须带理由前缀（`over-scrutiny:` / `out-of-scope legacy:` / `hypothetical input:`），前缀即校准口径。
- 去重判据改成"一处修复能否同时解决两条"，不是同主题。

**C. 维度规则库落成文件（两天）**
把现在的临时切面沉淀成 `references/dimensions/*.md`，每个四段（清单 / 怎么查 / 算什么 / 不算什么）+ `skip_when`。先落六个最贵的：支付与结算、权限与授权、数据删除与保留期、跨层合同（浏览器投影/助手/服务端/结算闸）、发布闸与回滚、UI 状态（空/加载/错/边界）。每个文件必须有一段 "Not violations"，否则会复发过度工程。

**D. 固定加一个 simplifier 镜头（半天）**
现有分面之外，每次审查必须有一路只回答一个问题："这里有什么可以删掉而不损失目标？"产出写成"可删清单 + 理由"，与 findings 分开列。它专治审查驱动的过度工程。

**E. 历史漏网 → 可重放攻击（一天）**
`REVIEW-EVALS.md` 每行补一条可跑命令（负控或复现脚本），加一个入口 `npm run review-evals` 全量重放；漏网缺陷只有在重放里变红才算销账。

## 4. 拿新尺子量我这一轮（自指）

| 项 | 本轮实际 | 按上面的尺子 |
|---|---|---|
| 独立性 | 子代理分面取证 + 主审证伪，同模型同会话 | 只做到"换上下文"，没做到"换厂"；应标 `independence: same-model` |
| 方案版本 | 报告写了基线 commit，但方案文件当时正在被另一只手改 | 缺方案指纹，应写"审的是哪一版文字" |
| 裁决形态 | 自由文本表 + 严重度 + A–D 证据等级 | 无 JSON、无 `false_positive` 理由前缀 |
| 证据强度 | F-01/F-02/F-03/F-06/F-07 都有探针复现 | A 级成立 |
| F-05（覆盖率比执行宽） | 代码对照证明两处口径不同（A 级），但**没跑**"含 NBSP 的行进 runMatch 会漏"的端到端探针 | 应降为 A−，并把端到端复现列入未决 |
| 过度工程 | 13 条里 3 条是存量（F-09/F-10/F-11），已标"来源"列 | 符合校准口径，但没有"Not violations"段说明排除了什么 |

这一节不是自我批评表演——它给出的是下一版 skill 的验收点：**没有这几项，审查报告就是"我说我审了"。**

## 5. 我们比公开实践做得好的地方（别改掉）

- **负控**（弄红一次才算数）：公开实现里只有零星的 "proof checks"，我们把它写成了四式。
- **分歧离散化**（AGREE / DISAGREE_EVIDENCE / DISAGREE_CONCERN，F1 0.457 → 0.533）：claudex-loop 与 deep-review 都只做"验证者改判"，没有强制批评者给离散结尾。
- **"覆盖缺口"节**与 **NOT RUN 就写 NOT RUN**：公开模板里有 `need_more_context`，但没有把"这次没查什么"当成正式交付项。
- **成本闸**：按风险配额开对抗环（约 4.5× token，仓库复杂或根因定位才值得），公开实现里 claudex-loop 有 round 上限，但没有风险分档。

## 6. 覆盖缺口（本次没查的）

- Reddit / Twitter / 小红书 / B 站评论区：本机 `agent-reach`、`mcporter`、`gh` 均不可用（都是命令不存在，不是权限问题），这轮走的是 WebSearch + curl 直连 GitHub API，所以**社区讨论的口径缺失**。
- 论文只读摘要与二手笔记，未读全文；涉及具体百分比的数字（变异分数 34–52%、顺序翻转率 0.469）**均为 C 级**，只能当线索，不能当判据。
- 星数是 2026-10-26 的 API 快照，会变。
- 没有安装或运行 promptfoo / garak / PyRIT，只读了描述与文档摘要。
- 没有实测"跨厂审查"在本项目的效果；上表 +18.1pp / −8.6pp 来自我们 skill 里已有的引用，本轮未复跑。
