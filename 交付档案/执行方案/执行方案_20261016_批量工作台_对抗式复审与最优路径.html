01对抗式复审：六路反方

成立反方 1：你的第 1 层是个空壳 UI，比不做更糟

四个区里三个是纯文本占位。用户打开批量工作台，能录入路径、能排序，然后没有任何下一步——看起来像个坏掉的功能。更要命的是占位文案写着「移植 coverage-matrix.tsx」「移植 multi-psd-flow.ts」，而这两样早就接在原工作台里了。

证据：batch-workbench-view.tsx（本轮已删除）；design-file-card.tsx:608-676；workbench-view.tsx:2137-2155
成立反方 2：你犯的正是本项目自己点名的病

AGENTS.md 原文：「反复把"已有能力"当"待新建"派活（实例：学习子系统九环皆有代码与库表，曾被当新东西提出）」。我上一版正是如此——多稿能力已经是完整的：

它们唯一的「毛病」是：被一个全局 flag 门控，且该 flag 一开就把原工作台整体换掉。

第四轮更正：上表最后一行我原先写「已实现」——那是错的。MultiPsdOrchestrator 没有任何 import，真正在跑的是 workbench-view.tsx 里 handleExperimentStart / handleExperimentPsdComplete + experimentTrigger 这对回调。该文件来自 cde98a7，已在第四轮删除。

成立反方 3：「原工作台零改动」是个错误的约束

我上一版写「关键纪律：原 workbench 视图及其组件树零改动」。但这条纪律和「真正并列」是矛盾的：只要 design-file-card.tsx:600 那段「开关开就 return 整套多选 UI」还在，顶替的机关就还在，并列只是靠「别打开那个开关」维持的纪律，不是结构事实。

修正后的约束：不是「零改动」，而是「单文件路径行为必须逐字节不变」——这可以用一个默认 false 的 prop 做到：改动是加法，行为是等价。

部分成立反方 4：你说补了运营台开关入口，但你没验证它真能开

我上一轮补了原子覆盖函数 + API 分支 + 面板开关，却只跑了 tsc / lint / 白名单 smoke，没有一条测试覆盖这个新函数。若 SQL 写错，Owner 在运营台点「开启」不会有任何反应，而且看不出来——正是这个项目最怕的静默失效。

本轮已补：scripts/smoke-batch-workbench-flag.mjs（隔离库），断言默认值、原子写 true/false、以及「写本键不得覆盖其他键」（原子性的核心主张）。

成立（收窄）反方 5：你把「静态/运行时双语义」说大了

我上一版说它存在双语义。实测收窄到单文件：

workbench-view.tsx:175useFeatureFlags() —— 运行时
execute-step.tsx:402useFeatureFlags() —— 运行时
design-file-card.tsx:66featureFlags 模块常量 —— 编译期静态（唯一一处）

后果很实：静态=false 而运行时=true 时，文件卡还是单选、矩阵与编排却已按多稿走——错位。

成立（本轮不做）反方 6：粘贴入口没有串行扫描，体验是「粘 5 个、点 5 次」

串行扫描需要（a）一个「排队中」状态，但 PreparationClientState 没有、且不能加（会破坏 StateBadge 的 Record 穷尽性检查）；（b）队列驱动，它需要 multiScanningIdx 的 stale-closure 修复。

那个修复已经写好但未提交地躺在 worktrees/develop 的工作区里（state→ref，注释写明「第一次轮询就自我判废，状态永久卡 hashing」）。在这里重复一份会造成两份真值源 + 必然的合并冲突。⇒ 本轮不碰，列为 D10。

02最优方案：搬运，而不是重建

核心判断：批量能力已经端到端可用。所以最优不是新建四个区，而是换一个入口去用它。
信息架构（改后）

#workbench → <WorkbenchView /> —— 单文件工作台，多稿分支一律不渲染（行为与改前一致）

#batch → <WorkbenchView batchMode /> —— 批量工作台，同一套步骤，文件区换成多稿列表 + 覆盖率矩阵 + 逐稿编排

两者共用同一套步骤组件，靠 batchMode 区分。

四项收益
  1. 批量工作台立刻可用——语言选择、覆盖率矩阵、逐稿编排、批次链、计费、回执全都在，零重建。
  2. 顶替从结构上不可能——单文件模式下多稿分支根本不渲染，与任何全局开关解耦。
  3. ISSUES #151 收口——design-file-card 不再读编译期静态值，改由 prop 决定。
  4. 零重复——不存在「两套渲染分支」的维护成本。
为什么保留 multiPsdExperimentEnabled 键而不删

删键 = 改配置 schema = Owner 的决定，不是我的。保留键 + 移除全部读取，效果等价（无人读 ⇒ 存什么覆盖都没用），且零 schema 风险。

为什么「一次录入多个」是「粘贴」而不是「拖拽」：浏览器出于安全不向网页暴露被拖入文件的绝对路径（File.path 是 Electron 专有，Chrome 只给文件名），而助手链路需要绝对路径 masterPath。所以纯 Web 页拿不到可用的拖拽输入；粘贴多行路径是可靠入口（与单文件区既有的「粘贴即扫描」同源）。真正的一次多选要等助手端 OpenFileDialog 加 Multiselect（第 2 层）。

致命7.1 批量工作台其实根本跑不起来（推翻我前三轮的结论）

症状：在批量工作台点某个设计稿的「扫描」，状态会永久停在「读取文件」，永远不会变成「已扫描」。

根因（design-file-card.tsx 的 handleMultiScanEntry）：轮询函数 poll 由 window.setTimeout(poll, …) 启动，它闭包捕获的是启动那一刻的 multiScanningIdx——那一刻该 state 还是 null（setMultiScanningIdx(index) 尚未重渲染）。于是第一行守卫：

if (multiScanningIdx !== index) return   // null !== index ⇒ 直接返回

第一次轮询就自我判废，且不再排下一次定时器 ⇒ 状态永久冻结。

这条我早就知道：第三轮我自己在 D10 里写下过——「那个修复已经写好但未提交地躺在 worktrees/develop 的工作区里（multiScanningIdx state→ref，注释写明「第一次轮询就自我判废，状态永久卡 hashing」）」。我把它当成「后续层的一个 feature 依赖」，没有意识到它同时是「批量工作台能不能用」的开关。于是我在第三、四轮反复宣称「批量工作台立刻就是可用的」——这三轮的说法都是错的。所有单测都是绿的，因为没有任何一条测试碰得到 React 组件内部的轮询闭包。

修法：轮询守卫改走 ref（multiScanningIdxRef.current），与 worktrees/develop 那份未提交的修复逐字一致（diff 逐行比对 0 差异 ⇒ develop 将来提交时不会产生分歧）。
