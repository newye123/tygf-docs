### 2.1 findings（全部有实跑证据）

**F-01（Important，已修）英文站根本没有用思源黑体。**
证据：`src/components/site/home-view-en.tsx:615` 在根节点上写死了内联 `fontFamily: '"Segoe UI", "Helvetica Neue", Helvetica, Arial, …'`，把 `home-v17.css:41` 的 `font-family:"Tuyigf Source Han Sans", …` 整个盖掉。浏览器实测 `performance.getEntriesByType('resource')` 里**字体请求数 = 0** ⇒ 英文站渲染的是 Windows 系统字体。原注释还写着一句理由（"13.5 MB 中文可变字体，英文页别用"）—— 这个理由本身站不住（见 F-02），但**当时的执行确实做到了"英文页不下载思源黑体"**，只是方式是"换成系统字体"而不是"换成轻量思源黑体"。

**F-02（Important，已修）英文页改用思源黑体，不能直接引全量文件。**
证据：仓库那份 `public/fonts/SourceHanSansSC-VF.woff2` 实测 **14,129,688 字节（13.47 MiB）**。英文站引它 = 每个首次访问的英文访客都下 13.5 MB。对一个营销页是 LCP/转化事故级代价，而本项目的 GEO/SEO 日基线盯的就是这一项。
实测过四条取小文件的路，三条走不通：

- `subset-font` + `wawoff2` 解不开这份 14 MB 文件（`ConvertWOFF2ToTTF failed`）；同一调用对 24 KB 的 woff2 正常 ⇒ 是体积/表结构限制，不是文件坏了。
- 本机 `python` 是 WindowsApps 存根，**没有 pip / ensurepip** ⇒ fontTools 路线不可用。
- Adobe 只在 847 MB 的 release zip 里发 VF；`raw.githubusercontent` 下那份 29.3 MB OTF 实测 ~8 KB/s，300 秒只拿到 2.4 MB ⇒ 不可作为可复现构建步骤。
- npm 上的 `cn-fontsource-source-han-sans-sc-vf` 确实是 Adobe 版（family 就是 `Source Han Sans SC VF`），但它只发 CJK 分片，**没有拉丁分片**。

⇒ 唯一实测可复现的小体积路线是 Google Fonts CSS2 的 `text=` 按字集子集。实测产出：**33,976 字节、231 个码位、wght 100–900 可变轴**，自托管入 git，运行期零外部依赖。

**F-03（Important，已修）图一"文案被挡住"不是图片盖字，是标题不许换行。**
证据链：
- `home-v17.css:120` `.hero-title-line { display:block; white-space:nowrap }` —— 整行不许折。
- `home-v17.css:119` `h1 { font-size:clamp(50px,6vw,78px); letter-spacing:-.055em }` —— 这套值是照中文标题定的：中文第一行是「让设计师改语言」7 个字，英文第一行是 "Make changing languages" 23 个字母。
- 实测（1440 桌面，`.wrap`=1240，左栏 608px，右侧产品卡左沿 678px）：标题行**真实绘制宽度 849px**，溢出左栏 241px，与产品卡**重叠 171px**。最窄双栏（1081px）重叠 **278px**。
- 谁盖谁：`.app-card` 背景是不透明白 `rgb(255,255,255)`，DOM 顺序在标题之后，两者 `z-index` 都是 `auto` ⇒ 后绘制的产品卡直接盖住标题。

**为什么当初没被发现**（这条值得记）：`white-space:nowrap` 让 `<span>` 的**盒子**宽度还是栏宽 608px，只有**画出来的字**跑到 849px。任何按"元素盒子"量的检查都会报"没溢出"——包括我自己第一次量的时候。必须用 `Range.selectNodeContents()` 量真实绘制宽度。

**F-04（Important，已修）同病根的另外三处英文版式毛病。**
- 390px 窄屏导航溢出：品牌 152 + 间距 26 + 导航动作 199 = 377 > 可用 358 ⇒ 实测 `scrollWidth 394 > clientWidth 390`。
- 示意卡头 `translations.xlsx / 6 languages` 在全大写 + `.08em` 字距下折成两行，卡片高度错位。
- 装饰大字（"Do less" / "Find less" / "Be sure"）压在英文说明文字上（英文说明 3~4 行，中文只有 1~2 行），两层叠字，两边都读不清。

**F-05（Important，已修）英文版式参数必须独立成套，不能只修标题一处。**
证据：英文文案句长是中文的 2~4 倍。除了标题，`h1` 字号、`letter-spacing`（拉丁用 `-.055em` 会挤成一团，实测改 `-.03em`）、分区标题（中文 mock 的 68px 在英文上会变成三行巨型标题）、按钮 `nowrap`（英文 CTA "Pilot it on a project that is changing languages →" 在 391~560px 会横向溢出）全部要单独一套。
处置：全部规则挂在 `.home-v17--en` 作用域下，**中文站一行不改**（中文首页 HTML 保持逐字节一致的合同不受影响）。

**F-06（Important，已修）英文页不能拉中文站那份全量 VF，但也不能因此退化到系统字体。**
处置：英文站单独一个字体族 `Tuyigf Source Han Sans EN`（按字集子集），`html[lang="en"]` 整棵子树生效；中文站仍然用原来的 `Tuyigf Source Han Sans` 全量 VF，**一个字节都没动**。守卫 `scripts/smoke-en-layout.mjs` 会同时断言这两件事：英文页字体 ≤256 KB 且**不得**出现全量 VF；中文页**必须**出现全量 VF。

**F-07（记录在案）仓库那份 VF 的字重轴和 CSS 声明对不上。**
证据：`home-v17.css:7-12` 的 `@font-face` 写 `font-weight:100 900`，而实测该文件的 wght 轴是 **250–900**（默认实例 ExtraLight 250）。100~249 这段字重实际上被钳到 250。中文站当前没用到那个区间，所以看不出问题。新做的英文子集是 100–900（真·100 起步）。**未改**——改中文站字重声明属于另一件事，且可能影响已在用的编辑层探针。

**F-08（记录在案）英文站没有登录入口，也没有工作台路由。**
证据：
- `home-view-en.tsx` 的英文导航只有 `Download` / `中文版` / `Request a pilot`，**没有账号菜单**（中文站首页有 `HomeAccountMenu`）。
- `src/app/en/` 下只有 `page.tsx`、`download/`、`terms/`、`privacy/`、`privacy/subprocessors/`、`not-found.tsx` —— **没有 `auth/`**。
- 工作台挂在中文站：`app-shell.tsx:48-49` 按 `view === 'workbench' | 'batch'` 渲染，`view-context.tsx:19-24` 从 `location.hash` 读；`/en` 的布局（`src/app/en/layout.tsx`）是**裸壳**，没有 `AppShell` / `ViewProvider` ⇒ 英文站根本没有能承载工作台的路由。
- 好消息：会话 cookie 的 `path` 是 `'/'`（`src/lib/auth/session.ts:143-149`）⇒ 英文登录不需要动任何鉴权代码，登录后照样能进工作台。

**F-09（记录在案）做英文工作台的文案体量与门禁爆炸半径（实测）。**
- 去注释后仍是中文的**字符串字面量共 1,463 处**：`src/components/workbench/*` 683 处、`src/lib/workbench/*` 约 680 处、`src/config/siteContent.ts` 的 `workbench` 节（约 230 键）与 `auth` 节（6 键）、`src/app/(zh)/auth/*` 若干。
- 至少 **8 个门禁脚本在断言"工作台组件源码里必须出现某句中文"**，文案一旦搬进字典就会集体变红：
  `smoke-workbench-ui-contract.mjs:17-19,70-74`、`smoke-batch-workbench-guards.mjs:101-121,171`、`smoke-home-session-ui.mjs:85-87`、`smoke-content-studio-v1.mjs:236`、`smoke-preparation-bulk-import.mjs:115,125`、`smoke-assistant-auth-barrier.mjs:125` 等。

**F-10（记录在案）英文工作台真正的大头不在网页，在本地助手。**
证据：工作台里大量用户可见文案来自本地助手（`download/local-assistant/server.js` 的错误分支、`v15-runner.js`）与助手产出的 HTML 报告。网页翻成英文后，助手吐出来的中文仍会出现在英文界面里 ⇒ **英文工作台要"纯英文"，必须连助手制品一起动**，而助手有自己的 runtime 身份与发版纪律（改动要 bump 版本、同步安装包与发布声明，见 `AGENTS.md`）。

## 四、Wave 1～4：英文登录页与英文工作台（待批）

### 4.1 为什么必须分波，不能一次做完

工作台是**中英共用同一套组件**的（`workbench-view.tsx` 200 KB、`execute-step.tsx` 166 KB）。1,463 处文案 + 8 个门禁脚本改写，在中文站同一棵树上一次做完：

- 出错就是中文站事故（中文站是当前唯一在用的产品面）；
- 半成品英文工作台（界面英文、助手报错中文）比没有更伤；
- 门禁脚本自身改写会削弱它们（它们现在钉的是"这句中文必须在"，改写后要改成"这句英文必须在且与中文一一对应"）。

⇒ 分波原则：**每一波自成闭环、能独立验收；未完成的波不暴露入口。**

### 4.2 波次与判据

### 4.3 W2 的接缝怎么设计（关键决策，建议照此）

- **键用中文原文**，不用另起名字：`t('智能检测')` 而不是 `t('workbench.review.detect')`。好处：机械改写脚本能自动生成键；中文原文就是它的 ID，改文案即改 ID，不会"键名和文案对不上"。
- **英文字典按模块就近放**（`src/components/workbench/<模块>.en.ts`），不堆到一个大文件——1,463 条堆一个文件没法维护。
- **缺翻译必须失败**，不能静默回退中文：守卫扫一遍"所有 `t('…')` 调用都有英文条目"，缺一条即红。
- **中文站零改动**：locale 缺省就是 zh，现有调用点一个不用改。

### 4.4 门禁要跟着改（不能不改）

现有门禁里"源码必须出现某句中文"的断言要改成"**英文字典里必须有对应条目**"——断言对象从"组件源码"换成"字典"，钉的东西不变（那句术语必须存在、必须与中文一一对应），但不再依赖中文留在组件里。
清单（实测点名）：`smoke-workbench-ui-contract.mjs`、`smoke-batch-workbench-guards.mjs`、`smoke-home-session-ui.mjs`、`smoke-content-studio-v1.mjs`、`smoke-preparation-bulk-import.mjs`、`smoke-assistant-auth-barrier.mjs`、`smoke-local-assistant-errors.mjs`、`smoke-batch-workbench-guards.mjs`。

### 4.5 不在本次范围（但会被英文用户碰到）

- **本地助手的运行时文案**（`download/local-assistant/server.js` 等）与它产出的 **HTML 报告**：网页翻英文后它们仍是中文（见 F-10）。助手制品改动要 bump runtime 身份、同步安装包与发布声明。
- **验证/重置密码邮件**：目前是中文模板，英文用户收到的仍是中文邮件。
- **运营台（`/admin`）**：不对外，无英文需求。
