## 一、我上一轮错在哪（先自我证伪）

上一轮报告里我写了两句，都被本次实测推翻：

| 上轮结论 | 本次实测 | 错因 |
|---|---|---|
| 「`newye123/tygf-workspace-backup` 不存在，记账仓零异地备份」 | 备份远端从来不是 workspace-backup，而是 `newye123/tygf-docs`，它**存在且可写** | 只看了 `git remote -v` 的当前值，没追问"为什么这个 URL 会出现在这里"，也没试其它密钥 |
| 「建议 Owner 二选一：重建 workspace-backup 私有仓 / 并入 tygf.git 孤儿分支」 | 两个选项都不必要；重建要 Owner 去后台操作，并入会把记账混进代码仓 | 把"当前配置指向不存在的仓库"误判为"没有备份仓"，跳过了"是否存在另一个正确配置"这一步 |

**教训（已写进本次的防复发闸）**：判断"备份是否还在"时，只认**远端实读**，不认本地配置，也不认本地 remote-tracking ref——这次骗过所有人的正是后者。

## 二、断链真相（证据链，逐条可复现）

### 2.1 时间线

| 时刻 | 事件 | 证据 |
|---|---|---|
| 2026-10-31 17:11:48 | 最后一次成功同步（提交 `a741d31`） | `git log -1 --format=%ci a741d31` |
| 之后某时刻 | `tygf-docs` 这个 remote 从 `.git/config` 消失，只剩指向不存在仓库的 `origin` | `.git/config` 全文仅剩 `[remote "origin"]` |
| 2026-11-01 09:46 | 本地又提交 `05a1b2d`（未同步） | `git rev-list --count a741d31..master` = **1** |
| 2026-11-02 08:2x | 盘点时发现 `git ls-remote origin` 报 Repository not found | 本轮首条命令 |

### 2.2 为什么不是"仓库被改名"

GitHub 官方文档明确：改名后旧的 clone/fetch/push URL **会自动重定向到新名**。所以如果 `tygf-workspace-backup` 是被改名，旧 URL 应当仍然可用；实际报 not found，说明它要么被删除、要么从来只是笔误占位。

### 2.3 正确仓库是怎么找到的

本机 `~/.ssh/` 下有三把专用部署密钥。逐把做身份探测（`ssh -T`），返回的正是该密钥所属仓库名：

```
id_ed25519_tygf_github  → Hi newye123/tygf!            （代码仓）
id_ed25519_tygf_docs    → Hi newye123/tygf-docs!       ← 记账仓的正确远端
id_ed25519_tygf_samples → Hi newye123/tygf-samples!
```

再用 docs 密钥实读该仓：

```
git ls-remote git@github.com:newye123/tygf-docs.git
  refs/heads/main    5c1daa50…
  refs/heads/master  a741d311999c383ef00b8cf6d11b70a465a8bfb1
```

`master` 与本地残留的 `refs/remotes/tygf-docs/master` **逐位一致**——两条独立线索互相印证，确认这就是原备份远端。写权限 dry-run 显示 `a741d31..05a1b2d master -> master`，即只需补 1 个提交。

**根因归纳**：`.git/config` 里 `tygf-docs` remote 被删、`~/.ssh/config` 里没有 `github-tygf-docs` 这个 Host，而 `origin` 指向一个不存在的仓库。三者叠加的结果是：任何人执行 `git push` 都会失败，而且失败信息看起来像"仓库没了"，没人再去追。

## 四、安全性核查：推之前先确认没有密钥

把记账仓推到 GitHub 之前，必须回答一个问题：历史里有没有不该外传的东西。三轮扫描（覆盖全部 142 个提交的所有 blob）：

| 扫描项 | 结果 |
|---|---|
| 历史中出现过 `.env`／`credential`／`secret`／`id_rsa` 等文件名 | 只命中两个**密钥扫描脚本自身**（`scripts/scan-secrets.mjs`） |
| 历史 blob 中含飞书 webhook URL 形态（`open-apis/bot/v2/hook/<uuid>`） | **0 命中** |
| 历史 blob 中含私钥头（`BEGIN … PRIVATE KEY`） | 唯一命中是某份执行方案里"应 grep BEGIN PRIVATE KEY"这句**检查清单文字** |
| 当前跟踪文件中含 `SECRET/TOKEN/PASSWORD/WEBHOOK` + 32 位以上密文形态 | **0 命中** |

结论：**可以安全推送**。这条必须做——备份一旦推错，等于主动泄露，比不备份更糟。

## 五、业界怎么做（调研结果与取舍）

| 来源 | 做法/结论 | 对本项目的含义 |
|---|---|---|
| GitHub 官方《Renaming a repository》 | 改名后旧 URL 的 clone/fetch/push 全部重定向到新名；**若在旧名下新建仓库，重定向立即失效** | 本次故障不是改名造成的；但也说明"URL 指向哪"不能靠猜，必须实测 |
| GitHub 官方《Repository limits》 | 单文件硬限 100 MB，**推荐单文件不超过 1 MB**；push 上限 2 GB | 当前 `AI_MEMORY/TASK_LOG.md` 已 **2.26 MB**，超过推荐线 2 倍，且每次追加都存一整份新副本 |
| git 官方 `git-bundle(1)` | bundle 明确支持"全量与增量备份"，用于离线传输 | 我们用它做第二副本是正路，且可做增量 |
| GitLab 官方《Back up GitLab》 | GitLab 备份时**为每个仓库生成 git bundle** 再打包 | 大厂同款做法，不是土办法 |
| monorepo vs polyrepo 通用权衡（Microsoft Learn 等） | 同仓便于一次拿全、分仓隔离权限与体积 | 本项目代码与记账**已分仓**，这个结构是对的，不该为了备份去合并 |

**取舍结论**：保留"代码仓 / 记账仓"两仓结构不动（合并会把 Owner 决策、内部事故记录暴露给所有代码仓协作者，且 1.2 MB 记账内容配 500 MB+ 代码仓历史不划算），把记账仓的远端修好、把备份做成可验证的日常动作。

## 六、防复发闸（已落地，含正负控）

`scripts/control-plane.sh` 在 ledger 判定之后、飞书回读闸之前，新增一段：

- 判据**只认远端实读**：`git ls-remote origin refs/heads/master`，25 秒超时保护；
- 三种结论：一致 → ✅；落后 N 笔 → ⛔ 并给出应执行的命令；远端不可达/不存在 → ⛔ 且文案与"落后"区分（避免把"没验证"说成"已备份"）；
- 工作树有未提交项时给一行提示，**不计告警**（日常本来就脏，计告警会变噪声）；
- 退出码并入总退出码（`backup_exit`）。

真实读数：

```
正向：记账仓备份：✅ 本地 master=05a1b2d 与远端一致
      [control-plane] ledger_exit=1 readback_exit=0 backup_exit=0

负控①（模拟远端落后 1 笔）：
      ⛔ 记账仓备份：远端落后 1 笔（本地 05a1b2d / 远端 a741d31）⇒ 跑 git push origin master
      backup_exit=1

负控②（模拟远端不可达）：
      ⛔ 记账仓备份闸：远端不可达或仓库不存在（无法验证是否已备份）
      backup_exit=1
```

两条负控都真跑过、都会红——这是它区别于"孤儿红门"（ISSUES #295 那种红了没人看的门）的关键。

## 七、仍未解决的三件事（按优先级，需 Owner 拍）

现状：备份只覆盖 **1210 个已跟踪文件**（1.2 MB），但工作树里还有 **1221 个未跟踪文件**，其中约 300 个是 `交付档案/` 下的审查报告、执行方案、模拟件（例如 OpenMontage 系列、10-24～10-26 的多份审查报告）。

风险：这些正是最有价值的交付件，一旦硬盘故障，git 恢复不回来。

三个选项（我建议 A）：
- **A. 入库**：把有长期价值的交付档案 `git add` 并提交，一次性清空缺口。代价：提交量较大，需要先剔除临时截图。
- **B. 归档**：移到 `_parked/`（已在忽略规则内），承认它们不进版本库。
- **C. 明确排除**：在 `.gitignore` 写明规则，接受丢失风险。

### P2　`TASK_LOG.md` 已 2.26 MB，超过 GitHub 推荐单文件上限 2 倍

每次追加都重写全文，142 个提交里存了 142 份 2 MB 快照（压缩后仍占大头）。

建议：按自然月切分（`AI_MEMORY/TASK_LOG_2026-10.md`、`-11.md`），当前月保持在 200 KB 以内；主文件保留最近一个月的索引。
风险：`grep`／脚本里有对 `TASK_LOG.md` 的硬引用（`source` 指针大量指向 `AI_MEMORY/TASK_LOG.md:1`），切分需要同批改这些指针，**属于结构变更，需要 Owner 一句话**。

### P3　bundle 第二副本没有自动刷新

本次是手工跑的一次。建议做成每月一次（或每次大交付后），增量 bundle 追加到服务器同一目录，保留最近 3 份。
