## 0. 一句话路径

P0′ 基础设施（本方案，约 1.5 天净工时）→ 字体功能接入（字体方案 P1，白名单先行）→ 逐步扩名单 → 条件触发再议 Unleash。

核心设计三条：开关默认 false、白名单按人（betaUserId）、判定全部在服务端。客户端只拿「对我开没开」一个布尔，永远不拿名单本身。

## 1. 与既有 canary 机制的关系（先读懂再动手）

本仓库已有一套安装级 canary：环境变量 TYGF_BATCH_EXECUTION_MODE=canary 加 TYGF_BATCH_CANARY_INSTALL_IDS 白名单（batch-execution-mode.ts:20,70-78,163-171），服务端判定、fail-closed、显式 reasonCode——语义是「哪些电脑能用批量执行」，配置在环境变量里，改名单要动部署。

本方案补的是另一层：用户级、库内、可在运营台实时改的「哪些账号能看到和使用灰度功能」。两层不冲突——将来字体功能真正进入执行时，仍要过既有批量门控。

为什么不用环境变量做这一层：改 env 要动部署，做不到「运营台一点、最坏 30 秒全收敛」；而且白名单是运营数据，不是部署配置。

## 2. P0′ 六步

**第一步：旗标形状扩展（零迁移）**

src/config/featureFlags.ts 加 typographyCustomizationEnabled: false（布尔），并加入 FeatureFlags 的运行时覆盖名单（同 multiPsdExperimentEnabled 先例，featureFlags.ts:59-77）。红线：默认必须 false，生产站不部署运营台覆盖时行为逐字节不变。

白名单不放进 featureFlags 形状——sanitizeAgainst 对空数组默认值直接判 undefined（site-settings.ts:227-236），放进去永远存不下来；白名单走独立 SiteSetting 键。

**第二步：白名单存储（独立键 + 原子更新）**

src/lib/server/feature-flags-store.ts 加两个函数：getTypographyBetaUserIds() 与 saveTypographyBetaUserIdsOverride(ids)，独立键 typographyBetaUsersV1，子键原子 upsert（照 saveSiteCopyInlineEditOverride 模式，feature-flags-store.ts:61-85，避免旧标签页互相覆盖）。

服务端校验：数组、最多 100 人、每项非空且不超过 64 字符、去重；写入前校验每个 ID 在 BetaUser 中存在，未知 ID 返回 400。

**第三步：服务端判定（唯一权威）**

新 src/lib/server/feature-flag-gating.ts：isTypographyCustomizationEnabledFor(betaUserId) —— 全局开关 ON 且名单非空且用户在名单，三者同时成立才为 true。任何异常、未登录、空名单一律 false（fail-closed）。

空名单语义=谁都不开（与批量 canary 的「空=全放」相反，故意从严）：这是「特定人群」实验，不是个人使用场景。

**第四步：按人读取端点（客户端唯一真相源）**

新 src/app/api/workbench/feature-access/route.ts：GET，用 getCurrentUser(cookie) 解析身份（照 auth/me 路由模式：账号 active、未注销、未过期），返回 { ok: true, features: { typographyCustomization: 布尔 } }。未登录返回 200 加 false（不泄漏任何信息）。

**第五步：客户端收敛（杀开关「最坏 30s」）**

改 src/lib/workbench/use-feature-flags.ts：模块级缓存加 30 秒 TTL、30 秒定时刷新、visibilitychange 回前台刷新。现状 :8-12 是永不失效——这是「关不掉」的病根，属必修。

新 src/lib/workbench/use-feature-access.ts：同机制读 feature-access 端点（TTL 30 秒 + 定时 + 回前台）。

验收话术统一「最坏 30 秒」，不写「秒级」。in-flight 的 PS 执行不受旗标影响（旗标只拦新进入）——这是能力边界，写进说明文案。

**第六步：运营台编辑 + 占位探针**

src/app/api/admin/feature-flags/route.ts：POST 加 typographyBetaUserIds 分支（校验 + writeAuditLog(session, 'feature-flags.save') 调用记录，先例 route.ts:45,57,67）；GET 返回值附带 typographyBetaUsers: [{ id, name, status }]（解析后给运营台显示姓名）。

src/components/admin/settings-panel.tsx：开关区加「字体定制灰度名单」块——当前名单（姓名 + ID）、每行一个 ID 的文本框、保存按钮。最小可用，不建独立页面。

src/components/workbench/photoshop-step.tsx：引入 useFeatureAccess()，名单命中时渲染占位块「排版定制（内测预览）——功能建设中」。占位块只为 P0′ 独立可验收；字体方案 P1 落地时原位替换为真面板。文案不含内部术语（#30 教训：develop AI_MEMORY/ISSUES.md:1172）。

## 5. 红线合规检查

不静默降级：开关或名单关闭 = 功能隐藏走旧流程，不是降级运行。支付 flag 不碰。助手不动（无版本纪律触发）。零 schema 迁移（避开 #129 迁移门）。白名单每次变更落 AdminAuditLog（writeAuditLog 现成）。白名单只存 betaUserId 不存邮箱；端点不向客户端泄漏名单。产物只在测试站使用；生产部署需 Owner 单点授权，本方案不申请。用户可见文案过 #30 教训检查。

## 6. 风险与止损

R1 占位块首渲染闪烁（hook 默认 false，先隐后现）：可接受，fail-closed 方向正确。
R2 名单 ID 填错：服务端存在性校验返回 400，运营台可见错误。
R3 30 秒轮询的负载：内部内测规模下可忽略（每标签页每 30 秒一次轻请求）。
R4 「最坏 30 秒」在页面长时间停留时靠定时刷新兜底；若浏览器冻结标签页，回前台刷新兜底。
R5 与设置面板旧标签页冲突：名单走独立键原子更新，不受整包 flags 保存影响。
R6 将来有人把白名单塞进 featureFlags 形状：smoke 锁定独立键路径，审查可见。
