## 0. 第一性原理：「换行」其实是五个独立环节

| 环节 | 定义 | 我们当前的真实状态 | 证据 |
|---|---|---|---|
| ① 断点集 | 哪些位置**允许**断开 | 只有 `\s` 与码点近似字素；无 UAX#14 机会点、无禁则、无连字符词典 | `binding-core.ts:1395-1420` |
| ② 预算 | 每行**能放多宽** | em 字符数近似，无 px、无 fontSize 入参、无"每行上限"入参；算出的 `maxWidthRatio` 被丢弃 | `binding-core.ts:1360-1392`、`:1569-1570` |
| ③ 求解 | 选哪 N−1 个断点 | 贪心均衡拆分行数；只在「原稿多行 + 译文单行」时启动 | `binding-core.ts:1480-1550` |
| ④ 落笔 | 让 Photoshop **真的排成 N 行** | 直赋含 `\n` 的字符串给 `textItem.contents`，**无 `\n→\r` 转换**，POINTTEXT 后果无实测 | `Thin_Executor.jsx:109` |
| ⑤ 取证 | 证明像素上换了 | 只证明**字符**里有换行符；回读把 `\r\n?→\n` 归一 → 行分隔符形态差异**永远看不见**；本轮 V6 截图 NOT RUN | `Thin_Executor.jsx:34-36`、`v15-runner.js:84`、`report-renderer.js:533-539` |

**结论性判断（概率排序，待 W0 定案）**：Owner 看到的"换不了行"最可能是 ④（落笔形态从未被证实生效）与 ①+③ 的**覆盖面边界**（单行原稿按已批准范围**根本不换行**），而不是 ③ 的算法质量。
算法质量只决定"换得好不好"，不决定"能不能换"。**因此本方案把最贵的活（引库、自研求解器）排在定案之后。**

## 2. 前置工程：wrapProfile 版本隔离（W1，任何写入语义改动之前）

对抗审查（合同/账务轴）的硬结论：断行后的写入文本进 `assignmentDigest`（`evidence-foundation.ts:205`），**不进** `bindingPlanDigest`（`binding-core.ts:215` 注释明示排除、`:272`）。所以求解器/词典任何变更的表现是——**报价照过、执行才炸** `READINESS_ASSIGNMENT_MISMATCH`（`execution-manifest.js:198`）、回读炸 `REOPEN_READBACK_MISMATCH`（`v15-runner.js:84`），即"新站 + 旧助手混跑 → 历史 attempt 409 → 已扣不释放 → 用户重试产生第二预留"。这是本项目 09-12 事故的孪生形态。

必须新增（缺任何一项都不得改写入语义）：

1. `wrapProfile = { solverVersion, dictionarySha256[], widthModel, autoWrap }` 作为 `compileBindings` 的**必填输入**，缺字段即抛，**禁止默认回退**。
2. `wrapProfileDigest` 同时进入 `bindingPlanDigest`（v3）与 `assignmentDigest` 的 decisions，并冻结到 `ExecutionBatch` / `ExecutionLanguageAttempt` 列。
3. 三处比对：报价 / 派发 accept / 回读结算。历史批次按其 pin 的 profile 用**旧求解器代码**重算（旧码不删）。
4. profile 进 `config/release-identity.json` 与 runtime provenance，并把 Scanner/Reopen JSX 一起 pin（现状仅 TTL 缓存，`script-fetcher.js:23,113`）。
5. 结算闸补断言：计费 units 必须等于译文表原值长度（防止"换行新增行"从口径上漏出去）。

## 4. 可直接复用的东西（Fetch 结论 + 许可/体积/接入形态核实）

**接入形态的唯一可行方式**（核实 `scripts/build-local-binding-core.mjs:18-22,103-118`）：裸 tsc 只编译 3 个入口，**不会 inline 任何 npm 包**（助手 package.json 零依赖、pkg 快照无 node_modules）。但 tsc 会跟随**相对路径 import** 把 `src/lib/trust-chain/vendor/*.ts` 一起 emit 到 `generated/vendor/`，`server.js:77` require 即被 pkg 打入。所以：

- 库源码 → vendor 成 `.ts`；词典/模型 → **转成 `.ts` const 导出**（不能留 JSON asset：tsc 不拷 JSON，pkg assets 与 Web fetch 双轨必漂移）。
- vendor 文件必须 **LF**（`:34-38` 的 CRLF 归一化）。
- `--check` 现在只 digest 3 个源文件（`:58-77`），**必须扩为含 vendor 全集**，否则产物漂移仍不被捕获（本轮审查已知 `smoke-binding-core-generated` 是孤儿）。

## 5. 需要 Owner 决策的四件事（不定则无法收口）

1. **BOXTEXT 谁负责？** 技术上已有答案（见 §10 修订 R1）：PS 存**软换行 `\x03`**（Shift+Enter 语义，视觉换行但不切段落），所以"给 BOX 插换行"不会像 `\r` 那样把一段切成多段、把段级设置打散——spec §5:51 把"插换行"与"切段落"绑在一起是伪二分。仍需你裁决的是产品语义：BOX 图层**我们插软换行**，还是**开 PS 自动断词（§10 修订 R2）让它自己折**，还是维持现状只做溢出提示。
2. **`autoWrap=off` 落点**：对抗审查结论明确——只能落在 `compileBindings` 的必填输入（进 bindingPlanDigest decisions + ExecutionBatch 列 + 报价/派发/结算三处比对）。服务端下发或助手本地 config **都错**：金额虽不变（计费取译文表原值），但写入文本分叉 → 执行期 409、预留悬挂、报告与 PSD 相反。
3. **单行档「+1 行」是否批准**（W5）：现明写在 `20260917-auto-wrap.md` OUT OF SCOPE，且需 S0.5 区域数据。不批准则单行原稿的 3–14 个例外（spec §6 自证）永远"换不了行"——**这大概率就是 Owner 的体感来源**。
4. **历史批次是否追溯**：若 W0-A 判定 `\n` 从未生效，则 5294/5477 已交付批次与 spec §6 基线数字、Acceptance 1 需作废重做，并同步修正 AI_MEMORY 记录。

## 7. 风险登记（Top 3）

- **R1｜纸面证据风险（最高）**：若 W0-A 判定 `\n` 在 PS 里不分行，则 S0.1 上线以来"自动换行：原稿 N 行 → 译文 N 行"的**全部报告证据不可信**（normalize 掩盖使其不可见，且 V6 截图本就 NOT RUN），已交付批次需返工，spec §6 基线与 Acceptance 1 作废，AI_MEMORY 需追溯修正。**触发即停线**：只做对账与告知，不自动重跑（AGENTS「未知执行不得自动重试」）。缓解：W2 先于一切语义改动。
- **R2｜exe 端 ICU 依赖**：`binding-core.ts:1401` 的 `/\p{M}/u` 会随 `generated/` 打进 exe。`build-engine.bat:28` 目标是 `node18-win-x64`，其基座是否 small-icu **未实测**——若属性转义行为与 Web 端不同，则 3.6.59 修的 #60（泰文组合符号移行首）在 exe 端可能失效，且会造成双端 digest 漂移。缓解：W0-② 探针（在打包后的 exe 引擎内跑 `\p{M}` / `localeCompare` / `Intl.Segmenter` 三项）；W6-① 用 `find-cluster-break` 彻底摆脱该依赖。
- **R3｜预算缺失导致收益无法闭环**：Acceptance 2「每行 ≤ 原稿最宽行」当前**无法自动判定**（求解器无宽度上限入参）。若不先做 W4，W5/W6 引入的任何断点改善都拿不出可度量收益。
- 次级：`bounds` 单位不保证是 px（scanner 取 PS 文档标尺单位，`doc.resolution`/标尺从未采集，字段却叫 `wrapWidthPx`）→ 一切 px 预算前必须先定 W0-③；`horizontalScale/verticalScale` 采集了但无人参与宽度换算（横向缩放 50% 的层，em 预算与真实墨迹宽完全不成比例）；`linesFitFrame` 仍在校验白名单但扫描器已删除 → 恒缺字段。

### 10.1 三条会改方案的硬证据

**R1｜行分隔符：PS 引擎内部段落终止符是 `\r`，软换行是 `\x03`，`\n` 不在词表里。**
- 直接证据：`ag-psd/src/text.ts` 双向映射——读 `Editor.Text.replace(/\r/g,'\n')`，写 `replace(/\r?\n/g,'\r') + '\r'`（[ag-psd text.ts](https://github.com/Agamnentzar/ag-psd/blob/master/src/text.ts)）。
- 成熟脚本一律先归一再赋值：`creold/photoshop-scripts/jsx/MultiEditText.jsx:94` `replace(/[\r\n]+/gm,'\r')`，同文件用 `\x03` 表软换行（注释 "End of Text (ETX) to line break"）；`alicewish/lettering` 的 `Text to psd.jsx` 直接 `contents += '\r'+…`。
- Adobe 官方文档对行分隔符**完全沉默**；UXP `TextItem` 只界定 point text「从点击处开始」/ paragraph text「用边界控制字符流」→ 只有段落文本有折行边界。
- 判定：我们现在写 `\n` 的后果，最可能**挤成一行（65%）**，次可能夹一个未知字符方块（25%），正常分行 10%。W0-① 三条命令即可定案。
- **推论**：`\r` 会把一段切成多段（段级对齐/缩进/前后距/断词按行生效），所以 **BOX 图层要断视觉行应该用 `\x03` 软换行**——这把 §5 决策 1 从"要不要插"变成"用哪种换行"。

**R2｜Photoshop 自带断词与禁则，可能让我们省掉词典。**
- UXP（Min Version 24.1，可读可写）：`textItem.paragraphStyle.hyphenation` + `hyphenationFeatures{wordsLongerThan, afterFirst, beforeLast, limit, zone, capitalWords}`，同级还有 **Kinsoku（禁则）** 与 `justificationFeatures`（[HyphenationProperties](https://developer.adobe.com/photoshop/uxp/2022/ps-reference/objects/options/hyphenationproperties)、[ParagraphStyle](https://developer.adobe.com/photoshop/uxp/2022/ps-reference/classes/paragraphstyle)）。
- 引擎层字段在 PSD 里可读：`autoHyphenate / hyphenatedWordSize / preHyphen / postHyphen / consecutiveHyphens / zone`（[ag-psd/src/psd.ts](https://github.com/Agamnentzar/ag-psd/blob/master/src/psd.ts)）→ 意味着既能读原稿设置，也可能写回去让 PS 自己断。
- ExtendScript DOM 层**未找到** hyphenation 属性，AM key 名**未找到**公开文档 → 需 Alchemist 录制实测。"Auto-Shift-Word-Wrapping / optical margin correction" 在 PS 里不存在（属 InDesign/TeX）。
- **新增一档 W3.5**：若实测 PS 断词+禁则生效，则 §4 第一批里的 `css-line-break`(UAX#14 禁则) 与第二批 `hyphen` 9 语 pattern（≈0.49MB + 逐语许可负担）**可以整块不做**，我们只负责"决定开不开 + 给框宽 + 事后量行数"。这是收益/成本比最高的一条待验证项。

**R3｜"可用宽度"不是非等 S0.5 不可。**
- PSD 文件里**有**文本框几何：`LayerTextData{shapeType, pointBase, boxBounds, orientation, antiAlias}` + `paragraphStyleRuns`（justification/leading/indent）→ **段落文本框宽可从文件直接拿**；但**自动折行的逐行宽度不落盘**（Adobe 官方[文件格式规范](https://www.adobe.com/devnet-apps/photoshop/fileformatashtml/) 只有段落级键），psd-tools 同理。
- 我们扫描器现在就在 PS 里跑，却从未读 `textItem.bounds`（本地勘查：全库未读）。→ 补这一处即可给 BOX 图层真预算；POINTTEXT 预算取"原稿行墨迹宽"，或按 `boxBounds`/画布宽给容忍上限。
- 因此 §5 决策 3 的前提要改：**"+1 行"不必等 S0.5 区域数据**，只需要 (a) 拿到框宽或容忍系数、(b) Owner 批准多一行。

### 10.3 结论：有没有的抄

**没有。** 没有任何开源项目做过"按原图层行数重排译文"这个精确目标；成熟品类做的一致是"**往框/气泡里塞**（真字体度量 + 词级贪心 + 词典音节连字符 + 字号二分/阶梯降级 + 扩框或允许溢出）"。所以：

- **可直接抄（许可允许）**：comic-translate 的**降级阶梯形状**（Apache-2.0）；`tex-linebreak` 的**失败即显式异常 + fallback 事实**（MIT）；BallonsTranslator 的**逐行原稿宽预算**思路（GPL-3 仅思路）；InDesign 的**三档适配 + 溢出可见**产品语义；`insert_textbox` 的教训（不要全有全无、不要静默越界）。
- **必须自建的只有两块**：① 逐行宽度的**测量权威**（PS 侧 `textItem.bounds`/每行量，或 PSD `boxBounds`）；② **固定行数的 DP 求解器**——`O(n·N)` 分段 DP 约 **60 行 JS**（比 v1 估的 100 行更少），签名 `f(断点集, 每 token 宽度, 预算宽, N) → 行划分 | 降级档 + degraded 标记`，纯函数、可重放、进摘要。
- **可能整块不做的**：`css-line-break` 禁则表与 `hyphen` 9 语词典——取决于 R2 实测（PS 自带断词+Kinsoku 若可用，就把它们降级为"Web 侧预览用"）。

### 10.5 W0-① 已用真机产物定案（2026-09-19，实测完成）——假设 A 证伪

样本：`F:\工具开发\自动改语言\批量改语言测试\Amazon-SJ日本站-5294主图+A+改语言-金娜\..._ALL_11LANG__20260918_210226`（助手 **3.6.59 / `typo-wrap-space-fix-20260918-r1`**，11 语言，报告 535 行明细，341 已验证 / 0 待复查）。

- **字节级取证**：输出 `__DE.psb` 里我们插入的断行，在 Photoshop 存储层是 **`00 0D` = UTF-16BE CR**（层 75 `"PH1-Schlüssel"<CR>"SL5-Schlüssel"`、层 161 同理），与原始 `.psb` 里 Photoshop 自己存的 CR 完全一致（对照缝隙字节 `000d`）。→ **`\n` 写入被 PS 归一为 CR 并真实分行，假设 A 不成立**，"这两天做的换行"确实生效了。
- **覆盖面取证（用报告数据重算）**：多行原稿且行数已对齐 **99 件**；多行原稿但行数不符 **0 件**；**单行原稿 + 译文超宽 ≈ 134 件（每语言约 12 件，DE 23 / FR 21 / IT 21 / ES 18 / ID 11 / MS 12 / TH 10 / VI 11 / JP 7）**，中位超宽 **1.85×**（字符宽度粗估，需换真墨迹宽重算）。这 134 件走的是 `binding-core.ts:1526` 的 `SOURCE_SINGLE_LINE` 早退分支——**从未进入换行逻辑**。
- **结论修正**：主诉根因是 **B（覆盖面：单行原稿按已批准范围根本不换）**，不是 A，也不是求解器质量（D：我们换的 99 件零失误）。
- **对方案的连带影响**：① W3 的"分隔符修正"降级为**加固项**（显式写 `\r`，不依赖 setter 归一行为），不再是止血项；② 仍必须补 W2 的像素级取证（本次结论靠字节推断，截图/`textItem.bounds` 行数仍缺，V6 至今 NOT RUN）；③ 工作量重心整体移到 **W5（单行档 +1 行）+ W4（真宽度预算）**，§4 的词典类依赖可再往后压——单行变两行多数只需空格/标点断点即可满足。

### 10.6 现在的解决方法（定案后版，按此顺序）

1. **放开单行档**：`structuralTargetText` 不再对 `sourceLines<=1` 早退，改为「按预算宽度求 `N = ceil(译文宽 / 预算宽)`，N>1 时拆 N 行，最多 `1 + maxExtraLines` 行」。
2. **预算换成真宽度**：入参加 `maxLineWidthPx`；来源＝原稿该行墨迹宽（`bounds.width`，先做 §1 W0-③ 单位定案），不再用 em 字符数。这是 134 件能否换对的前提。
3. **断点先用最省的**：拉丁按空格 + 已有连字符断，CJK/泰按字素断；**不引词典**即可覆盖这批（词典留待"断得难看"的证据出现后再买，见 §10.1 R2 也可能整块省掉）。
4. **落笔显式 `\r`**（POINT 与 PARAGRAPH 分别用 `\r` / `\x03` 由 §5 决策 1 定），回读侧改读结构化行数（PS 侧 `textItem.bounds`/行度量）→ 补像素级证据。

6. **验收基线现成**：用这 134 件做改前/改后对照——要求"1.85× 以内的全部变成 2 行且每行不超原稿宽"，并抽样截图入 records。
