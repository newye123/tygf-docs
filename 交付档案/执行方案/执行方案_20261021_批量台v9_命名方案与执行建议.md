## 阶段一 · 命名：新工作台有自己的词表，旧词表只归单稿台

### 1.1 为什么必须分开命名

- **旧名是单稿台的资产**：`准备素材 / 选择设计文件 · 只读预扫描 / 选择语言 / 重选译文表 / 智能检测` 都在单稿工作台里，**改了它就破坏"原样保留"这条前提**。
- **旧名也表达不了新东西**：「准备素材」里没有"表从哪来"这一层；「重选译文表」是单稿语义（一稿一表），批量台是**每份交付物各有来源**。
- ⇒ **两套词表并存，各说各的；同一个概念在批量台内部必须只有一个说法。**

### 1.2 命名对照表

### 1.3 命名的五条规则（写进方案当硬约束）

1. **用用户嘴里的词，不用内部词。**
   ✗ 译库 · 切片 · 绑定 · 覆盖率矩阵 · owner value · slice
   ✓ 译文表 · 这一稿用哪张表 · 这一份从哪张表取 · 对稿覆盖率
   （内部术语只活在代码里：`binding / slice / dataset / coverageDrafts`。）
2. **旧名只归单稿台，新名只归批量台，不混用。** 界面上出现旧名 ＝ 串台了，是 bug。
3. **每个数字都要有分母和对象。** 「72 就绪」单独出现是无效信息 ⇒ 必须同时给「88 本批要做的交付物」和「144 矩阵格数（12×12）」。
4. **状态词要能回答"我现在该做什么"。**
   - 就绪（可以往下走）· 待检查（等你确认）· **有 N 处要处理**（说清几处）· **缺语言**（这一份**做不出来**，不是"再等等"）。
   ⇒ 「有 N 处」是批量台**唯一**的文案钩子（单稿台是逐行看），所以 N 必须随状态实时变。
5. **一处一个说法。** 同一概念在标题、按钮、徽章、报告、飞书推送里必须同名；批量台说「译文表」，就不许别处冒「译库/表格包」。

### 1.4 一处必须一起改的文案联动（改一处就要看全链）

| 概念 | 出现位置 |
|---|---|
| 「设计稿」 | 导轨第 1 步 · 第 1 步标题 · 列表区标题 · 抽屉里的文件名 · 报告里的批次标题 |
| 「译文来源」 | 第 1 步副标题 · 矩阵卡片标题 · 图例 |
| 「对稿覆盖率」 | 矩阵单元格 · 设计稿卡片 · 抽屉 · 汇总条 · 报告 |
| 「就绪 / 有 N 处要处理」 | 矩阵单元格 · 设计稿卡片 · 汇总条 · 执行前提示 |

⇒ **命名单独立一单**（它本身是产品行为，且会改动多处文案），**先过 Owner 审，再进代码**。

## 阶段二 · 执行建议（我的推荐顺序）

### 2.1 核心原则

> **先立闸，再动代码；先只读，再进执行；先新增文件，再碰共享文件。**

### 2.2 九个阶段（每一阶段都能独立验收、独立回滚）

| 阶段 | 做什么 | 验证口径 | 风险 |
|---|---|---|---|
| **0 · 闸** | 写 **`#workbench` 快照断言脚本**：`batchMode=false` 下渲染单稿台，抓关键 DOM 节点数 / 文案集合 / 按钮集合，存基线 | 脚本 rc=0；基线可复现 | **无**（纯新增） |
| **1 · 命名** | 批量台新词表定稿（§1.2）＋ 走查全链文案 | Owner 过目；清单逐条勾 | 无（文档） |
| **2 · 纯函数** | 新增 `src/lib/workbench/binding/*`：行身份、归属、切片、合并、证据分级 | 单测：共享表 / 一对多 / 零命中 / 缺列 / 覆盖 / 专表 / 补充表 | 无（纯新增） |
| **3 · 只读来源视图** | 新增 `source-matrix.tsx`，**先喂 mock 数据**、不接真数据 | 浏览器实拍 12×12；矩阵与设计稿栏一致 | 无（纯新增） |
| **4 · 批量台导入器** | 新增 `table-batch-importer.tsx`（多选＝分给多稿；不改 `csv-step.tsx`） | 12 张表一次导入；逐张点名失败 | 无（纯新增） |
| **5 · 按格审查** | 新增 `review-cell-panel.tsx`（不改 `review-step.tsx`） | 单格审查可用；确认按 (稿,语种) 存 | 无（纯新增） |
| **6 · 挂载** | **这时才**在 `workbench-view.tsx` 的 `batchMode` 分支里挂 3/4/5 | 闸 0 快照 rc=0（**单稿台未变**）＋ tsc/lint rc=0 | 中（首次动共享文件） |
| **7 · 行集合并** | `execute-step.tsx` **新增**批量专用「按格合并行集」实现（原实现保留） | 单测：合并后同原文冲突按 `binding-core.ts:930-939` 抛；**写入层语义不变** | 中 |
| **8 · 覆盖率取数口** | `coverage.ts` **只新增**「每格一行集」函数 | 三档口径不变；组件与闸仍同一份 | 低 |
| **9 · 接执行** | 批量台走通"生成交付"；助手得分接口（**独立一单**，只读、不改执行语义） | 12 批次 × 88 份；积分与预估一致 | 高（最后才做） |

### 2.3 三条刻意的取舍

- **阶段 3 先只读、不接真数据。** 用户先看到"每份交付物从哪张表取、覆盖率多少"，确认这套模型合不合手，**再**接执行。错了改的是一屏界面，不是执行链。
- **阶段 4/5 各写一份，不复用共享组件。** 代价是少量重复（导入器 ≈ 200 行、按格审查外壳 ≈ 150 行），换来**单稿台一行不碰**。
- **阶段 9 的助手接口单独排期。** 它是唯一动助手的部分，只读、不改执行语义，不与前端抢排期。

### 2.4 阶段 0 为什么必须第一个做

「与原行为逐字节一致」是仓库既有的成文验收尺（`app-shell.tsx:41-47`），但**没有断言脚本，它就只是一句话**。阶段 0 的产物让后面每一次提交都能自动回答"单文件台变了吗"，也是本方案唯一能把前提从承诺变成事实的东西。
