## 一、结论（三句话）

1. **我上一版的「第 1 层骨架」形状是错的**——它想在一个新视图里从头搭四个区，而批量能力**在这个仓库里早就端到端跑通了**，只是长错了地方（长在原工作台里面，一开开关就把原工作台顶替掉）。这犯了本项目自己点名的病：**把已有能力当待新建**。
2. **最优路径不是重建，是搬运**：把「多 PSD 能力」从原工作台里**搬进 `#batch` 视图**，原工作台恢复成纯单文件。这样批量工作台**立刻就是可用的**（覆盖率矩阵、逐稿编排、批次链、计费全都在），代价只有约 10 处小改。
3. **已按此执行**：`#workbench` 与 `#batch` 现在是同一个组件、两种模式（`batchMode`），**单文件路径逐字节不变**；顺带把 ISSUES #151 的「静态/运行时双语义」收口。

### 反方 3：「『原工作台零改动』是个错误的约束」

**成立。** 我在上一版方案 §5.1 写了「关键纪律：原 `workbench` 视图及其组件树零改动」。但这条纪律**和「真正并列」是矛盾的**：只要 `design-file-card.tsx:600` 那段 `if (开关) return 整套多选 UI` 还在，顶替的机关就还在，并列只是靠「别打开那个开关」维持的**纪律**，不是结构事实。

**修正后的正确约束**：不是「零改动」，而是「**单文件路径的行为必须逐字节不变**」。这可以用一个默认 `false` 的 prop 做到——改动是加法，行为是等价。

**本轮已补**：新增 `scripts/smoke-batch-workbench-flag.mjs`（隔离库），断言默认值、原子写 true/false、**以及「写本键不得覆盖其他键」**（这是原子性的核心主张）。

### 反方 5：「你把『静态/运行时双语义』说大了」

**成立（收窄）。** 我上一版说 `multiPsdExperimentEnabled` 存在「静态/运行时双语义」。实测收窄：

- `workbench-view.tsx:175` → `useFeatureFlags()`（**运行时**）

### 反方 6：「你的粘贴入口没有串行扫描，体验是『粘 5 个、点 5 次』」

## 三、最优方案：搬运，而不是重建

### 核心判断

批量能力**已经端到端可用**。所以最优不是新建四个区，而是**换一个入口去用它**：

```
#workbench  →  <WorkbenchView />            单文件工作台（行为与改前一致）
#batch      →  <WorkbenchView batchMode />  批量工作台（同一套步骤，文件区换成多稿列表）
```

两者**共用同一套步骤组件**，靠 `batchMode` 区分。收益：

1. **批量工作台立刻可用**——语言选择、覆盖率矩阵、逐稿编排、批次链、计费、回执全都在，零重建。
2. **顶替从结构上不可能**——单文件模式下多稿分支**根本不渲染**，与任何全局开关解耦。
3. **ISSUES #151 收口**——`design-file-card` 不再读编译期静态值，改由 prop 决定。
4. **零重复**——不存在「两套渲染分支」的维护成本。

### 具体改动（10 处）

| 文件 | 改动 |
|---|---|
| `workbench-view.tsx` | 加 `batchMode?: boolean`（默认 false）；`:262` 与 `:2137` 两处 flag 读取换成 `batchMode`；向 `DesignFileCard` / `ExecuteStep` 透传 |
| `design-file-card.tsx` | 加 `batchMode?: boolean`；**删掉模块级静态常量** `EXPERIMENT_ENABLED`（:66）；多选分支改判 `batchMode`；新增「粘贴多行路径」一次录入多个 |
| `execute-step.tsx` | 加 `batchMode?: boolean`；`:1907` 与 `:2038` 两处 flag 读取换成 `batchMode` |
| `app-shell.tsx` | `#batch` 改渲染 `<WorkbenchView batchMode />`；删掉空壳视图的动态分包 |
| `config/featureFlags.ts` | `multiPsdExperimentEnabled` 标注**已停用**（保留键、不再被任何代码读取） |
| `scripts/smoke-batch-workbench-flag.mjs` | **新增**：开关契约测试 |
| 删除 | `batch-workbench-view.tsx`、`batch-file-list.tsx`（被取代的空壳） |
| 删除 | `local-assistant-client.ts` 的 `selectDesignFilesDirect`（无调用方，避免死代码） |

### 为什么保留 `multiPsdExperimentEnabled` 这个键而不删

删键 = 改配置 schema = **Owner 的决定**，不是我的。保留键 + 移除全部读取，效果等价（无人读 ⇒ 存什么覆盖都没用），且零 schema 风险。

## 四、已执行

改动规模：**修改 13 文件 + 新增 1 文件（+319 / −37）**。

关键点：

- `#workbench` → `<WorkbenchView />`（`batchMode` 默认 false）⇒ **多稿分支不渲染**，单文件行为等价。
- `#batch` → `<WorkbenchView batchMode />`，且仍受服务端合并开关 `batchWorkbenchEnabled` 门控（默认 false）。
- `design-file-card.tsx` 的静态常量删除，双语义收口。
- 批量卡片新增「一次录入多个 · 粘贴路径（每行一个）」：一次粘贴多行 → 逐行清洗、去重、过滤 `.psd/.psb`、受 12 个上限约束 → 加入列表（复用 `addMultiPsdEntry`）。

### 为什么是「粘贴」而不是「拖拽」

浏览器出于安全**不向网页暴露被拖入文件的绝对路径**（`File.path` 是 Electron 专有，Chrome 只给文件名），而助手链路需要绝对路径 `masterPath`。所以纯 Web 页拿不到可用的拖拽输入；**粘贴多行路径**是可靠入口（与单文件区既有的「粘贴即扫描」同源）。真正的一次多选要等助手端 `OpenFileDialog` 加 `Multiselect`（第 2 层）。

### 8.1 致命：批量工作台其实**根本跑不起来**（推翻我前三轮的结论）

**症状**：在批量工作台点某个设计稿的「扫描」，状态会**永久停在「读取文件」**，永远不会变成「已扫描」。

```ts
if (multiScanningIdx !== index) return   // null !== index ⇒ 直接返回
```

**第一次轮询就自我判废**，且不再排下一次定时器 ⇒ 状态永久冻结。

**这条我早就知道**：第三轮我自己在 D10 里写下过——

> 「那个修复已经写好但未提交地躺在 `worktrees/develop` 的工作区里（`design-file-card.tsx` 的 `multiScanningIdx` state→ref，注释写明「第一次轮询就自我判废，状态永久卡 hashing」）」

### 10.2 第 3 个真实产品缺陷：执行入口未受执行开关约束（静默回退）

**症状**：执行开关关闭时（`TYGF_EXECUTION_ENABLED≠1`），批量面板里的**实验入口按钮「开始执行（逐 PSD 编排）」仍可点击**。点击后 `onExperimentStart → handleExperimentStart → experimentTrigger → runExecution`，命中客户端 `V15_EXECUTION_REQUIRED` 拦截后，**界面静默退回翻译校对阶段，没有任何失败提示**——用户看到的只是「点了没反应，页面自己跳回去了」。

**根因**（`execute-step.tsx:2131`，修复前）：该按钮写的是 `disabled={!ready || running}`，**漏了 `!v15ExecutionEnabled`**。同文件主线按钮「开始替换」（约 :2420）早就写对了：`disabled={executionInFlight || !v15ExecutionEnabled}`。⇒ 同一个执行开关，两个入口只堵了一个。

**修法**（与主线按钮对齐）：

```tsx
disabled={!ready || running || !v15ExecutionEnabled}
title={!v15ExecutionEnabled ? '当前测试环境仅开放 Web 功能，真实执行暂未开放。' : undefined}
```
