对抗式审查 · 第三轮/批量台 v4/2026-10-20

绑定不是「配对」，是「划分」

上一版把「归属」当成表的属性。这一轮继续往下推，发现归属是行的属性：表本身不归属任何文件，要归属的是「哪些行属于哪个文件」。于是绑定问题从配对升级成分配问题——可以出得分、可以自检、而且把上一版排在 P2 的合同变更整条删掉了。

02阶段一 · Critical Thinking（再往下一层）

v3 说「表＝数据集，文件＝按归属切出的一片」。再问一层：归属是表的属性吗？把一张表切成片，片有归属；表本身没有归属——它是很多行的容器。一行译文属于哪个文件，取决于这一行是哪一稿的文案。

推论 1 · 绑定不是配对，是分配

绑定单元从「表 → 文件（整张）」变成「行 → 文件」。差别是实质的：一个表能给几稿用，由表里内容决定，而不是由产品配置决定；12 SKU 一张合表从此天然可表达。

v3（配对）v4（分配）
绑定单元表 → 文件（整张）行 → 文件（可切）
一个表能服务几稿要么独占、要么"组"（另立一个对象）任意，由内容决定
12 SKU 一张合表表达不了（v3 的 E1 已认）天然可表达：它就是"要分区的一张表"
证据规则级联逐对得分（可排序、可比较）
推论 2 · 宽表不是特例，是可计算的判据

一个表是不是宽表，不需要人来声明：它对多少个文件高分，它就是宽表。一行只有一格高分＝这一稿的独占表；一列在很多行都高分＝这一列是宽表 ⇒ 要分区，不是直接绑定。

推论 3 · 证据是一个数，不是四档

证据的真实含义只有一个：这张表的行，能对上这一稿的几层。档位只是这个数的人话投影：强正（≥阈值且明显高于次高）＝「对得上」；强负（对任何表都无交集）＝「对不上」；中间＝「说不清」。判据必须是覆盖率这一套口径，不许另起一套。

推论 4 · 物理约束：得分只能助手侧算

浏览器拿不到逐层正文（扫描摘要里只有指纹与层计数）⇒ 得分矩阵必须助手算、浏览器只收分；助手可回传逐层哈希而非正文（更脱敏、跨次可比、hex 天然合规）。

推论 5 · 本轮最重要的减法

若先把表切成片，片内行只属于一个文件，同原文多行就是数据错误（现有 V15_DUPLICATE_SOURCE_ROW 已拦）⇒ 不需要改匹配键。⇒ v3 排在 P2 的「行身份升级（改匹配键）」整条删掉，方案风险面从「要动执行合同」降到「纯绑定与展示层」。

公理 A

交付物的键 = (文件, 语种)

证伪：若计费单位不是 (文件, 语种)。

公理 B

译文的键 = (归属, 原文, 序号)

文件不是原语。

公理 C

归属是行的属性

证伪：若"表属于文件"是必需语义。

公理 D

绑定＝行集合的划分

证伪：若任意表必须整体绑定且不可切。

公理 E

证据＝匹配得分

证伪：若证据必须是不可比较的枚举。

公理 F

切片到位 ⇒ 不改匹配键

证伪：若歧义无法靠划分消除。

04阶段三 · Deep Thinking（v4 方案）

Dataset（译库）   { id, name, rows[], langColumns[] }
  └─ Slice（片） { datasetId, ownerValue?, rowIds[] }      ← 划分结果
       └─ Binding { draftKey → { datasetId, sliceId, languageScope } }
            └─ Evidence { hitRate: 0..100, runnerUp: number, tier: 对得上|说不清|对不上 }

得分矩阵（助手侧算，浏览器只收分）

行＝12 个稿，列＝M 张表，格＝该表对本稿的命中率。算子：该表的行（按语种切片后）能命中该稿多少个文字图层，分母＝该稿可翻译图层数，口径＝coverage.ts 三档之一。成本 ≈ 50 万次归一化比较（一次性），按「表指纹 × 稿指纹」缓存（Y3/Y4 提供稳定键）。

分区自检（新增安全闸，三条任一不过就不给执行）

自检判据失败时
互斥每行 id 恰好属于一片（无行落进两片）拦批并点名重叠行
命中每片对本稿命中率 ≥ 阈值该片拦批，其余片照跑
有据每片都有归属证据（得分达标）该片拦批

歧义早报（把执行期的硬错提前到绑定期）

今天「同原文不同译文」在执行期炸 V15_DUPLICATE_SOURCE_ROW（binding-core.ts:930-939），代价是整批拒、孤儿 attempt（#195 的形态）。⇒ v4 在绑定期就问：「这 2 行原文相同、译文不同，分别属于哪一稿？」

记录编号：哈希短码 ⇒ D17 结构性消失

v3 需要靠纪律维持「编号必须过助手白名单」；v4 改为 记录编号 = "L" + sha256(层级路径+出现序号).slice(0,16) —— 十六进制 ⇒ 天然纯 ASCII、天然 ≤128、天然匹配白名单，不再需要"转码"这套纪律，也不可能踩 #195。（#195 治的是用户表里的编号，仍要治，两条并存。）

界面：2 个界面 ＋ 1 个检查器（比 v3 少一个）

① 批次总览（常驻、跨 4 步）：交付物矩阵，按交付包折叠，行头人话徽章　→　② 单稿详情＝图二那一行　→　③ 绑定检查器：得分矩阵 ＋ 候选排名 ＋ 分区自检 ＋ 歧义早报。

05阶段四 · Review（第三轮 12 条）

#级攻击处置
T1🟠「全局最优分配」说过头了：逐对打分＋贪心是错的（94/91 接近时贪心随便挑）；「一张表能服务几稿」是容量约束，是产品决策不是算法能推出来的诚实改写：得分矩阵只做证据与排序，不做自动指派；指派永远是人的动作，除非唯一且明显（与次高差 ≥ 阈值）。不宣称"全局最优"
T2🟠得分与覆盖率分母不同（层 vs 语种）⇒ 同一行两个不同含义的 "%"，用户会混同源同分母：两者都以「这一稿的文字图层」为分母，语种覆盖率是它的子集；命名区分：对稿命中率 vs 该语种命中率，界面标注分母
T3🟡回传逐层哈希会不会把隐私现状搞复杂哈希是从正文派生的不可逆摘要，不新增正文外泄面；评分阶段不需要正文 ⇒ 反而减少上传。但隐私口径要加一项并经 Owner 过目
T4🟠逐层哈希不是完美脱敏：常见营销语（"Free Shipping"）的哈希可能被字典反查默认只回传聚合得分（"12 层里对上 12 层"）；逐层哈希降级为可选加强模式，需带盐哈希（盐来自 scanId，不落盘）并单独论证
T5🟡108 次匹配会不会太贵≈50 万次归一化比较，一次性可接受；按「表指纹 × 稿指纹」缓存
T6🟠指纹稳不稳定两级指纹：① 文件级（现有 fingerprint，判"稿有没有变"）② 行级（判"这一行属于哪一稿"，允许随内容变）。跨版本凭证只能靠①＋覆盖关系
T7🟡「两两不相交」怎么验表解析后按行 id 分片 ⇒ 不相交是可计算的不变量。补两条：每片非空、片数 ≤ 表里出现的归属值数
T8🟠「版本一致」会不会天天误报（设计稿小改很常见）降级为「需复核」而非「作废」：fingerprint 变 ⇒ 重算得分；新得分仍高 ⇒ 保留绑定并提示「稿已更新，表可能需要更新」
T9🟡「交付包」是谁定义的不进数据模型：只做矩阵的视图折叠，分组是视图状态
T10✅v4 相对 v3 是净减还是净增净减风险面：多了得分矩阵/自检/歧义早报/哈希指纹；少了合同变更整条、共享组对象、包对象、默认逐层哈希
T11🔴本轮推得太远了吗：P0 的得分矩阵要动助手（新增只读接口），这是方案里唯一动助手的部分诚实说清：P0 不是纯前端。若 Owner 要求本轮全在前端，得分矩阵降级为"名字规则提案"，证据退到"推定档"。建议做助手接口——它一次解决"错绑"这个唯一不可逆风险，且不改执行语义（只读）
T12🟡「144 份交付物」是不是比用户脑子里的单位更细Owner 脑子里的单位可能是"一个 SKU 的一次交付（12 个文件一起交）"⇒ 144 格保留（细粒度不亏），但必须有包级滚降（包行＝"12 份里 8 份完成"）——与 T9 的折叠是同一件事

P1-2 · 宽表分区

只存 稿→库+片（不存表内容）。P2 不再触碰执行语义 ⇒ 不触发合同变更门。
