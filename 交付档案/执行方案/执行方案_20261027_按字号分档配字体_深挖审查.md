- **承接**：2026-10-22《字体排版按字号分档：审查结论与执行方案》＋刀二（S4 逐层配脸）。Owner 2026-10-27 真实事故：英文稿标题与正文是两种字体，改中文时中文也需要两种字体，现在做不到。
- **方法**：yt-adversarial-review 五步（固定基线 → 分面只读取证 → 逐条证伪 → 收敛 verdict → 负控）。本轮**只读**，未改业务代码、未跑门、未碰两站。子代理并行取证被当日额度拦下（Chat usage limit），三路取证由主审顺序自跑——**独立并行审查这一步没做成，如实记在覆盖缺口里**。
- **一句话结论**：字号数据早就扫出来了、也传到浏览器了，缺的不是"扫描"，是**"一份设置"这个模型**＋**失败说不清是哪一层**。而且原方案把"先标定字号单位"当成硬前置，这条被本轮推翻——改成锚定稿内实测字号就不必先定单位，风险从"阻塞"降为"显示"。

## 先说这对你意味着什么

1. **你要的东西不是从零建**。扫描器每层都读了字号（字段 `fontSizePt`），学习子系统已经在按「字体×字号×对齐」分桶统计。新做的部分是：把这些字号摆给你看、让你按字号各设一套字体、执行时按层挑档。
2. **你的场景能覆盖，但有一个前提**：英文标题和正文的**字号不同**才分得开。如果同稿里有"14 点标题"和"14 点正文"，光看字号分不出来——那是按图层单独覆盖，属下一项目（选项 B）。
3. **免 PS 通道这轮不做**：引擎侧今天一份排版都不落（实测 0 处引用），而且 #276 写回冻结还在。所以这条链只在 Photoshop 通道生效，界面必须如实说，不能沿用现在这句含糊的"执行时不会被应用"。

## 本轮新钻出来的三条（原方案没写的）

**F-1（CRITICAL）字号的单位标签被丢掉了——但这条不必阻塞本轮。**
扫描器读的是 `textItem.size.value`，只取数值、**不取 `.type`**（`TYGF_V15_Preparation_Scanner.jsx:144`）。同文件 `:145` 的 leading 同样只取 value，而执行器读回 leading 时拿到的是带单位的 `UnitValue`——注释自陈实测是 `"30 pt"`（`TYGF_V15_Thin_Executor.jsx:102`）。也就是说 PS 侧这些字段本来就是带单位的量，我们**主动把单位扔了**，字段名再叫 `fontSizePt` 就是猜的。
原方案据此要求"先跑真机探针，否则匹配逻辑不许按点写死"。**这条我推翻**：`src/lib/workbench/overflow-estimator.ts:8-9` 记着 2026-09-17 实测"fontSizePt 与墨迹高 1:1、不再乘 1.333"，而 `changes/active/20260921-external-display-denoise.md:44` 又把同一个数当"点"解释（300pt 墨迹 21px ⇒ 判为图层被缩放）——**同一份数据被两种单位口径各自用过，且两种解释都自洽**。这说明"先把单位钉死"这件事比想象中难钉，把它设成硬前置＝把整条链挂在一个短期拿不到唯一答案的问题上。
**改法**：档位阈值**锚定本稿实测字号**（界面上你点的是"300 这一档"，不是"≥212 点"），匹配是"拿这层读到的数值，去命中你从同一份稿里挑出来的那组数值"——同机同通道下自洽，单位错也只错在**显示**上，不错在**匹配**上。同时仍补一个廉价修复：扫描时把 `size.type` 一起带回来（一行 jsx＋契约一字段），让显示口径以后能钉死。

**F-2（CRITICAL）失败清单连"哪一层"都说不出来。**
`typoIssue()` 的聚合键是 `字段|错误码`，只累加 `count`（`TYGF_V15_Thin_Executor.jsx:60-65`）。所以今天"字体被 PS 悄悄换成 MyriadPro"这件事，最细只能说到"face 字段错了 3 次"，说不出是哪三层、原想要哪张脸。逐层配脸之后这会立刻变成主要投诉源（"我明明给标题设了 A，怎么没变"）。**这条必须先于档位上线**，否则新功能不可诊断。

**F-3（WARNING）免 PS 通道今天一份排版都不落，且界面不区分通道。**
`grep -c typography download/local-assistant/pc-executor.js` = **0**、`pc-channel.js` = **0**；`pc-executor.js:440` 只留了 #276 的字距降级注释。而 `grep -rn "photoCraft|免PS" src/components/workbench/workbench-view.tsx` 无输出——面板不知道这单走哪条通道。现措辞"字段会送出，但执行时不会被应用"只在能力位 false 时出现；能力位在 PS 通道为 true 时，免 PS 通道是否也报 true **未核实**（要跑一次真机或读 `/ping` 判定逻辑才能定）。若报 true，这句话在免 PS 通道上就是**过度承诺**，触"不得静默降级"红线。列为 P0 前置核实项。

## 执行方案（P0→P5，每步都能单独验收）

**P0 前置核实（半天，不动业务代码）**
1. 免 PS 通道下 `/ping` 的 `typographyApplyReady` 到底是什么值（读 `server.js:1569-1580` 配对规则＋真机一次）。结论决定界面措辞判据，**不许猜**。
2. 扫描时补带 `size.type`（jsx 一行＋`preparation-contract.ts:228` 附近加可选字段），真机跑一次把 type 读数记下来。这条**不阻塞** P1，只把 F-1 从"未知"变成"有读数"。

**P1 失败可见（1 天）**：F-2 的逐层取证＋界面消费。先做这条的理由：后面每一步都要靠它自证。

**P2 字号分布只读（1 天，可当天给你看）**：面板里加一块「本稿字号分布」——每个字号多少层、当前会落到哪一档，点一个字号就能建档。**这一步不改任何写回**，纯粹把已有数据摆出来。今天就能回答"我这稿到底有几个字号"。

**P3 档位模型与写回（3 天）**：`TypographyProfile` → 每语言一组档位（≤8 档、阈值降序唯一、必须有默认档、只允许脸名/字距/行距/自动字距/伪粗/伪斜六个字段）；旧单一设置升为默认档（不清空、不变行为）；助手 `validateTypographyTiers` 旁挂信封；执行器逐层解析命中档后调 `applyTypography`。

**P4 预览保真（1 天）**：字重按脸名样式词映射真值；缺字体明说不可用。

**P5 真机整批验收＋上测试站**：三字号夹具（大/中/小）一次跑完，逐层读回；故意给一档不存在的脸，界面必须点名是哪层。生产按三段轨等你点头。

## 三个要你拍的（其余我按推荐做）

1. **同字号不同角色要不要本轮做？** 推荐**不做**（选项 A：只做字号档位）。你今天的场景是标题/正文，字号多半不同；同字号分角色要按图层覆盖，界面与回执都要再大一圈。若你的稿里确实有"同字号不同角色"，选 B，我加图层级覆盖，工期 +2 天。
2. **档位轴用什么？** 推荐**锚定本稿实测字号**（点字号建档），不是手输点数——理由见 F-1。
3. **P2 要不要单独先上一版？** 推荐**要**：一天出活、零写回风险，你先用真实稿看分布对不对味，再决定 P3 的档位数量与默认值。

## 明确不做（守住范围，防过度工程）

改字号（会重新折行、牵动行数判据与报价口径）；水平/垂直缩放；基线偏移；消除锯齿；语言方向/大小写/下划线删除线；免 PS 通道排版写回（#276 冻结中）；云端回执 schema 一个字段不动。
