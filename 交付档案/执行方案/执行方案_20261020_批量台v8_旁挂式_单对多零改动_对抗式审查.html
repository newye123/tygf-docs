  • 「与原行为逐字节一致」是本项目已有的成文验收尺（app-shell.tsx:41-47、workbench-view.tsx:252-258「这从结构上杜绝了『多 PSD 实验顶替原工作台』再次发生」），不是我这轮新造的。

五道不变式闸（任一不过，不许合入）

闸 1 · 结构

入口那一行不许动

app-shell.tsx:46-47 的 {view === 'workbench' && <WorkbenchView />} 与 {view === 'batch' && … <WorkbenchView batchMode />} 这一行不改。单文件台仍然不传 batchMode。

闸 2 · 渲染

多稿能力一律包在 batchMode 里

来源矩阵、逐稿编排、覆盖率矩阵、批量动作、批量样式——必须在 batchMode && 内或 if (!batchMode) return … 之后。先例：workbench-view.tsx:1766/1786/1802。

闸 3 · 行为

快照比对（可执行）

在 batchMode=false 下渲染 #workbench，对关键 DOM 节点数 / 文案集合 / 按钮集合做快照，与基线逐字节比对，差异即失败。加一条本地可跑的断言脚本，纳入提交前门。

闸 4 · diff

改既有文件必须逐条带上下文

批量台改造优先只新增文件；对既有文件的改动必须落在 batchMode 块内或只是加带默认值的 prop。提交前用 git diff 逐条核；凡是无法说明「为什么不会影响单文件台」的行，不许合入。

闸 5 · 单一真值

「哪个模式」只能有一个真值来源

渲染形态只认视图传下来的 batchMode；禁止任何第二真值（编译期 featureFlag 常量、URL 参数、全局开关）能单独决定它。先例 ISSUES #151。

共享什么、不共享什么

共享纯函数（解析、合并、切片、覆盖率口径——无渲染副作用，抽出来不会影响任一工作台）；不共享 UI 组件（组件带渲染路径，共享就是让两台再次交汇）。

04阶段三 · 对抗式审查（对我自己这一轮的攻击）

#级攻击处置
D1🔴我前五轮的做法本身违反前提：一直在改共享组件（csv-step.tsx 的多选语义、buildRowsByLang()、review-step.tsx 的回写键）。加 batchMode 分支看着安全，但共用文件一改，单文件台就有被顺带改到的风险——共享组件正是两个工作台的交汇点形态从「改共享组件」改成「旁挂新组件 + 五道不变式闸」；csv-step.tsx 与 review-step.tsx 整份降级为「不动」
D2🟠「零改动」要不要连「共享组件加默认 prop」也禁掉？严格讲，加 prop 也是改这个文件判定：允许加带默认值的 prop，但默认路径必须逐字节等价（闸 3 能证明）；凡是需要改既有 prop 处理逻辑的 ⇒ 一律改成新组件。本轮已把两个共享组件降为「整份不动」
D3🟠「并排」会不会变成两个各自为政的产品？用户会遇到两套心智模型缓解：共享的是「概念」，不是「代码」——两台用同一套文案与术语（原文／译文表／语种／交付物）；代码不共享是因为共享代码正是顶替与串改的源头（仓库自己的注释就是这么写的）
D4🟡「两台逻辑一样」的部分要不要抽公共库？抽纯函数，不抽 UI 组件（组件带渲染路径，抽了就等于让两台再次交汇）
D5🟡「每稿一表 / N:M」这套，用户在单文件台怎么用？单文件台不需要：它就是「1 稿 : 1 表」的特例（来源矩阵是 1 行 12 格）。但按前提，这一版不在单文件台做这个——单文件台继续用现在那套「选表 → 语言 → 逐语言审查」
D6🟠闸 3 的快照比对会不会太脆（文案一改就红）？快照取结构与集合（节点数、按钮/文案集合、关键 DOM 路径），不取像素；只在批量台的改动不会让单文件台的集合变 ⇒ 不红。确实要改单文件台文案时，必须走 Owner 明令
D7🟡「不碰共享组件」会不会逼出大量重复、后期难维护？接受的代价，用闸 3 + 闸 4兜住：重复的是展示层，行为各由各的工作台负责，且重复面被限制在批量台专属组件内不扩散。若将来两边真要合并，前提（Owner 明令保留单文件台）也就不成立——那是另一个决策
