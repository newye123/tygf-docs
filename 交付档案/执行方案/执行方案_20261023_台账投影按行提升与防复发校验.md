## 0 一句话结论

> **把"全有或全无"的快照提升改成"只提升真正写成功的行"，并让被拦下的行不再把自己的"想写值"混进基准；同时在源头把非法日期格式挡在写盘之前。**
> 现在这套闸的失效方式不是写错数据，而是**一行坏数据让报警器永久停摆**——并且它"恢复"的那一刻，会把历史上所有被拦下的行变成假"人改过"。

## 2 改动清单（四个文件，按可独立合入的顺序排）

### C1 源头挡刀：账本日期列格式校验（最先合，零风险、纯增量）

**落点**：`scripts/control-plane.sh` 增一节（Owner 每早必跑，报"格式非法行"）＋ `scripts/sync-task-ledger.mjs` 在 `buildPayload` 前加一道行级校验。

- 规则：`kind==='time'` 的列必须匹配 `^\d{4}-\d{2}-\d{2}( \d{2}:\d{2})?$`；`kind==='date'` 的列必须匹配 `^\d{4}-\d{2}-\d{2}$`。
- 行为（关键）：**不合规只排除该行**，`summary.errors.push({taskId, col, reason:'格式非法'})`，其余行照常生成计划；退出码保持"有异常＝1"的语义，但异常从"整批炸"变"点名一行"。
- **不自动"修好"**（不擅自把 `20:1x` 静默降级成 `20:00`）：那是把占位字母伪造成实测读数，违反"日期列只写实测钟点"的既有纪律。降级必须是属主自己重贴。

**为什么先做这个**：它不改变提升语义，合进去就止住新的坏数据；且给 C2/C3 的测试提供"可控的坏样本"。

### C2 按行提升：pending 只用于筛，final 只收已证实写入的行（核心）

**落点**：`scripts/sync-task-ledger.sh:135-146`。不再新增 manifest 文件——exec log 里已经有逐行结果（`:298-304`、`:333-339` 生成的 echo 形如 `[ok] create <taskId>` / `[ok] update <taskId>`）。

新逻辑（伪码，等价 `newP = oldP ⊕ {pending[t] | t ∈ OK}`）：

```bash
OK_SET=$(grep -oE '^\[ok\] (create|update) [A-Za-z0-9._-]+' "$EXEC_LOG" | awk '{print $4}' | sort -u)
# 提升：以旧 final 为底，只覆盖 OK_SET 里的行；其余行保持原值；OK_SET 里没有的 pending 行一律丢弃
node scripts/promote-state.mjs --base "$STATE_FILE" --candidate "$STATE_PENDING" --ok-from "$EXEC_LOG" --out "$STATE_FILE.promoted"
[ -s "$STATE_FILE.promoted" ] && mv -f "$STATE_FILE.promoted" "$STATE_FILE"   # 原子替换，不直接 mv pending
```

- `scripts/promote-state.mjs`＝新增小工具（**~40 行、纯本地、不联网**）：读三个 ndjson，按 taskId 合并，打印 `promoted=N dropped=M kept_old=K`。
- 守卫三条：① `OK_SET` 为空 ⇒ **一律不提升**（防止解析形状变化导致"静默全量替换"）；② 提升前把旧 final 备份到 `tmp/readback/backup-<日期>/final-before-<时刻>.ndjson`；③ 只接受 `^\[ok\] ` 前缀行，任何 `[fail]` 的 taskId 若同时出现在 `[ok]` 里（理论不该发生）⇒ 拒绝提升并点名。
- 退出码不变：**有任何失败仍 exit 1**（让调用方知道没干净），但摘要多一行 `promoted=N/总计划K`，并新增 `连续失败点名`（见 C4）。

### C3 held 行不污染基准：把"透传旧值"变成显式语义

**落点**：`mjs:304/317/329/339` 四个 `snapshotRows.push`。

| 分支 | 现状 | 改成 |
|---|---|---|
| create（`:304`） | push L | 保留（由 C2 保证只有 `[ok]` 才被提升） |
| update（`:339`） | push L | 同上 |
| skip（`:329`，L==F） | push L | 保留（L 与飞书一致，等价于登记事实） |
| **held（`:317`）** | push L | **改 push 旧 P**（`state.map.get(taskId)`）；无旧 P ⇒ **不写进 candidate**，并把该 taskId 计入新字段 `summary.unbaselined`，wrapper 摘要里点名"N 行从未建立基准，需人工确认或 --force" |

这一改直接消灭 R4：被拦下的行不再带着"从没写进飞书的值"进基准，"恢复即中毒"的路径断掉。

### C4 可观测性：让"恒失败行"从第一天就可见

- wrapper：把 `[fail]` 行连同**该条命令的 stderr 尾部**一起落进 `EXEC_LOG`（现 plan 用 `|| echo [fail] …`，把 lark-cli 的报错吞在管道里）——改成 `|| { echo "[fail] …"; <复跑一次仅取 stderr 前 200 字>; }` 或 `2>>"$EXEC_LOG"`。
- 新增 `tmp/readback/failing.json`：`{taskId: 连续失败次数}`；每次跑更新（成功清零）。**连续 ≥2 次 ⇒ 摘要置顶一行**「⛔ 恒失败行：USAGE-LIMIT-TRIAGE（第 3 次，原因片段…）」。这就不再需要人来推断。
- 摘要里补 `promoted / unbaselined / failing` 三个新计数（向后兼容：只增字段）。

## 6 风险、回滚、影响面

- **最大风险**：提升语义改错方向 ⇒ "不该提升的被提升"。三道防线：`OK_SET` 为空不提升；提升前备份 final；`[ok]` 与 `[fail]` 同 taskId 并存时直接拒绝提升。
- **退化方向是安全的**：若 `[ok]` 解析形状变化（如 lark-cli 改 echo），最坏是"永远不提升"＝回到今天现状，**不会写坏飞书**。
- 不改：飞书表结构、字段权限、`STATUS_ENUM`、`update==--record-id` 闸、`--force` 的"显式强推"语义（本方案只让**单行**强推成为可能，见下待拍 O3）。
- 回滚：四个文件各自一笔，`git revert` 即可；基准有 `backup-20261023/`。
- 谁受影响：所有会话的投影（每天多次）。所以**先合 C1（只挡新坏数据）观察一天，再合 C2/C3/C4 并做迁移**——迁移必须在低并发时段（夜间），避免别的会话正好在写账本。

## 7 对抗式审查（对这份方案本身，Round 1）

| 攻击 | 结论 |
|---|---|
| "manifest 更干净，为何不新增一个字段文件？" | 否。exec log 已有逐行 `[ok]/[fail]`，再造一份就是两处真值；少一个可错点。**保持 grep 单一来源** |
| "L==F 才纳入基准，会不会把 Owner 手改的行漏掉，导致下次覆盖它？" | 不会。Owner 手改⇒F≠L⇒**不纳入**基准⇒下次仍按 `human-edit/conflict` 拦下；这正是我们要的行为 |
| "按行提升后，是不是就永远没人修那行坏日期了？" | 风险成立，所以 C4 的**连续失败点名**＋早晨体检是配套必做，不是可选。二者缺一，本方案只是把"卡死"变成"慢性病" |
| "为什么不直接 `--force` 一次解决？" | 否。`--force` 是全量覆盖（`:23` 原文），同批 held 含 Owner 手改行；用它打通知情，等于用事故换便利 |
| "迁移第 2 步要不要顺手把 held 行的 L 也写进基准？" | 否（这就是 R4）。**只写双证一致的** |
| "promote-state.mjs 是新工具，算不算工具膨胀？" | 它是 wrapper 里一段 bash 无法可靠表达的原地合并（跨三个 ndjson），且必须可单测；接受，但限定 ≤40 行、纯本地、无网络 |
| "C1 的严格正则会不会误伤合法写法（如带 T 的 ISO）？" | 会。故正则允许 `[T ]` 分隔；`normTime` 已容 ISO，校验也用同一口径，两处不许各定一套 |
| 覆盖缺口 | 没审 `feishu-readback.mjs`（回读闸）是否也假设"整批提升"；合入前需一并复核，否则早晨体检可能报假漂移 |
