# 网站慢的 A 方案：改了什么、能治多少、还有两处要你在 Cloudflare 点

**日期**：2026-10-25 · **范围**：`worktrees/develop` @ `cdc40807`（已推 `origin/develop`）· **生产站未动**

## 一句话结论

你拍的 A（改代码治标）里，能纯靠代码做掉的是 **A2 字体缓存**，已经改完并上了测试站；**A1（首页 HTML 进边缘缓存）和 A4（协议）必须在 Cloudflare 后台点**，我没有那两把钥匙；**A3（合 chunk）我否掉了**——算下来只省 2 个请求、0 字节，不划算。

但要说实话：**A 的天花板不高**。我实测到一个反直觉的数——**连 Cloudflare 已经缓存的 CSS，这条线路上也出现过 43 秒首字节和 60 秒超时**。也就是说，瓶颈不在"要不要回源"，而在"广州 → Cloudflare 边缘落洛杉矶（LAX）这跳，丢包 50%"。A 能把次数压下去，压不掉那一跳。

## 这次到底改了什么（A2）

`next.config.ts` 加了一条响应头规则，只作用于 `/fonts/*`：

```
Cache-Control: public, max-age=3600, stale-while-revalidate=86400
```

为什么这么写：

- 源站查到的是 `public, max-age=0` + ETag（Next 服务 `public/` 下静态文件的默认值）。`max-age=0` 的意思是"你先存，但每次用之前必须回来问我一声"。
- 于是 Cloudflare 边缘每次都回源做条件校验：实测 6 次请求里有 4 次 `cf-cache-status: REVALIDATED`；对照组 `/_next/static/*` 是 `HIT` + `Age 6566`。
- 一次页面加载要拉 5 个分片（共 406,956 B），**等于凭空多 5 次 LAX↔SIN 往返**——正撞在这条链路最慢的一段上。
- 字体分片文件名**不带 hash**（`public/fonts/shsc/manifest.json` 只记 sha256，文件名是固定的 `zh-subset-0..3.woff2`），所以不能像 `/_next/static/*` 那样给 immutable，否则以后换字体，用户会长期拿旧文件。
- 折中方案：**边缘 1 小时新鲜 + 1 天后台刷新**。字体更新最迟约 1 小时被边缘重新拉走，常规访问不再回源。

### 本地实测对照（生产构建 + 真服务，不是我猜的）

| 路径 | 改前 | 改后 | 说明 |
|---|---|---|---|
| `/fonts/shsc/zh-subset-0.woff2` | `public, max-age=0` | `public, max-age=3600, stale-while-revalidate=86400` | 本次目标 |
| `/fonts/zh-supplement.woff2` | `public, max-age=0` | 同上 | 第 5 个分片也覆盖到了 |
| `/_next/static/chunks/*.css` | `public, max-age=31536000, immutable` | 未变 | 对照组，证明没误伤 |
| `/`（首页 HTML） | `private, no-cache, no-store, max-age=0, must-revalidate` | 未变 | 见下节，故意不动 |

**首页 HTML 我一行没碰**。首页服务端要读 `draftMode()`、会话 cookie（`src/app/(zh)/page.tsx:32,35`）、功能开关，HTML 里带着登录态摘要。把这种响应做成可缓存，一旦边缘缓存没配好"带 cookie 就绕过"，就可能把 A 用户的登录态页面发给 B 用户。所以 HTML 缓存只能和 Cloudflare 规则**成对**上线，见后面 A1。

## A3 我否掉了，附否掉它的证据

原本想"合 chunk 减往返"。逐个量过之后：

- **字体全量预载不是浪费**：首页 585 个码位，落在全部 5 个分片上（分片命中数 155 / 179 / 173 / 76 / 2），`waste = 0`。想靠预载瘦身，没有可瘦的。
- **JS 没有肥肉**：线上 JS 一共 203 KB（gzip 后），最大两块各 73 KB 和 43 KB，是 React/Next 运行时本身；framer-motion 只被工作台用（`src/components/workbench/*` 六处），已经在懒加载包里，首页不下载。另外 HTML 里那个 40 KB 的 `noModule` 脚本是给旧浏览器的，现代 Chrome 根本不下载。
- **合 CSS 只省 2 个请求、0 字节**：三个 CSS 分别是 Tailwind 工具类 23.5 KB、首页 `.home-v17` 5.7 KB、字体 `@font-face` 3.4 KB（都是 gzip 后线上字节）。把它们并成一个文件，省的是 2 次 HEADERS 帧，字节一个不少；而且会把 9 KB 中文字体定义塞进英文站。

结论：**A3 不做**。真要减字节，只能动那 407 KB 字体（占全站 712 KB 的 57%），而那是产品要用的字符集，不是浪费。

## A1：首页 HTML 进边缘缓存——需要你在 Cloudflare 点（约 3 分钟）

**为什么必须你点**：这台机器上没有任何 Cloudflare 凭据。查过了——`CLOUDFLARE_API_TOKEN` / `CF_API_TOKEN` / `CLOUDFLARE_ACCOUNT_ID` 等在三处（User / Machine / Process 环境变量）都不存在；项目里唯一读它们的地方是 `scripts/configure-mail-routing.mjs:35-36`（邮件路由脚本），也没配。

**操作路径**：Cloudflare Dashboard → 选 `tuyigf.com` → **Rules → Cache Rules → Create rule**

- **Rule name**：`home-html-edge-cache`
- **When incoming requests match**（用 Expression Editor 粘贴）：

```
(http.request.uri.path in {"/" "/en"})
and not (http.cookie contains "tygf_user_session")
and not (http.cookie contains "__prerender_bypass")
and not (http.request.uri.query contains "_rsc")
and not (http.request.uri.query contains "edit")
and not any(http.request.headers["rsc"][*] eq "1")
```

- **Then**：
  - **Cache eligibility** → `Eligible for cache`
  - **Setting: Edge TTL** → `Ignore cache-control header and use this TTL` → **5 minutes**
  - Browser TTL 保持默认（`Respect origin cache-control`），这样浏览器那边仍然是"不缓存 HTML"

**每个排除项拦的是什么**（少一条就出事）：

- `tygf_user_session`（会话 cookie 名见 `src/lib/auth/session.ts:23`）：登录用户的下发 HTML 里有他的登录态摘要，**绝不能进公共缓存**。
- `__prerender_bypass`：运营台"就地直改"的草稿会话 cookie（`src/app/api/admin/site-content/edit-mode/route.ts:1`），带它的人要看到草稿，不是线上版。
- `_rsc` 查询参数 与 `RSC` 请求头：App Router 的客户端导航取的是 RSC 数据流，不是 HTML；两者共用同一个 URL，不排除的话点站内链接可能拿回一整页 HTML。
- `edit`：`?edit=1` 就地编辑入口。

**上线后怎么验**（你在浏览器或让我跑都行）：

1. 无痕窗口开 `https://tuyigf.com/` 两次，第二次响应头应出现 `cf-cache-status: HIT`。
2. 登录后刷新，应仍是 `BYPASS` / `DYNAMIC`（说明会话没被缓存）。
3. 站内点几个链接，页面要正常跳转（说明 `_rsc` 排除生效）。

**副作用**：你在运营台改完文案，最多 5 分钟后才对访客生效；要立刻生效就在 CF 后台点一次 Purge。

## A4：我上一版方向说反了，这里更正

上一版报告里我写"关 h3"，实测后确认**说反了**：

- 真浏览器现场：23 个资源**全部跑 h2**（`nextHopProtocol: h2`），刷新后仍是 h2。
- h2 在这条 50% 丢包链路上是"整条连接一起卡"：实测 8 个 JS chunk 同时 t=11.4 s 发起、同时 t=134.3 s 才拿到首字节，整批 263.5 s，页面 `readyState` 一直停在 `loading`。这就是 h2 队头阻塞的指纹。
- 便携实测对照：同一台机器、同一目标，**h1 五次里成三次（3/5），h2 五次全败（0/5）**。
- 服务端侧 `alt-svc: h3=":443"; ma=86400` 是 Cloudflare 注入的（直连源站没有这个头），说明 **h3 对我们这个域名是开着的**，只是浏览器这段链路上没跑起来（大概率是本机/联通拦了 UDP 443，或浏览器没启 QUIC）。

**所以 A4 的正确动作不是关，而是确认 h3 可用**：CF → **Speed → Settings → Protocol Optimization**，看 `HTTP/3 (with QUIC)` 是否 On（大概率已经是 On）。同时有个坏消息：**"关掉 HTTP/2、退回 h1.1 隔离丢包"这条路免费版走不通**——Cloudflare 官方文档明写"Domains on Free plans cannot disable Cloudflare's HTTP/2 setting"。

**A4 的验证只能换网络做**：拿手机热点（非联通）或不挂代理的另一条线路开一次站点，看 `performance.getEntriesByType('navigation')[0].nextHopProtocol` 是不是 `h3`。如果是，说明是本机联通拦 QUIC；如果那边也还是 h2，就得在 CF 后台确认 HTTP/3 开关与 QUIC 端口。

## 说实话：A 的天花板在哪

这轮实测里最该记住的一个数：

| 请求 | 期望 | 实测 |
|---|---|---|
| `/_next/static/chunks/05noaa5fb1i77.css`（CF **已缓存**，HIT） | 快 | 3 次里 1 次 43.2 s 首字节、2 次 60 s 超时 |
| `/fonts/shsc/zh-subset-0.woff2`（REVALIDATED，要回源） | 慢 | 60 s 超时 / 48.8 s / 5.07 s |
| 源站直连（不经 CF）同文件 | — | 1.01 s 首字节、2.5 s 下完 80 KB |

**已经命中的缓存也要 43 秒**，说明 A 类"减少回源"的动作只能治到一部分；真正致命的是广州联通到 LAX 那跳。这就是 B 方案（换边缘/换线路/换 CDN）的事，做不做由你定。
