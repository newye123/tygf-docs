## 3. 三条路线与决策

| 路线 | 做法 | 判定 |
| --- | --- | --- |
| **A 真实 app 逐帧采集 + 合成器运镜**（demo-video-skill 架构） | Playwright 驱动运行中的工作台，每步截一帧；相机/光标/脉冲/字幕在合成阶段叠加 | ✅ **主干**：演示段全部走这条 |
| B 场景 JSON 实时录制（silky-recorder） | 场景脚本 + headless 实时录 | ⚠️ 只借它的**脚本格式与遮罩字段**；实时录不满足 D3 |
| C 组件工程浏览器挂载 + 派发真事件 | 在现有视频工程里 client-mount 真组件，用 `dispatchEvent` 驱动状态机 | ❌ 不用于演示段：没有后端与真异步，本质仍是"看起来像"。只保留**片头字卡与落版** |

决策记录：
1. **演示段 = 路线 A**，宣传段保留 C 的字卡。
2. **场景脚本用 silky 的 `meta + steps` 形状**，落到 `demo/scenario.json`，与我们既有 `plan.json` 并存不冲突。
3. **合成器用 Node 自研**（Playwright 截图 + ffmpeg 叠加 + SVG→PNG 矢量光标），不引入 Python/Pillow。理由：这台机 `python/python3` 是商店占位、pip 不在 PATH（只有 `py`），再叠一套图像依赖会让复现成本上升；而运镜规范是**与语言无关的常量**，可以直接照搬。风险与缓解见 §9 攻击 8。
4. 复用上游代码时保留 MIT 许可与出处，写入 `demo/NOTICE.md`，不把借来的东西当自研。

## 6. 合成与运镜规范（照搬 demo-video-skill 的实测结论）

1. **相机与光标解耦**：相机对准稳定区域，动作在里面发生；跟鼠标走=抖。
2. **一个镜头只放大一次，然后稳住**：用 `fit_zoom([...], hi=1.75)` 上限；**1.5–1.9×** 最耐看，宁小勿大。
3. **换镜后留 ~20 帧让相机落定**（EMA 0.11/0.13 实测够）。
4. **结尾 zoom out 到 1.0 再停一拍**，不硬切。
5. **`still` 与 `hold` 分清**：页面静止只有相机在动 → 一帧代表 n 帧；**应用自己在动（点击过渡、spinner、拖拽、检测结果出现）必须连拍 live 帧**——产品大量用 framer-motion，用 still 会把动画冻住。
6. **长等待密采后压**：PSD 扫描大文件常态 >3 分钟（`design-file-card.tsx:44-46` 注释），12 语言执行更久。按 ~40ms 间隔密采，后期用 speed region 压缩，**并在画面上如实标"已加速"**；不要为了省事在采集端跳帧——跳掉的帧回不来。
7. **速度要读得完**：拖拽 1.2–1.5 秒，动作前后各留一拍，重点指示器多停。
8. **采全视口**，让画面读起来是"真的在用一个 app"，靠相机推近而不是裁掉界面。
9. **绝不放大 app 自己的画布**（Ctrl+= / 滚轮）——脏且逼你重拍。

字体分工写死以免误会：**演示段用 app 自己的字体栈**（Segoe UI / 微软雅黑，产品内部设计不动）；**思源黑体只用于宣传字卡与落版**（工程内已冻结）。
