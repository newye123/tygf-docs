# 本地助手整改：开源参考、复核结果与执行沙盘

（更正：上一版卡片把外部参考概括成三件，实际是四类六条，以此版为准。）

这轮我把 GitHub 和公开资料翻了一遍，也把上一版方案逐条拿回自己的代码里对了一遍。结论先说：外部真正能用上的参考有六条，归成四类；最该点名拒绝的是三件。但真正该先动手的，是我们自己代码里回读出来的三个问题。

对您意味着什么：客户端的程序一定会被读懂，这是所有桌面软件的共同处境，不是我们独有的漏洞。所以钱不能押在"把代码藏起来"，要押在"就算读懂了，也改不了结算"。

## 自己代码里的三个问题

第一，空证据也能收费。云回执只发一个摘要，不发被检查的对象清单；服务端拿不到可重算的输入，只能看"摘要是不是非空"。而空清单算出来的摘要是 4f53cda1 开头的一串合法值，非空，所以一个被改过的客户端发这个值、再加一行"已完成"，就能进入结算。这条比上一版方案判得更重：不是服务端懒得算，是它没有东西可算。

第二，没有 beta 这条路。代码里只有"允许未签名测试版"的开关，它放行之后照常写生产清单，只把状态标成"未签名"。所以删掉一个开关不够，必须先把目录和清单隔离出来，让生产路径无条件拒绝未签名包。

第三，配置读不到时会被覆盖。启动时配置读失败就退回默认值，然后存一次盘；而保存前的备份顺序是"先删旧备份、再改名"，一次失败就把最后一份好配置丢了。另外"只读启动"这个说法也不成立——程序读到备份时会主动把备份复制回当前文件，所以验收要写成"备份文件的哈希不变"，不能写"任何文件都不动"。

## 外部能用上的参考：四类六条

授权按进程身份号（SID）走，不按用户名。域账号和同名本地账号并存时，按名字会锁到错的那个人，客户表现为配对一直失败。

Inno Setup 的四个签名位加时间戳：安装包、内层引擎、托盘程序、卸载器一次覆盖；带时间戳之后，证书过期了旧安装包仍然有效。

回执用事务性 outbox 加墓碑：确认收下之前先留一个"已结算"标记，重启恢复时先查这个标记，就不会把已经成功的批次重新数成"未知"。

本地 HTTP 补三样：Host 白名单、Private Network Access 响应头、Vary: Origin。现在只校验了请求来源，少了一道纵深。

## 看着能用、但这轮不抄的三件

DPAPI 或系统凭据加密：同一个用户下的其它进程仍然能解密，等于把"文件读不了"换成"换电脑或改密码后解不开"，故障更难查。

SQLite：我们的打包目标是 Node 18，内置的 SQLite 模块不在里面；单文件状态也用不上数据库。

混淆、加壳、反调试：公开的逆向工程已经证明收益很低，还会伤我们自己的排障能力。

## 执行顺序

顺序不能换：先核对客户机身份（版本号和构建号对不上，先升级，别在旧引擎上修新问题），然后 ACL 按 SID 授权加启动自愈，再改状态机与备份顺序（这两件必须同一次发布），接着做发布闸隔离与签名，再做回执墓碑，然后是证据重算，最后补本地 HTTP 边界和文档取舍。

其中证据重算优先级最高，它决定"被改过的客户端能不能白拿钱"。发布闸的代码这周可以落，证书什么时候到位我不做承诺——证书没到之前，生产发布保持失败关闭。

## 逆向工程那件事

Melee 的 matching decompilation 项目有 2,440 星，10 月 16 日还在推进；PS2Recomp 3,657 星；PS5 翻译层 KytyPS5 9,643 星，都是 10 月 23 日取的数。机理是三件事：静态重编译把机器码翻回可读源码，matching 用编译器当验证器，AI 把读二进制的单位成本打下来。

对我们的三条结论：护城河不在客户端；判定权必须在服务端；分发完整性靠签名，内容可信靠重算。反过来也有收益：公开实现变多，可以读行为、做对标，但许可不明的代码不复制进产品。

配套做了一个可点的沙盘，六个场景：同名账号 ACL、配置读不到、回执误报未知、伪造来源、未签名发布、空证据过闸。每个都能切"旧行为/新行为"看差别，另有 19 张参考决策卡和一张依赖顺序图。它模拟的是行为，不是真机读数，但每条都能对到代码行。
