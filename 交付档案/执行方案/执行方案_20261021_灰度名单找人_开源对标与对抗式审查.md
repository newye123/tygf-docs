# 灰度名单"找不到人"怎么修：开源对标 + 对抗式审查 + 执行方案

日期：2026-10-21　｜　对象：运营台「字体排版定制灰度名单」卡　｜　结论档：有条件放行 B 案，判死 C 案

## 一句话结论

问题不在"报错文案写得不好"，在于**这张卡只让人手填内部用户 ID，而全站没有任何一个地方能看到这个 ID**。修法要按"先让人找到人、再让他点选"来改，不是按"让后端猜邮箱"来改——我本来想提的后者，被自己这轮的实测数据判死了。

## 这轮先说清楚：为什么"直接收邮箱"不能做

我原本的建议是：输入框邮箱和 ID 都收，后端把邮箱解析成 ID 再存。听起来顺，实测三处全塌：

- **邮箱在库里的覆盖率只有 10/68。** 生产站 68 个内测用户里，只有 10 个有邮箱凭证（EmailCredential 表，邮箱唯一且已小写化）。剩下 58 个人**没有可用的邮箱**。测试站 38 人里只有 4 人有。也就是说收邮箱这条口子，对八成账号根本不起作用。
- **BetaUser 上那个看起来像邮箱的字段（contact）是自由文本，且没有唯一约束。** 生产站 68 人里 **54 人这个字段是空的**，另有 **8 个人的值是 "sw"**（不知道谁随手打的）。同一个值能命中多个人，后端就没法"唯一解析"，只能猜——猜错就是把面板开给了错的人。仓库自己的测试夹具（`scripts/smoke-feature-flag-whitelist.mjs:41-51`）里两个用户用的是**同一个 contact**，等于已经把这个歧义写死在盘上了。
- **大小写会静默查不到。** SQLite 的等值比较是大小写敏感的（实测 `'ABC' = 'abc'` 返回 CASE_SENSITIVE；拿 `FREEDESIGNYES@GMAIL.COM` 去查真实数据得 0 行，小写才得 1 行）。你手打的邮箱只要有一个字母是大写，就会得到"用户不存在"，而且**永远不会有人告诉你为什么**。

三条合起来：让后端猜邮箱，是把一个"界面不好用"的问题，换成一个"可能把内测面板开给错的人"的问题。后者更贵。

## 开源上别人怎么解这个问题

看了 6 个成熟实现（Unleash/GitLab、GrowthBook、LaunchDarkly、Flagsmith、PostHog、Django admin），它们在这个坑上高度一致，可以归纳成三条：

1. **名单里存的永远是"应用自己定义的稳定标识"，不是邮箱。** Unleash 的 `userWithId` 策略收的是逗号分隔的任意字符串，但它明确要求"这个 ID 必须等于 SDK 调用时传进去的 context.userId"；GitLab 文档里的示例甚至直接用邮箱当 ID（`user@example.com`）——因为它压根不规定 ID 长什么样，只规定"两边必须一致"。LaunchDarkly 更直接：上下文的 `key` 要用稳定、非敏感的内部标识，邮箱只是"属性"之一，并且明说客户端规则不能承担真正的授权控制。→ 我们现在"存 ID、服务端 fail-closed 判定"的形状是对的，不该动。
2. **人填的是"标签"，机器存的是"键"——这两件事在界面上分开。** 这就是 Django 后台的 `raw_id_fields`（让你直接填主键）和 `autocomplete_fields`（让你搜人话、表单仍然提交主键）的区别，后者要求被关联的模型声明 `search_fields`。GrowthBook 的做法是"先选属性（id / email / country / plan），再选操作符，再填值"，把"你在按什么找人"这件事显式摆在界面上；它的 ID 输入框还是个多选控件，你敲进去的陌生值直接变成一枚标签而不是报错。PostHog 的发布条件里，值选择框会**拿真实用户值做候选**。→ 我们要的正是这个：把"手填 ID"换成"搜人 → 点选 → 存 ID"。
3. **可复用的命名名单，而不是每次现粘。** GitLab 有"用户列表"对象（先建一个有名字的列表，功能开关引用它），GrowthBook 有 Saved Groups（条件里直接引用组）。→ 对 100 人规模的内测名单是过度设计，这轮不做，记在"以后再说"里。

## 对抗式审查输出（审的是我自己刚提的方案）

```
VERDICT: 有条件放行（B 案可做；C 案打回）
范围: worktrees/develop@0510572 工作树（含未提交现场，未触碰）| Round 1/3
改动: 0 个文件（本轮只做调研与审查，未改代码）
已证实: 9 条（Important 6 / Nit 2 / Pre-existing 1）
未决: 3 条
覆盖缺口: 见末节
```

已证实的缺陷（ID 简写，严重度）：

- **F-101（Important）界面拿不到 ID，等于功能不可用。** 名单卡保存后才回显 `姓名 · ID`（`settings-panel.tsx:1040-1045`），而用户列表只有按钮（`installs-credits-panel.tsx:350-358`）、360° 详情全文没渲染过 userId。唯一能看到 ID 的地方，前提是你已经知道 ID。
- **F-102（Important）"收邮箱"的解析源不可靠。** 见上节三条实测（`EmailCredential` 覆盖 10/68；`BetaUser.contact` 54 空 + 8 个 "sw"、无唯一约束 `schema.prisma:57-70`；等值比较大小写敏感）。
- **F-103（Important）粘贴切分只认换行。** `settings-panel.tsx:432-435` 用 `split('\n')`，中文逗号、分号、空格都不切；后端也只 `trim()`（`feature-flags-store.ts:201`）。从别处复制一串邮箱进来，会被当成**一条**。
- **F-104（Important）保存后 textarea 会被服务端返回值整块覆盖。** `settings-panel.tsx:439` 把返回值里的 id 拼回输入框；若某条被后端丢弃，行数会**静默变短**，没有任何差异提示。
- **F-105（Important）新增后台路由必撞安全守卫。** `scripts/smoke-admin-security.mjs:323` 断言 `extraRoutes` 为空数组——只要新加一条 `/api/admin/*` 而没同步补门断言，门直接红。**这条决定了 B 案必须复用现成接口，不要新建查找路由。**
- **F-106（Important）名单改动不可追溯。** 六处保存一律 `writeAuditLog(session,'feature-flags.save',null,null,req)`（`route.ts:75/91/102/113/125/135`），审计只落动作不落内容（`schema.prisma:37` 明确边界），名单只有一行当前值、无历史表。"谁把哪个账号加进生产灰度"事后查不到。
- **F-107（Nit）错误文案把"字段用错"说成"人不存在"。** `route.ts:69` 原样回显提交串，读起来像账号丢了。
- **F-108（Nit）卡片文案在生产运营台上指路测试站。** `settings-panel.tsx:1034` 那句"名单内账号在测试站…可见"，在 ops.tuyigf.com 上是误导（判定不看环境，`feature-flag-gating.ts:11-24`）。
- **F-109（Pre-existing）名单是盲写整体覆盖，无并发保护。** `feature-flags-store.ts:237-244` 无 CAS、无 etag，`updatedAt` 只写不比；两个标签页各改一份，后保存的吃掉前一个。不是本次引入，但 B 案要在同一张卡上动手，顺手记一笔。

未决（还缺什么证据）：

- **U-1** 复用 `/api/admin/installs?q=` 做搜索，单次响应要跑多少 SQL、点一次搜索框多少毫秒——没量。缺：真实浏览器计时。若超过 300ms 要加最小延迟与取消。
- **U-2** 把被丢弃的行显示成差异，会不会与"过程性清单全部撤下"的产品口径冲突（Owner 定过：界面只留三类告知）。缺：Owner 一句话。
- **U-3** 审计里到底能不能落"变更的 ID 列表"。缺：Owner 对 `schema.prisma:37` 那条边界的解释（ID 算不算"业务正文"）。

## 建议怎么做（三档）

**A 档 · 只改文案（半小时，治不了病）**：把提示改成"这里填用户 ID（形如 `cms68etxy…`），不是邮箱；不知道 ID 就去用户列表点 360° 详情"——但详情里现在也不显示 ID，所以 A 档等于把人指向一个没有答案的地方。**不推荐单做。**

**B 档 · 卡内加"按邮箱/姓名找人 → 点选入名单"（推荐，1 个前端文件 + 1 处文案）**

- 名单卡上方加一个搜索框：输入邮箱、姓名、公司或 ID，直接调**现成的** `/api/admin/installs?q=`（它已经按 姓名 / 邮箱凭证 / 联系方式 / 公司 / 用户 ID / 邀请码 / 项目名 搜，见 `api/admin/installs/route.ts:113-127`，返回体含 `userId`、`email`、`name`、`userStatus`，见 `:334-340`；鉴权与这张卡同一个 owner 门 `:86`）。**不新建路由，F-105 自然不触发。**
- 结果每行显示「姓名 · 邮箱或联系方式 · 状态」，右侧一个「加入」按钮；点一下把这个人的 **userId** 追加进输入框（存的一直是 ID，服务端形状一字不改）。
- 输入框保留可手填 ID（高级路径），但切分改成"换行 + 逗号 + 分号 + 空格"都切（治 F-103）。
- 保存前给一行"将保存 N 人 / 其中 M 条不是有效 ID，已标出"的**单行摘要**，不铺清单（治 F-104 的静默变短，且不违反"过程性清单撤下"的口径）。
- 卡片标题旁加环境徽标：**生产 / 测试**。数据源现成，不用新代码：服务端有 `profileEnvironment()`（`src/lib/server/profile-identity.ts:3-10`），免鉴权的 `/api/runtime-provenance` 已回 `environment` 字段（`api/admin` 侧同理可直接读）。治 F-108。
- 错误文案改成"这些账号在库里找不到：X、Y（这里要的是用户 ID，可用上方搜索按邮箱找人）"。治 F-107。

**C 档 · 后端收邮箱自动解析（打回）**：F-102 三条实测任一都足以否决。若将来非做不可，前提是先补两件事——给 `BetaUser.contact` 加唯一约束并清干净存量脏值，以及把 `EmailCredential` 覆盖率提上去。这两件都不是这张卡该顺手带的。

**顺手可做的两件小的（各一行，建议一起做）**

- 360° 详情头部把 userId 显示出来并给个复制按钮（F-101 的另一半，纯展示）。
- 名单保存的审计里带上"人数"（不带邮箱、不带正文），至少事后知道规模（F-106 的最低成本缓解）。

## 执行序与验收尺（可复跑）

1. 先跑基线留底：`npm run test:feature-flag-whitelist`、`npm run test:admin-security`、`npm run test:assistant-device-policy`，三条退出码抄进台账。
2. 改 `settings-panel.tsx`（搜索选人 + 切分 + 摘要 + 徽标 + 文案）与 `route.ts` 的错误文案，**不动** `feature-flags-store.ts` 的存取形状、不动 `feature-flag-gating.ts`。
3. 给守卫脚本补 4 条断言（写进 `smoke-feature-flag-whitelist.mjs`，因为 F-101/F-103 是它的覆盖面）：① 名单里存的仍是 ID 数组（等值不变）；② 含中文逗号/分号的输入被切成多条；③ 未知条目的错误文案同时含"用户不存在"和"用户 ID"两个关键字；④ 负控：故意塞一条 65 字符的串必须仍被拒。
4. 类型与静态门：`npx tsc --noEmit`、`npm run lint`。
5. 真机验收（浏览器实测，两站各一遍）：搜索自己邮箱 → 点选 → 保存 → 徽标显示姓名·ID → 刷新仍在；**负控**：搜索一个不存在的邮箱必须显示"无匹配"而不是报错。
6. 部署纪律：B 案**不碰**计费/回执/行排除语义，不触发合同变更四层；但按发布线规矩，测试站先上、复验通过才谈生产。
