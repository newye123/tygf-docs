# 执行方案：Node.js 22.23.4 安全升级与系统安全更新

日期：2026-10-22
授权：Owner 本会话直述「使用对抗式审查看看然后给我执行方案，最后按方案执行」
对象：生产站 tuyigf.com（systemd）与测试站 test.tuyigf.com（pm2），两站同机
风险档：High（生产运行时 + 系统包 + 主机重启）

## 一、对抗式审查结论

VERDICT：有条件放行
范围：本方案涉及的 Node 运行时、系统安全更新、自动更新配置；Round 1/3
改动：运行时目录替换 1 处；系统包 254 个（含内核）；自动更新配置 1 处；不改业务代码
已证实：6 条（Important 5 / Pre-existing 1）
未决：3 条（每条注明还缺什么证据）
覆盖缺口：未做漏洞利用验证、未做全链路业务回归、未核其他服务器、未做入侵痕迹排查

### 已证实

1. 两站共用同一个运行时路径，替换会同时影响生产和测试。证据：`/etc/systemd/system/tygf.service` 的 `ExecStart=/opt/tygf-node-v22/bin/node ...`；`pm2 describe tygf-test` 的 `script path` 同样是 `/opt/tygf-node-v22/bin/node`。另有 `tygf-auth-mail`、`tygf-smart-review` 两个常驻 systemd 服务和 8 个 `tygf-*` 单元引用该路径。处置：保留旧目录，版本化安装后用同名软链接切换；切换前停服务，切换后逐个验 `/proc/<pid>/exe`。

2. PM2 把 Node 二进制本身当作 `script path`，只改 PATH 或环境变量不会生效。证据：`pm2 describe tygf-test` 显示 `script path /opt/tygf-node-v22/bin/node`、`interpreter none`。处置：切换软链接后执行 `pm2 save` → `pm2 kill` → `pm2 resurrect`，让三个测试站进程用新二进制重新拉起；核每个进程的 `/proc/<pid>/exe`。

3. 主机重启是内核生效的必要步骤，重启后能否自动恢复取决于 enablement 和 PM2 dump。证据：`systemctl is-enabled tygf`、`nginx`、`pm2-ubuntu` 均为 enabled；`/home/ubuntu/.pm2/dump.pm2` 存在（11:08）；`tygf-auth-mail`、`tygf-smart-review` 为 enabled。处置：重启前再跑一次 `pm2 save` 和 enablement 检查；重启后逐项验收，不把「服务应该会起来」当证据。

4. 新内核是新包名，普通 `apt-get upgrade` 可能把它留下；`dist-upgrade` 才保证装上，但可能带来删除。证据：模拟 `upgrade --with-new-pkgs` 与 `dist-upgrade` 都是 254 个 Inst、0 个 Remv，且都包含 `linux-image-generic 6.8.0-124 → 6.8.0-147`。处置：用 `upgrade --with-new-pkgs`，执行前再模拟一次并核对删除数为 0；保留旧内核，异常时可从 GRUB 回退。

5. 自动更新服务一直在跑，但没有覆盖安全仓。证据：`/etc/apt/apt.conf.d/50unattended-upgrades:8` 的 `-security` 行被注释；`/var/log/unattended-upgrades/unattended-upgrades.log` 的 `Allowed origins are: o=Ubuntu,a=noble`；`apt list --upgradable` 中 158 个来自 `noble-security`，上次 apt 动作是 7 月 28 日。处置：备份配置后只放开 `-security`，保持 `Automatic-Reboot` 为 false；用 dry-run 验证。

6. 磁盘余量够但不宽裕。证据：`/` 40G、已用 33G、可用 4.9G（88%）；旧 Node 目录 204M。处置：升级前确认可用空间不低于 3G；升级后清理 apt 缓存可回收空间，但不在本轮删旧运行时或旧内核。

### Pre-existing（不算本次引入）

7. `tygf-test-photoshop-reconcile.service` 在本轮之前就是 failed。证据：`systemctl list-units "tygf*"` 显示该单元 `failed`，其余常驻单元 active。处置：本轮不修它，也不把它记成本次升级的红；重启后如果仍是 failed，按存量问题登记。

8. PM2 CLI 和守护进程用的是系统 `/usr/bin/node` v20.20.2（已 EOL），但测试站业务进程显式用 `/opt/tygf-node-v22/bin/node`。证据：`command -v pm2` → `/usr/bin/pm2`，shebang `#!/usr/bin/env node`；`node -v` → v20.20.2。处置：本轮不动系统 Node，避免扩大写入面；登记为后续独立项。

### 未决

9. Node 十月安全公告里的 Brotli 越界写（CVE-2026-111497）是否会被我们的请求路径实际触发，未验。缺的是对本应用请求体解压路径的逐条审计和受控利用验证。结论只写到「运行时落后一个安全版本，必须补」，不写到「已被利用」。

10. 系统安全更新里是否有会改变服务行为的包（例如 OpenSSL、systemd、nginx 依赖），未逐包评估。缺的是逐包 changelog 审阅；本轮用「旧内核保留 + 服务验收 + 回滚路径」控制风险。

11. 其他服务器是否也跑着旧 Node 或有 PHP，未核。缺的是资产清单；本方案只覆盖 tygf-server 这一台。

### 覆盖缺口

没有做业务全链路回归（上传、报价、执行、回执），没有做压力测试，没有做入侵痕迹排查，没有做整机快照。以上都不写成「已验证」。

## 二、执行步骤

### 阶段 0：预检与备份

1. 记录当前状态：两站健康、provenance、Node 版本、内核版本、pm2 列表、systemd 失败单元、磁盘、apt 模拟结果。
2. 建备份目录 `/var/backups/tygf-security-20261022/`；备份生产库 `custom.db`（13M，sqlite3 在线备份或停服后复制）、`50unattended-upgrades`、PM2 dump、`dpkg --get-selections`、systemd 单元清单。
3. 下载 Node v22.23.4 linux-x64 官方 tarball，核对 SHA-256：`1805bcd35e6815559bd2eb97db438d3fdb0eb3a5e6a977b7c1badca76337e9ce`；再从腾讯镜像核对同一行，两个来源一致才继续。
4. 解压到 `/opt/tygf-node-v22.23.4`，不覆盖旧目录；跑 `bin/node -v`、`process.versions.modules`、`process.versions.openssl`，确认版本为 v22.23.4 且 modules 仍为 127（与旧版一致）。
5. 再模拟一次 apt：`upgrade --with-new-pkgs` 的 Inst 数、Remv 数、是否含新内核；Remv 不为 0 就停下重新评估。

### 阶段 1：Node 运行时切换

1. 停四个每 10 分钟运行的 reconcile timer，避免切换窗口内竞态。
2. 停生产 `tygf`、`tygf-auth-mail`、`tygf-smart-review`；停测试 PM2 三个应用。
3. 备份并切换：`/opt/tygf-node-v22` 改名为 `/opt/tygf-node-v22.23.2`，新建软链接 `/opt/tygf-node-v22` → `/opt/tygf-node-v22.23.4`。
4. 启动生产三个服务；测试站执行 `pm2 save`、`pm2 kill`、`pm2 resurrect`；恢复四个 timer。
5. 验收：三个生产服务 active；三个测试应用 online；两站 `/api/runtime-provenance` 仍为 BOUND（生产 319bc13、测试 8d81d877）；`/proc/<pid>/exe` 指向新目录；`/` 与 `/download` 返回 200；日志无启动错误。
6. 任一项失败：停服务，删软链接，把 `/opt/tygf-node-v22.23.2` 改回 `/opt/tygf-node-v22`，按原顺序启动，记录回滚证据。

### 阶段 2：系统安全更新

1. `apt-get update`；再次模拟并记录 Inst/Remv/内核三项。
2. 用 `DEBIAN_FRONTEND=noninteractive NEEDRESTART_MODE=l apt-get upgrade --with-new-pkgs -y` 执行，完整日志落到 `/var/log/tygf-security-updates-20261022.log`。
3. 验收：`dpkg --audit` 为空；`apt-get -s upgrade --with-new-pkgs` 剩余 Inst 为 0；新内核 6.8.0-147 已安装；旧内核仍在。
4. 备份后修改 `/etc/apt/apt.conf.d/50unattended-upgrades`：只取消 `-security` 的注释；确认 `Automatic-Reboot` 为 false；跑 `unattended-upgrade --dry-run -d`，确认允许来源包含 `noble-security`。
5. `pm2 save`；重启前再验一次两站健康。

### 阶段 3：主机重启

1. `sync`；确认 `tygf`、`tygf-auth-mail`、`tygf-smart-review`、`nginx`、`pm2-ubuntu` 均 enabled；确认 PM2 dump 是刚保存的。
2. 重启；等待 SSH 回来（上限约 90 秒）。
3. 验收：内核 6.8.0-147；两站健康与 provenance；Node 进程 exe 指向 v22.23.4；pm2 三个应用 online；`systemctl --failed` 只允许出现重启前就 failed 的 `tygf-test-photoshop-reconcile`；安全更新剩余为 0。

### 阶段 4：记账与交付

1. 写执行报告（md + HTML），附命令回显摘要、时间、版本、剩余风险。
2. `AI_MEMORY/TASK_LOG.md` 置顶追加；`ledger.jsonl` 追加一行并投影；`ISSUES.md` 只登记存量 failed 单元和系统 Node 20 两项，不把已修项写成新问题。
3. 飞书发送执行方案与执行报告。

## 三、回滚方案

Node：停服务 → 删 `/opt/tygf-node-v22` 软链接 → 把 `/opt/tygf-node-v22.23.2` 改回原名 → 启动服务；旧目录全程保留。
内核：GRUB 里保留 6.8.0-124；如新内核起不来，从云控制台进 GRUB 选旧内核。
系统包：没有整机快照，逐包降级不作为首选；优先用旧内核 + 服务回滚。这个限制在报告里明写。
自动更新配置：恢复备份文件即可；该配置在下一次 timer 运行时才生效，不需要重启服务。
