# 执行方案：本机可用内存不足时「不投下一稿」——对抗式审查与落地

## 1. 被审的两个提案

- **A（原口述版本）**：每份稿子处理完，读一次系统可用内存；低于线就不再投下一稿，界面如实说明。

A 是我上一轮口头给的，挂点说错了，本轮第一个要审的就是它。

## 2. 对抗式审查结论（先证伪再下结论）

### F-A1｜Important｜我上一轮的说法被推翻

- 原说法：「挂点已经现成——`server.js:7458-7462` 那里本来就在解析 `ASSIGNMENT_DONE 3/27`，可以在那里判内存」。
- 反证（本会话实测行号）：`ASSIGNMENT_DONE` 是执行器脚本**自己**在 PS 进程内的循环里打的进度行——`scripts/TYGF_V15_Thin_Executor.jsx:184` 是 `for (var index = 0; index < assignments.length; index++)`，`:222` 打 DONE；Node 侧只是 tail 读进度（`server.js:1769-1778` `readProgressLog`、`:1971-1980` 每 `PS_PROGRESS_POLL_MS = 1000` 轮询），读到之后唯一动作是发心跳与写诊断（`server.js:7462-7464`）。**它手里没有「投不投下一稿」这个决定权**，下一稿的执行动作还在同一个 JSX 循环里继续跑。
- 新结论：真正的稿件边界是**一次 HTTP 受理**——浏览器按语言逐个派发（`src/lib/workbench/v3-batch-flow.ts:387` / `:524` 每语言一次 `deps.executeLanguage` → `src/lib/workbench/local-assistant-client.ts:1856` `POST /v1.5/batch/execute`），一个 attempt 对应一种语言。闸要做在助手受理入口，不是进度解析处。

### F-A2｜Important｜「中途优雅停手」不存在，只能硬杀，硬杀即进人工救援态

- 证据：`TYGF_V15_Thin_Executor.jsx` 全文件只有三处 `.exists`（`:22`、`:177`、`:240`），信封 `readJson(envelopeFile)` 在循环**之前**只读一次（`:172`）；循环体内 4 处 `return`（`:190`/`:196`/`:203`/`:212`）全是「这稿数据不对，关掉自保」，**没有任何外部标志文件、配置或超时判断**。Node→JSX 没有反向通道：Node 唯一的写盘发生在 launch 之前（`v15-runner.js:204` `atomicJson(envelopePath…)`）。
- 唯一的停止手段是 `server.js:1893 requestExecutorStop` → `:1904 taskkill.exe /F /T /PID`（只杀 wscript 树，注释 `:1901` 明确绝不杀 Photoshop）。被杀后 `executionExitConfirmed !== true`，`:2068-2076` **故意不 resolve**（注释原话：WScript 退出不能证明 COM 动作已停），走 `handleUnconfirmed` → `markBusyRecoveryRequired`（`:2411-2441`，落盘 `.tygf_executor_recovery.json`），此后 `setBusy(true)` 直接抛 `ASSISTANT_RECOVERY_REQUIRED`（`:2293-2295`）。
- 后果：这一态**普通用户自己出不来**——界面只有「解除扫描锁」按钮，助手对执行类锁明确拒绝（`:5955-5959` `RECOVERY_OWNED_BY_ATTEMPT`），文案写的是「交由技术人员核对」（`src/components/workbench/design-file-card.tsx:1381-1390`）。
- 结论：**任何「跑到一半暂停」的设计都会把用户推进这个口子**。本轮只做「受理前拦」。

### F-A3｜Important｜拒绝必须复用「attempt 从未本地接受」这一族既有形状，否则会造孤儿

- 证据：`src/lib/workbench/batch-error-policy.ts:8-10` 注释即历史事故——「6 连拒 + 6 个 DISPATCHING 孤儿——继续撞闸只会产生更多孤儿」；处置是把批次级共享门放 `SYSTEMIC_PRE_EXECUTION_CODES`（`:17-46`），首拒即停止后续派发。账务侧：从未被本机接受的 attempt 由 reaper 终态化为 `ATTEMPT_ABANDONED_NEVER_DISPATCHED`（`src/lib/server/execution-batch.ts:1655-1658`，注释「账务与锁释放照旧」），结算按已验证单位、为 0 即 `RELEASED` 全额释放冻结（`:2060-2070` → `releaseReservation`），批次停滞 15 分钟自动收口（`:990` `BATCH_STALL_SETTLE_AFTER_MS`）。
- 已有可直接照抄的形状：忙碌类码 `execute-step.tsx:1329-1343`——best-effort `abandonBatchLanguage` 释放该语言，再抛系统性码上抛，文案明写「不会重复扣费」。
- 结论：新码必须同时进 `SYSTEMIC_PRE_EXECUTION_CODES` 并走这条 abandon+throw 路径，**且不需要改任何计费代码**。

### F-A4｜Important｜直接把码吐给用户 = 不讲人话

- 证据：系统性中止的用户可见句在 `v3-batch-flow.ts:664-666`，原文是「本地助手或批次共享执行门失败（${abortedSystemicCode}），已停止后续语言派发。」——会显示成 `（LOCAL_MEMORY_LOW）`。中文映射表在 `local-assistant-client.ts:1288`（`V15_ERROR_CODE_ZH`），未知码回退「批次语言执行被拒绝（原码）」（`:1891-1893`）。
- 处置：新码必须进映射表，句子要带实测数和「该怎么做」，不说「翻译失败」。

### F-A5｜Important｜阈值本身是 D 级推断，必须做假阳性防护

- 证据：判据只能用 `os.freemem()`（同一函数已在 `memory-probe.cjs:196` 被记成 `osFreeMB`，纯记录、从不判定）。本机实测样本只有几个点：小稿批次空闲 9,009→9,024 MB；开过 2.53 GB 大稿后空闲 7,634.6 MB 而 PS 私有内存 12,097 MB。**没有任何用户机的可用内存分布数据**，也没有「低于多少就一定跑不成」的实测边界（不会为测它把机器压到 OOM）。
- 处置（把 D 降级风险关进笼子里）：① 连续两次采样（间隔 400 ms）都低于线才拒，单次抖动不拒；② 线取 `max(2,048 MB, 10% × 系统总内存)`，8 GB 机 → 2,048 MB、16 GB → 2,048 MB、32 GB → 3,254 MB，可解释；③ 支持侧可用 `TYGF_MIN_FREE_MEM_MB` 显式覆盖；④ 拒绝句里报出实测 MB 和线，用户可以自己判断是不是真的没内存。

### F-A6｜Important｜本轮不覆盖单语链（范围声明，不是遗漏）

- 证据：单语执行链是另一个入口 `server.js:6376 /v1.5/execute/run`（其 `launchExecutor` 在 `:6233`/`:6251`），账务面走 PhotoshopJob 约定（`src/lib/server/photoshop-billing.ts:1052` `releasePhotoshopJobBeforeStart`），与批次的 attempt/reaper 形状不同。
- 结论：同一风险在单语路径仍然存在，本轮不加闸；要加得单独审一次账务面。这条写在覆盖缺口里，不假装已解决。

### F-B1｜Nit｜私有内存要新起 PowerShell 子进程

- 证据：`memory-probe.cjs:180-200` 现字段集合只有 `psCount/psTotalMB/psMaxMB/osTotalMB/osFreeMB/engineRssMB`，工作集来自 `tasklist` 解析；私有内存 `tasklist` 给不出，需要 `Get-Process` 的 `PrivateMemorySize64`（本轮大稿实测即用此法，工作集 8,182 MB vs 私有 12,795 MB）。
- 处置：新增异步读取，硬超时 1.5 s，失败一律 `null`，永不 reject、永不阻断；`analyze-batch-memory.mjs` 判定字段不动（避免动既有判据）。

### F-B2｜Pre-existing｜读数盲区不是本轮引入

- 上一份方案已登记同类缺陷（`执行方案_20261020_批量内存阈值清缓存_对抗式审查与实测.md` 的 F-08：`memory-probe.cjs:193-197` 只记工作集）。本轮是补它，不算新账。

### 更正

- 原说法（我上一轮对 Owner 讲的）：「挂点已经现成，`server.js` 解析 `ASSIGNMENT_DONE` 那里就能判内存」。
- 反证：见 F-A1——`ASSIGNMENT_DONE` 由 PS 进程内的 JSX 循环打出（`jsx:184`/`:222`），Node 只 tail（`server.js:1769-1778`），该时刻没有「下一稿」可拦。
- 新结论：闸放在 `/v1.5/batch/execute` 受理入口（`server.js:6983`，早于 `:7349 acquire`/`:7360 setBusy`），每语言一次判定；这才是真实的稿件边界。

## 3. 第一性原理：这件事要成的只有一句

**任何一次 Photoshop 受理之前，先证明本机还剩得下这一稿的内存；不够就不启动 PS、不建事实、不扣钱，并如实告诉用户为什么停、还剩多少、怎么继续。**

反过来说不做的三件事：不在执行中途停（F-A2 会造人工救援态）、不 purge（上一轮已实测 0 释放）、不改计费代码（本方案复用既有「未接受即零副作用」形状）。

## 4. 执行方案（按此顺序落地）

1. **新增纯函数模块** `download/local-assistant/memory-guard.cjs`：`resolveFreeMemoryFloorMB(totalMB, overrideMB)`（线）、`evaluateMemoryGate({ samples, floorMB })`（双采样判定）、`memoryGateMessage(...)`（含实测数的中文句）。不依赖 PS、不依赖网络，可直接单测。
2. **助手受理前插闸**：`server.js` 在 `/v1.5/batch/execute` 取得执行锁之前调用；不足则返回 `503 { ok:false, code:'LOCAL_MEMORY_LOW', message, freeMemMB, floorMB }`。位置在既有同族拒绝之后、`attemptRuntime.acquire` 之前，保证零副作用（不建 journal、不 `postAttemptAcceptance`）。
3. **前端处置同族化**：`LOCAL_MEMORY_LOW` 进 `batch-error-policy.ts` 的 `SYSTEMIC_PRE_EXECUTION_CODES`；`execute-step.tsx` 按忙碌类那条形 best-effort `abandonBatchLanguage` 再抛；`V15_ERROR_CODE_ZH` 加中文句（带「关闭其他程序或重启 Photoshop 后可重试」「未执行的语言不会扣费」）。
4. **只读读数补私有内存**：`memory-probe.cjs` 加 `psPrivateTotalMB`/`psPrivateMaxMB`（PowerShell 一次采全部 Photoshop 进程，1.5 s 硬超时、失败 `null`）。
5. **自检**：新增 `scripts/smoke-assistant-memory-gate.mjs`（阈值公式、双采样、拒/放、文案含数、env 覆盖、码已登记、脱敏、powershell 不可用回退）＋ 扩 `smoke-assistant-memory-probe.mjs`；`npm run test:assistant-memory-gate` 入口。
6. **验证**：`npx tsc --noEmit`、两个 smoke 全绿、一次性 harness 真调 guard（不启动 PS、不联网）。
7. **不做出包/发布**：助手行为变化要落到用户机上必须真建 exe 并 bump 版本（9 文件 + 1 exe 同步面），那是发布线的另一拍，本轮不碰。

## 5. 判据（怎么算做完）

- 夹具层面：空闲 ≥ 线 ⇒ 放行；连续两次 < 线 ⇒ 拒绝且返回码与含数文案；单次低谷 ⇒ 放行（负控）。
- 契约层面：`LOCAL_MEMORY_LOW` 在策略集合里（否则会被当成单语言失败继续掀批）；拒绝路径不写 journal、不调 acceptance（静态断言 + 代码走查）。
- 读数层面：PowerShell 不可用 ⇒ `null` 且不抛、日志行仍写、分析器判定不变。

## 6. 覆盖缺口（本次明确没检查/没做的部分）

- 没有在真实低内存的用户机上端到端跑过一轮；阈值线是按「保守且可解释」取的值，缺用户机可用内存分布（未决 1）。
- 没有覆盖单语链 `/v1.5/execute/run`（F-A6），也没有覆盖「attempt 已被本机接受后才内存不足」的情形（那时只能走既有看门狗，会进恢复锁）。
- 没有验证 PS 2023/2024 上的行为，也没有跑 2 GB 级 20 稿批。
- 助手改动未打包、未发布、未做真实 runtime 身份验证；本轮只到「源码 + 自检」。
- 没有实现「内存恢复后自动继续」，剩余语言需要用户手动再点一次（这是有意保留用户控制权，不是偷懒：见 F-A2，自动重投要先把执行恢复锁的人工出口补上，那条动回执语义，需要 Owner 单独授权）。

### 未决（缺什么证据）

1. 用户机可用内存分布：缺真实机器的 `osFreeMB` 采样；现在只有本机两个时点（9,024 / 7,634 MB）。缺到就能把 10% 这条线换成实测分位。
2. 「低于多少就一定跑不成」的经验边界：缺一次受控的低内存实测（隔离虚拟机 + 知情同意），不能拿客户机做。
3. 执行恢复锁的人工出口：`server.js:5955-5959` 明确拒绝执行类锁自助解除，缺 Owner 对「用户确认现场后可否终态化」的决策——这条动回执与计费，属红线，本轮不自动执行。**已立案**：根账 `AI_MEMORY/ISSUES.md` 的 **#192**（2026-10-20 落笔前探针 `grep -c "^## #192"`＝0；注意 develop 账同号另有其案，引用必须带账本名）。
