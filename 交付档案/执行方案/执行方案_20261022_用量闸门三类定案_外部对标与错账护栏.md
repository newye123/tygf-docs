## 1 本轮目标为什么是这个

你的原话是"以后碰到这种没接触过的都不要自己想象怎么做，先去做大量参考后使用对抗式审查再结合我们的实际情况来进行调整优化"。

第一性原理拆一下：「限额」这件事本质上要成的是——**在没有人被冤枉的前提下，让真金成本不可失控、让账不出错**。它有三个不可再分的职责，历史上被我们混在一个词里：

| 职责 | 判据（可测） | 混在一起的后果 |
|---|---|---|
| 保护用户不超支 | 用户能自己看到并选择 | 变成"隐形墙"，用户以为是坏了 |
| 保护我方成本 | 按真实成本驱动量计（token／外部 API 调用） | 卡积分＝只卡用户自己的余额，管不到我的钱 |
| 保护账的正确性 | 报价金额超出"正常业务最大可能值"即拒绝 | 撤了天花板之后服务端对整单金额零校验 |

"限额/配额"在我们仓库里没有成体系设计，全是历史单点常量。所以本轮动作＝外部真实实现逐文件取证 → 抽可抄机制 → 用我们自己的事实筛 → 三类定案 → 工作包。

### 2.8 可抄机制清单（每条挂至少一个已取证位置）

1. **闸与观测分开**：先影子模式记量，再决定拦不拦（nginx `limit_req_dry_run` + `$limit_req_status`）。
2. **拒绝必须带"什么时候可以再试"和"还剩多少"**（Laravel `:300-318`、DRF `views.py:91-92`、Figma/华为云规范）。
3. **限额存在配置里、运行时可改**（upstash `dynamicLimitKey`；我们已有 `ApiCredential` 与 site settings 两个现成载体）。
4. **限额与已用量都要摆出来给人读**（k8s `spec.hard` + `status.used`）。
5. **软/硬是每条闸自己的属性**（openmeter `is_soft_limit`）。
6. **数由自家分布定（P50/P90），不抄别人的数**（Stripe）。
7. **先告警，后拦人**（GitHub 75/90/100%、OpenAI 告警与上限分离）。
8. **记账时机可选：先扣后做 vs 按结果扣**（Laravel `:164` vs `:171-173`）——我们"全成功才核销、否则整笔释放"属于后者，是对的，别改。
9. **桶主键以用户/installId 为主，IP 只兜底，且键要做归一化**（Laravel `:285`、DRF `:23-40`）。

### 2.9 看起来流行但抄不动的（写下来防止下次我又动这个念头）

- DRF 每键存整个时间戳列表（`throttling.py:139-140`）：O(n) 内存，按积分计费这量级白烧。
- nginx 的缺省 503 与共享内存令牌桶：那是连接层护栏不是账；而且**照抄 503 会把"你没额度了"和"服务暂不可用"糊成同形**——这个坑我们已经踩过一次（`PLATFORM_BREAKER_OPEN` 503 的话术让用户以为是自己的积分问题）。
- upstash/Redis 那一整套 Lua + 缓存块：等于在积分账旁边再造第二个事实源，且 `reset` 是 Unix 毫秒而非业务周期。
- k8s 的 Scope 选择器＋协调控制器：形状可借（"哪些算这份额度要声明式"），机制对一个内测单机产品太重。

## 10 更正五（15:4x，你那句"为什么一定要限额"问出来的）

**结论：不是一定要。我把 C1 那条自己提的"整单错账上限"撤了。** 你这一问让我去核一件我先前没核的事：**服务端能不能自己把单位重算出来**。实测结果——

- v2 单语链**能**：报价函数是服务端读快照正文自己算的（`src/lib/server/photoshop-billing.ts:172` 读 `snapshot.tableJson` → `:181-185` `estimateBilling`），而每行超过 15 单位会被直接判不合格并抛 `BILLING_ROWS_BLOCKED`（`rules.ts:116-126`）。⇒ v2 的整单金额本来就是**结构性有界**（≤2000 行 × 15＝30,000），再加一道人工阈值只会挡合法大单。**不要。**
- v3 批次链**不能**：库里 `ExecutionBatchRow` 只存 `standardUnits` 与 `languageUnitsJson`，**没有正文**（这是隐私设计，服务端不存客户正文），所以只能收助手报的数；而"受信证据直返"绕过了每行 15 的封顶（`batch-v3.ts:61-63`），校验只卡到 ≤1,000,000（`billing-challenge.ts:176,180`）。

所以剩下的不是"要不要给用户设限"，而是"证据里的每行每语言单位必须落在定价规则自己的域里"。⇒ 换成 **C1'：把 0..15 从静默封顶改成校验拒绝**（超域即拒证据）。它对合法业务 100% 通过，因为它断言的就是规则本身；它防的是"一个 bug 造出天文冻结额、而 ps_execute 冻结不参与惰性释放"（`credits.ts:1015-1030`）。P1 工作包已按这个改写，原 400,000 阈值与那条定案实验一并取消。

一句话原则（写下来防我下次再犯）：**"限额"和"错账防护"是两件事，判据是——它会不会拒绝一笔合法业务。会＝限额，不该有；不会＝防护，该有。**

**充值那条按你的话挂起**：个人营业执照（个体工商户）没下来 ⇒ 支付宝商家收款本来就办不了，这不是代码能解决的。我把 ISSUES #251 的状态改成"等主体，Owner 明示暂缓"，不动任何 flag。留一句提醒：生产页面上那个买包入口现在能点、点下去必失败，等你想收拾这条对外假话时，改法只有两档——把 `creditPacksEnabled` 关回去，或把文案改成"充值通道待开放"。两档都不用写代码。
