## 01 中台现状（参考基线）

| 维度 | 现状 | 位置 |
|---|---|---|
| 技术栈 | Next.js 16.3 + Tailwind 4 + shadcn/ui + Prisma SQLite + React 19 | package.json |
| 中台页面 | admin（应用/邀请/用户/计费/备份/反馈）、workbench（本地助手 API）、billing、auth、site-content | src/app |
| 核心能力 | 应用邀请、计费信用、本地助手协议（serve 行协议/预检归类/双闸超时）、发布预检链路 | src/app/api、scripts/* |
| 治理机制 | 发布预检（release-preflight）、台账投影（sync-task-ledger）、回读闸（feishu-readback）、控制面日检（control-plane） | scripts/ |
| 冻结语义 | 支付 flag 保持 false；不得静默降级；不得从 develop 直建生产 | AGENTS.md / PROJECT_CONTEXT |

中台已有较完备的治理链路，但能力天花板可见：无字段级权限、无多视图（仅表格/列表）、无工作流自动化、无插件式视图区块、元模型（表/字段/视图）薄弱。飞书多维表投影是中台的首个外部视图客户端，协议已定（机器列永不触碰「Owner 批注」）。

关键事实：
- NocoDB 与 NocoBase 同源公司，但定位不同：NocoDB 是「数据库 → 表格 UI」，NocoBase 是「业务对象 → 系统构建」。
- Baserow 协议 MIT（最宽松），其余主流多维表格多为 AGPL-3.0（改动需开源，对内测版商业化有合规风险）。
- 我们中台已有 Prisma Schema（数据建模）与发布预检/台账治理，不缺「数据库」，缺的是「可插拔的视图层与字段级权限」。

## 03 对抗式审查：四个候选升级方案，逐个冷刀

| 候选 | 描述 | 最狠的刀 | 裁决 |
|---|---|---|---|
| 甲 | 中台整体替换为开源多维表格/低代码平台（NocoBase/NocoBase），飞书投影直接对接其 API | 与现有 Next.js 代码、Prisma Schema、飞书投影协议、计费/信用体系、本地助手协议全部不兼容；AGPL-3.0 改动需开源；40+ smoke 合同需重写；数据迁移成本极高 | <span class="tag bad">弃</span> |
| 乙 | 保留现有中台，借鉴开源能力做模块化升级（插件架构 + 字段级权限 + 多视图 + 工作流），如 NocoBase 插件区块、Plane Modules/Views、Focalboard 多视图 | 现有代码量大，引入插件架构侵入性大；飞书投影协议与中台权限模型需重新对齐；过度设计风险（现有 admin 已有权限与备份） | <span class="tag warn">部分采用（字段级权限、多视图、工作流骨架）</span> |
| 丙 | 中台分层升级：数据层保留 Prisma/SQLite；视图层引入开源参考的「表/字段/视图/自动化」元模型（NocoDB 数据建模 + Baserow 实时协作/Plane Views）；控制面层保留并加强；飞书投影作为首个外部视图客户端 | 元模型抽象层需新增代码；现有表结构需逐步对齐元模型；对现有 admin 页面有渐进式侵入 | <span class="tag ok">采用（主方案）</span> |
| 丁 | 不做大改，仅接入开源前端组件（@tanstack/table 已在用，追加拖拽/看板），中台能力不变 | 不解决中台天花板（无字段级权限、无工作流、无多视图）；对「升级中台」诉求无响应 | <span class="tag warn">降 P2（只做 UI 组件微升级）</span> |

攻防要点记录：
- 「换平台」解决不了「飞书投影协议」——协议是我们自己定的（机器列/Owner 批注），换平台反而要重构协议。
- 「纯前端组件」解决不了「字段级权限」——权限在后端 Prisma + API 路由，前端组件只能装饰。
- 元模型方案可渐进：先让飞书投影走新元模型，再把 admin 页面逐页迁移，不中断现有合同。

## 04 主方案：中台分层升级（丙 + 乙部分能力）

### 04-1 分层设计

| 层 | 职责 | 开源参考 | 现状 |
|---|---|---|---|
| 数据层 | Prisma + SQLite，业务表与计费/信用/邀请 | —— | 已有，保留 |
| 元模型层 | 表/字段/视图/自动化元数据，字段级权限、工作流触发器骨架 | NocoDB 数据建模、NocoBase 插件式/字段级权限 | 缺失，新建 |
| 视图层 | 多视图（表格/看板/日历/画廊）、视图持久化、视图区块插件 | Focalboard 多视图、Plane Views、NocoBase 区块 | 缺失，新建 |
| 控制面层 | 发布预检、回读闸、控制面日检、冻结语义、台账投影 | —— | 已有，加强 |
| 外部客户端 | 飞书多维表投影（首个外部视图） | Baserow API-first 设计 | 已有，协议不变 |

### 04-2 执行阶段

**P0（本轮，约半天）：元模型基础 + 飞书投影对齐**
- 新增元模型表：`Table`、`Field`、`View`、`FieldPermission`（字段：可读/可编辑/隐藏，角色级）；`WorkflowTrigger`（字段变更触发器骨架，先不嵌执行器）。
- Prisma Schema 增加元模型模型，与现有业务表并行（不改现有表结构，零破坏）。
- 飞书投影协议对齐新元模型：「机器列」映射到元模型字段并受字段级权限保护；「Owner 批注」列继续永不触碰（延续已有治理）。
- 验收：`scripts/test-sync-reconcile.sh` 风格的夹具覆盖元模型读写；投影空跑 update=0；控制面全绿。

**P1（下轮）：多视图 + 插件式区块 + 工作流自动化**
- 视图层：表格/看板/日历/画廊四视图，保存过滤与排序（Focalboard/Plane Views 参考）。
- 视图区块插件：中台页面可嵌入自定义区块（NocoBase 区块参考）。
- 工作流：字段变更 → 自动化动作（更新另一字段、发通知、触发预检），先支持骨架，动作按需扩展。
- 验收：新增一个中台页面使用多视图 + 区块；工作流触发一次端到端。

**P2（后续）：AI 字段与多租户**
- AI 字段/自动提醒（Teable/Baserow AI 字段参考）；中台多租户与商业化（Plane 商业版参考：工作流审批门、审计日志）。
- 仅在 P1 全绿后启动。

### 04-3 飞书投影协议（不变，作为外部视图客户端示例）

| 你动了什么 | 发生什么（升级后） |
|---|---|
| 「Owner 批注」写任何字 | 永不覆盖；日检/同步读取、落实，推送回你 |
| 机器列（受字段级权限保护）手改 | 视为你的命令；采纳+记账（来源注明「飞书手改」）；元模型字段级权限校验 |
| 任务ID 手改 | 身份列恢复原值+告警 |
| 新增整行 | 新任务请求：内容齐→进账「等您定」；空行→告警 |
| 删行 | 不生效（下次投影补回来）；要停任务请在批注写「不做/删掉」 |

## 05 执行顺序与回滚

1. 元模型模型 + Prisma 迁移（sqlite，可回滚为删除新表）；
2. 飞书投影协议对齐 + 夹具验证；
3. P1 多视图/区块/工作流，逐页迁移 admin；
4. P2 AI 字段/多租户（按需）。

**回滚**：元模型为新增表，删除即可恢复；飞书投影协议保留旧版兼容；不改现有业务表与 smoke 合同；无不可逆步骤。
