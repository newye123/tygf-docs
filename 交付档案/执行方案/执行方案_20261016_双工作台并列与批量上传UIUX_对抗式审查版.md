## 一、先说结论（三句话）

1. **现在的批量功能是「就地改造原工作台」，不是「多一个工作台」。** 多 PSD 实验直接改的是原工作台的两个核心组件（`design-file-card.tsx` / `workbench-view.tsx`），靠一个开关切换渲染分支——开关一开，原单文件工作台就被顶替掉了。这正是你说的那个问题。
2. **现在文件对话框一次只能选一个 PSD，写死在助手端。** 要「一次多选」必须改本地助手的 PowerShell 对话框并**重新发版、用户重装**——这是本方案最大的成本项，需要你先拍板。
3. **建议分三步走，每步都能单独回滚**：① 先做「并列骨架」（纯前端、不动助手、不碰执行链）→ ② 再改助手端多选（要发版）→ ③ 最后上批量队列与进度呈现。

## 四、开源参考（GitHub）

按你的要求去 GitHub 上看了同类场景的开源实现。筛选标准：**必须解决「多文件 + 本地执行 + 串行队列」这个组合**——因为你的场景特殊在「浏览器工作台 + 本地 Windows 助手 + Photoshop 单实例串行」。

### 4.1 五个直接相关的项目

| 项目 | 为什么相关 | 可借鉴的点 |
|---|---|---|
| **Uppy**（`transloadit/uppy`，MIT） | 模块化多文件上传器，Dashboard 插件是业界最成熟的多文件列表 UI | 见 §4.2 |
| **Transloadit 官方最佳实践**（同团队） | 专讲「批量文件处理」的工程与 UX 原则 | 见 §4.2 / §4.3 |
| **handbrake-web**（`TheNickOfTime/handbrake-web`） | **自托管 Web 界面 + 单一队列 + 多设备共享处理**——与你的「Web 工作台 + 本地执行器 + 串行队列」几乎同构 | 队列是**一等公民**：独立页面、可增删、可看每项状态 |
| **HandBrake GUI** | 桌面批处理标杆 | 「加入队列」与「开始」解耦：先攒够文件再统一开始，而不是选一个跑一个 |
| **Crowdin「Uploading Source Files」** | 翻译平台的批量源文件上传 | 批量上传时的**选项面板**（cleanup mode、labels），而不是上传完才配 |

### 4.2 可以直接搬的模式

1. **「选择」与「开始」解耦**（Uppy 的 `autoProceed: false`；HandBrake 的队列）
   - 你的现状是反的：选完立刻扫（`design-file-card.tsx:413` 单文件、`:594` 多文件）。
   - 批量场景应改成：**先攒文件 → 逐个扫描（可后台）→ 用户确认覆盖率和语言 → 统一开始执行**。

2. **每文件独立状态位 + 独立操作**（Uppy Dashboard 的 StatusBar）
   - 每个文件行要有自己的：状态徽章、进度、重试/删除/重扫按钮。
   - 你已经有雏形（`design-file-card.tsx:619-646` 每行有 `StateBadge`），但**缺删除单个**、缺重排、缺「失败只看失败项」。

3. **批量级操作**（Uppy：全选 / 批量暂停 / 批量删除 / 重试失败）
   - 你只有「清除全部」（`design-file-card.tsx:664`）。缺：删除单个、只重试失败、全部重扫。

4. **上传/扫描优先，处理异步继续**（Transloadit「Prefer asynchronous processing」）
   - 原话：让用户等完整处理会直接伤害 UX；更好的模式是「先上传/导入，处理异步进行」。
   - 对你的意义：扫描阶段可以后台跑，用户不必盯着；执行阶段因为 PS 串行必须等，但**扫描不该串行阻塞添加**。

5. **按 ID 映射结果，不依赖顺序**（Transloadit「Do not rely on result ordering」）
   - 你的结果目录是 `<PSD>_ALL_<N>LANG__<ts>`，矩阵格与文件靠**下标**关联（`coverage-matrix.tsx:102-119`）。一旦中途删掉某个 PSD，下标就会错位。**建议改成按 `masterPath` 或稳定 ID 关联。**

6. **输入数量要设上限**（Transloadit：单批 500–1000 文件）
   - 你的 12 是硬上限（`MAX_PSD_ENTRIES`）。建议上限**可配**并说明理由，而不是写死。

### 4.3 要避开的反模式

| 反模式 | 出处 | 你的风险 |
|---|---|---|
| 静默吞掉部分失败 | Transloadit 明确警告：`ignore_errors` 会让失败「less visible」，必须有意使用并监控 | 批量里「某个 PSD 失败了但整批显示完成」——必须显式分层 |
| 让用户等完整处理 | Transloadit | 扫描串行阻塞添加（§2.3） |
| 结果靠位置对齐 | Transloadit | 矩阵格靠下标（§4.2 第 5 条） |
| 把「选文件」和「开始执行」耦死 | HandBrake / Uppy | 你现状如此 |

## 五、方案：并列双工作台

### 5.1 信息架构

```
首页 (#home)
├── 工作台        (#workbench)  ← 原样保留，一行不动
└── 批量工作台    (#batch)      ← 新增，独立视图
```

- 扩 `view-context.tsx:5`：`export type AppView = 'home' | 'workbench' | 'batch'`
- `app-shell.tsx:40` 旁增一行：`{view === 'batch' && <BatchWorkbenchView />}`
- 批量视图**动态加载**（`dynamic(..., { ssr: false })`），与现有 `WorkbenchView` 同策略（`app-shell.tsx:13-16`），保证不进访客 bundle
- **入口**：顶栏导航加一项「批量工作台」，受独立开关 `batchWorkbenchEnabled` 控制（默认 false）

**关键纪律：原 `workbench` 视图及其组件树零改动。** 多 PSD 实验那 6 个文件的改动，要么回滚、要么全部收敛进新视图。

### 5.2 批量工作台的四个区

| 区 | 内容 | 复用现有 |
|---|---|---|
| ① 文件区 | 文件列表（增/删/重排/状态/单文件重扫），「一次多选」按钮 | 复用 `StateBadge`、扫描链路 |
| ② 语言区 | 目标语言多选（现有语言选择器） | 复用 `review-step` 的语言表 |
| ③ 覆盖率矩阵 | M×N 矩阵 + **执行前显式放行闸** | 复用 `coverage-matrix.tsx`，补拦截 |
| ④ 执行区 | 队列、总进度、逐 PSD 进度、失败分层、结果下载 | 复用 `multi-psd-flow.ts` + 现有批次链 |

### 5.3 「一次多选文件」的实现路径

分三层，**逐层可独立上线**：

**第 1 层（前端先行，不需发版）**
- 新增 `selectDesignFilesDirect(anchor): Promise<string[]>`（保留原单值函数不动，避免回归）
- 文件区加「拖拽区 / 粘贴多个路径」作为**多选的兜底入口**——不依赖助手端改动就能一次录入多个
- 列表支持删除单个、重排

**第 2 层（助手端改造，需发版 + 重装）**
- `picker-dialogs.cjs:57-62` 加 `$d.Multiselect = $true`
- OK 分支从 `$d.FileName` 改为输出 `$d.FileNames`（需 JSON 序列化以支持中文路径）
- `server.js` 的 `/v1.5/select-file` 增加 `filePaths: string[]` 返回（**保留 `filePath` 兼容旧前端**）
- 前端 `selectDesignFilesDirect` 消费数组

**第 3 层（队列）**
- 一次多选后**不要**立刻逐个 `setTimeout` 触发扫描（现在 `:594` 的做法）
- 改为：全部入列 → 后台**串行**扫描（PS 串行约束）→ 每个扫完刷新状态 → 用户点「开始执行」再跑

### 5.4 队列与进度

- `MultiPsdOrchestrator`（`multi-psd-flow.ts`）目前是「顺序 for 循环」，缺真正的队列语义
- 建议补：**暂停 / 恢复 / 中止当前项 / 跳过失败项继续**
- 修 `abort()` 的语义（`multi-psd-flow.ts:88-95`）：现在只是标记，正在跑的那批停不掉——需要把中止信号透传给 `runBatch`

### 5.5 失败处理（对齐 §4.3 反模式）

三层呈现，缺一不可：
1. **行级**：哪个 PSD 的哪个语言失败了（矩阵格标红 + 悬停原因）
2. **批次级**：本批 X/Y 成功，失败项可「只重试失败」
3. **整批级**：全失败时给可下载的失败报告（生产站已有 `failure-report.ts` 的成熟实现，见 `worktrees/production/src/lib/workbench/failure-report.ts`，390 行，可直接移植）

| 复用（不改） | 新建 |
|---|---|
| `psd-selection.ts` 的类型与 `addMultiPsdEntry` | `batch-workbench-view.tsx` |

## 七、对抗式审查（自己找自己的漏洞）

### 反方 1：「并列双工作台是过度设计，同一工作台里加开关更省事」
**回应**：省事但**不可回滚**。现状已证明代价——开关一开，原工作台整体被替换，用户没有「继续用旧的」这个选项。并列的代价是多一个视图容器（约 100 行骨架），换来的是**两个视图可以独立开关、独立回滚、独立验收**。对「测试站要给人用」的场景，这个代价值得。
**但**：如果 Owner 的目标只是「测试站上让人试用批量」，那也可以先只做「入口 + 并列骨架」，批量区内部先复用现有组件——**方案保留了这条捷径**（§5.3 第 1 层可独立上线）。

### 反方 2：「改助手端风险太高，历史踩过版本纪律的坑」
**回应**：成立。所以方案把助手端改动放在**第 2 层**，并且要求前端做**能力探测 + 自动降级**。即使助手端永远不发版，第 1 层（拖拽/粘贴多路径 + 列表管理）也能提供「一次录入多个」的能力。**建议：先上第 1 层，助手端改动单独评估。**

### 反方 3：「覆盖率矩阵只是提示不拦截，是既有设计，不是新问题」
**回应**：是既有问题（ISSUES #140/#153），但**批量场景把它放大了**——单文件时用户能肉眼看出问题，12 个 PSD × 3 语言时没人会逐格检查。所以本方案把它列为必须一并处理的项，而不是「以后再说」。

### 反方 4：「结果按 ID 映射是过度工程，现有下标够用」
**回应**：单文件单语言时确实够用。但批量场景下**用户一定会删文件**（选了 12 个，扫完发现 2 个不对，删掉）——此时下标必然错位。这不是理论风险，是必然路径。

### 反方 5：「万一测试站上开关真的是开的」→ **已查实：就是开的，我初版判断错了**

**更正（2026-10-16 18:2x）**：初版我只查了 `SiteSetting`（覆盖层）就下了「关着」的结论，**漏查代码默认值（基础层）**。实际合并规则是 `feature-flags-store.ts:37` 的 `{ ...featureFlags, ...覆盖 }`，站点设置没有该键时不覆盖、直接用代码默认值；而 `aefc8a8:src/config/featureFlags.ts:61` 是 **`true`**。⇒ **测试站上批量实验确实是开着的**，Owner 看到的工作台确实被顶替。

**更严重的是**：`aefc8a8` 的提交信息写「默认关闭」，却在同一提交里把 `multiPsdExperimentEnabled` 从 `false` 改成 `true`（`git show aefc8a8 -- src/config/featureFlags.ts`）——**提交信息与代码不符，且改动夹带在与 P0′ 无关的提交里**。

**这一条教训要写进纪律**：判断一个开关的真实状态，必须**同时查两层**——① 代码默认值（`featureFlags.ts` 里那个字面量）② 站点设置覆盖值（`SiteSetting.featureFlagsV1`）。**只查一层就是假绿。**

### 反方 6：「你说不动原工作台，但多 PSD 的代码已经合进 develop 了，怎么保证？」
**回应**：`cde98a7` 的 6 个文件改动**尚未合进 main**（`develop` 独有）。所以有两条路：① 在 develop 上把这 6 个文件的改动**回滚**，批量能力全部在新视图重建；② 保留改动但**把开关永久锁死**，作为「未来复用」的代码。**我倾向 ①**，因为保留锁死的代码会持续制造「两套渲染分支」的维护成本，而 §5.6 已证明核心资产（编排器、矩阵、类型）可以整体搬到新视图。

## 八、灰度与部署纪律

**这次的根因不只是技术，还有流程**：批量代码**在开关被打开的状态下**随 `aefc8a8` 一起上了测试站（见 §2.4 更正），而这次部署的执行者一度不明（`ISSUES.md` #154 记录了消息未留存）。所以方案附四条纪律：

1. **部署前必须点名**：任何上测试站的部署，`AI_MEMORY/TASK_LOG.md` 里必须写清「谁批准、谁执行、部署了什么 commit」。参照 `AGENTS.md` 的发布挂号条款。
2. **批量代码不进 `develop` 主干**：在方案批准前，批量能力只在独立分支开发；`develop` 保持「只有已批准能力」。
3. **探针要加白名单**：当前部署探针（`worktrees/v1.5-trust-chain/scripts/deploy-probe.cjs`）条件满足就自动部署。**建议加一条：只部署白名单内的 commit 或分支**，否则「自动」会绕过第 1 条。
4. **开关改动不得夹带（本次新增）**：任何提交，**提交信息必须与代码里的开关取值一致**；开关值的变更**不得夹带在与主题无关的提交里**。`aefc8a8` 就是反例——它自称「默认关闭」，实际把 `multiPsdExperimentEnabled` 打开了。建议在发布门禁加一条断言：`featureFlags.ts` 里的默认值若与上一个 commit 不同，提交信息必须显式提及。

### 11.3 执行中发现的三件事（原方案未覆盖）

**① 运营台对普通布尔开关是「只读」的——这是 flag 事故的结构性成因。**
`settings-panel.tsx:887-919` 的「模块开关」面板只渲染徽标（自述「本面板只读」）；`admin/client.ts:552` 的通用 `saveFeatureFlags` **无任何 UI 调用**。⇒ 此前 Owner 想开一个普通布尔开关**只能改代码**，这正是 `multiPsdExperimentEnabled` 在 `aefc8a8` 被夹带提交的机制。
**已补**：按 `saveSiteCopyInlineEditOverride` 同款，新增 `saveBatchWorkbenchEnabledOverride`（原子单键 `json_set`，不覆盖其它键）+ API 分支 + 面板开关卡。
**由此得出一条纪律**：任何新增布尔开关，必须同时补「原子覆盖函数 + API 分支 + 面板入口」，否则它等于「默认 false 且无人能开」。

**② 浏览器拖拽文件拿不到绝对路径 ⇒ 第 1 层的多路径入口只能是「粘贴」。**
`File.path` 是 Electron 专有；Chrome 出于安全只给文件名，而助手链路需要绝对路径 `masterPath`。故「拖拽区」在纯 Web 页是死路；可靠入口是**粘贴多行路径**（与 `design-file-card.tsx:687`「粘贴即扫描」同源）。真正的一次多选要等第 2 层助手端 `OpenFileDialog` 加 `Multiselect`。
⇒ **§5.3 第 1 层「拖拽区 / 粘贴多个路径」中的「拖拽」应降级为「不做」或「仅接受路径文本」**，以粘贴为准。

**③ `PreparationClientState` 无「已录入未扫描」态，且不能加。**
加新值会破坏 `design-file-card.tsx:878` 的 `Record<PsdSelection['state'], …>` 穷尽性检查，而原工作台组件树必须零改动。
⇒ 第 1 层批量列表用 `string[]` 路径（不用 `MultiPsdEntry`）；`MultiPsdEntry` + 串行扫描 + 队列语义留到第 3 层。
