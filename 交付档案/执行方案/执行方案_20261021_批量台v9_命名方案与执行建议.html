01判定

Verdict · 命名独立成一单 ＋ 执行顺序先立闸

命名必须分开，不是"换个说法"，是"分两套词表"：旧名（准备素材 / 选择设计文件 · 只读预扫描 / 重选译文表 / 智能检测）是单稿台的资产，动了就破坏"原样保留"；而且旧名也表达不了"这一份交付物从哪张表取"这一层。⇒ 批量工作台有自己的词表，单稿台一字不改。

  • 执行建议的核心是顺序：先立闸（阶段 0 写快照断言脚本）→ 再定名（阶段 1）→ 再写只读来源视图（阶段 3）→ 挂载（阶段 6）→ 最后才接执行（阶段 9）。理由：「与原行为逐字节一致」是仓库既有的成文验收尺，但没有断言脚本，它只是一句话。
  • 阶段 3 先只读、不接真数据：用户先看到"每份交付物从哪张表取、覆盖率多少"，确认模型合手，再接执行链——错了改的是一屏界面，不是执行链。
  • 阶段 4/5 各写一份，不复用共享组件：代价 ≈ 350 行重复（导入器 + 按格审查外壳），换来单稿台一行不碰。
  • 助手得分接口独立排期（阶段 9）：唯一动助手的部分，只读、不改执行语义，不与前端抢排期。

命名的五条规则（写进方案当硬约束）

  • 1
    用用户嘴里的词，不用内部词。✗ 译库 · 切片 · 绑定 · 覆盖率矩阵 · owner value · slice　✓ 译文表 · 这一稿用哪张表 · 这一份从哪张表取 · 对稿覆盖率。内部术语只活在代码里（binding / slice / dataset / coverageDrafts）。
  • 2
    旧名只归单稿台，新名只归批量台，不混用。界面上出现旧名 ＝ 串台了，是 bug。
  • 3
    每个数字都要有分母和对象。「72 就绪」单独出现是无效信息 ⇒ 必须同时给「88 本批要做的交付物」和「144 矩阵格数（12×12）」。
  • 4
    状态词要能回答"我现在该做什么"。就绪（可以往下走）· 待检查（等你确认）· 有 N 处要处理（说清几处）· 缺语言（这一份做不出来，不是"再等等"）。「有 N 处」是批量台唯一的文案钩子（单稿台是逐行看），所以 N 必须随状态实时变。
  • 5
    一处一个说法。同一概念在标题、按钮、徽章、报告、飞书推送里必须同名；批量台说「译文表」，就不许别处冒「译库／表格包」。

「设计稿」出现在：导轨第 1 步 · 第 1 步标题 · 列表区标题 · 抽屉文件名 · 报告批次标题；「译文来源」：第 1 步副标题 · 矩阵卡片标题 · 图例；「对稿覆盖率」：矩阵单元格 · 设计稿卡片 · 抽屉 · 汇总条 · 报告；「就绪／有 N 处要处理」：矩阵单元格 · 设计稿卡片 · 汇总条 · 执行前提示。⇒ 命名单独立一单（它本身是产品行为、且牵动多处文案），先过 Owner 审，再进代码。

03阶段二 · 执行建议：九阶段

核心原则

先立闸，再动代码；先只读，再进执行；先新增文件，再碰共享文件。

0

三条刻意的取舍

  • A
    阶段 3 先只读、不接真数据。用户先看到"每份交付物从哪张表取、覆盖率多少"，确认这套模型合不合手，再接执行。错了改的是一屏界面，不是执行链。
  • B
    阶段 4/5 各写一份，不复用共享组件。代价 ≈ 350 行（导入器 ≈ 200 行、按格审查外壳 ≈ 150 行），换来单稿台一行不碰。
  • C
    助手接口单独排期。它是唯一动助手的部分，只读、不改执行语义，不与前端抢排期。
