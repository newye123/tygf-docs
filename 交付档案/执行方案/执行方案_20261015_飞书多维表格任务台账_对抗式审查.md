# 飞书多维表格当任务台账：开源调研 + 对抗式审查 + 执行方案

- 日期：2026-10-15
- 缘起：Owner 令「是不是可以把工作计划全部做到飞书多维表格里面？这样我不就知道哪些做没做到什么地步，谁领了任务等等了吗？到 github 上看看有没类似的开源项目可以参考，然后使用对抗式审查给我一个执行方案」
- 调研范围：GitHub 开源项目 + 飞书官方能力 + 本机现状实测
- 一句话裁决：**方向可行且值得做。但它不该是「第四本账」，而该是「账的显示窗口」。** 前提是先装官方 CLI（本机现在没有）。

---

| 前提 | 实测 | 判定 |
|---|---|---|
| 飞书连接器授权 | `feishu` connector：`bound: true`、`enabled: true`，随附 28 个 `lark-*` skill（含 `lark-base` 多维表格、`lark-task` 任务） | ✅ **已就绪** |

## 二、GitHub 开源调研

### 2.1 直接可用

| 项目 | 是什么 | 裁决 |
|---|---|---|
| **`@larksuite/cli`（飞书官方）** | 飞书官方开源 CLI，MIT 协议，约 2.8K★，覆盖 12 个业务域（含多维表格、任务），200+ 命令、19 个 Agent Skill | **直接用**。本机 connector 本来就基于它，装上即可 |
| **飞书官方模板中心** | 公开的项目管理 / 任务看板 / 甘特图模板库，`+template-search` 可按关键词搜 | **用**。字段设计不用从零想 |

### 2.2 借架构、不照抄

**`popipo-ai/popipo-feishu-skill`** —— 与需求最贴近的参考。链路是「用户反馈群 → 多维表格归档 → 飞书任务分配」，值得抄的是它的**四个工程习惯**：

1. **增量拉取**：`sync_chat_to_base.py --start <日期>` 只拉新增，不全量重写；
2. **一话题一行**：主键稳定，不重复插入；
3. **`--dry-run` 预览**：写入前先看「将新增多少行」；
4. **Agent 中间步骤**：新进表且字段空的行，由 Agent 补全「工程问题描述」再进任务——**即"AI 负责填、人只看"**。

裁决：**借形状，不装代码**。它的脚本是 Python + 自建应用凭据，与本机 CLI 授权体系不同。

### 2.3 反面教材（重要）

**`ddddnet/FeiShuDataBase`** —— Python 封装多维表格当免费数据库。功能本身能用，但它的 README **把 `APP_ID` 和 `APP_SECRET` 明文写在示例里**（真实凭据）。

裁决：**不装**。理由不是功能，是**它示范了一种会把凭据带进仓库的写法**——本项目已有「密钥只放环境变量或后台，禁明文进文档/提交」的红线，这条必须写进方案里当反面案例。

### 2.4 备查

- **`feishu-cli`**（社区项目，非官方）：Markdown ↔ 飞书文档双向无损转换。我们的台账本体就是 md，将来若要「把某份报告推成飞书文档」可用。
- **飞书集成平台 anycross**：有定时同步模板（多维表格 ↔ MySQL 等）。属重方案，暂不需要。

### 2.5 明确不装

**Plane / Vikunja / Focalboard / OpenProject / Taiga** —— 自托管项目管理工具，生态成熟，甚至有 Vikunja MCP Server 可让 AI 直接管任务。

裁决：**不装**。理由与上月否决 Unleash 同族——**本仓库已有一条完整的任务台账链路（TASK_LOG + ISSUES + 交付档案），再装一套就是重复建设**，且新增一个要部署、要备份、要升级的系统。我们要的是「换个窗口看账」，不是「再开一本账」。

## 三、对抗式审查（八问）

### 问 1｜这会不会变成第四本没人写的账？——**头号风险**

三账（官制／待投递／待复验）为什么休眠 8 天？因为**靠人写**。日报链停更 17 天，也是靠人写。如果飞书表格同样靠人手动更新，它会以同样的方式烂掉。

**裁决**：表格内容**必须机器写**。写手是 AI 会话（装上 CLI 后会话就能直接写表），时机是**会话收尾那一步**——与「追加 TASK_LOG」合并成同一个动作，不新增人的负担。

**可判定标准**：表格超过 7 天没更新，而 git 同期有提交 ⇒ 投影链断了，立案。

### 问 2｜谁是真相源？

如果表格是真相源，那么：飞书故障 = 项目失忆；且表格与 git 无法互证，出现分歧时不知道该信谁。

**裁决**：**单向投影，git 为准**。`AI_MEMORY/TASK_LOG.md` 与 git 是真相，表格只是它的视图。推论：
- 「表格没更新」**不算事故**（可能只是投影没跑）；
- 「git 有、表格没有」**才算事故**（投影漏了）。

这一条同时回答了 Owner 的核心诉求——您要看的是「进度」，而进度的权威定义来自 git，表格只是让您看得见。

### 问 3｜表格里放什么？

不能全量塞。四本账 + 18 个交付目录 + 58 份任务书全进去，等于把混乱从文件系统搬到云端，还是没人看。

**裁决**：只放**两类**——① 需要 Owner 决策的；② 需要跨会话可见的（谁在做什么、做到哪）。目标规模 **20–40 行**，不是全量 backlog。

**不放**：代码级细节、单个 bug 编号、历史归档件。

### 问 4｜谁来写、什么时候写？

- **写手**：AI 会话（不需要您操作）；
- **时机**：会话收尾，与 TASK_LOG 追加同一步；
- **补充**：可另加一个定时任务做「兜底扫描」（比对 git 提交与表格行数，发现漂移就补）。

### 问 5｜多会话并发写会不会冲突？

本项目是多窗口并行的（今天就有 opencode、总控等多手同时在写）。若各会话都往表格 append，会出重复行。

**裁决**：**主键幂等**。任务 ID 用稳定键（如 `T-20261015-01`），写入前先查后写（update-or-insert），**禁止 append**。`popipo` 那个项目的「一话题一行」就是同一手法。

### 问 6｜写失败怎么办？

飞书 API 会限流、会超时，CLI 可能没登录。

**裁决**：**不阻塞交付**。与现有飞书推送纪律一致——失败只登记、继续干活。**表格绝不能成为开工的前置条件**，否则飞书一抖，全线停摆。

### 问 7｜凭据放哪？

CLI 的授权凭据存本机（`lark-cli auth login` 之后由 CLI 自己管），**不进仓库、不进文档、不进提交**。

**反面教材已在 §2.3**：那个把 `APP_SECRET` 写进 README 的项目。本项目密钥红线不变。

### 问 8｜这会不会又是一个仪式？

判据只有一个：**您能不能用它回答「谁领了任务、到哪一步」**。答不了，就是失败，应当撤掉而不是硬撑。

附带自省：本方案**不做**仪表盘、不做甘特图、不做自动化 workflow。第一版只要能回答上面那句话。

## 四、执行方案 P0′（五步，约半天）

### 步 1｜装 CLI 并授权（约 10 分钟，需要您扫码一次）

```
npm install -g @larksuite/cli          # 版本要求 ≥1.0.97
lark-cli.cmd config init --new --lang en
lark-cli.cmd auth login --recommend    # 这一步需要您扫码
lark-cli.cmd auth status               # 应返回 identity: user
```

> 说明：本机 connector 已授权，但那是 WorkBuddy 侧的授权记录；CLI 装好后是否可直接复用、还是需要重新 `auth login`，**属待确认项**（见 §六）。

### 步 2｜建 Base 与表结构

两条路，建议**先看模板再决定**：
- **路 A**：`lark-cli base +template-search --keyword 任务` 找官方项目管理模板，直接套用；
- **路 B**：`+base-create --name 图译工坊任务台账 --table-name 任务 --fields '<字段数组>'` 自建。

建议字段（第一版只保留 7 列）：

| 字段 | 类型 | 说明 |
|---|---|---|
| 任务ID | 文本（主键） | 稳定键，如 `T-20261015-01` |
| 标题 | 文本 | 一句话 |
| 状态 | 单选 | 待定 / 进行中 / **等您定** / 已完成 / 已暂缓 |
| 负责人 | 单选 | 会话槽（opencode / 总控 / 待派） |
| 下一步 | 文本 | 谁、做什么 |
| 出处 | 文本 | `路径:行号`，便于回溯 |
| 更新时间 | 日期 | 自动 |

### 步 3｜写投影脚本（约百行）

- **输入**：`AI_MEMORY/TASK_LOG.md`（条目）+ git 状态（未提交/未推）；
- **输出**：飞书表格行；
- **行为**：`--dry-run` 先预览将新增/更新多少行（抄 popipo 的习惯），确认后写入；按任务 ID 幂等；
- **落点**：`scripts/sync-task-ledger.mjs`（与现有 `send-feishu-report.mjs` 同目录同风格）。

### 步 4｜接进会话收尾流程

在 `AGENTS.md` 的「任务结束必做」里加一条：追加 TASK_LOG 之后，跑一次投影脚本（失败不阻塞）。

### 步 5｜验证与降级

- **验证**：表格里能看到今天的条目、状态正确、能按负责人筛；
- **降级**：CLI 未登录 / 网络失败 / 限流 → 脚本退出码非 0，只登记，**不影响交付**。

## 五、跟总控 A/B 方案的关系（这一节最重要）

Owner 这个提议，**实际是总控今早提的 A/B 之外的第三个选项**：

| 选项 | 内容 | 谁提的 |
|---|---|---|
| A | 补回三账，恢复派工与复验节拍 | 总控 |
| B | 三账停写归档，改用 git + TASK_LOG + 机器判据当唯一台账 | 总控（推荐） |
| **C** | **把工作计划搬到飞书多维表格** | **Owner（本方案）** |

**我的建议：B + C 组合，而不是 C 替代 B。**

- **B 解决「账没人写」**——真相源必须是不依赖人自觉、可机器校验的东西（git 有提交就有记录）；
- **C 解决「账没人看」**——您要的是一个打开就能看、能筛、能按人分组的窗口。

两者不冲突：**B 是真相层，C 是视图层**。若只做 C 不做 B，表格会变成第四本靠人写的账（问 1 的失败路径）；若只做 B 不做 C，您仍然要翻 md 文件——那正是您现在抱怨的事。

**所以本方案的正确读法是**：接受 B 的真相源定义，把 C 作为它的显示窗口。
