## 3. 对抗式审查裁决（核心结论）

### 推翻的（初版方案四处硬伤）

1. 部署 Unleash + PG + OpenFeature 全栈 —— 本仓库已有完整 DB 可配置开关链路，再建一套就是双账本（#137 同类病）。详见第 4 节证据。
2. 硬版本闸（minAssistantVersion 一刀切）—— develop AI_MEMORY/ISSUES.md:1152 实录：3.6.14 用户被 3.6.15 门槛卡死全流程；当时结论「canary 空白名单=放行」与版本门槛矛盾。
3. 「秒级杀开关」话术 —— use-feature-flags.ts:8-12 模块级 cached 永不失效；in-flight PS 执行分钟级，旗标只断新进入。修正为「最坏 30s」。
4. 10% 随机放量 —— 内测基数为十位数（待确认），10% 只有 2-5 人，无统计意义，只制造偶发不可复现的客服负担。改为显式名单 + 阶段扩名单。

### 保留 / 新增的真风险（第一轮漏掉的头号漏洞）

配置随代码发布：灰度默认值写死在 src/config/featureFlags.ts，随部署上线。默认值误设 true，生产站下次部署即全量生效，灰度直接归零。

铁律：新旗标默认 false；生产开启必须是运营台的独立动作（SiteSetting 覆盖），永不随代码部署生效。

### 「不影响生产用户」的三条风险排序

1. 配置随代码发布（部署即生效）→ 默认值纪律（上一条）。
2. 灰度用户拿到坏输出（字体缺失静默替换是 #66 家族已实证机制）→ 字体灰度必须捆绑 readback/coverage 门禁，否则明知有坑还放人进去。
3. 「实时处理生产问题」缺地基：#143（源站 :80 对公网开放、cf-connecting-ip 可伪造）> #138（限流不敢开）> #120（access.log 无 $host 与 $request_time，按站归因不可能）。源站加固比灰度系统本身更优先。

## 6. 开源候选记录（推迟备查）

- Unleash：Node SDK 成熟 + 分群策略全 + 10s Proxy 热刷，但需要 PostgreSQL——本项目 SQLite 单机不匹配。
- GoFeatureFlag：Go 单二进制 + 无 DB + OpenFeature 兼容——若复议首选。
- Flipt：Go 单二进制 + SQLite 默认。
- OpenFeature：CNCF 标准规范，Provider 可换，长期方向。
- Argo Rollouts / Flagger / Istio：K8s 专属，本项目无 K8s，永不适用。
