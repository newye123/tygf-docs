## 1 这半小时实测到的五个硬事实

| # | 事实 | 证据 |
|---|---|---|
| 1 | **Cloudflare 账号 ID 不用你给，我自己找到了** | 服务器 `/etc/cloudflared/token` 是隧道令牌（base64 JSON），其中 `AccountTag` = `5c60acb98ca519b17b7e8a10f9d5b591`。反向确认：用这个 ID 访问 Workers 列表 → `http=200`；换成假 ID（全 0）→ `403 Authentication error` ⇒ **账号 ID 正确** |
| 2 | **令牌的写权限没有生效** | `GET /accounts/<id>/workers/scripts` → 200（0 条）；`PUT .../workers/scripts/tygf-probe-perm` → **403 `No access to the specified resource`**；`GET .../email/routing/addresses` → **403 `Authentication error`**；`GET .../email/routing/rules` → **403**。真账号与假账号在邮件路由接口上都报同样的 403 ⇒ 不是账号 ID 问题，是权限没给 |
| 3 | **飞书通道实测通了（已发真消息）** | 用生产 `/var/www/tygf/.env` 里真实的 `ADMIN_NOTIFY_WEBHOOK_URL` ＋ `ADMIN_NOTIFY_WEBHOOK_SECRET`，跑 Worker 里同一段代码发样例提醒 → `{"ok":true}`。通道配置实测：`ADMIN_NOTIFY_MODE=webhook`、webhook 81 字符、**签名密钥 21 字符已启用**（⇒ Worker 必须做 HMAC 签名，不签会被拒） |
| 4 | **走「站点发版」这条路这段时间走不通** | 生产服务是 `tygf.service`，`ExecStart=/var/www/tygf-current/.next/standalone/server.js`，实际指向 `/var/www/tygf-releases/319bc13…`（该提交在 `main` 上，`git merge-base --is-ancestor` rc=0）。`main` 树里**没有**邮件入口（`git ls-tree -r main -- src/app/api/mail-notifications` 为空），而 `main..origin/develop` = **78 笔**，其中含别人尚未获批的 `20261022120000_quote_billing_scope` 结构迁移（该迁移不在部署脚本批准名单里）⇒ **为了一个邮件提醒去推 78 笔上生产，风险不成比例** |
| 5 | **时间口径与运行时区解耦了** | 服务器 `timedatectl` = `Asia/Shanghai (+0800)`；原 `fmtTime` 用运行时区取时分，换机器就会漂（Worker 跑在 UTC 边缘节点上）⇒ 已改为固定 +08:00 渲染，站内与 Worker 两处一致 |

## 2 改后的链路：一条规则、两个动作、提醒直推

```
访客/用户发信到 tuyi@tuyigf.com
        ↓
Cloudflare Email Routing（一条规则，两个动作）
        ├── 动作① 转发到 353099912@qq.com            ⇒ 信箱收到（A 方案要的）
        └── 动作② 触发 Worker tygf-mail-notify
                        ↓  直接 POST 飞书 webhook（带 HMAC 签名）
              飞书提醒 ⇒ 与「新的内测申请」同一个机器人、同一个会话
```

**为什么把「站内接口」这一跳去掉**：原设计是 Worker → 站内 API → 飞书。它的好处是站内有去重、限流、应用日志；代价是**必须先上生产**（见事实 4）。
一个「收到邮件就告诉我」的提醒不该被一次跨 78 笔提交的发版卡住 ⇒ 改成 Worker 直推；站内入口与 `mail-notify.ts` 全部保留，将来站点上了这个入口，把 `FEISHU_WEBHOOK_URL` 去掉、绑 `SITE_BASE` + `MAIL_HOOK_SECRET` 就切回去（同一份文案、同一个通道）。

## 4 还差什么（都在你这边，二选一）

### 4.1 首选：给同一枚令牌补 3 项权限（约 1 分钟，令牌值不变）

Cloudflare 后台 → 右上头像 → **My Profile / API Tokens** → 找到你刚建的那枚（`cfut_…`）→ **Edit** → 在 Permissions 里加三条，**全部选 Account 级、权限选 Edit**：

| 权限（Cloudflare 界面上的名字） | 作用 |
|---|---|
| `Account` → **Workers Scripts** → **Edit** | 让我能把邮件 Worker 传上去 |
| `Account` → **Email Routing Addresses** → **Edit** | 建 `353099912@qq.com` 这个收信地址（会发验证信） |
| `Account` → **Email Routing Rules** → **Edit** | 建「tuyi@ → 转发 + 触发 Worker」这条规则 |

顺便建议再加两条**只读**权限（不是必须，但以后我能自己排查，不用再问你要东西）：
`Account` → Account Settings → Read；`Zone` → Zone → Read。

> 注意：这三条要选 **Account（账号级）**，不是 Zone（域名级）。Zone 级的邮件路由权限对账号级接口无效——这也是这次 403 的常见原因。

### 4.2 或者：你在后台手点（约 3 分钟，不用改令牌）

Cloudflare 后台 → `tuyigf.com` → **Email** → **Email Routing**：

1. **Destination addresses** → 添加 `353099912@qq.com` → 去 QQ 邮箱点 Cloudflare 的验证信；
2. **Routing rules** → 新建：`tuyi@tuyigf.com` → 动作勾上 `Send to 353099912@qq.com`；
3. Worker 那一半得我来（需要 Workers Edit 权限）——若你只想先要「信箱收到」，做完 1、2 就已经生效，飞书提醒以后再补。

### 4.3 还要点的那个验证（Cloudflare 强制，只有信箱主人能做）

Cloudflare 会往 `353099912@qq.com` 发一封验证信（**很可能在垃圾箱**）。点开确认，转发才会真正生效。

## 7 风险与退路

| 风险 | 处置 |
|---|---|
| 你补权限后仍有 403 | 说明令牌还带着「账号资源范围」或「客户端 IP 过滤」限制；我会把原始错误码打出来定位（不打凭据） |
| 验证信始终收不到 | 走方案 B：把站上 10 处对外邮箱改成 `353099912@qq.com`（首页 2 处在运营台改，其余 8 处改代码），不再依赖 Cloudflare 转发 |
| 你不想给 Cloudflare 权限 | 改成「服务器定时收 QQ 信箱 → 调同一个站内接口 → 飞书提醒」，需要 QQ 邮箱 IMAP 授权码 |
| 提醒重复刷屏 | Worker 只发一条；将来切回站内接口后还有进程内 message-id 去重 |
| 正文隐私 | 提醒只带发件人/主题/前 300 字，**正文全文不出邮箱** |
