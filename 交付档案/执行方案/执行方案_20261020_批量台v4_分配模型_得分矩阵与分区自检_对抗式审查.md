## 阶段一 · Critical Thinking（再往下一层）

### 1.1 v3 的模型在哪儿还不对

v3 说：「表 ＝ 数据集，文件 ＝ 按归属切出的一片」。

**再问一层**：归属是**表的属性**吗？把一张表切成片，片有归属；表本身呢？

不是。**归属是「行」的属性**——一行译文属于哪个文件，取决于这一行是哪一稿的文案。一张表是很多行的容器，它**不归属任何文件**；"这张表是谁的"这个问题，从一开始就问错了主体。

⇒ **推论 1：绑定不是「把表配给文件」，是「把 M 张表的行划分到 N 个文件」。**

这是一个**分配问题（partition / assignment）**，不是一个配对问题。差别是实质的：

| | v3（配对） | v4（分配） |
|---|---|---|
| 绑定单元 | 表 → 文件（整张） | 行 → 文件（可切） |
| 一个表能给几稿用 | 要么独占、要么"组"（另立一个对象） | **任意**——由表里内容决定 |
| 12 SKU 一张合表 | 表达不了（v3 的 E1 已认） | **天然可表达**：它就是"要分区的一张表" |
| 证据 | 规则级联 | **逐对得分**（可排序、可比较） |

### 1.2 于是「宽表」不再是特例

一个表是不是宽表，**不需要人来声明**：**它对多少个文件高分，就是宽表**。

- 一行里只有一个高分格 ⇒ 这一稿的独占表
- 一列在很多行都高分 ⇒ 这一列是宽表 ⇒ 要**分区**，不是直接绑定

⇒ 这条判据是**可计算的**，不是配置项。

### 1.3 再问一层：证据到底该长什么样

v3 的证据是"归属值 + 原文集覆盖"的规则级联。**不对**：那是我用集合包含拍的板，会对合法表误报（表只列了客户要翻的句子时，"覆盖"必然不成立）。

**证据的真实含义只有一个：这张表的行，能对上这一稿的几层？** 这是一个**数**，不是档位。

⇒ **推论 2：证据＝匹配得分（一个数），不是四档枚举。**
档位只是这个数的**人话投影**：

| 投影 | 判据 | 人话 |
|---|---|---|
| 强正 | 命中率 ≥ 阈值，且明显高于其它候选 | 对得上 |
| 强负 | 对任何表都无交集 | 对不上 |
| 中间 | 有交集但不唯一 | 说不清 |

⇒ **判据必须是「覆盖率」这一套口径**（`coverage.ts` 已有的 strict / whitespace / substring 三档），**不许另起一套**（`coverage.ts:106-110` 的明文教训：组件与闸必须同一份口径）。

### 1.4 再问一层：物理上做得到吗

要算"这张表能对上这一稿几层"，需要**这一稿的逐层原文**。

⇒ **Fetch 核实的硬事实**：浏览器**拿不到**逐层原文。

- 扫描摘要 `BrowserPreparationSummary`（`preparation-contract.ts:305-319`）**只有** `fingerprint`（SHA-256）、层计数（text / hidden / uneditable / layerError）、`issues`、排版白名单 `typographyLayers` —— **没有 textLayers**。
- 这正是 `coverage-matrix.tsx:86-92` 那段说明的由来："估算需要设计稿里每个文字图层的原文，而它只留在本机助手侧"。

⇒ **推论 3：得分矩阵只能由助手侧算，浏览器只收分。**
但助手可以回传**逐层哈希**而不是正文 —— 更脱敏、跨次可比，**而且 hex 天然过助手 ID 白名单**（见 §3 的 D17 消解）。

⇒ **推论 4：v3 排在 P2 的"行身份升级（改匹配键）"整条可以删掉。**
理由：若先把表切成片，**片内行只属于一个文件**，同原文多行就是数据错误（现有 `V15_DUPLICATE_SOURCE_ROW` 已拦，`binding-core.ts:930-939`）⇒ **不需要改匹配键**。
⇒ **方案的风险面从「要动执行合同」降到「纯绑定与展示层」。** 这是本轮最重要的**减法**。

### 1.5 v4 的六条公理

| # | 公理 | 证伪条件 |
|---|---|---|
| A | 交付物的键 = (文件, 语种) | 若计费单位不是 (文件, 语种) 则推翻 |
| B | 译文的键 = (归属, 原文, 序号)；**文件不是原语** | 若系统任何一处按"文件+原文"唯一确定一行，则推翻 |
| C | **归属是行的属性，不是表的属性** | 若"表属于文件"是产品必需语义，则推翻 |
| D | **绑定＝行集合的划分（分配问题）**，不是配对 | 若任意表都必须整体绑定且不可切，则推翻 |
| E | **证据＝匹配得分（一个数）**，档位只是人话投影 | 若证据必须是枚举且不可比较，则推翻 |
| F | **切片到位 ⇒ 不需要改匹配键** | 若歧义无法靠划分消除，则推翻 |

## 阶段三 · Deep Thinking（v4 方案）

### 3.1 数据模型（四层引用，全部只存引用）

```
Dataset（译库）   { id, name, rows[], langColumns[] }
  └─ Slice（片） { datasetId, ownerValue?, rowIds[] }      ← 划分结果
       └─ Binding { draftKey → { datasetId, sliceId, languageScope } }
            └─ Evidence { hitRate: 0..100, runnerUp: number, tier: 对得上|说不清|对不上 }
```

对比现状：今天只有 `parsedTables[draftKey]`（一份副本）。v4 是**四层引用**，表只存一份、每稿只存"哪一片"。

### 3.2 得分矩阵（新增，助手侧算，浏览器只收分）

```
行 = 12 个稿        列 = M 张表        格 = 该表对本稿的命中率
```

一条得分的算子：**该表的行（按语种切片后）能命中该稿多少个文字图层**，分母＝该稿可翻译图层数，口径＝`coverage.ts` 的三档之一（strict / whitespace / substring）。

**成本**：≈ Σ(表行数 × Σ稿层数) ≈ 12×60×12×60 ≈ 50 万次归一化比较，助手内存内一次性可完成；**按「表指纹 × 稿指纹」缓存**（Y3/Y4 提供稳定键）。

### 3.3 分区自检（v4 新增的安全闸）

把一张宽表切成 N 片后，**必须**验三条，任何一条不过就不给执行：

| 自检 | 判据 | 失败时 |
|---|---|---|
| **互斥** | 每行 id 恰好属于一片（无行落进两片） | 拦批并点名重叠行 |
| **命中** | 每片对本稿命中率 ≥ 阈值 | 该片拦批，其余片照跑 |
| **有据** | 每片都有归属证据（得分达标） | 该片拦批 |

### 3.4 歧义早报（把执行期的硬错提前到绑定期）

今天"同原文不同译文"在**执行期**炸 `V15_DUPLICATE_SOURCE_ROW`（`binding-core.ts:930-939`），代价是整批拒、孤儿 attempt（#195 的形态）。
⇒ v4 在**绑定期**就问：「这 2 行原文相同、译文不同，分别属于哪一稿？」——早一个阶段，代价小一个数量级。

### 3.5 记录编号：哈希短码 ⇒ D17 结构性消失

v3 的 P1-1 要求"记录编号必须自己过助手 ID 白名单"，那是一条**需要靠纪律维持**的约束。
⇒ v4 改为：`记录编号 = "L" + sha256(层级路径 + 出现序号).slice(0,16)`。
**十六进制 ⇒ 天然纯 ASCII、天然 ≤128、天然匹配 `^[A-Za-z0-9][A-Za-z0-9._:-]{0,127}$`** ⇒ **不需要"转码"这套纪律，也不可能踩 #195**。

（#195 治的是**用户表**里的编号不合规，那条仍要治 —— 两条并存，见 ISSUE #202。）

### 3.6 界面：2 个界面 ＋ 1 个检查器（**比 v3 少一个**）

1. **批次总览**（常驻，跨 4 步）：交付物矩阵，按交付包分组折叠；行头带人话徽章（对得上 / 说不清 / 对不上 / 没配表）
2. **单稿详情**＝图二那一行（矩阵一行的展开，不是另一个页面）
3. **绑定检查器**：得分矩阵 ＋ 候选排名 ＋ 分区自检 ＋ 歧义早报

（v3 的第 4 个视图"译库与切片"并入检查器；"现状对照"是文档不是产品面。）

### 3.7 减法清单（v4 相对 v3 明确**少做**的东西）

| 少做 | 理由 |
|---|---|
| **P2 的「行身份升级（改匹配键）」整条** | 切片到位就不需要改键（公理 F）⇒ **合同变更这条风险整条消失** |
| **「共享表组」作为一等数据对象** | 它只是"一个库切成多片"的一个参数，不需要单独的模型 |
| **「交付包」作为一等数据对象** | 先做**视图层折叠**即可，不进数据模型 |
| **逐层哈希的默认回传** | 见 T4：默认只回传**聚合得分**；逐层哈希是可选加强模式 |
