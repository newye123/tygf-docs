同构问题在行业里长什么样

  • ①
    Trados Studio 社区「Different source files for different target languages」（community.rws.com … /studio/53500/）——提问者的形状与 Owner 几乎一样：源文件自带目标 locale、内容还不一样。行业结论：Trados 的模型是源文件在每个目标语言下都要复制一份，不支持「按文件里的数据直接对上不同目标语言」；社区给的唯一实操路径是把所有版本都传上去、再在每个目标语言下删掉不适用的文件，删完「Manager view 就能一屏看到所有目标语言」。
    对本项目的两条意义（方向相反）：① 不能靠「UI 上不显示」表达「这一稿不做这个语种」——Trados 就是这么被逼出「删文件」这种苦活的，所以文件×语种的作用域必须在数据模型里显式存在；② 「一屏看到所有目标语言 × 所有文件」正是行业认定的正确总览形态，也就是本方案的真矩阵。
  • ②
    Crowdin「Target File Bundles」（support.crowdin.com/bundles/）——把一组源文件打成一个 bundle、bundle 可有各自的目标文件与语言。即「一组文件共享一份交付物」是行业一等公民，对应本方案的「表组／共享表」。
  • ③
    Lokalise「Downloading translation files」（docs.lokalise.com/en/articles/3150682-downloading-translation-files）——同时提供「One file per language」与「每个源文件一份翻译文件」两种形态。即共享表与独立表两种模式并存，不是二选一。
  • ④
    设计工具里的主流形态：一语言一页面／一语言一文件（Figma 生态的 Transifex／Crowdin／Lokalise／iTranslate AI Batch Translation 插件）——批量时选多个 frame 一次翻多语。印证语种是列、稿件是行是设计工具的通用形状。
  • ⑤
    可借的机制名：file mapping——Crowdin CLI／Lokalise 都有「文件映射」：用规则把源文件对上目标文件，而不是手工一对一手配。本方案的「规则自动配对」就是它的桌面版。

05数据模型改造：表提为实体，绑定只存引用

Table（表本体）

{ tableId, name, parsed, rowCount, langColumns }——只解析一次，可被多稿引用。

Binding（每稿的绑定）

{ draftKey → { tableId, mode: 'own'｜'shared', languageScope } }——每稿只存引用，不存副本。

languageScope（新增一等状态）

这一稿实际要翻哪些语种，默认＝该表全部语言列。缺列＝本稿要做但表里没有 → 红框并拦批。

三种配表手段并存

① 规则自动配对（主力，带预览）② 共享表组 ③ 手动逐稿选（保底＋纠正口）。

一次改造解决四件事

共享表不用复制文件；换表＝改一行绑定；「改了这张表会影响哪几稿」可算；持久化只需存绑定关系（表内容仍可不落盘）。

A10 · 关键取舍

共享表只共享表，不合并执行批次。理由：批次是计费与结算的单位（按语种分别计费，pack/page.tsx:594），合批会让「这一稿出了事只退这一稿」变得不可能。（这条推翻了方案起草时自己最初「共享组按组执行」的想头。）

07防错绑三道体检（最关键的安全设计）

为什么必须做

SKU 之间原文高度相似是常态（同一套文案改几个词）。错绑之后：SKU-A 的表绑到 SKU-B → 两稿原文几乎一样 → 覆盖率算出来 100% → 现有所有闸门全绿 → 把错的译文写进客户 PSD，没有任何一处报警。这是本次改造里唯一会造成不可逆错误（写进客户设计文件）的路径。

G1

覆盖率体检（已有，沿用）

矩阵已算绿／琥珀／红；低于 95% 阈值要显式放行，放行记入本批执行摘要。

G2

表 ↔ 稿指纹体检（新增 · P0 不可延后）

表的原文集合 vs 该稿图层原文集合（逐层原文只在助手侧有）：① 命中率 < 60% → 判「这张表可能不是这一稿的」；② 表多出 ≥N 行本稿没有的原文 → 提示「表比稿多 N 行，可能是混稿」。落点：助手侧第 3 步 + 执行前闸。
与既有提示的区别：现有「表多出 N 行」是信息级（提示行号与文案）；缺的是「表可能是别人的」这一层。

G3

缺列体检（新增 · P0）

本稿要做但表里没有的语种 → 红框列出，并拦下「本批开始」。

5.1 · 与同日 08:59 v7 审查已批准结论的冲突点（必须点名，不能默默沿用）

同日 08:59《批量工作台 v7：每稿一表 · 对抗式审查》F9 条写的是「写错风险＝0：match.ts:41-53 归一化原文严格相等配对，外稿行配不上、不会误写」。
这条只在「外稿原文与本稿完全不重叠」时成立。逐字核 src/lib/workbench/match.ts:41-76：runMatch 用 normalizeText 后的原文严格相等建索引（:51）、按行的 sourceText 取命中（:58/:68），取不到即 NO_LAYER_MATCHED（:69-76）。

情形结果
外稿原文与本稿完全不重叠全部 NO_LAYER_MATCHED，一个字都不会写 ⇒ F9 成立（安全，但这一稿也交不出东西）
外稿原文与本稿有重叠（同一套文案改几个词的 SKU——正是 Owner 说的「多个不同 SKU 的亚马逊改语言」）重叠的那几行正常命中，写进去的是另一个 SKU 的译文 ⇒ F9 不成立，错字真会写进客户 PSD
结论

F9 把「外稿行」当成了「必然配不上的行」，漏掉了「原文高度相似 ⇒ 照样配得上」这一档。这不是推翻 v7 的每稿一表设计（那个设计仍然正确、仍然要保留），推翻的是它的风险评估结论：v7 假设「每稿一表」本身足以防住写错；实测不够，因为真正防住写错的是「表和稿是对应的」这个前提，而界面没有、也不曾有办法验证这个前提是否成立。
⇒ G2 升为 P0，且必须排在 v7 已上线部分之外单独排期；在 G2 落地前，批量台每稿一表的能力不得对外宣称「不会写错」。

08批次与计费预告

按 F10，12 稿 → 12 个批次，每批次是该稿已确认的语言数；计费按语种累计（pack/page.tsx:594：50 行 × 12 语种 = 600 分）。因此执行区必须先出一张本批预估表，否则 Owner 看到「12 批次 / 80 语种」会误操作。

本批将产生：12 个批次 · 80 个语种执行 · 预计 4,000 积分（按 50 行 × 80 语种 × 1 分/行·语种 估）
其中：SKU-04 尚未确认任何语言 → 该稿不会进入本批（先做别的稿）

O1「每稿一表」是硬约束还是默认？① 保持硬约束 ② 允许共享表（主表组）②。Owner 已明说「共用一个语言表格这个方向也没有错」；且 12 个 SKU 共用主表是极常见交付形态，①会把它挡死
O2一稿多表（同一稿按语种用不同表）要不要支持？① 不要 ② 要①。② 会把矩阵变成三维（稿×语×表），且与「稿与稿隔离」的信任链前提冲突；真要时用共享组近似
O3绑定关系要不要能恢复？① 不做 ② 只持久化绑定关系（稿路径→表文件名+语种子集+指纹），表内容不落盘②。12 稿刷新一次重绑 12 次不可接受；表内容落本地有隐私顾虑，所以只存「哪张表」
