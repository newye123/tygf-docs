## 一句话

这轮我让两路调研互相打，**它们结论相反**：一路说"断行应该做成数据（行数组 + CSS 决定是否生效）"，另一路说"断行根本不该给运营，交给 CSS `text-wrap:balance`，运营只选样式角色"。我用线上实测裁定：balance 会把中文从词中间切断。所以 v3 的模型是——**断点作数据、版式作角色枚举、内容里不留任何语法**。

## 对抗式审查：v2 被推翻六条（三条是我自己的错）

1. **自相矛盾（撤）**：我上一版批评 Tina 把换行存成私有 `\`，自己却造了 `[[短语]]` 哨兵。业界更根本的做法是**不把版式放进内容**——Webflow 与 Dato 都把版式权限隔离在设计侧。
2. **"零迁移"说轻了**：批注协议注释明写「改动需两侧同步」（`inline-edit-context.tsx:6`），首页硬编码断行/不折行手段实测 **47 处**（`<wbr/>` 8、`<br/>` 7、断行 span 16、`nowrap`/`phrase` span 16），每处都要判"撤还是搬进数据"。
3. **死区方向搞反（实测推翻）**：我写"真正的失效区是 561—1080px"。三档实测：1281px 字号 77px、标题列宽 597px ⇒ 11 字溢出 **202px**；1001px 字号 60px、列宽 938px ⇒ 不溢出；701px 字号 50px、列宽 654px ⇒ 不溢出。风险集中在 **>1080px 的两栏布局**，不是中屏。
4. **排除"换 Tiptap/Lexical"**：① 95 个键 × 每键一个编辑器实例，`useEditor` 生命周期、`immediatelyRender:false`、SSR `generateHTML` 全要跑一遍；② 发布前 before→after 清单与审计要从字符串 diff 改成节点树 diff，那是重写不是补功能；③ ProseMirror 作者自己在文档写「If you're looking for a simple drop-in rich text editor component, ProseMirror is probably not what you need」。顺带纠正一个可能被编出来的名字：Tiptap v3 **没有「ContentKit」**，只有 StarterKit 与 TableKit。
5. **排除"用现成套件替掉我们那 700 行"**：Tina 必须跑它的 GraphQL 层、Sanity `<VisualEditing/>` 依赖 stega + Studio、Payload 依赖 Admin Panel、Directus visual-editing 仓库 **2026-04-22 已归档**、`react-contenteditable` 最后发布 2023-02。结论：**我们那 700 行不是重复造轮子，是这一层的常态**。
6. **v2 完全漏掉的一条**：`text-wrap: stable` 是 MDN 明写"专为 contenteditable 设计、光标前的行不跳动"的能力，正好治就地编辑时的抖动 ⇒ 补进方案。

## 裁定两路冲突的那条实测（balance 对中文不成立）

线上把 6 个 `.section-title` 的碎片合并成整句、交给已启用的 `text-wrap:balance`，用 Range 逐字定位断点：

- 「别让已经确定的版本生产**一 / 直**占着下一份设计的时间」⇒ 切坏「一直」
- 「批量不是一键全自动确**定 / 的**先走」⇒ 断在「的」前
- 「轻松，不是不用改是手上**少 / 做**」⇒ 切坏「少做」
- 「改一个语言不难难的是每个语言都要从头来」⇒ 两行收成一行，节奏丢失

机制解释（调研给的）：balance 是在 UAX#14 合法断点上选点，而中文每字可断，它优化的是行宽均匀，不是词完整性。⇒ **断点必须由作者控制**，但控制方式不是往字符串里塞语法。

## v3 模型三件事

1. **断点＝数据（行数组）**：一个文案键从 `string` 升成 `string[]`，每元素一个视觉行。Owner 在输入框里回车＝新增一行，**他的直觉本来就是对的**；不需要 `\n` 语义、不需要哨兵。CSS 决定是否按这些断点断（宽屏用手动行、窄屏改自动折行）——这是 CSS-Tricks《Injecting a Line Break》的公开做法。现有 33 个碎片键正好机械折成数组元素。
2. **版式＝角色枚举，可用集由设计侧声明**：每个键带 `roles` 白名单，运营选「大标题行 / 强调行 / 副标题行 / 小标签」，role 决定字号与是否折行，**运营看不到 px 和 CSS 类名**。同族做法：Figma Text styles（官方口径覆盖字体/字重/字号/行高/字距/大小写/OpenType，**不含对齐与颜色**，可作用于层内一段）、Apostrophe `styles:[{label,tag,class}]`、Sanity `styles/marks` 的 `{title,value}`。这也正面回答"调字体"——单字体站里它的真实含义是"这句要更重/更大/别断开"，role 全覆盖且不破坏设计语言。
3. **守卫＝词边界提示 + 真实宽度实测，不承诺正确**：`Intl.Segmenter('zh',{granularity:'word'})` 本机可用，把词边界画成刻度、断点落进词内时提示；但实测 3 个坏断点只抓到 1 个（「一直」抓到，「少做」「确定的」漏掉，因为它把很多单字当词）⇒ **只当提示**。硬判据用真实 DOM：行宽 `scrollWidth>clientWidth` 即拦发布；编辑区加 `text-wrap:stable`。

明确不做：内容里的转义符/markdown 标记；换 Tiptap/Lexical；给运营字号数字；"换行只在 ≥某视口生效"的字段语义（两路调研都查不到任何 CMS 提供，按未核实处理，视口差异交给 CSS 与 role）。

## 业界给的那条边界（很重要，改变了我对"给多少权限"的判断）

- Webflow Editor 官方定位是「更新内容、不碰 Designer」，可编辑范围由设计者在 Element settings 的 **Editor permissions** 预先声明。
- Dato visual editing 官方更直白：用隐形 Unicode 元数据把 DOM 映射回字段，**编辑者只能改字段值，版式与样式不可经该工具修改**。
- Notion 官方把语义分开：Enter 换块、Shift+Enter 块内换行。
- Sanity 官方明写常见模式是"一个精简配置（只给 emphasis 和内链，用于 caption）+ 一个全量配置（用于正文）"——**同一字段按位置给不同工具集**，比"加转义符"更贴我们的场景。

⇒ 运营抱怨的"要版式权限"，业界答案是**给受控枚举入口，不给语法**。v3 就是照这条边界设计的。

## 执行顺序

1. **行数组 + 角色枚举 + 三视口预览（估 3—4 天，不碰生产写锁）**：内容树允许 `string | string[]`（读侧兼容、写侧白名单同步）；弹层改"一行一个输入框 + 增删/上下移"；每键带 `roles` 白名单；预览三档（1281/1001/560 按实测参数复刻）；发布前真实 DOM 拦溢出；JSON-LD 与长度上限按"剥离行结构后的可见文字"计。验收：三视口无裁字、`test:seo-consistency` 0 FAIL、`test:content-studio-v1` 加"行数组读写 + 溢出拦截 + 非白名单 role 被拒"用例（含负控）。
2. **47 处硬编码断行手段逐处判"撤/搬"（估 1—2 天）**：`<wbr/>` 与 `<br/>` 多数可被行数组取代，`.nowrap`/`.phrase` 转成 role；每撤一处做截图回归；键名变更走"新键并存 + 自愈迁移"，**不能直接改名**。
3. **覆盖面 + 漏标 lint 守卫（估 2 天）**：页脚 8 处、下载页、EN 站；抄 `eslint-plugin-i18next` 的 `no-literal-string`。
4. **生产放行（仍排最后）**：只是把能力从测试站搬到生产，且触碰生产库写入，等你明令。

## 待你拍两件

1. **行内强调要不要留**：撤掉标记后，"句中某个词更重"有两条路——（推荐）把它拆成单独一行、行 role 选"强调行"，零新语法，现状首屏第二行就是这么做的（`titleLine2` 包在 `<strong>` 里）；或允许标准 markdown `**词**`，业界通用有解析器，但内容里就有语法了、守卫面要扩。默认按前者。
2. **开工顺序**：先做刀一（行数组 + 角色 + 三视口，3—4 天），还是先补覆盖面。我建议刀一——它才是你说的那个"最基本的"。
