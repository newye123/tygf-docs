# 执行方案：批量执行的内存/耗时只读读数（2026-10-20）

> 一句话：先给「第 N 稿会不会越跑越慢」装上只读仪表，20 稿真机跑完用数据决定要不要保护闸；本轮不做任何自动重启或清缓存动作。
>
> **2026-10-20 更新**：20 稿真机已跑完（20/20 成功、每稿 137/137 层），判定**未衰减**——不建保护闸。结果见第 7 节。

## 0. 第一性原理

本质要成的不是「内存到阈值就重启」，而是这一句可判定的话：

**同一次批量里，第 16—20 稿的首跑成功率与中位耗时，和第 1—5 稿没有实质差别。**

满足 → 不需要保护机制，省掉一整条会碰用户 Photoshop 的危险链路。
不满足 → 才有资格谈「每 K 稿分批续跑」这类保护动作，且动作形态必须是「不关用户文档」。

现在这句话无法判定：全仓没有一个「逐稿内存 / 耗时」读数，问题账 `worktrees/develop/AI_MEMORY/ISSUES.md:1187-1190`（R1-106）早就登记「没有 50/100/300 行 × 10/20 语种的容量、内存、恢复证据」，状态 MISSING。

## 1. 现状核对（本次实测，非记忆）

- 每稿落到 PS 的释放只有文档级：一份稿 `app.open` 一次、循环写完所有层，收尾 `close(DONOTSAVECHANGES)`（`download/local-assistant/scripts/TYGF_V15_Thin_Executor.jsx:179/184/262`）。
- 每稿的临时工作副本跑完整目录删除（`v15-runner.js:307` → `:969-973` 的 `fs.rmSync`）；这是磁盘面清理，不是内存面。
- PS 进程全程复用、从不重启：代码明写「Photoshop is a shared COM host and must never be killed by image name」（`server.js:1901-1902`）。
- 唯一的内存字段 `memAvail: $.memCache` 只出现在诊断握手（`server.js:2111/2117`），写完临时文件即 `secureDelete`，没有任何阈值逻辑消费它（全仓扫描：真正运行的 `server.js` 两处，其余三处是 `.next/standalone` 与 `copyright/v1.0`、`v2.0` 存证副本）。
- 执行是串行的：同一时刻只允许一个 Photoshop 任务，忙碌即拒绝新任务（`server.js:2305-2306`）。
- 本机只读实测（10:32:32）：系统 31.8 GB / 空闲 10.9 GB；正在使用的 Photoshop PID 33788 工作集 3,890 MB；另有一枚 11 MB 的残留实例（PID 25308，08:08 起）。

## 2. 对抗式审查（先审本方案自己，六面）

| 面 | 会怎么失败 | 本方案的处置 |
| --- | --- | --- |
| 重复建设 | 已有 engine.log 轮转与脱敏、已有临时目录清场、已有进程自愈 | 不建监控服务、不建新进程；只加一个模块 + 一处接线；日志单独文件，不掺进 engine.log 的脱敏面 |
| 写侧强制力 | 采样逻辑一旦抛错会把「这稿失败」变成「功能坏了」 | 采样全程 try/catch，任何异常返回 null；执行链路不 await 它，失败绝不阻断；负控：注入会抛的 exec 实现，执行必须照跑 |
| 危险动作 | 自动重启/清缓存会关掉用户正在编辑的未保存文档 | 本轮零动作：不 kill、不 purge、不改 PS 首选项、不改 JSX（避免脚本身份哈希变化） |
| 外泄面 | 日志落在用户机器上，等于对外文件，可能带路径/文件名/译文 | 只写 attemptId（不透明串）+ 数字 + 枚举；不写任何文件名、路径、语言译文；负控：正则扫行，命中盘符 / UNC / 邮箱 / `.psd` 即判红 |
| 并发 | 采样阻塞事件循环、两行日志乱序、多人同改同一文件 | 用异步 `execFile`；单行 <4KB 追加；分析器按 attemptId 配对、按时间排序，不依赖行序；本轮只改 `v15-runner.js`（git 现场干净），不碰 `server.js`（11:18 有他人未提交改动）、不提交 |
| 更便宜反方案 | 完全不做也能上线，本方案是不是白干 | 这是唯一能让「要不要保护闸」变成可证伪判断的读数；替代（翻 Windows 事件日志、等 PS 崩溃报告）更贵且拿不到逐稿耗时与序号 |
| 可证伪判据 | 读数接歪了照样出绿 | 三条负控：坏输入不抛；合成「末 5 翻倍」日志必须判衰减；合成「持平」日志必须判未衰减；另加样本 <20 判样本不足 |

## 3. 执行步骤

1. **新增** `download/local-assistant/memory-probe.cjs`：异步调用 `tasklist /FI "IMAGENAME eq Photoshop.exe" /FO CSV /NH` 解析每枚 PS 的 PID 与工作集，叠加 `os.totalmem/freemem` 与本进程 `process.memoryUsage().rss`，写一行 `[mem]` 到 `logs/batch-memory.log`（2MB 轮转，超限改名 `.1`）。任何异常静默。
2. **接线** `v15-runner.js` 的 `runV15Execution`：进入时采一次 `phase=start`（带 assignments 数与 batchId），在 `finally` 采一次 `phase=end`（带状态、完成数、耗时）。
3. **新增** `scripts/analyze-batch-memory.mjs`：按 (batchId, attemptId) 配对，默认只分析最新一批、`--batch` 可回看旧批，输出总数、首 5 与末 5 的 p50 耗时、PS 工作集中位、失败率，给出「衰减 / 未衰减 / 样本不足」判定；样本门槛 20 稿。
4. **新增** `scripts/smoke-assistant-memory-probe.mjs` 并挂 `npm run test:assistant-memory-probe`：解析（含中文系统列名、千分位、多实例）、坏输入、脱敏、三条判定负控、轮转，全断言。
5. **真机一击**：对当前机器上正在跑的 Photoshop 直接跑一次只读采样，证明解析在真实环境成立（不碰文档、不杀进程）。
6. **记账与送达**：`worktrees/develop/AI_MEMORY/TASK_LOG.md` 置顶；根 `AI_MEMORY/ledger.jsonl` 追加（状态「待复验」）并跑投影脚本（失败不阻塞）；方案 md 发飞书（`FEISHU_BOT_WEBHOOK` 通道）。

## 4. 判据与负控

- 主判据：单次批量 ≥20 稿，第 16—20 稿与第 1—5 稿的中位耗时差 ≤10%，且失败率不升 ⇒ 判「无衰减，不建保护闸」。
- 负控 A：喂坏 tasklist 输出 → 采样返回 null 且不抛，执行不受影响。
- 负控 B：合成 24 稿、末 5 稿耗时翻倍 → 分析器必须判「衰减」。
- 负控 C：合成 24 稿、耗时持平 → 必须判「未衰减」。
- 负控 D：合成 10 稿 → 必须判「样本不足」，不得给结论。
- 脱敏闸：日志行不得出现盘符、UNC、`@`、`.psd/.psb`、中文原文。
