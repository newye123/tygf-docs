02 为什么不能简单地"给漏译行一条 AI 译文"

三层原因，都不是 UI 问题

① 产品合同禁译，四处写死：deepseek-align.ts:222「禁止翻译、润色、补写、扩写、改写，也禁止根据常识补全缺失内容」、:218「只能从这里抽取 target」、:309「不能自行翻译，不能补写」、:319「target 必须原样复制候选的 text 字段」。依据是 agents.md Product Drift Guard 第 8 条「概率/置信度不能替代权限」。
② 有缺译时 AI 根本不跑（P0-1），谈建议是空的。
③ 空译行在确定性引擎里的产物是排除（bilingual-align.ts:257 → :76-78，文案"该行无译文，已排除出本次执行"），不是补译。

我的建议：不放开 AI 代译，改成三条不需要翻译的出路

补＝一键聚焦到那格（就地输入框本来就有，review-step.tsx:1186-1208，缺的是"从提示跳到光标"）；借＝从同一张表的其他语言/其他行取现成译文候选（候选池已存在，只是不能点，纯搬运不违反禁译）；排＝这格本来就不该有译文（版权行、色块文字）→ 一键标"不翻译"。这正好也是你说"点进去"的实际意思。

03 外部对照：顺手否证了仓里那句"这个领域没有"

盘上 总控/uiux_20261003/工作台减法_三套版式.html:508 写着「GitHub 上有没有开源的可以直接抄？—— 结论：这个领域没有」。它按"PSD 批量翻译"搜（最好的一个 35 star、功能同题的 0 star），那句在它自己的搜索范围里成立，但搜错了问题。我们的问题是"逐行审阅＋建议＋不阻塞执行"，这条路有很成熟的工业先例：

机制它怎么做到不卡人我们能不能照搬
Weblate 建议与快捷键Ctrl+M 开建议、Ctrl+M+1..9 采纳第 N 条；建议永不自动写入正文；批量补漏译只填空行、不覆盖已有译文，填完标 Needs editing能。直接对应"借候选＋标待复核"
Weblate 状态机Untranslated → Needs editing → Waiting for review → Approved，Approved 只由审核权限置——批准是权限，不是流程卡点能。把"确认当前语言并继续"改成"状态标注＋一次批量批准"
memoQ QA 分级warning 可 Ignore 并置灰；只有 error 级（如标签不配对）不可忽略且导出会失败能，且是我们最该抄的分层——现在我们把"缺一行译文"也当闸用
Phrase TMS 三档强制①默认所有警告可跳过 ②PM 可按检查项关掉跳过 ③mandatory 拦的是"标 Completed"，不拦导出；风险进交付报告能。最合我们"报价／执行"两段式
Trados 自动确认门限只有 100% 精确匹配默认自动确认，fuzzy 必须人工——用门限决定自动与否，不是用拦截能。照搬成"同源唯一候选才允许进批量"
Crowdin 预翻译与 QA批量走队列，完成出 added/skipped 报告；编辑器 QA 是保存时的警告条，可继续能。我们的批量采纳要给同一张报告
Google Docs Suggesting／Notion Suggested edits建议与正文分层存放，可"全部接受"，接受前有整篇预览能。采纳前必须给"改前/改后"整表预览
GitHub PR 批量建议的安全阀"Apply N suggestions" 只对可批量项开放；pending review／行已被改／建议过期 → 一律踢出批量、强制逐条能，而且正好治我们"一格改动作废整批"这个粗暴闸门（P0-3）
Tabulator 校验三档blocking / highlight / manual 三种强度能。建议直接借这三档做内部口径命名
必须一起抄的另一半：一键采纳会让人盲点

用了自动化建议的组，对错误建议的盲从比例高约 26%（综述转述，经典实验 Skitka et al. 2000）；东北大学 2026 实验 107 名开发者用被植入恶意路径的 AI 代理，94% 最终合并、有人自述"已习惯直接点批准"（报道转述，原始论文未核实）。被证明有效的是认知强迫函数（批准前必须做一个动作），而"提醒你警惕"无效。MTPE 研究还发现：同一段文字，被告知"这是机器译文要译后编辑"与"这是人工译文要校对"，人的投入显著不同（出处）。
⇒ 三条硬约束：建议必须露出改前/改后；来源必须标注（确定性算子／同表候选），置信度只用于排序不用于替人签字；批量采纳必须附"动了什么/没动什么"报告＋被踢出的条目清单。
