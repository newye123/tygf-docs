03GitHub 开源调研

3.1 直接可用

直接用

@larksuite/cli（飞书官方）

飞书官方开源 CLI，MIT 协议，约 2.8K★，覆盖 12 个业务域（含多维表格、任务），200+ 命令、19 个 Agent Skill。本机 connector 本来就基于它，装上即可用。

用

飞书官方模板中心

公开的项目管理 / 任务看板 / 甘特图模板库，+template-search 可按关键词搜。字段设计不用从零想。

3.2 借架构、不照抄

借形状

popipo-ai/popipo-feishu-skill

与需求最贴近的参考：链路是「用户反馈群 → 多维表格归档 → 飞书任务分配」。值得抄的是四个工程习惯：

  • 增量拉取：只拉新增，不全量重写
  • 一话题一行：主键稳定，不重复插入
  • --dry-run 预览：写入前先看「将新增多少行」
  • Agent 中间步骤：字段空的行由 AI 补全再进任务——即「AI 负责填、人只看」

裁决：借形状，不装代码。它的脚本是 Python + 自建应用凭据，与本机 CLI 授权体系不同。

3.3 反面教材（重要）

不装

ddddnet/FeiShuDataBase

Python 封装多维表格当免费数据库，功能能用。但它的 README 把 APP_ID 和 APP_SECRET 明文写在示例里（真实凭据）。

裁决：不装。理由不是功能，是它示范了一种会把凭据带进仓库的写法——本项目已有「密钥只放环境变量或后台，禁明文进文档/提交」的红线。

3.4 备查与明确不装

备查

  • feishu-cli（社区，非官方）：Markdown ↔ 飞书文档双向无损转换。台账本体就是 md，将来要推文档可用。
  • 飞书集成平台 anycross：有定时同步模板（多维表格 ↔ MySQL）。属重方案，暂不需要。

明确不装

  • Plane / Vikunja / Focalboard / OpenProject / Taiga：自托管项目管理，生态成熟，甚至有 Vikunja MCP 可让 AI 直接管任务。
  • 理由与上月否决 Unleash 同族——本仓库已有一条完整台账链路，再装一套就是重复建设，且新增一个要部署、备份、升级的系统。我们要的是「换个窗口看账」，不是「再开一本账」。

04对抗式审查 · 八问

1

这会不会变成第四本没人写的账？头号风险

三账休眠 8 天、日报停更 17 天，根因都是靠人写。如果飞书表格同样靠人手动更新，它会以同样的方式烂掉。

裁决：表格内容必须机器写。写手是 AI 会话（装上 CLI 后会话就能直接写表），时机是会话收尾那一步——与「追加 TASK_LOG」合并成同一个动作，不新增人的负担。

可判定标准：表格超过 7 天没更新、而 git 同期有提交 ⇒ 投影链断了，立案。

2

谁是真相源？

若表格是真相源：飞书故障 = 项目失忆；且与 git 无法互证，分歧时不知道信谁。

裁决：单向投影，git 为准。推论：「表格没更新」不算事故；「git 有、表格没有」才算。这条同时回答您的核心诉求——进度权威定义来自 git，表格只是让您看得见。

3

表格里放什么？

不能全量塞。四本账 + 18 个交付目录 + 58 份任务书全进去，等于把混乱从文件系统搬到云端，还是没人看。

裁决：只放两类——① 需要您决策的；② 需要跨会话可见的（谁在做什么、做到哪）。目标规模 20–40 行。不放：代码级细节、单个 bug 编号、历史归档件。

4

谁来写、什么时候写？

写手＝AI 会话（不需要您操作）；时机＝会话收尾，与 TASK_LOG 追加同一步；另加一个定时兜底扫描，比对 git 提交与表格行数，发现漂移就补。

5

多会话并发写会不会冲突？

本项目是多窗口并行的（今天就有 opencode、总控等多手同时在写）。各会话都往表格 append 会出重复行。

裁决：主键幂等。任务 ID 用稳定键（如 T-20261015-01），写入前先查后写（update-or-insert），禁止 append。popipo 那个项目的「一话题一行」就是同一手法。

6

写失败怎么办？

飞书 API 会限流、会超时，CLI 可能没登录。

裁决：不阻塞交付。与现有飞书推送纪律一致——失败只登记、继续干活。表格绝不能成为开工的前置条件，否则飞书一抖，全线停摆。

7

凭据放哪？

CLI 的授权凭据存本机（auth login 后由 CLI 自管），不进仓库、不进文档、不进提交。反面教材见 §3.3——那个把 APP_SECRET 写进 README 的项目。

8

这会不会又是一个仪式？

判据只有一个：您能不能用它回答「谁领了任务、到哪一步」。答不了，就是失败，应当撤掉而不是硬撑。

附带自省：本方案不做仪表盘、不做甘特图、不做自动化 workflow。第一版只要能回答上面那句话。

05执行方案 P0′ · 五步

1

装 CLI 并授权（约 10 分钟，需要您扫码一次）

npm install -g @larksuite/cli          # 版本要求 ≥1.0.97
lark-cli.cmd config init --new --lang en
lark-cli.cmd auth login --recommend    # 这一步需要您扫码
lark-cli.cmd auth status               # 应返回 identity: user

说明：本机 connector 已授权，但那是 WorkBuddy 侧的授权记录；CLI 装好后能否直接复用、还是需要重新登录，属待确认项。

2

建 Base 与表结构

路 A：lark-cli base +template-search --keyword 任务 找官方模板直接套用；路 B：+base-create 自建。建议先看模板再决定。

字段类型说明
任务ID文本（主键）稳定键，如 T-20261015-01
标题文本一句话
状态单选待定 / 进行中 / 等您定 / 已完成 / 已暂缓
负责人单选会话槽（opencode / 总控 / 待派）
下一步文本谁、做什么
出处文本路径:行号，便于回溯
更新时间日期自动
3

写投影脚本（约百行）

输入：AI_MEMORY/TASK_LOG.md 条目 + git 状态；输出：表格行；行为：--dry-run 先预览将新增/更新多少行（抄 popipo 的习惯），确认后按任务 ID 幂等写入。落点：scripts/sync-task-ledger.mjs（与现有 send-feishu-report.mjs 同目录同风格）。

4

接进会话收尾流程

在 AGENTS.md 的「任务结束必做」里加一条：追加 TASK_LOG 之后，跑一次投影脚本（失败不阻塞）。

5

验证与降级

验证：表格里能看到今天的条目、状态正确、能按负责人筛。降级：CLI 未登录 / 网络失败 / 限流 → 脚本退出码非 0，只登记，不影响交付。

06跟总控 A/B 的关系

这一节最重要：您这个提议，实际是总控今早提的 A/B 之外的第三个选项。

选项内容谁提的
A补回三账，恢复派工与复验节拍总控
B三账停写归档，改用 git + TASK_LOG + 机器判据当唯一台账总控（推荐）
C把工作计划搬到飞书多维表格您（本方案）
我的建议

B + C 组合，而不是 C 替代 B。

B 解决「账没人写」

  • 真相源必须是不依赖人自觉、可机器校验的东西——git 有提交就有记录。
  • 这正是总控推荐 B 的理由，我认同。

C 解决「账没人看」

  • 您要的是一个打开就能看、能筛、能按人分组的窗口。
  • md 文件翻起来累，这正是您现在抱怨的事。
正确读法

B 是真相层，C 是视图层。若只做 C 不做 B，表格会变成第四本靠人写的账（问 1 的失败路径）；若只做 B 不做 C，您仍然要翻 md 文件。所以本方案的正确读法是：接受 B 的真相源定义，把 C 作为它的显示窗口。

07待确认（未核实，禁止当事实用）

  • CLI 授权能否复用——本机 connector 已 bound，但 CLI 装好后是直接可用、还是需要重新扫码登录，未实测。
  • API 写入频率限制——飞书多维表格接口限流值未实测；第一版按「会话收尾写一次」设计，理论上远低于任何限流，但未验证。
  • 建表权限——您的飞书账号是否有创建 Base 的权限（个人版/企业版差异），未核实。
  • 模板可用性——官方模板字段名与我们的 7 列是否吻合，未实查；可能仍需自建。
  • 异步可见性——skill 明确提示写入是异步链路，「写成功但立刻读不到」是已知行为，验收时需留缓冲，未实测具体延迟。
