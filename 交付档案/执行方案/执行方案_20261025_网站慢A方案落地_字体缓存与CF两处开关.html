01改了什么：字体分片的缓存头

只动了一个文件 next.config.ts，加一条响应头规则，只作用于 /fonts/*：

改法　Cache-Control: public, max-age=3600, stale-while-revalidate=86400

意思是：边缘先存 1 小时，过期后先拿旧的顶着、同时在后台去源站取新的（最多顶 1 天）。常规访问不再回源。

为什么不能更狠（比如像 /_next/static 那样给一年 immutable）：字体分片文件名不带 hash——public/fonts/shsc/manifest.json 只记了 sha256，文件名永远是 zh-subset-0..3.woff2。给一年，以后换字体用户会长期拿旧的。1 小时是「改字体最多 1 小时生效」和「常规访问不回源」之间的折中。

路径改之前改之后（实测）说明
/fonts/shsc/zh-subset-0.woff2public, max-age=0public, max-age=3600, stale-while-revalidate=86400本次目标
/fonts/zh-supplement.woff2public, max-age=0同上第 5 个分片也覆盖到
/_next/static/chunks/*.css一年 immutable未变对照组：没误伤
/（首页 HTML）private, no-store, must-revalidate未变故意不动，见 03 节

为什么首页 HTML 一行没碰：首页服务端要读草稿模式、会话 cookie（src/app/(zh)/page.tsx:32,35）、功能开关，HTML 里带着登录态摘要。把这种响应做成可缓存，一旦边缘规则没配好「带 cookie 就绕过」，就可能把 A 用户的登录页发给 B 用户。所以 HTML 缓存只能和 Cloudflare 规则成对上线。

顺手否掉的一个假设：我原来怀疑「5 个字体分片全量预载＝浪费」。实测首页 585 个码位确实散落在全部 5 个分片上（命中 155 / 179 / 173 / 76 / 2），浪费 0 字节。全量预载是合理的，这条不动。

03A1：首页进边缘缓存——要你在 Cloudflare 点（约 3 分钟）

这台机器上没有任何 Cloudflare 凭据：CLOUDFLARE_API_TOKEN / CF_API_TOKEN / CLOUDFLARE_ACCOUNT_ID 等在三处（User / Machine / Process）都不存在；项目里唯一读它们的是 scripts/configure-mail-routing.mjs:35-36（邮件路由脚本），也没配。

路径　Cloudflare Dashboard → 选 tuyigf.com → Rules → Cache Rules → Create rule，名字填 home-html-edge-cache。

匹配表达式（用 Expression Editor 粘贴，一行一条）：

(http.request.uri.path in {"/" "/en"})
and not (http.cookie contains "tygf_user_session")
and not (http.cookie contains "__prerender_bypass")
and not (http.request.uri.query contains "_rsc")
and not (http.request.uri.query contains "edit")
and not any(http.request.headers["rsc"][*] eq "1")

Then 部分：Cache eligibility 选 Eligible for cache；Edge TTL 选 Ignore cache-control header and use this TTL，填 5 minutes；Browser TTL 保持默认。

排除项拦的是什么少写会怎样
tygf_user_session登录会话 cookie（src/lib/auth/session.ts:23）登录用户的页面进了公共缓存，可能发给别人
__prerender_bypass运营台「就地直改」的草稿会话编辑者看到的是线上版，不是草稿
_rsc / RSCApp Router 客户端导航取的数据流站内点链接可能拿回一整页 HTML，跳转坏掉
edit?edit=1 就地编辑入口编辑态被缓存，改完看不到

上线后怎么验：① 无痕窗口开两次 https://tuyigf.com/，第二次响应头应出现 cf-cache-status: HIT；② 登录后刷新应仍是 BYPASS/DYNAMIC（说明会话没被缓存）；③ 站内点几个链接，跳转要正常（说明 _rsc 排除生效）。

代价　你在运营台改完文案，最多 5 分钟后才对访客生效。要立刻生效，就在 Cloudflare 点一次 Purge。

04A4：我上一版说反了，这里更正

上一版报告写「关 h3」。实测后确认说反了——现在跑的是 h2，而 h2 正是那个 134 秒的元凶。

现场真浏览器

23 个资源全部 nextHopProtocol = h2，刷新后仍是 h2。8 个 JS chunk 同时第 11.4 秒发起、同时第 134.3 秒才拿到首字节——h2 队头阻塞的标准指纹。

对照同一台机器

h1 五次里成三次（3/5），h2 五次全败（0/5）。高丢包下，一条连接扛所有文件反而是放大伤害。

h3Cloudflare 侧

响应头有 alt-svc: h3=":443"; ma=86400（直连源站没有，是 CF 注入的）⇒ h3 对我们域名是开着的，只是这段链路没跑起来。

堵死免费版限制

「关掉 HTTP/2 退回 h1.1 隔离丢包」这条路免费版走不通——Cloudflare 官方文档明写 Free 计划不能关闭 HTTP/2。

所以 A4 的正确动作：CF → Speed → Settings → Protocol Optimization，确认 HTTP/3 (with QUIC) 是 On（大概率已经是）。真正的验证只能换一条网络做：手机热点开一次站点，看导航的 nextHopProtocol 是不是 h3。是 ⇒ 本机联通拦了 QUIC；还是 h2 ⇒ 要在 CF 后台确认开关与 QUIC 端口。
