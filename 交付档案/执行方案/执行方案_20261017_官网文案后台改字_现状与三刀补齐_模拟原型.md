## GitHub 参照后的两处自我更正

调研 Tina CMS / Keystatic / Decap / Payload / Sanity / Apostrophe 的公开文档与仓库后，推翻我自己上一版方案两处：

- **守卫该用 lint，不该用发布门数 DOM**。原方案是「发布门比对 DOM 文本节点 vs 有键节点」；正解是抄 i18n 生态现成轮子——`eslint-plugin-i18next` 的 `no-literal-string`（默认只查 JSX 纯文本节点、支持白名单组件）或 `@lingui/eslint-plugin` 的 `no-unlocalized-strings`，改写成「站点组件里出现未经 `sc()`/`<T>` 包裹的中文文本节点即 error」。写代码阶段就报、精确到行，比出包时才发现便宜一个量级。再进一步是 `<T p="homeV17.hero.copyA">默认文案</T>` 组件（key 自动查内容树、未命中即报错），一次解决「标注成本高」和「漏标」两件事——Apostrophe 的 `<Field>` 与 Sanity「文案必须来自数据层」合起来就是这个形态。
- **结构编辑不该在页面上给每行加箭头**。Tina 的 `list`、Payload 的 `blocks` 都把增删排序放在侧栏表单；唯一贴近「就地 + 数组」的 Apostrophe 也是**一次 patch 一个块**。我们的正确形状是把 `faq.items` 当数组字段整体对待，编辑层给整块控件、**一次写回整个数组** + 结构级 diff。现状 `patchStringLeaf`（`site-content-paths.ts:57` 起）只在目标确为字符串时写入，所以动不了条。

另一处框更正：**生产 403 不是缺陷**。Keystatic 官方 recipe 就是「生产环境禁用 Admin 路由」，与我们现状同构。所以「要不要开生产写」是**选路线**：路线 A＝生产禁写、文案一律走代码默认值 + 发版（现状，最严，Owner 改一个字要等出包）；路线 B＝生产可写，但配字段级权限 + 审计 + 批准到期（Payload / Apostrophe / Sanity 形态）。Owner 的诉求指向 B，代价是生产库多一个写面。

还有一条最该抄而我原方案漏了：**按 key 前缀的字段级权限**（Payload `access-control`）——法律页 `privacy.*` / `terms.*` 应只允许 Owner 且必填理由；现状是 owner 一刀切，「谁能读草稿」也没有（10-16 法律页那单已登记此缺口未做）。

明确不抄：iframe 双栏后台预览、git 分支草稿→PR 合并状态机（Decap）、Yjs 多人实时协同、全量 stega 零宽编码（要求全站文案走数据层）、富文本 WYSIWYG 与拖拽排版。业界**没有**字段级三方合并的成熟形态，只有版本快照+diff、分支走 PR、把写粒度压到单字段三种替代；我们已是「digest + 单字段 PATCH + 发布清单」，属主流，不要上 CRDT。

**刀二 · 覆盖 + lint 守卫（估 2—3 个工作日）**
