## 一句话

**你要的不是「再做一个看板」，是一个「控制面」（中台）。**

飞书多维表格只是**显示窗口**——它把「有哪些事」摊开了，但它管不住「同时在办几件」「谁在做」「做完了算不算数」。这三件才是你说「还是不够」的真正缺口。GitHub 上成熟做法几乎一致：**真相放在 git，状态靠一个固定的状态机，用「限值＋闸门」把在办数量压下来，看板只是它的一个视图**。

所以本方案 = 在现有飞书表之上，加一层**最小控制面**，并把「在办上限」从现在的 7 条压到 **2 条**。这是全部建议里唯一真正治本的一条。

### 3.1 六类成熟做法

| # | 项目 | 是什么 | 可搬的一句话 |
|---|---|---|---|
| 1 | **`issue-orchestrator/issue-orchestrator`** | 给编码 Agent 做的「**headless 控制面**」：把 GitHub issue 变成隔离 worktree 里的有界运行，经校验/复验/返修/人工批准四道门才推进 | **「Agent 提议、编排器裁决」**；**Agent 不能合并 PR，人合并**；每个 issue 一个 worktree、一个状态机；改状态前**先重观测**（防崩坏） |
| 2 | **`open-agentos/agentos`** | **把 GitHub 当 AI 操作系统**：issue 走 label 状态机（`status:plan/todo/in-progress/blocked/done`），每次迁移触发一个 Actions 工作流派发给对应角色的 Agent | **状态机即路由**；**每个角色一个最小权限身份**（reviewer 不能推代码）；`AGENTS.md` 是全体 Agent 的操作手册 |
| 3 | **`nordinit/agent-hq`** | 「控制面」：`task → route → agent run → **evidence** → outcome → transition` | **完成必须交证据**（evidence gate），没证据不推进 |
| 4 | **`luminik-io/alfred`** | 全在 GitHub 上实现的**认领状态机**：label 载状态、结构化注释载审计；无共享数据库 | **认领/释放原语**——防止两个执行者重复做同一件；带黏性闸 `do-not-pickup`／`needs:human-scope`／`plan-pending-approval` |
| 5 | **`skdhir/ai-agent-orchestra`** | **单人创始人**跑多 Agent 的实操手册（120+ PR、3 Agent、1 个人） | **Agent 之间靠「文件」协调，不靠对话**；**人是瓶颈不是 Agent**——3 个并行是单人复验上限；写码前先给 2–3 个选项等批准 |
| 6 | **`ParallelPilot`（arXiv 2609.33113）＋ agentpatterns** | 学术与工业界对「并行 AI 编码」的同情式研究 | 归纳出 **PILOT**（Planning/Isolating/Logging/Observing/Triaging）；**Brooks 定律对 Agent 同样成立**——并行一多，协调开销会超过收益 |

**旁证（大厂同向）**：GitHub 自己把「Agent Control Plane / Mission Control」做成了产品（企业级审计 + 会话活动 + 审批）；GitHub Issues 2026 也加了「Agent 自动化控制」——**approvals / confidence / rationale**（高置信自动应用，中低置信挂起等你批）。⇒ **「控制面」不是我的发明，是行业共识。**

### 3.2 六家的共同结论（也是给你的答案）

1. **真相必须是「外部的、崩了也还在的」东西**——首选 git / issue label，**不是**一个新的数据库或看板。
2. **状态机要固定、要有限**——不是「任意进度文字」，而是几个枚举状态 + 迁移规则。
3. **要有「闸门」**——完成不等于自报完成，要过证据门/复验门；发布要过人工批准门。
4. **要有「限值」**——同时能「在办」的数量必须卡死；跨过就排队。
5. **要有「认领」**——同一件同时只能一个人（或一个会话）在做。
6. **看板只是窗口**——把上面五条做好，看板自然能用；反过来先做看板，就是第四本没人写的账。

## 五、中台设计：三层 + 五个机制

### 三层（借 3.2 的结论）

```
视图层  飞书多维表格（已有）＋ 每天一条 watchdog 日检
          ↑ 只读投影，单向
控制层  中台本体：状态机 · 在办限值 · 五个闸门 · 认领锁      ← 本方案要补的就是这层
          ↑ 只写 ledger.jsonl
真相层  git 提交历史 ＋ AI_MEMORY/TASK_LOG.md ＋ AI_MEMORY/ledger.jsonl
```

**单向**：只有真相层能被写；控制层读真相层算判据；视图层只显示。**「表没更新」不算事故，「git 有而表没有」才算事故。**

### 五个机制（逐个对应上面的缺口）

| 机制 | 做什么 | 借自 | 对应你的哪个痛点 |
|---|---|---|---|
| **① 认领锁** | 一个任务同一时刻只有一个会话认领；重复认领必须失败 | alfred | 「谁在做」说不清 |
| **② 在办限值 = 2** | 同时在办 ≤2（1 产品 + 1 应急）；超了就排队，开新的必须先关一件 | Personal Kanban / GitHub Projects | 「线太多、顾不过来」 |
| **③ 决策闸** | 只有 `等您定` 的才占你的注意力；其余机器干 | 项目既有四档排期 | 「都想要做」 |
| **④ 证据闸** | 翻「已交付」必须带证据（`file:line` + 真实 rc）；自报不算数 | agent-hq / issue-orchestrator | 「做没做到什么地步」 |
| **⑤ 发布挂号闸** | 任何进 `main` 的合并，同一次提交带一行挂号（sha/包名/时刻/复验件）；查不到即立案 | 项目自身 R1 | 今晨发布无台账 |
| **＋到期断路器** | 每条线写到期日；到期未完成→自动降级「已搁置」，不占名额 | Shape Up | 线永远挂着不清 |
