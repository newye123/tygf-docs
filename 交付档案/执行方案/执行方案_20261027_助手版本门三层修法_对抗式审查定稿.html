011. 审计结果（这是决定方案形状的证据）

事实实测
契约三元组变了吗没变：reportSchemaVersion=local-report-v2、reportRendererVersion=renderer-v3、替换脚本 sha256 两边同为 882a4a8655ed…
那什么在挡 3.7.15只有两道：版本下限 3.7.28（:69-72）＋ assistantBuildId 逐位相等（:75-84）
助手侧真实改动量origin/main..HEAD 有 27 笔碰 download/local-assistant
其中含必修修复吗含。按主题判读至少四类不在契约三元组里体现：本机 HTTP 卫生（Vary: Origin／PNA 预检／Host 回环白名单，66cbb30e）、会话文件读不出来时不再被默认配置覆盖（3a220b9c，数据丢失级）、执行期技术目录搬出客户素材目录（f049969b）、回执链留痕与不再自崩（a624e8c6，ISSUES #247）
被挡的客户有出口吗没有。文案是"升级本地助手到 v3.7.28 后重启"（batch-execution-mode.ts:225）、"升级本地助手后刷新页面"（batch-execution-client.ts:233），附近 grep href/download/Link 0 命中——叫客户升级，不给按钮

⇒ 直接"降门放 3.7.15 进来"= 把这 27 笔里的安全与数据安全修复一起绕过去，正是本项目红线"不得静默降级"要拦的事。A 原样否决。

022. 但 A 里有一条独立成立的真缺陷：buildId 相等会拒掉"更新"的助手

:75-84 是 !== 逐位相等，不是"不低于"。⇒ 一个比网页更新、但 buildId 不同的助手同样被拒。

现实场景：内测客户从测试站装了 3.7.28+，回到生产（生产声明 cors-preflight…/transport-hardening… 另一枚）就被挡；或将来发 3.7.29 而网页还钉在 3.7.28。

这条与"要不要放行旧版"无关，是方向性 bug：兼容判断把"更新"当成不兼容。

033. 定稿：三层，按能不能立刻做排序

P0（纯界面，无门风险，随下次发布生效）

被挡时给客户能点的出口，而不是一句"请升级"：

  • 在版本不足/构建不符的提示位加"下载新版助手"入口（/download 页已在，安装包随包在 public/downloads/）
  • 文案补一句可操作的"完全退出（含托盘）后再打开"——现在只说"完全重启"，没说托盘
  • 不改任何判定逻辑，只改呈现。落点：src/lib/server/batch-execution-mode.ts:225、src/lib/workbench/batch-execution-client.ts:233 的调用方界面

P1（改门语义，属发布身份路径 ⇒ 永远需要人批，我不自己动）

两件事一起做，缺一不可：

  1. assistantBuildId 从"拒绝条件"降为"遥测字段"——照常上报、照常入库、照常用于取证，但不再据此拒绝。理由：它不提供任何兼容性信息，契约三元组才是；而它现在的 !== 语义会误伤更新的助手（§2）。
  2. 版本下限保留，但抬它要有判据：只有满足下列任一条才允许抬，并须在 config/release-identity.json 旁留一行"本次为什么抬"：

- 契约三元组任一变化（schema／renderer／替换脚本摘要）

- 随车含安全或数据安全类助手修复（如 §1 那四类）

- 服务端新增助手必须支持的接口

⇒ 效果："只是重打包、契约没变、没带必修修复"的发布不再砸客户；而真需要修的那一版，仍然响亮拒绝，不静默降级。

  1. 同批必须扫掉与这道门绑定的说法（本项目立过的纪律：撤一条闸要同批撤它的对外说法，否则上线就是一句假话）。P1-1 一旦生效，以下三处要同时改：

- 发布线记录里"身份门核 size＋sha256／核构建一致"一类的表述（该口径已记过一次证伪与一次更正，不能再留旧说法）

- runtime-provenance 的字段语义说明：expectedAssistantBuildId 从"拒绝依据"变成"记录字段"，消费方（后台读数、诊断件、任何拿它判'版本对不对'的地方）要跟着改口径

- 守卫反向锁死：加一条断言，防止有人日后把 !== 判据悄悄加回来而不清掉 whyBumped 机制（两者必须同生同死）

落点先 grep 再定，未列清单前不许动 P1-1——这条是 P1-1 的前置，不是后续。

P2（真解，你 09-25 15:4x 已批、至今零代码）

自动更新。现状取证：助手源码里 autoUpdate|checkUpdate|updater|downloadNewVersion 0 命中；两本任务书在（任务书_AUTO-UPDATE-REPLACE_安装包自替换勘察_20260925.md、任务书_AUTO-UPDATE-IMPL_助手自签更新_20260925.md），实现发当时被裁"不开"。

已知硬前置（勘察件记录）：须能自停托盘＋引擎两进程、静默装完不自动拉起、不弹 UAC；"谁负责重启、失败怎么回滚"全仓无落点；仓内零签名私钥接入点，三件要从零建。

⇒ 这条要单独立项，不要为了今天的痛点仓促上（它同时是安全面）。

044. 对抗式审查：审这份方案自己

#攻击判定与处置
1P1-1 删掉 buildId 相等 ⇒ 改了助手 JS 但没动契约三元组的版本会混进来（例：3a220b9c 会话覆盖修复就是纯 JS 修复）成立，是 P1 的真漏洞。处置：P1 必须同时做 1 和 2——下限保留 + 抬下限要有判据并留痕。单做 1 等于拆门。
2"抬下限要有判据"靠人自觉，没人遵守怎么办按本项目纪律＝无效判据。处置：判据要能机器查——发布前比对 release-identity.json 的 assistantVersion 是否抬升，若抬升则必须存在同笔的 whyBumped 行，否则出包红。这条落点是 scripts/check-release-identity.cjs（已存在的门，不新建）。
3P0 给了下载按钮，但客户下了没完全重启，还是被挡，反而更像我们的锅成立。处置：P0 文案必须同屏给"退出托盘再打开"的动作指引，不能只给按钮。
4现在就把下限降回 3.7.15 以解燃眉否决（§1）：会绕过 Host 回环白名单、会话覆盖防护、素材目录污染、回执自崩等修复。
5这套改完，本次生产发布就能推了吗不能。发布仍卡在上一次审查的四条前置（合 main 2 笔／生产补 ApplicationAttribution 表／助手随发决定／多稿补声明）。本方案只解决"以后不再每版砸客户"，不解决"这一版怎么上"。
6我对 27 笔的定性可靠吗只按提交主题判读，未逐笔读 diff。§1 那四类是主题级证据；真要放行某一版，需逐笔定性。列入覆盖缺口。
7P1-1 拆掉 buildId 拒绝后，信任链会怎样本轮 grep 出的新事实，比门本身更要紧：expectedAssistantBuildId 不止用于拒绝，它被写进签名执行清单（src/lib/trust-chain/execution-manifest.ts:98、:183 断言、:283 落成 expected_assistant_build_id）。⇒ 只删拒绝而不动这里，清单会出现"期望构建 ≠ 实际构建而无人拦"的记录，证据链内部一致性主张失真。处置：P1-1 必须同时定信任链口径——buildId 作为证据字段照记，但"一致"不再是有效性条件；且 batch-execution-mode.ts:232 那句让用户"确认构建、报告 schema 和 renderer 三项一致"的提示须同批改，否则界面教客户去凑一个已经不拦的东西。
