02裁定两路冲突的那条实测

verdict

「撤掉手动断点、交给 text-wrap:balance」这条路在中文站不成立：balance 是在 UAX#14 合法断点上选点，而中文每个字都可断，它优化的是行宽均匀，不是词完整性。

线上标题（合并碎片后）balance 实测断点结果
别让已经确定的版本生产一直占着下一份设计的时间…生产一 / 直占着…切坏「一直」
批量不是一键全自动确定的先走，拿不准的先停…全自动确定 / 的先走…断在「的」前
轻松，不是不用改是手上少做，眼里少找……手上少 / 做，眼里…切坏「少做」
改一个语言不难难的是每个语言都要从头来不断（收成 1 行）两行节奏丢失

所以：断点必须由作者控制（这条两路调研都不反对），但控制方式不是往字符串里塞语法，而是把"一行"做成数据；版式（字号、是否折行）另做成设计侧声明的角色枚举。这也正是 Webflow Editor 与 Dato visual editing 的共同边界——Dato 官方直白：编辑者只能改字段值，版式与样式不可经该工具修改；Webflow 的可编辑范围由设计者在 Element settings 的 Editor permissions 预先声明。

04v3 模型：三件事，内容里不留语法

① 断点＝数据（行数组），不是标记

核心

一个文案键从 string 升成 string[]（每元素一个视觉行）。Owner 在输入框里回车＝新增一行，他的直觉本来就是对的；不需要 \n 语义、不需要哨兵。CSS 决定是否真的按这些断点断（>1080px 用手动行，窄屏改自动折行）——这是 CSS-Tricks《Injecting a Line Break》的公开做法，不是我们发明的。

现有 33 个碎片键（titleL2a/L2b/L2c 等）正好一一折成数组元素，迁移是机械的

② 版式＝角色枚举，由设计侧声明可用集

核心

每个键带一份 roles 白名单（设计侧写死），运营在框里选：大标题行 / 副标题行 / 强调行 / 不折行短语 / 小标签。role 决定字号与是否折行，运营永远看不到 px 和 CSS 类名。同族做法：Figma Text styles（官方口径：覆盖字体/字重/字号/行高/字距/大小写/OpenType，不含对齐与颜色，且可作用于层内一段）、Apostrophe styles:[{label,tag,class}]、Sanity styles/marks 的 {title,value}。

顺带解决"字体"这条：他要的"调字体"在单字体站里的真实含义是"这句要更重/更大/别断开"——role 全覆盖，且不破坏设计语言

③ 守卫＝词边界提示 + 溢出实测，不承诺正确

辅助

Intl.Segmenter('zh',{granularity:'word'}) 本机可用（实测），可以把词边界画成刻度、并在断点落进词内时提示。但实测它 3 例只抓到 1 例（「一直」抓到，「少做」「确定的」漏掉，因为它把很多单字当词）⇒ 只当提示，不当保证。硬判据用真实 DOM：行宽 scrollWidth>clientWidth 即拦发布；编辑区加 text-wrap:stable 防光标跳动。

明确不做

不做内容里的转义符/markdown 标记（v2 那条撤了）；不换 Tiptap/Lexical；不给运营字号数字；不做"换行只在 ≥某视口生效"的字段语义——两路调研都查不到任何 CMS 提供这个（记为未核实），视口差异交给 CSS 与 role，不交给内容。

① 行内强调要不要留

需拍
