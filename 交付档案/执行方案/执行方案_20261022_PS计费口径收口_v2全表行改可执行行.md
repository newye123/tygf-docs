**运行版本**：10-22 那笔任务实际跑的是 Web `9b0d566f18d4f4432501ab5e20abcb7def885421`、助手 3.7.19

## 一、先给结论

1. 10-22「B级 8 图」：账上扣 68，应该有 31，**多收 37**。
   - 67 行译文，68 个计费单位；其中第 55 行原文 239 字符、译文 258 字符，按规则算 2 单位。
   - 报告里 36 行"无对应对象"；这 36 行合计 37 单位，第 55 行就在其中。
   - 真正发生替换的 31 行 = 31 单位。68 − 37 = 31。
2. 10-21「设计x8」：112 行 → 110 单位 → 扣 110，账本算术自洽；但这台机器上没有它的执行报告，服务端也不存报告正文，**无法判定是否也多收**。不能凭猜测退款。
3. 这不是 10-20 或 10-21 改坏的：单语链"按全表行计费"从 2026-07-18 / 07-29 就是这样；把 10-20 / 10-21 的代码退回来，同样的 67 行仍然扣 68。
4. 真正的根因是两条链口径不一致：单语链（v2）按快照全表报价、整单成败结算；批量链（v3）按 `INCLUDED` 可执行行报价。v3 是对的，v2 缺了"排除未覆盖行"这一步。

> 证据等级：下面所有关键数字都是 A 级——本会话复跑的测试站只读查询、本机报告原文、账本记录；不是转述。

- 本机报告：`F:\改语言\ 5857\(B级)Amazon-5857-主副图-8-祝叶子__20261022_083709188\图译工坊执行报告.html`
  - "译文表 36 行无对应对象"清单共 36 行，包含第 55 行；
  - "已写入 / 计划 29 / 29"、"应完成 29 / 已收到 29"；
  - "排除图层" 8 个。
- 36 行未覆盖里，只有第 55 行是 2 单位，其余 35 行各 1 单位 → 未覆盖合计 37 单位；67 行总 68 单位 − 37 = 31 单位。
- 账本：10-22 08:36:45 这笔 reserve −68、commit −68、release 0，余额 14689；对应 attempt `b95b33eb-b853-431b-a8fa-db2ccc4df079`、runId `424f2dac-adf5-4913-ac87-485ad85cdf9f`。

### 2.2 服务端为什么没拦住

- 报价：`execute-step.tsx:918-923` 把全部 `reviewRows` 写进快照；`photoshop-billing.ts:144-145` 对全部快照行调用 `estimateBilling`；报价 API 只收 snapshotId / manifestHash / quoteRequestId（`app/api/billing/photoshop/quote/route.ts:35-41`），没有"哪些行不该计费"的入参。
- 结算：`photoshop-billing.ts:602-611` 是整单成败——只要 `deliveryStatus === 'complete'`、导出文件 > 0、错误数为 0，就把 `quote.standardRowCount` 全部记为成功。
- 回执：`settlement-adapter.ts:26` 只要产物已发布就把 `deliveryStatus` 设为 `complete`；`:35` 把 `skippedLayers` 写死 0。于是 `photoshop-billing.ts:606-607` 那条"有未匹配 / 跳过就不算完整"的旧分支永远走不到。
- 报告：`report-renderer.js:716` 写着"未覆盖对象不计费"，但 v2 实际照收。这句话现在是假话。

### 2.3 v3 为什么是对的

- `execute-step.tsx:1040-1080`：先用 `buildBatchExecutableRows` 排除忽略行，再把未匹配行的 `scopeStatus` 标成 `EXCLUDED`、`requiredObjectCount` 置 0。
- `batch-v3.ts:59`：`scopeStatus !== 'INCLUDED'` 直接返回 0 单位。
- `execution-batch.ts:188-190`：服务端只对 `INCLUDED` 行报价。
- 所以同一个 67 行输入走 v3，不会按 68 收。

### 2.4 为什么"退回之前"不成立

- 单语链的全表快照代码：`execute-step.tsx:918-923` 来自 2026-07-18；全表估算 `:788-792` 来自 2026-07-29；计费规则 `rules.ts` 自 2026-07-29 未变。
- 10-20 的 `3d85a2ad` 只是把 `batchMode` 改名为 `useBatchChain` 并加了多稿判断；10-21 的 `525559c4` 没碰计费标识。
- `git diff 9b0d566f..HEAD` 对五个计费文件（`photoshop-billing.ts`、`rules.ts`、`execute-step.tsx`、`local-assistant-client.ts`、`v15-execution-orchestrator.ts`）输出为空，退出码 0（本次复跑）。
- 结论：退到 10-20 / 10-21 的包，同样输入仍然扣 68。回退只会把别的东西退坏，不会修多收。

## 三、执行方案

原则：**前向修复，不回退；一次合同变更，四层同笔；先测试站，生产等批准；历史账不自动退。**

### P0 冻结与定责（0.5 天，无代码）

### P1 报价范围合同（1 天，Web / Server）

目标：报价只对"真正会发生替换的行"计费，快照仍然保留全表证据。

1. 报价 API 增加可选 `billingScope`：`[{ language, rowIndex, reason: 'IGNORED' | 'UNMATCHED' }]`。
   - 校验：快照存在；语言匹配；rowIndex 在快照内；无重复；reason 合法；**全部行都被排除时拒绝报价**（`BILLING_SCOPE_EMPTY`），不冻结积分。
2. `BillingQuote` 增加 `billingScopeJson`、`billingScopeDigest`（可空）；把 digest 纳入 `requestPayloadHash`，同一请求号 + 同一范围幂等，范围变了就是新报价。
3. `createPhotoshopQuote` 把范围内行按 `ignored: true` 传给 `estimateBilling`：`rawRowCount` 保持 67（全表证据），`standardRowCount` 变成 31（可计费）。
4. 不改 `ReviewSnapshot.tableJson`、不删 decision：这样 `manifestHash`、`normalizeReviewDecisions` 的 `REVIEW_DECISION_LANGUAGE_MISMATCH` 校验都不受影响（`review-evidence.ts:168-171`）。
5. 浏览器：`execute-step.tsx` 用当前语言的 `ignoredTranslationRowIds` + `unmatchedTranslationRowIds` 组范围，经 `local-assistant-client.ts` 和 `v15-execution-orchestrator.ts:177-183` 传给报价。
6. 执行前对账：prepare 返回后，拿助手真实未覆盖集合与报价范围比对；不一致就停止并释放预留，不进入执行。
7. 验收：67 行 / 36 行未覆盖的 fixture，报价必须是 31（不是 68）；同一输入走 v3 也必须是 31；全排除必须拒绝且不扣费。

**注意**：P1 单独上线只能挡住"浏览器已经知道的未覆盖行"；助手在 prepare 时新发现的未覆盖行仍可能被计费。所以 P1 必须和 P2 同笔发布，不能只发 P1 就上生产。

### P2 行级证据与结算闸（2 天，助手 3.7.21 + 服务端）

目标：结算能证明"报价的每一行都真的被替换了"，而不是只数对象。

1. 助手 prepare 返回真实的 `unmatchedTranslationRowIdsByLanguage`（现在 `server.js:6786`、`local-assistant-client.ts:1608`、`v15-execution-orchestrator.ts:277` 都是写死 0）。
2. 执行清单 / 回执增加行级覆盖证据：`expectedRowTokens`、`verifiedRowTokens` 的摘要与计数（只放 token / 摘要，不放正文）。
3. `ExecutionAttempt` 增加可空的行覆盖字段（或新表），保存报价范围摘要、实际覆盖摘要、未覆盖数量；回执校验摘要一致。
4. 结算闸改成：**覆盖行集合 == 报价行集合**才按报价计费；否则整单释放、0 扣费、转人工复核。本轮不做按比例扣费（比例扣费要再乘每行单位，容易二次出错）。
5. 旧助手兼容：低于 3.7.21 的助手对**新报价**直接拒绝执行，并给出可读提示；不允许"没有行证据也照全扣"。
6. 验收：
   - 29 / 29 对象但只覆盖 31 / 37 行 → 0 扣费 + 人工复核；
   - 覆盖 31 / 31 行 → 扣 31；
   - 回执缺行证据 / 摘要不符 → 0 扣费；
   - 旧助手 → 执行前就被挡住，不产生预留。

**四层同笔**：浏览器投影（P1 第 5 条）、助手 evidence（P2 第 1-3 条）、服务端报价（P1 第 1-3 条）、结算闸（P2 第 4 条）+ fixture，必须同一个提交；HANDOFF 标【合同变更】。
