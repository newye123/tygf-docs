02开源参考（GitHub）

筛选标准：必须同时解决「多文件 + 本地执行 + 串行队列」——因为你的场景特殊在「浏览器工作台 + 本地 Windows 助手 + Photoshop 单实例串行」。

项目为什么相关可借鉴
Uppy（transloadit/uppy, MIT）最成熟的多文件列表 UI（Dashboard 插件）每文件独立状态/进度/操作；批量暂停·重试·删除；autoProceed:false 选完不自动跑
Transloadit 最佳实践专讲批量文件处理的工程与 UX 原则上传/扫描优先、处理异步；结果按 ID 映射不靠顺序；输入设上限；别静默吞失败
handbrake-web自托管 Web + 单一队列 + 多设备共享处理，与你几乎同构队列是一等公民：独立页面、可增删、逐项状态
HandBrake GUI桌面批处理标杆「加入队列」与「开始」解耦：先攒够再统一跑
Crowdin 源文件上传翻译平台批量上传批量上传带选项面板，而不是传完才配
要避开的反模式：① 静默吞掉部分失败（Transloadit 明确警告失败会「less visible」）② 让用户等完整处理 ③ 结果靠位置对齐 ④ 把「选文件」和「开始执行」耦死——你现状四条全中。

03方案：并列双工作台

信息架构首页 #home / 工作台 #workbench（一行不动）/ 批量工作台 #batch（新增，独立视图、动态加载、独立开关）
批量四区① 文件区（增删/重排/状态/单文件重扫）② 语言区 ③ 覆盖率矩阵（升级为执行前必过闸）④ 执行区（队列/总进度/失败分层/结果）
一次多选三层递进：第1层 前端先行（拖拽/粘贴多路径兜底，不需发版）→ 第2层 助手端加 Multiselect（需发版+重装，前端做能力探测自动降级）→ 第3层 入列后串行扫描，不再「加一个扫一个」
失败处理行级（矩阵格标红+悬停原因）/ 批次级（只重试失败）/ 整批级（可下载失败报告，可移植生产站已有 failure-report.ts）
合同边界不动计费/回执/行排除语义；每个 PSD 仍独立一个 ExecutionBatch

05对抗式审查（六路反方）

  1. 反方1｜并列是过度设计，加开关更省事 → 省事但不可回滚。现状已证明代价：开关一开原工作台整体被替换，用户没有「继续用旧的」这个选项。并列只多约 100 行骨架，换来两视图独立开关/回滚/验收。
  2. 反方2｜改助手端风险高（历史踩过版本纪律坑） → 成立。故助手端改动放第 2 层，且要求能力探测+自动降级；即使永远不发版，第 1 层也能提供「一次录入多个」。
  3. 反方3｜覆盖率不拦截是既有设计不是新问题 → 是既有问题（#140/#153），但批量把它放大了：12×3 时没人会逐格检查。故列为必须一并处理。
  4. 反方4｜结果按 ID 映射是过度工程 → 批量下用户一定会删文件（选 12 个、扫完发现 2 个不对），下标必然错位。不是理论风险，是必然路径。
  5. 反方5｜万一测试站开关真是开的 → 已查实：就是开的，初版判断错了。错因是只查了覆盖层没查代码默认值。教训：判断开关真实状态必须同时查两层——① 代码默认值 ② 站点设置覆盖值；只查一层就是假绿。
  6. 反方6｜批量代码已合进 develop，怎么保证不动原工作台 → 该 6 文件改动未进 main。两条路：回滚重建（倾向）或锁死保留。保留会持续制造「两套渲染分支」维护成本。

06灰度与部署纪律

根因不只是技术：批量代码在开关被打开的状态下随 aefc8a8 一起上了测试站，而该次部署的执行者一度不明（ISSUES #154 记录消息未留存）。
  1. 部署前必须点名：任何上测试站的部署，TASK_LOG 必须写清「谁批准、谁执行、部署了哪个 commit」。
  2. 批量代码不进 develop 主干：方案批准前，批量能力只在独立分支开发。
  3. 探针加白名单：当前部署探针条件满足即自动部署；建议只部署白名单内的 commit/分支，否则「自动」会绕过第 1 条。
  4. 开关改动不得夹带（本次新增）：提交信息必须与代码里的开关取值一致；开关值的变更不得夹带在与主题无关的提交里。建议发布门禁加断言：featureFlags.ts 默认值若与上一 commit 不同，提交信息必须显式提及。

执行中发现的三件事（原方案未覆盖）

  1. 运营台对普通布尔开关是「只读」的——这是 flag 事故的结构性成因。settings-panel.tsx:887-919 的「模块开关」面板只渲染徽标（自述「本面板只读」）；admin/client.ts:552 的通用 saveFeatureFlags 无任何 UI 调用。⇒ 此前 Owner 想开普通布尔开关只能改代码，这正是 multiPsdExperimentEnabled 在 aefc8a8 被夹带提交的机制。已补：按 saveSiteCopyInlineEditOverride 同款新增原子覆盖函数 + API 分支 + 面板开关卡。由此得纪律：任何新增布尔开关必须同时补「原子覆盖函数 + API 分支 + 面板入口」，否则等于「默认 false 且无人能开」。
  2. 浏览器拖拽文件拿不到绝对路径 ⇒ 第 1 层的多路径入口只能是「粘贴」。File.path 是 Electron 专有；Chrome 出于安全只给文件名，而助手链路需要绝对路径 masterPath。故「拖拽区」在纯 Web 页是死路；可靠入口是粘贴多行路径（与 design-file-card.tsx:687「粘贴即扫描」同源）。⇒ 原方案第 1 层的「拖拽」应降级为「不做」或「仅接受路径文本」。
  3. PreparationClientState 无「已录入未扫描」态，且不能加。加新值会破坏 design-file-card.tsx:878 的 Record<PsdSelection['state'], …> 穷尽性检查，而原工作台组件树必须零改动。⇒ 第 1 层批量列表用 string[] 路径（不用 MultiPsdEntry）；MultiPsdEntry + 串行扫描 + 队列语义留到第 3 层。
