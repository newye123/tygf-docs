02阶段一 · 为什么 Owner 的推广是对的

关系真实场景在 v7 模型里是什么
1 稿 : 1 表常规：一份 PSD 配一张自己的表默认：每格取主表该语种的行
N 稿 : 1 表一套主文案给 12 个 SKU 变体共用（文案一样、图不同）多个稿的默认行集来自同一张表（表内无同原文多译文时才合法）

往下再问一层：绑定的原子

交付物的原子 ＝ (设计稿, 语种)；一行译文的原子 ＝ (原文, 语种) → 目标文本；表不是原子——它是行的容器，而且容器可以横跨多个稿（主表）、也可以只带一门语言（专表）。
⇒ 真正的绑定单元是「(稿 × 语种) → 一组行」。把绑定下沉到这一格，四种关系就自动涌现，不再是四种模式。

04阶段三 · 模型与判据

Table   { tableId, name, rows[], langColumns[], hasSameSourceConflict }   // 库
Slice   { sliceId, tableId, ownerValue, rowIds[] }                        // 库按归属切出的一片
Binding { draftKey → {
    mainSliceId,                                  // 主表片（默认来源）
    localeOverrides: { locale → sliceId },         // 语种覆盖
    supplements: sliceId[]                        // 补充片（按原文差集并入）
} }

rows(D, locale) =
    (localeOverrides[locale] ?? mainSlice) 的该语种行
  ∪ supplements 各片中「主表里没有的原文」的行
⇒ 同原文多译文 ⇒ 点名冲突（沿用 X2 的既有检查）
「整表共用」vs「必须切片」——可计算的判据

表内存在「同一原文、不同译文」⇒ 必须切片；不存在 ⇒ 可以整张给多稿共用。判据来自表自身的行集合（解析期即可算，与稿无关）⇒ 零配置项、零猜测。整表共用时，多出来的行由助手判 EXCLUDED（X3）⇒ 不会写错，只会少写；界面要如实显示「这稿用到该表的 12/42 行」。

05阶段四 · Review（第四轮 12 条）

#级攻击处置
R1🔴合并粒度必须是 (稿, 语种)，不能是整表：若先把多张表合成一张再分发，同原文不同译文的冲突面会被放大到不相关的稿之间合并只在每格内发生（X1 出口），冲突检查随 X2 原样落在每格
R2🟠「整表给多稿共用」什么时候合法？表里有同原文不同译文时，两稿都会命中它 ⇒ 一稿同时对上两行可计算判据（§04）：有冲突 ⇒ 必须切片；无冲突 ⇒ 整表共用合法。不留成配置项
R3🟠「1 稿 ← 2 表」会不会逼写入层改语义？不会：合并发生在 fragments 之前（X1），信任链分组与冲突检查（X2）原样复用 ⇒ 不触发合同变更
R4🟡多出来的行会怎样？助手判 EXCLUDED、不写入、单位 0（X3）⇒ 风险是漏不是错写；但同原文同表内不同稿的译文会命中 ⇒ 正是 R2 要切片的理由。界面须显示「用到该表的 12/42 行」
R5🟡144 格逐格配置会不会把界面炸掉？例外驱动：默认 12 次，其余例外才动手；界面呈现的是系统推导出的来源矩阵
R6🟠「这一格做不做」和「这一格从哪取」是两个轴，容易混成一种颜色做/不做决定格有没有内容，从哪取决定内容；关系类型用第二行小字标，不与状态色混用
R7✅证据还是一个数吗？是。每格的证据 ＝ 合并行集对该稿的对稿命中率；表级只留一个可计算标签：可整表共用 / 必须切片
R8✅会不会退回「自动指派」？不会。提案仍只给排序与例外，人拍板（v4 的 T1 自我更正继续成立）
R9✅「共享表组」这个概念还要不要留？不留。N:M 下它是 N:1 的特例；模型里只剩「多稿指向同一张表或同一切片」
R10🟠主表 / 语种覆盖 / 补充表三种关系会不会打架？优先级定死：语种覆盖 > 主表 > 补充表；补充表只补「主表里没有的原文」（原文集合差集），带来同原文不同译文 ⇒ 点名冲突，不静默覆盖
R11🟠覆盖率口径会不会分裂？不会，但取数口要改：calcCoverageMatrixForDraftTables（X5）从「每稿一表」改成「每格一行集」，三档口径（X4）不变 ⇒ 组件与闸仍共用一份
R12🟡合并后行集变大，性能与缓存怎么办？按 (表指纹 × 稿指纹 × 语种) 缓存合并结果（preparation-contract.ts:311 的指纹已是现成稳定键）
