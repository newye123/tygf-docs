不变式：单对多工作台「与原行为逐字节一致」

这条不是口号，是四个可执行的闸。任何一条不过，改造不许合入。

闸 1 · 结构

入口那一行不许动

app-shell.tsx 的 {view === 'workbench' && <WorkbenchView />} 与 {view === 'batch' && … <WorkbenchView batchMode />} 这一行不改（现 :46-47）。单文件台仍然不传 batchMode。

闸 2 · 渲染

多稿能力一律包在 batchMode 里

来源矩阵、逐稿编排、覆盖率矩阵、批量动作、来源矩阵的样式 —— 必须在 batchMode && 内或 if (!batchMode) return … 之后。现成先例：workbench-view.tsx:1766/1786/1802。

闸 3 · 行为

快照比对（可执行）

在 batchMode=false 下渲染 #workbench，对关键 DOM 节点数 / 文案集合 / 按钮集合做快照，与基线逐字节比对，差异即失败。加一条本地可跑的断言脚本，纳入提交前门。

闸 4 · diff

改既有文件必须逐条带上下文

批量台改造优先只新增文件；对既有文件的改动必须落在 batchMode 块内或只是加带默认值的 prop（默认走原路径）。提交前用 git diff 逐条核，凡是无法说明「为什么不会影响单文件台」的行，不许合入。

闸 5 · 单一真值

「哪个模式」只能有一个真值来源

渲染形态只认视图传下来的 batchMode；禁止任何第二真值（编译期 featureFlag 常量、URL 参数、全局开关）能单独决定它。先例：ISSUES #151——design-file-card.tsx:74-83 的注释记着「原先把是否渲染多选 UI 绑在编译期静态值上，而 workbench-view 读的是运行时 useFeatureFlags() ⇒ 静态与运行时两套语义 ⇒ 出现『文件卡还是单选、但矩阵与编排已按多稿走』的错位」。本轮改造不能再引入第二真值。

这一轮对抗式审查对自己的攻击

攻击 1｜我前五轮的做法本身违反前提我一直在改共享组件（csv-step.tsx 的多选语义、buildRowsByLang()、review-step.tsx 的回写键）。加 batchMode 分支看着安全，但共用文件一改，单文件台就有被顺带改到的风险——而这个项目里共享组件正是两个工作台的交汇点。处置：改为「只加不改」——批量台的自有能力一律新组件/新模块实现；共用组件要么整份不动，要么只加带默认值的 prop。
攻击 2｜「零改动」要不要连「共享组件加默认 prop」也禁掉？严格讲，加 prop 也是改这个文件。⇒ 判定：加带默认值的 prop 是允许的，但默认路径必须逐字节等价（闸 3 的快照比对能证明）；凡是需要改既有 prop 的处理逻辑的 ⇒ 一律改成新组件。本轮已把 csv-step.tsx 与 review-step.tsx 降级为「整份不动」。
攻击 3｜「并排」会不会变成两个各自为政的产品？若两台各自演化，用户会遇到两套心智模型。⇒ 缓解：共享的是「概念」，不是「代码」——两个工作台用同一套文案与同一套术语（原文／译文表／语种／交付物）；代码不共享是因为共享代码正是顶替与串改的源头（仓库自己的注释就是这么写的：design-file-card.tsx:600 的就地 return「整体换掉」单文件工作台）。
攻击 4｜那"两台逻辑一样"的部分要不要抽公共库？可以抽纯函数（解析、合并、切片、覆盖率口径）——纯函数没有渲染副作用，抽出来不会影响任一工作台的行为。但仍不抽「UI 组件」（组件带渲染路径，抽了就等于让两台再次交汇）。⇒ 抽纯函数、不抽组件。
攻击 5｜那"每稿一表/N:M"这套，用户在单文件台怎么用？单文件台不需要：它就是「1 稿 : 1 表」的特例，来源矩阵是 1 行 12 格。但按前提，这一版不在单文件台做这个——单文件台继续用它现在那套「选表 → 语言 → 逐语言审查」，与批量台各自最优。
结论本轮把改造形态从「改共享组件」改成「旁挂新组件 + 四道不变式闸」。代价是要多写一份批量台专用的导入器与审查面板外壳（≈ 少量重复），换来的是单对多工作台可以拿「零改动」这个硬承诺去交付。
