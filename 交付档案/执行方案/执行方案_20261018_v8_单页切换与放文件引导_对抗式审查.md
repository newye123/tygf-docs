## 1. 第四条先答：命名怎么改

### 1.1 为什么「一对多 / 多对多」不能当界面词

Owner 说这两个词不行，我同意，而且理由是硬的：

- **它们在描述关系，不是在描述用户要干的事。** 用户心里想的是"我这次要弄几个稿"，不是"我要建立几对几的映射"。
- **两者其实是同一件事**：一个设计稿 × N 语言，和十个设计稿 × N 语言，**流程完全一样**，只是稿数不同。用"一对多/多对多"会让人以为是两套流程，反而坐实了"两个产品"的错觉。
- **唯一的变量是稿数。** 所以界面只需要表达这一个维度。

### 1.2 定名

| 位置 | 旧 | 新 | 理由 |
|---|---|---|---|
| 顶部导航 | 工作台 + 批量工作台（两项） | **工作台**（一项） | 只有一个产品，导航只给一个入口 |
| 页面 h1 | 工作台 / 工作台（两页同名） | **工作台** | 不变，本来就对 |
| 页内切换器 | 无 | **单个设计稿 ｜ 多个设计稿** | 只表达稿数这一个变量 |
| 空间紧张时 | — | 单稿 ｜ 多稿 | 侧边、面包屑、移动端用短版 |
| 副标题（单稿） | 扫描设计稿、导入译文并在本机生成多语言文件；设计文件不会上传。 | 保留 | 原文已经准确 |
| 副标题（多稿） | — | **一次处理多个设计稿：每个稿各自对账、各自生成，互不影响。设计文件不会上传。** | 明确"各自"，打消"会不会串"的疑虑 |

**不做的事**：不叫「批量」。理由——"批量"在中文软件语境里常指"批量操作某些东西"（批量删除、批量重命名），是**动作**；而这里选的是**范围**。用"多个设计稿"是名词，符合它其实是个范围选择的本质。

### 1.3 URL 怎么办（向后兼容）

现有 `#workbench` / `#batch` 已经发出去过，不能断。

- 保留 `#workbench` = 单个设计稿
- 保留 `#batch` = 多个设计稿（**旧链接继续可用**）
- 切换器切换时**只改 hash，不整页跳转**（`setView` 已经是这个行为，`view-context.tsx:52`）
- 顶部导航「工作台」点进去 = `#workbench`；已经在工作台里再点它 = 不做事（不重置当前模式）

## 2. 第三条：切换器放哪、长什么样

### 2.1 落点

放 **h1 右侧、与 h1 同一行**（`workbench-view.tsx` 的 `<header>` 内，`h1` 之后）。

不选其他位置的三个理由：
- 放 SiteHeader ⇒ 又变成"两个导航项"，回到被否的老路
- 放 StageRail 上方 ⇒ 会被误读成"第 0 阶段"
- 放文件卡内 ⇒ 只影响文件区，但多稿模式会改语言区和执行区，作用域对不上

### 2.2 形态

**分段控件（segmented control）**，两个等宽段，当前段实底墨绿、另一段描边：

```
┌──────────────┬──────────────┐
│ 单个设计稿 ● │  多个设计稿   │
└──────────────┴──────────────┘
```

不用下拉菜单（选项只有 2 个，下拉要多一次点击）；不用开关（开关暗示"开启某功能"，而这是"选范围"）。

### 2.3 切换时的行为（这条最容易做错）

| 场景 | 行为 |
|---|---|
| 空手切换 | 直接切，无提示 |
| 已选 1 个稿，切到多稿 | 直接切，那 1 个稿带过去，不丢 |
| 已选 3 个稿，切到单稿 | **不静默丢 2 个**。弹确认：「切到单个设计稿后，只保留第 1 个（1.psd），其余 2 个会移出本批。继续？」 |
| 已扫描完，切换 | 扫描结果保留（同一批文件），不重扫 |
| 执行中 | 切换器**禁用**，title 提示「执行中不能切换，等这一批跑完」 |

第四条是"不静默跳过"红线的延伸：**跨模式的数据丢失必须问**。

## 3. 第二条：怎么放文件（这次最重要的一条）

### 3.1 先承认一个约束，否则引导会写错

我查了数据模型：**译文表是全局一张，供整批所有稿共用**。
`workbench-view.tsx:463` 的 `translationsFor(language)` 从单一 `parsed` 派生，没有"每稿一张表"的字段。

所以**不能**写"把每张表放在各自稿的目录里，系统会自动配"。那是假的。
正确的引导必须说：**表是整批共用的一张（可多选合并），系统只负责帮你找出来，不替你决定用哪张。**

### 3.2 引导做成什么形态

在「从文件夹导入」卡里，**点选之前**就显示一个目录树示例 + 5 条规则。不是折叠的帮助文档，是卡内常驻。

```
┌─ 从文件夹导入 ─────────────────────────────────────┐
│                                                    │
│  选一个文件夹，子文件夹里的设计稿会一起找出来。      │
│                                                    │
│  ┌─ 这样放，最好认 ──────────────────────────┐     │
│  │  我的项目/                                │     │
│  │  ├─ 首页.psd            ← 设计稿，全部找出 │     │
│  │  ├─ 详情页.psd                            │     │
│  │  ├─ 活动页.psd                            │     │
│  │  └─ 译文/                                 │     │
│  │     ├─ 英语.xlsx        ← 译文表，只列候选 │     │
│  │     └─ 日语.xlsx                          │     │
│  └───────────────────────────────────────────┘     │
│                                                    │
│  · 只认 .psd / .psb，其他文件不会被当成设计稿       │
│  · 子文件夹会一起找，最多往下 6 层                  │
│  · 最多加入 12 个，多的按路径顺序排在后面，会逐条告诉你是哪些 │
│  · 表格（xlsx / csv / tsv）只列出来，不会自动套用    │
│  · 一张译文表服务整批；扫到多张可以多选合并          │
│                                                    │
│  [ 选择文件夹… ]                                    │
└────────────────────────────────────────────────────┘
```

### 3.3 为什么这样写（每条都有依据）

| 规则 | 依据 |
|---|---|
| 「子文件夹会一起找」+ 深度 6 | Adobe **Photoshop Image Processor** 的做法：`Source Folder` + `Include All Sub-folders` 复选框。设计师天天用，认得这个语义 |
| 只认 `.psd/.psb` | 助手侧 `server.js` 的扫描接口本来就只收 PSD/PSB（`/\.(psd|psb)$/i`），不能承诺更多 |
| 超 12 逐条列出 | 「不静默跳过」红线。既有 `addMultiPsdEntry` 满了是静默 `return`（`psd-selection.ts:55`），**这个洞要一起补** |
| 表格只列候选、不自动套用 | 数据模型一张表服务整批（见 3.1），自动绑必错译 |
| 多张可合并 | `csv-step.tsx` 的 `handleFiles` 已支持多文件 `mergeParsedTables`，白拿的能力 |

### 3.4 「不符合约定会怎样」也要说

只讲"怎么放对"是不够的，用户更想知道"我放错了会怎样"。所以卡里还有一行**结果预告**：

```
· 放错了也没关系：认不出的文件会被跳过，跳过了哪些会列给你看，不会闷着。
```

## 5. 业界参考（Owner 要求查的）

| 来源 | 拿它什么 | 不用它什么 |
|---|---|---|
| **Adobe Photoshop Image Processor** | 「Source Folder + Include All Sub-folders」这个心智模型，设计师零学习成本 | 它的批处理参数面板（我们不需要） |
| **Uppy**（开源上传库，业界标准） | `browse files` / `browse folders` **两套文案分开**，不是一个按钮兼两用 | 它不做目录组织引导（官方文档明说要用 `note` 自己写）⇒ **引导必须我们自己做**，这条反而是我们的差异化 |
| **i18n 业界约定** `locales/{lang}/translation.json` | 语言代码进文件名/目录名，是被验证过的约定 | 我们不做代码工程，不暴露目录结构给用户 |
| **Eagle / Adobe Bridge** | 「目录监测 + 无感导入」是设计师接受度最高的形态 | 常驻监听（我们是单次扫描，不做后台守护，避免权限争议） |
| **fdir**（thecodrr/fdir） | 只作为递归列举的实现参照（自然排序、忽略黑名单、软链不跟随） | **不引依赖**——助手是零依赖 `pkg` 单 exe，加依赖破出包。已自写 `listFolderRecursive` |

### 5.1 查完的结论

**没有现成开源方案能直接搬。** 原因：市面上要么是通用上传组件（Uppy，不管业务语义），要么是重型 TMS（Crowdin/Lokalise，要建项目、传文件、走审批流，比我们整个产品还重）。

我们这个场景——「本机选文件夹、只读扫描、不上传、一稿×N语言」——是**窄缝**，只能自己拼。能借的是交互心智（Image Processor 的子文件夹、Uppy 的两套文案），不是代码。

## 9. 诚实边界

- **译文表不自动配**：这是数据模型决定的，不是偷懒。要"一稿一表"得先改 `parsed` 为按稿分组，是另一个量级的改动，需 Owner 单独立项。
- **12 个上限**：现有 `MAX_PSD_ENTRIES = 12` 是既有约束，本方案不放开，只保证"超了会告诉你"。
- **深度 6 层**：超过 6 层的稿扫不到，会在结果里说明"更深层未扫描"，不假装扫全了。
- **模拟件是模拟件**：v8 HTML 用假数据，交互可点，但不连真实助手。
