## 0. 先回答 Owner 问的那个问题

**区分的钥匙是「物料（设计稿）」，不是「语言」。**

现在之所以觉得"分不清"，是因为界面把「语言」当成了主角：屏幕上那一行写着「德语 · 法语」，但不知道它属于 12 个 SKU 里的哪一个。正确的模型是把主角换成 SKU：

| 层级 | 谁是主角 | 装什么 |
|---|---|---|
| 物料层（行） | 1 个 SKU = 1 个 PSD | 自己的表、自己的语言子集、自己的确认进度、自己的扫描状态 |
| 语种层（列） | 1 个语种 | 这一稿在这一语种上的覆盖率 / 确认状态 / 缺列 |

于是：

- **12 个 SKU 各一张不同的表** → 表是「行」的属性，每行自带一张表，行与行之间天然不打架。
- **每个 SKU 的表语言不同**（SKU-05 只有德法英、SKU-09 有 12 列）→ 表里的语言列**不是全局语言表**，而是「这一行的列集合」。行与行的列可以不一样，矩阵里没有的格子就是那一行不适用。
- **区分靠什么** → 靠**配对规则**（同名 / 同 SKU 码 / 同目录）自动建议 + 逐条预览确认，而不是手工 12×12 地挑。

界面上，图二那种单稿形态**不再占整页**，它降级成矩阵右侧的**详情区**；矩阵本体是「行 = SKU、列 = 语言」的真表，一屏扫得完。这正好把 Owner 的两句话合成一件事：图二是「详情的样子」，图一是「总览的样子」，二者不冲突，只是现在的总览长成了另一个东西。

### 2.2 同构问题在行业里长什么样（三个可借的解法）

**① 同构问题的原始案例：Trados Studio 社区「Different source files for different target languages」**
（`community.rws.com/product-groups/trados-portfolio/trados-studio/f/studio/53500/`）

提问者的形状和 Owner 几乎一模一样：源文件**自带目标 locale**，每个源文件要翻成的目标语言不同，且不同源文件内容也不一样（某语言已经翻过的句子直接不在那个文件里）。

行业结论（原文口径）：
- Trados 的模型是**源文件在每个目标语言下都要复制一份**；
- 提问者问能不能"直接按文件里的数据把源文件对上不同目标语言"；
- RWS 工程师答：Trados 目前**不支持**；可以用「Multilingual XML FileType」（一个文件支持 9 种语言）绕；
- 社区给出的唯一实操路径是：**把所有版本都传上去，再在每个目标语言下删掉不适用的文件**——而且删完「Manager view 就能在一屏里看到所有目标语言」。

**这条对本项目的意义有两条，方向相反：**
- **不能靠"UI 上不显示"来表达"这一稿不做这个语种"**——Trados 就是这么被逼出删文件这种苦活的。**文件 × 语种的作用域必须在数据模型里显式存在**（本方案的 `binding.languageScope`），不能靠"这一列没勾"这种临时状态表达。
- **"一屏看到所有目标语言 × 所有文件"就是行业认定的正确总览形态**——这正好是本方案 §5 的真矩阵（Trados 删完文件后得到的那个 view）。Owner 要的"图二 + 12 SKU 各自的表"，在行业里长成的就是这个矩阵。

**② 共享/成组交付：Crowdin「Target File Bundles」**（`support.crowdin.com/bundles/`）
把一组源文件打成一个 bundle，bundle 可以有各自的导出格式与目标文件 —— 即**"一组文件共享一份交付物"是行业一等公民**，不是边角。对应本方案 §3.3 的「表组 / 共享表」。

**③ 两种导出形态并存：Lokalise「Downloading translation files」**（`docs.lokalise.com/en/articles/3150682-downloading-translation-files`）
Lokalise 同时提供「One file per language（所有语言合成一份）」和「每个源文件一份翻译文件」两种形态。对应本方案：**共享表**与**独立表**两种模式并存，而不是二选一。

**④ 设计工具里的主流形态：一语言一页面 / 一语言一文件**
Figma 生态的翻译插件（Transifex / Crowdin / Lokalise / iTranslate AI Batch Translation）主流做法是「每个语种一份 page / 一份文件」，批量时选多个 frame 一次翻多语。这印证：**语种是列、稿件是行**这个二维结构是设计工具的通用形状，不是我们拍脑袋发明的。

**⑤ 可借的机制名：file mapping**
Crowdin CLI / Lokalise 都有「文件映射」概念——用规则把源文件对上目标文件，而不是手工一对一手配。本方案 §4 的「规则自动配对」就是这个东西的桌面版。

## 3. 方案：数据模型改造（核心）

### 3.1 从"每稿一份副本"改成"表本体 + 绑定"

现状（F3）是 `parsedTables[draftKey] = ParsedCsv`，表是**值**，绑在稿上。要支持共享、要能换表、要能持久化，得把**表提成实体**：

```
Table   { tableId, name, parsed, rowCount, langColumns }        // 表本体，可被多稿引用
Binding { draftKey → { tableId, mode: 'own' | 'shared', languageScope: string[] } }
```

- `tables: Record<tableId, Table>` —— 表只解析一次，多稿可共享同一份。
- `bindings: Record<draftKey, Binding>` —— 每稿只存**引用**，不存副本。
- `languageScope` —— **这一稿要做哪些语种**（默认＝该表全部语言列）。

这样一次性解决四件事：共享表不用复制文件；换表＝改一行绑定；"表改了哪些稿受影响"可算；持久化只需存绑定关系（表内容仍可不落盘）。

### 3.2 三态语言语义（这是 Owner 说的"每个 SKU 表语言不一样"的正解呈现）

必须把三个集合分开，界面上也要分开画：

| 集合 | 含义 | 图二语言行的画法 |
|---|---|---|
| 表里有（`table.langColumns`） | 这张表提供哪些语种列 | 底色存在 |
| 本稿要做（`binding.languageScope`） | 这一稿实际要翻哪些 | 实心＝要做；虚线＝不做 |
| 本稿要做但表里没有 | **做不了的格子** | 红框 + 「缺列」 |

**缺列是本方案新增的一等状态**：SKU-10 的表只有 10 列、但本稿要做 12 语 → 繁体中文 / 荷兰语两格红框。现在这层信息在界面上**根本不存在**（F7 只画当前稿的已选语言），Owner 会在执行前才发现。

### 3.3 绑定模式（两种并存，回应"共用一条腿也要留着"）

| 模式 | 含义 | 界面 | 执行 |
|---|---|---|---|
| `own` 独立表 | 一张表只服务这一稿 | 卡上徽章「独立表」 | 该稿 × 该稿语言 = 1 批次 |
| `shared` 共享表 | 多稿指向同一 `tableId`（= 表组） | 卡上徽章「共享表 · 主表组 A（4 稿共用）」 | 仍按稿拆批次（1 稿 1 批次），**不合并批次** |

**关键取舍（对抗审查后定）**：共享表**只共享表，不共享执行批次**。理由：批次是计费与结算的单位（`src/app/(zh)/pack/page.tsx:594`：按语种分别计费），合批会让"这一稿出了事只退这一稿"变得不可能。

**闸门必须同步改**：F4 的「每稿一张表，互不共用」要改成「每稿**有绑定**（独立表或共享表都算）」，否则共享表场景被旧闸直接拦死。这是一处**文案 + 判定双改**，属合同语义变更，见 §8 门 G3。

### 3.4 表与稿的对应关系怎么建立（这是"怎么区分"的操作层）

三种手段并存，优先级从高到低：

1. **规则自动配对**（新，批量台的主力）——按规则命中即停，**命中结果逐条预览、确认后生效**：
   - 规则 1：同名同目录（`SKU-05.psd` ↔ `SKU-05.xlsx`）
   - 规则 2：同 SKU 码（`SKU-05_主图.psd` ↔ `SKU-05_德法英.xlsx`）
   - 规则 3：表名含 SKU 码且全局唯一
   - 规则 4：表在 `翻译/` 子目录且 basename 匹配
   - **一对多 / 零命中 → 一律不自动决定**，列出来让用户点（与既有取舍一致：`design-file-card.tsx:1017-1023` 的"只列候选、不自动套用"）
2. **共享表组**（新）——把多稿一次性指到同一张表，成组管理
3. **手动逐稿选**（保留）——保底路径，且是"自动配对错了"的纠正口

自动配对**必须带预览清单**（12 条逐条列出命中规则与判定），不允许静默生效。这是本方案唯一的批量写入动作，错了就是 12 稿一起错。

### 4.3 真矩阵的规格

- **行**：12 个 SKU（与物料栏同序、同高亮）
- **列**：12 个语种（列集合＝所有表的语言列的并集；某一稿没有的列留灰）
- **格状态**（每格必须可读，不许只有颜色）：
  - `已确认 98%`（绿）｜`待确认 94%`（琥珀）｜`62%`（红，低于 80%）｜`缺列`（红框）｜`— 不做`（灰虚线）
- **粘性**：表头（语种名）与首列（SKU 名）都 sticky，横向滚 12 列时不丢行名
- **点格**：跳到该 SKU 详情区并高亮该语种 chip
- **行尾**：该稿的语言确认进度 `x/y`
- 复用 `calcCoverageMatrixForDraftTables`（F9），只换渲染形态——**取数口径不动**，避免"矩阵和执行闸各算一套"（`coverage.ts:106-110` 的既有教训）

## 5. 防错绑：三道体检（本次最关键的安全设计）

**为什么必须做**：Owner 场景是"一批 SKU 的语言要改，每稿自己的表"。人一定会配错一稿。而 SKU 与 SKU 之间**原文高度相似**是常态（同一套文案改几个词）。错绑之后：

> SKU-A 的表绑到 SKU-B → 如果两稿原文几乎一样 → 覆盖率算出来 **100%** → 现有所有闸门全绿 → **把错的译文写进客户 PSD，没有任何一处报警**。

这是本次改造里**唯一会造成不可逆错误**的路径（写进客户设计文件），所以必须在执行前拦住。三道体检：

| 体检 | 判据 | 落点 | 级别 |
|---|---|---|---|
| **G1 覆盖率体检** | 现有矩阵已算（绿/琥珀/红）；低于 95% 阈值要显式放行 | 浏览器侧（已有） | 已有，沿用 |
| **G2 表↔稿指纹体检（新增）** | 表的原文集合 vs **该稿**图层原文集合（助手侧才有逐层原文）：① 命中率 < 60% → 判"这张表可能不是这一稿的"；② 表多出 ≥N 行本稿没有的原文 → 提示"表比稿多 N 行，可能是混稿" | 助手侧第 3 步（`prepare-check`）+ 执行前闸 | **新增，P0** |
| **G3 缺列体检** | 本稿要做但表里没有的语种 → 红框列出，并拦下"本批开始" | 浏览器侧（§3.2） | **新增，P0** |

G2 的形态与现有"表多出 N 行"提示不同：现有提示是**信息**（"译文表里没有对应行的文字对象有 N 处，默认不写入不扣积分"，`workbench-view.tsx:3497-3501` 附近），它防的是"表比稿多"；**缺的是"表可能是别人的"**这一层。

### 5.1 与 08:59 v7 审查已批准结论的冲突点（必须点名，不能默默沿用）

同日 08:59 的《批量工作台 v7：每稿一表（设计增量与实施单）· 对抗式审查》F9 条写的是：

> "**写错风险＝0**：`match.ts:41-53` 归一化原文严格相等配对，外稿行配不上、不会误写。"

**这条结论只在"外稿的原文与本稿完全不重叠"时成立。** 逐字核 `src/lib/workbench/match.ts:41-76`：`runMatch` 用 `normalizeText` 后的**原文严格相等**建索引（`:51`）、按行的 `sourceText` 取命中（`:58` / `:68`），取不到即 `NO_LAYER_MATCHED`（`:69-76`）。于是分两种情况：

| 情形 | 结果 |
|---|---|
| 外稿原文与本稿**完全不重叠** | 全部 `NO_LAYER_MATCHED`，**一个字都不会写** ⇒ F9 成立（安全，但这一稿也交不出东西） |
| 外稿原文与本稿**有重叠**（同一套文案改几个词的 SKU——正是 Owner 说的"多个不同 SKU 的亚马逊改语言"） | 重叠的那几行**正常命中**，写进去的是**另一个 SKU 的译文** ⇒ **F9 不成立，错字真会写进客户 PSD** |

**结论**：F9 把"外稿行"当成了"必然配不上的行"，漏掉了"原文高度相似 ⇒ 照样配得上"这一档。**这不是推翻 v7 的每稿一表设计**（那个设计仍然正确、仍然要保留），**推翻的是它的风险评估结论**：v7 假设"每稿一表"这件事本身足以防住写错；实测不够，因为**真正防住写错的是"表和稿是对应的"这个前提，而界面没有、也不曾有办法验证这个前提是否成立**。

这正是 A1 要修的东西，也是 G2 存在的全部理由。⇒ **G2 升为 P0，且必须排在 v7 已上线部分之外单独排期**；在 G2 落地前，**批量台每稿一表的能力不得对外宣称"不会写错"**。

## 6. 批次与计费预告（12 稿 × 12 语种会吓到人）

按 F10，12 稿 → 12 个批次，每批次是该稿已确认的语言数。计费按语种累计（`src/app/(zh)/pack/page.tsx:594`：50 行 × 12 语种 = 600 分）。

```
本批将产生：12 个批次 · 80 个语种执行 · 预计 4,000 积分（按 50 行 × 80 语种 × 1 分/行·语种 估）
其中：SKU-04 尚未确认任何语言 → 该稿不会进入本批（先做别的稿）
```
