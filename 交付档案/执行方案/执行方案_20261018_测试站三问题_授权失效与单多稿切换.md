## 一、测试站测不了

### 1.1 现场证据（全部实测，非推测）

| 观测 | 值 | 来源 |
|---|---|---|
| 助手进程 | `图译工坊引擎.exe` pid 22076，3.7.15，`transport-hardening-20261011-r1` | `GET 127.0.0.1:49152/ping` |
| 助手自评 | `alive:true`、`activationStatus:"active"`、`photoshopDetected:true`、`taskRoot:[configured]` | 同上 |
| 云端拒绝 | `POST /v1.5/authorization/check -> 403 code=ASSISTANT_DEVICE_INVALID origin=https://test.tuyigf.com` | 助手事件日志 21:39:40 / 21:40:16 / 21:41:24 |
| 票据校验同因 | `[ticket] verify rejected reason=ASSISTANT_DEVICE_INVALID cloudStatusCode=200` | 同上 |
| 另有网络故障 | 21:42:41、21:42:56、21:43:43、21:46:50 四次 `VERIFY_TIMEOUT`（10s 预算耗尽，`REQUEST_TIMEOUT`/`TLS_TIMEOUT`） | 同上 |

### 1.2 这个错误码的确切含义

`src/lib/server/assistant-authorization.ts:27-33`：令牌签名与有效期都过了，卡在

```
hasCurrentAssistantRedemption({ assistantCodeId, machineId, tokenJti })
→ SELECT id FROM AssistantCodeRedemption
   WHERE assistantCodeId=? AND machineId=? AND tokenJti IS ? LIMIT 1
```

查不到那一行 ⇒ `ASSISTANT_DEVICE_INVALID`。

### 1.3 测试站库里的实际状态（已排除的方向）

`/var/www/tygf-test/db/custom.db`（SQLite）实测：

- 运行码 `cmtpik8yf000ewjtpy2gwtey1`：`status=active`，`expiresAt=2099-12-31`
- 本机那行：`machineId=19ee9b79-…`、`tokenJti=29d7d427-d85e-42d4-b91f-82355b024acc`、`redeemedAt=2026-10-18 01:16:44`、`tokenExpiresAt=2026-11-01 01:16:44`
- 助手自报 `activationExpiresAt=2026-11-01T01:16:44+08` —— **与该行逐秒吻合**，说明当前令牌确实是 01:16:44 那次配对签出来的
- 直接跑 `tokenJti IS '<该值>'` 语义验证：命中 1 行 ⇒ SQL 与数据都没问题

⇒ **已排除**：运行码被停用/过期、令牌过期、库被清空、SQL 写法错误。

### 1.4 已钉死：旧版令牌没有 jti（22:1x 更新，推翻了上面"读不到"的说法）

**推翻前提**：`.tygf_session` 并非不可解。它的 AES 密钥就是 `sha256(MachineGuid)`（`server.js:289` `stateCipherKey()`），MachineGuid 从注册表 `HKLM\SOFTWARE\Microsoft\Cryptography` 读得到（本机 `19ee9b79-02f0-4c67-b62a-54a1df6fc399`）。所以本地可以自行解密——这一点我上一版判断错了。

解密后看清两件事：

1. **真正送去云端校验的不是全局 `assistantToken`，而是按来源分存的那份**。`authorizationForOrigin(cfg, cloudBase)` 取 `assistantAuthorizations[origin].token`；而 `requestCloudBase` 优先用浏览器的 Origin（只要它在 `allowedWebOrigins` 里）。**从哪个站点打开工作台，就用那个站点的那份令牌。**
2. 本机四份令牌实测：

| 来源 | exp | jti |
|---|---|---|
| `https://tuyigf.com` | 2026-10-27 | `be32f204…` |
| `https://test.tuyigf.com` | 2026-10-22 | **无** |
| `http://127.0.0.1:3422` | 2026-09-09（已过期） | 无 |
| `http://localhost:3000` | 2026-10-31 | `29d7d427…` |

`https://test.tuyigf.com` 那份 `exp` 2026-10-22，即 **2026-10-08 签发**；而 `tokenJti` 这个特性是提交 `6d9e169`（**2026-10-10**）才引入的。⇒ 这份令牌**结构上就不可能带上 jti**。

判据是 `hasCurrentAssistantRedemption` 里的 `tokenJti IS ${input.tokenJti}`。旧令牌 `tokenJti = null` ⇒ 只匹配 `tokenJti IS NULL` 的行；而 `cid = cmtpik8yf000ewjtpy2gwtey1` 在库里**只有一行**，且 `tokenJti = 29d7d427…` 非空。⇒ **永远不匹配，刷新一万次也一样。**

而 `http://localhost:3000` 那份是 2026-10-17 17:16:44 重新签的，带 jti，与库里那行逐字段相同（我用同样的 SQL 语义直查，命中 1 行）。这也解释了为什么 10-17 之后从隧道走能过、从 test.tuyigf.com 走不能过。

所以上一版列的三种可能，实际是第 3 种的一个特例：**不是"代次错"，是"这一代的令牌压根没有代次标记"**。云端返回 `cloudStatusCode=200`，是云端主动拒绝，不是网络问题。

### 1.4b 处置（更新）

**唯一有效动作**：在 test.tuyigf.com 上重新连接本地助手——重配会给这个来源写一份带 jti 的新令牌。或者直接走 `http://localhost:3000` 隧道，那份令牌已经有效。

**不做的事**：不放宽云端鉴权去接受无 jti 的旧令牌。它 4 天后自然过期，放宽只是把问题推迟，还白丢一层代次保护。

**已做的**：`ASSISTANT_DEVICE_INVALID` 的文案补上了（见 P0-3），现在两条链都会明确说「请回到工作台断开本地助手，再重新连接当前电脑」，不再让人去刷新。

### 1.5 处置（按顺序，每步有判据）

**P0-1 立刻可做（你点两下，1 分钟）**
在工作台横幅点「重新授权」，按提示重配一次。重配会走 `pair` 路由的 upsert，把 `redeemedAt`/`tokenExpiresAt` 刷新并用库里那代的 jti 重签。
**判据**：助手事件日志出现 `POST /v1.5/authorization/check -> 200`（或不再出现 DEVICE_INVALID），且横幅变绿。

**P0-2 若重配后仍 DEVICE_INVALID —— 加一条诊断（约 20 行改动，我可以直接做）**
现在 `pair` 响应与助手日志都不带 jti/machineId 的任何片段，所以永远只能猜。补两处：

- `src/app/api/local-assistant/pair/route.ts`：响应体加 `jti8: tokenJti.slice(0,8)`、`mid8: machineId.slice(0,8)`、`cid8: assistantCode.id.slice(0,8)`（只前 8 位，不泄密）；
- `download/local-assistant/server.js` 的 `authorization-check` 拒绝分支：把本地令牌解析出的 `cid8/mid8/jti8` 写进 `assistant-events.log`。

**判据**：一次失败后，把日志里的三组 8 位与库里那行比对，能一眼看出是"环境不对"还是"代次不对"。

**P0-3 顺手修一个真 UX 缺陷**
`download/local-assistant/server.js:3388` 的 `ticketFailureMessage` 有 `ASSISTANT_INSTALL_BINDING_INVALID`/`ASSISTANT_CODE_DISABLED`/`ASSISTANT_CODE_EXPIRED` 分支，**唯独没有 `ASSISTANT_DEVICE_INVALID`**，于是落到兜底文案「无法验证本次文件选择许可（ASSISTANT_DEVICE_INVALID），请刷新工作台后重试」——"刷新工作台"对这个问题毫无作用，把你往错方向引。应补一句「本机授权与云端这一代对不上，请重新连接本地助手」。

**P0-4 网络侧（独立问题，别混谈）**
四次 10s 超时是出口慢（已知：本机到 tuyigf.com TTFB 2–9s，曾 45s）。它不会产生 DEVICE_INVALID，但会让重配本身失败。若重配卡住，先看是不是又超时。

## 二、绿色变暗

### 2.1 根因（一句话）

`3b1309c feat(workbench): 文件夹递归导入 + 官网同款换肤`（今天 02:45）新建了 `src/components/workbench/workbench-tokens.css`，在 `.wb-brand` 作用域内**整体重映射 Tailwind 色板**：

```
--color-teal-600: #2d7356   /* 原 Tailwind 默认 #0d9488 */
--color-emerald-600: #2d7356
```

工作台里 13 处 `bg-teal-600`（`csv-step.tsx:328/:546`、`design-file-card.tsx:1135/:1218/:1310`、`execute-step.tsx:2935`、`typography-panel.tsx:494/:569`、`user-account-menu.tsx:94` …）**一行 className 没改，颜色全跟着变**。线上构建产物已确认生效：`.next/static/chunks/1hkv1uknfzaf9.css` 里就是 `--color-teal-600:#2d7356`。

所以"变暗"是换肤的必然结果，不是渲染错误。

### 2.2 但这次换肤本身有一处没对齐官网

官网 `home-v17.css` 里：`--accent:#2d7356`（绿，用于 chip/描边/文字强调），而**主按钮**是

```
.home-v17 .btn-primary { background:#121412; color:#fff }   /* home-v17.css:69 */
```

也就是说：**官网的"主操作"是近黑，绿色只做点缀**。换肤把工作台的实心主按钮也刷成了墨绿，于是既不像旧版（亮青绿），也不像官网（黑按钮）。

### 2.3 对比度实测（这条决定"能不能简单调亮"）

| 色值 | 白字对比度 | 结论 |
|---|---|---|
| `#0d9488`（旧） | **3.74:1** | 不达 WCAG AA 4.5:1 —— 旧版其实是不合格的 |
| `#2d7356`（现在） | **5.68:1** | 达标，但视觉确实沉 |
| `#17805f`（折中候选） | **4.90:1** | 达标且更亮 |
| `#121412`（官网主按钮） | **18.51:1** | 最稳，但与"绿"无关 |

⇒ **不能简单"调回旧绿"**：那等于把对比度不合格的颜色请回来。

### 2.4 三个选项（要你拍一个）

- **A（推荐，最贴官网）**：实心主按钮统一 `#121412`（官网 `btn-primary` 同款），绿色只留在 chip / 描边 / 成功态 / 焦点环。
  代价：工作台主按钮从绿变黑，一眼看过去和官网一致；绿色信息量更少但更准。
- **B（保留绿，提亮）**：`--color-teal-600` 由 `#2d7356` 改为 `#17805f`（4.90:1 仍达标），其余不动。
  代价：一处变量改动，最小；但与官网按钮仍不同款。
- **C（不动）**：接受当前墨绿，视为"官网同款"的既有决定。

## 三、单稿 / 多稿切换没变化

### 3.1 根因（可复现，file:line 齐全）

1. `workbench-view.tsx:298` 多稿状态初始化：`batchMode ? clearMultiPsdSelection() : null`
   —— 只有**用 `#batch` 直接进页面**时才是非空对象；正常从单稿页进来时是 `null`。
2. `workbench-view.tsx:1385-1400` `requestModeChange(true)` 只做了 `setBatchMode(true)`，
   **从头到尾没有 `setMultiPsdSelection(...)`**（该文件里 `setMultiPsdSelection` 只有 3 个写入点：298 初始化、1412 切回单稿、2303 卡片回调 —— 没有一个是"切到多稿"）。
3. `design-file-card.tsx:929` 批量分支的入口条件是
   `if (batchMode && multiSelection && onMultiSelectionChange)`
   —— `multiSelection` 为 `null` ⇒ **直接落回单稿卡片**。

⇒ 点「多个设计稿」的真实效果：副标题换了一句话，卡片还是单稿那张。你看到"没有变化"是对的。

### 3.2 为什么测试没拦住

现有 smoke 断言的是"切换器存在""文案正确""切回单稿要先确认"，**没有一条断言"切到多稿后渲染的是多稿卡片"**——这正是项目里反复出现的"入口在、代码在、测试绿，但真实路径不通"。

### 3.3 修法（一处主改 + 一条守卫）

- **主改**：`requestModeChange` 切到多稿时补
  ```ts
  setMultiPsdSelection((prev) => prev ?? clearMultiPsdSelection())
  ```
  （保留已有选择；`clearMultiPsdSelection()` 返回 `{ entries: [] }`，`psd-selection.ts:80`）
  切回单稿时（`confirmSwitchToSingle` 已处理）保持现有语义。
- **守卫**：在 `smoke-*workbench*` 里加一条静态断言——"`requestModeChange` 的 `nextMulti` 分支必须同时出现 `setBatchMode(true)` 与 `setMultiPsdSelection`"，并加一条反例负控（把 `setMultiPsdSelection` 删掉应当变红）。
- **顺带核**：`#batch` 深链路径（初始化非空）一直是对的，说明这是"后来加页面内切换时漏了一处"的回归，不是设计问题。

### 8.4 踩到的两个坑（记下来）

1. `download/local-assistant/server.js` 与 `scripts/*.mjs` 是 **CRLF**，`workbench-view.tsx` 是 **LF**。写变异正则时用了 `\n` 导致 `MUTATE-MISS`（一处没替换、一处静默 0 命中），差点把"对照实验没做"当成"做了"。改用 `\r?\n` 才真正命中。
2. `fold-no-report-loss` 的判据正则 `[^\n]{0,160}` **不跨行**，`→ 同屏展开` 必须和「折叠不得删报」写在同一行。第一版箭头写在注释第二行，R1 过了、R2 报"取不到落点"。
3. 出包时只给了 `PATH`（`file` 替身）却漏了 `CODEBUDDY_SAFE_DELETE_BULK_THRESHOLD=400`，于是 `test:contracts` 在第 9 段被本机删除护栏误杀（`count:50 threshold:50 scope:"turn"`）。**这条护栏误杀看着像代码缺陷，其实不是**——`release:package:test` 会自己再跑一遍完整 preflight，环境变量必须一起给。
