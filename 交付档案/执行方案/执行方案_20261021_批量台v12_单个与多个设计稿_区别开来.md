## 2 那为什么还是"分不开"？——四个缺口（每条都有坐标）

我逐处核过：多稿台**已经做了不少集合语义**，缺的恰好是最显眼的那几处。

| 缺口 | 现状（证据） | 后果 |
|---|---|---|
| **② 没有范围条** | 全站没有任何一处常态显示"这份稿 / 这一批 N 个"。切档后只有切换器本身变了色 | 用户切过去**不确定自己进了哪一档**，尤其从别处回来 / 刷新后 |
| **③ 顶部状态带仍是单稿语义** | `workbench-view.tsx:2685-2757` 未按 `batchMode` 分支，用的是 `psdSelection`（当前稿，`:384`；由 `multiPsdSelection` + `activeDraftKey` 同步，`:1728-1730`）⇒ 多稿下显示的是**某一个文件名 + N 个语言** | 多稿台顶部看起来跟单稿台**一模一样**。这是"像没切"的最大来源 |
| **⑤ 默认信息密度没区别** | 第 2/3 步（`ReviewStep` / 校对）在两种档下默认都全量展开 | 12 稿 × 3 语言的每一行都摊开 ⇒ 越多越不想看，多稿台的"工作方式"没被表达出来 |
| **⑥ 生成按钮不带范围** | 逐稿执行进度已有（`execute-step.tsx:2295` 正在执行第 N/M 个；`:2274` N/M 个设计稿已扫描），但**主按钮本身**没有范围 | 用户点「确认并生成」时不知道会生成 1 份还是 12 份 |

**已经有的、不用重做**（避免我重复发明）：

- 多稿列表与「全部扫描（按顺序）」：`design-file-card.tsx:1231`、`:856`、`:1087`（超 12 个逐条点名）
- 逐稿执行与"不会静默跳过"：`execute-step.tsx:2274/2281/2295/2342`
- 覆盖率矩阵（哪稿没导表 / 哪稿没扫完）：`coverage-matrix.tsx:59`、`:69`
- 档位切换器与副标题：`workbench-view.tsx:2637-2676`

## 3 建议：不动骨架，只改三处「看得见的范围」

> 一句话：**单稿台把细节摊开，多稿台把问题推到面前。**
> 两档不是"外观不同"，是"工作方式不同"：**单份＝逐份精修，多份＝例外处理。**

| 优先 | 改什么 | 怎么改 | 成本 | 风险 |
|---|---|---|---|---|
| **P0** | **加范围条** | 切换器右边常驻一个 chip：`这份稿：SKU-AX1001_主图.psd` / `这一批：12 个设计稿 · 已扫描 9 · 3 个要处理` | 极低（1 个组件，读已有 state） | 无（包在 `batchMode` 内） |
| **P0** | **状态带按档切语义** | 多稿下换成集合语义：`● 12 个设计稿 · 9 个已扫描 · 3 个待扫描` ＋ `[全部扫描]` ＋ `[3 项待处理 ▾]`；单稿保持原样逐字节不变 | 低（改一个 `div` 的渲染分支） | 低（`batchMode=false` 走原路径） |
| **P1** | **默认信息密度相反** | 多稿台第 2/3 步**只摊开"要处理的"**，其余折成「查看其余 N 个」；单稿台保持全量展开 | 中（需要"要处理"的排序口径＝已有 `NEEDS_CONFIRMATION` / 未对齐判据） | 中（不得隐藏，只折叠，且有"查看其余"出口） |

**为什么不建议做更大的改动**：换配色、换布局、加第五步、恢复两个并列入口 —— 见 §5。

## 4.5 「确认并生成」按错了怎么办 —— 取消 / 停止（2026-10-21 新增）

Owner 原话：「现在确认并生成后，如果是不小心按到的话，没有一个取消的按钮一起把这个也做了吧」。

**先说结论：这条不是加个按钮，它落在执行与计费的状态机上。** 我按"能不能安全地停下来"拆成三层，只有前两层能做。

### 4.5.1 现状：按下去之后，用户侧没有任何停下的入口

| 事实 | 证据 |
|---|---|
| 按「确认并生成」后只有**防双击锁**，没有停止 | `execute-step.tsx:1946-1958`（`submittingRef` / `unsettledExecution` 锁重试） |
| 全站唯一的"取消"按钮**只在失败后出现** | `execute-step.tsx:2834`（`failed && lastJobId` 才渲染） |
| 而**批次主链根本不产生单语言 jobId** ⇒ 该按钮在批量链下不会出现 | `execute-step.tsx:1903-1909`（注释原文：批次 v3 主链不产生单语言 jobId） |
| 批次链的退积分靠**系统自动核对**（约 15 分钟） | `execute-step.tsx:1905` |
| 服务端已有**安全**的取消语义，但只到 jobId 级 | `src/app/api/billing/photoshop/cancel/route.ts:1-4`（只有 reserved 且未跨 `TICKET_CONSUMED` 边界可原子释放；running/manual_review/未知态**禁止自动退款**） |
| **没有批次级取消接口** | `src/app/api/billing/photoshop/` 下只有 cancel / confirm / jobs/[id]/status / quote / reconcile / report（实测目录列举，无 batch cancel） |
| 批次流里只有**系统性中止**（故障驱动），没有用户侧停止 | `src/lib/workbench/v3-batch-flow.ts:286-288`、`:448` |
| **没有 PSD 备份机制**，只有"请自行备份"的免责文案 | `src/config/siteContent.ts:423`、`src/app/(zh)/terms/page.tsx:151` |

### 4.5.2 三层拆开：能做的、不能做的

| 层 | 用户看到什么 | 边界 | 能不能做 |
|---|---|---|---|
| **D1 前置确认**（先做） | 按下去先弹一次确认：`设计稿 12 · 语言 3 · 替换行数 58 · 预计 174 积分`，按「确认生成」才真的开始 | 确认之前**不冻结积分、不写文件** | ✅ 纯前端，**不触发**状态机门禁 |
| **C2 取消并退回** | 确认后、**第一份稿开始写入之前**：`取消并退回 174 积分` | 仅 reserved 且未跨 `TICKET_CONSUMED`；服务端语义已存在，缺**批次级聚合入口** | ✅ 要做后端（批次级），**触发**高风险门禁 |
| **C1 停止** | 已经开写之后：`停止这一批（已完成 6 / 12）` —— 停止后续派发，已完成部分正常结算 | **不还原已写入的 PSD**；未执行部分不扣费 | ✅ 要做后端（批次级停止信号），**触发**高风险门禁 |
| **C3 撤销已写入** | "把刚写进去的还原回去" | **没有源文件备份**，无法承诺还原 | ❌ **不做**；文案如实说"请用你自己的源文件覆盖" |

### 4.5.3 三条必须写进产品文案的边界（否则就是骗人）

1. **停止 ≠ 撤销。** 停止只保证"后面的不再派发、没执行的不扣费"，**已经写进 PSD 的不回退**。
2. **能全额退的时间窗很短**：第一份稿开始写入前。之后只能按已完成比例结算。
3. **已写入的还原靠自己**：产品没有 PSD 备份（`siteContent.ts:423` 就是这条免责），所以不能做"一键还原"按钮。

### 4.5.4 停止按钮也要带范围（与 ⑥ 同一条原则）

- 单稿：`停止这一份`
- 多稿：`停止这一批（已完成 6 / 12）`
- 停止后的结果面板必须把账摊开：`已写入 6 份 · 未执行 6 份 · 已结算 87 积分 · 未扣费 87 积分`

### 4.5.5 代价与门禁（这条不能"顺手做"）

- **D1** 只改 `execute-step.tsx` 的按钮层 ⇒ 不触发状态机门禁，可随 ②③⑥ 一起进 **2.5 阶段**。
- **C1 / C2** 改变的是 **Job / Attempt / Ticket / Reservation / Settlement / Ledger / Recovery** 的执行与计费语义 ⇒
  - **触发高风险状态机强制门禁**（12 问 → 状态机 → 失败窗口矩阵 → 对抗式审查 → 故障注入 → 并发测试 → 恢复验证 → 终审 → 记忆更新）；
  - **触发合同变更门**：同一提交内同步**四层**（浏览器投影 / 助手 evidence / 服务端报价 / 结算闸）＋ 更新 `test:batch-row-contract` fixture，并在 HANDOFF 偏差登记表标【合同变更】；
  - 未跑 `npm run test:batch-row-contract` 与 `test:trust-chain` **不得部署测试站**；
  - 依赖服务端**新增批次级 cancel**（现在只有 jobId 级），是真正的后端改动，不是 UI。
- ⇒ 建议顺序：**D1 先随 2.5 落地（消灭"误触"）→ C2/C1 单独立项走门禁 → C3 明确不做**。

## 5 三条「不做」（做了会反噬）

1. **不换配色 / 不换布局**：用户会以为进了两个产品，切换成本反而升高；也违背您定的"不要跟单个设计稿跳得太脱"。
2. **不加第五步**：「批次入口」放进第 1 步内部就行。`product-specs/workbench-flow.md:64` 写明流程仍是四步，"四步→三步"是目标态、未拍板不得当既成事实；反过来加第五步同样越界。
3. **不恢复两个并列入口 / 不用关系词**：`site-header.tsx:19-22`、`workbench-view.tsx:2634-2636` 已有 Owner 的否决记录（"看起来像两个功能"｜"一对多 / 多对多"这类词）。

## 6 用词：单个 / 多个，还是单份 / 多份？

- **线上现状**：「单个设计稿 / 多个设计稿」，且**硬编码在 `workbench-view.tsx:2654 / 2668`**。
- **建议：保持线上词不动。** 理由：① 两个词同维度、已经对称，问题不在词而在"看不见"；② 若要改成"份"，必须先处理**三处文案并存**——`siteContent.ts` 默认值 / `workbench-terms.ts` / 组件内硬编码，这是 `workbench-flow.md:70` 记的"改了不生效"根因，属额外成本而不产生价值。
- 若您确实偏好"份"，则**一次改全三处**，并同步 `aria-label="设计稿数量"`（`:2640`）与副标题（`:2672-2676`）。

## 7 对 v11 九阶段的修订

| **1** | 目录约定文案与引导 | 不变 |
| **2** | 读目录 ＋ 配对规则（纯函数） | 不变 |
| **2.5** | **两档可见性：范围条 ② ＋ 状态带集合语义 ③ ＋ 生成按钮范围 ⑥** | **新增**（P0，最小改动、最大区分） |

**合同变更门**：②③⑥ 与 **D1（前置确认）** 都是 `batchMode` 内的展示层/按钮层，**不触发**合同变更门，不碰执行链 / 报价 / 结算闸 / 助手协议 / 支付开关 / `binding-core` 匹配键。

**新增一条不变式**（补进五道闸）：**「单稿档逐字节不变」现在有了第二个风险点——③ 状态带。** 改 `:2685-2757` 必须落在 `batchMode ? ... : 原样` 分支内，且快照脚本要**同时抓 batchMode=false 与 batchMode=true 两套基线**（否则"多稿改了单稿"这类错永远抓不到）。
