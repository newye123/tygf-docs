### 1.2 我前五轮具体违反了哪里

| 我动过的 | 后果 |

### 1.3 本轮改法：从「改共享组件」改成「**旁挂**」

| | 上一轮（v2–v7） | 本轮（v8） |
|---|---|---|
| 形态 | 改共享组件，加 `batchMode` 分支 | **批量台的自有能力一律新组件/新模块**；共享组件要么**整份不动**，要么只**加带默认值的 prop** |
| 单对多工作台 | "应该不受影响"（靠自觉） | **零改动**（靠闸 1–5 证明） |
| 验收尺 | 无成文标准 | 沿用仓库既有的「**与原行为逐字节一致**」 |

### 2.2 五道不变式闸（任一不过，不许合入）

| 闸 | 内容 | 怎么执行 |
|---|---|---|
| **闸 1 · 结构** | 入口那一行不许动：`app-shell.tsx:46-47` 的 `{view === 'workbench' && <WorkbenchView />}` 与 `{view === 'batch' && … <WorkbenchView batchMode />}` | **diff 直接可见**（这两个文件本轮原则上不改） |
| **闸 2 · 渲染** | 多稿能力（来源矩阵、逐稿编排、覆盖率矩阵、批量动作、批量样式）**必须**在 `batchMode &&` 内或 `if (!batchMode) return …` 之后 | 先例：`workbench-view.tsx:1766/1786/1802` |
| **闸 3 · 行为** | `batchMode=false` 下渲染 `#workbench`，对**关键 DOM 节点数 / 文案集合 / 按钮集合**做快照，与基线**逐字节**比对 | **新增一条本地可跑的断言脚本**，纳入提交前门（这是唯一能把"逐字节一致"从口号变成事实的东西） |
| **闸 4 · diff** | 批量台改造**优先只新增文件**；对既有文件的改动必须落在 `batchMode` 块内或只是**加带默认值的 prop** | `git diff` 逐条核；凡是无法说明「为什么不会影响单文件台」的行，不许合入 |
| **闸 5 · 单一真值** | 「哪个模式」**只认视图传下来的 `batchMode`**；禁止任何第二真值（编译期 featureFlag 常量、URL 参数、全局开关）能单独决定渲染形态 | **先例：ISSUES #151**（`design-file-card.tsx:74-83` 注释记着静态 flag vs 运行时 flag 两套语义导致形态错位） |

### 2.3 共享什么、不共享什么

| | 共享 | 不共享 |
|---|---|---|
| **纯函数** | 解析、合并、切片、覆盖率口径（`coverage.ts` 的三档）——纯函数无渲染副作用，抽出来**不会**影响任一工作台 | — |
| **UI 组件** | — | **不共享**：组件带渲染路径，共享就是让两台再次交汇 |

⇒ 代价是批量台要多写一份"表导入器"与"按格审查面板"外壳（**少量重复**）；换来的是**单对多工作台可以拿「零改动」这个硬承诺去交付**。

## 阶段四 · 模型结论不变（v7 保留）

- 绑定的原子＝**(稿 × 语种) → 一组行**；1:1 / N:1 / 1:M / N:M 四种关系自动涌现。
- 人只有三种操作：换主表 / 语种覆盖 / 补充表；其余 144 格由系统推导并画出来。
- **不动写入层**：合并发生在 fragments 之前 ⇒ 信任链的冲突检查（`binding-core.ts:657`、`:930-939`）原样复用 ⇒ **不触发合同变更门**。
- 「整表共用 vs 必须切片」的判据可计算：表内有「同原文不同译文」⇒ 必须切片；无 ⇒ 可整张共用。
- 覆盖率三档口径不变（`coverage.ts:43-96`），只把取数口从「每稿一表」换成「每格一行集」。

**本轮唯一变化：以上能力全部落在「批量台专属的新文件」里，单对多工作台一行不碰。**
