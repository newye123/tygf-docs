01一句话

结论

飞书表管住了「有哪些事」，管不住「同时在办几件、谁在做、做完算不算数」。补这三件，才是中台。

04GitHub 上人家怎么做「中台」

issue-orchestrator

headless 控制面

把 GitHub issue 变成隔离 worktree 里的有界运行，经校验/复验/返修/人工批准四道门才推进。「Agent 提议、编排器裁决」；Agent 不能合并 PR，人合并；改状态前先重观测。

open-agentos / agentos

GitHub 即操作系统

issue 走 label 状态机，每次迁移触发 Actions 工作流派发给对应角色。状态机即路由；每个角色一个最小权限身份；AGENTS.md 是全体 Agent 的操作手册。

nordinit / agent-hq

证据门

task → route → agent run → evidence → outcome → transition。完成必须交证据，没证据不推进。

luminik-io / alfred

认领状态机

全在 GitHub 上实现：label 载状态、结构化注释载审计，无共享数据库。认领/释放原语防止两个执行者重复做同一件；带黏性闸 do-not-pickup／needs:human-scope。

skdhir / ai-agent-orchestra

单人创始人手册

120+ PR、3 Agent、1 个人。Agent 之间靠「文件」协调，不靠对话；人是瓶颈不是 Agent——3 个并行是单人复验上限；写码前先给 2–3 个选项等批准。

ParallelPilot（arXiv 2609.33113）

学术综述

归纳出 PILOT（Planning / Isolating / Logging / Observing / Triaging）。Brooks 定律对 Agent 同样成立——并行一多，协调开销会超过收益。

大厂同向（旁证）

GitHub 自己把「Agent Control Plane / Mission Control」做成了产品；GitHub Issues 也加了 approvals / confidence / rationale（高置信自动应用，中低置信挂起等你批）。⇒ 「控制面」不是我的发明，是行业共识。

六家的共同结论（也是给你的答案）

  • 真相必须是「崩了也还在的」外部东西——首选 git / issue label，不是新数据库或看板。
  • 状态机要固定、要有限——几个枚举状态 + 迁移规则。
  • 要有闸门——完成不等于自报完成，要过证据门/复验门；发布要过人工批准门。
  • 要有限值——同时在办数量必须卡死；跨过就排队。
  • 要有认领——同一件同时只能一个会话在做。
  • 看板只是窗口——先做看板就是第四本没人写的账。

06中台设计：三层 ＋ 五个机制

视图层   飞书多维表格（已有）＋ 每天一条 watchdog 日检
           ↑ 只读投影，单向
控制层   中台本体：状态机 · 在办限值 · 五个闸门 · 认领锁   ← 本方案要补的就是这层
           ↑ 只写 ledger.jsonl
真相层   git 提交历史 ＋ AI_MEMORY/TASK_LOG.md ＋ AI_MEMORY/ledger.jsonl
单向原则

只有真相层能被写；控制层读真相层算判据；视图层只显示。「表没更新」不算事故，「git 有而表没有」才算事故。

1

认领锁

一个任务同一时刻只有一个会话认领；重复认领必须失败。借自 alfred。→ 解决「谁在做说不清」。

2

在办限值 = 2

同时在办 ≤2（1 产品 + 1 应急）；超了就排队。借自 Personal Kanban。→ 解决「线太多、顾不过来」。

3

决策闸

只有 等您定 的才占你的注意力；其余机器干。→ 解决「都想要做」。

4

证据闸

翻「已交付」必须带证据（file:line + 真实 rc）；自报不算数。借自 agent-hq。→ 解决「做没做到什么地步」。

5

发布挂号闸

任何进 main 的合并，同一次提交带一行挂号（sha/包名/时刻/复验件）；查不到即立案。→ 解决今晨发布无台账。

＋

到期断路器

每条线写到期日；到期未完成 → 自动降级「已搁置」，不占名额。借自 Shape Up。→ 解决线永远挂着不清。
