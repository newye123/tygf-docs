## 零、一句话结论

六件事里，**两件不是"改法不对"而是"我们现在做不到"**：免 PS 写回**不是没接、是接了会出错**（三个 P0，其中两个已复验）；免 PS 安装包**不是没打包、是打包管线里根本没有这个形态**，硬做等于一次发布事件，会硬拦所有旧安装。
另外四件里有**两件是"文案在骗人"**（表格那两处指向了不存在的功能），一件**根因可能根本不在界面上**（排版定制的灰度开关默认全关），一件是**真正的新功能缺口**（每稿一表）。

## 一、必须先摆上桌的冲突

交接文档第 3 节白纸黑字写着：

> **对外口径：免 PS 当前只承担「扫描 + 预览」；写回继续走 PS。** 不要对 Owner 说"已支持免 PS 写回"。

## 二、对抗式审查：六问的事实

### 2.1 免 PS 走完一切 —— 不是没接，是接了会出错

**事实（源码面，全部可复核）**

- 写回执行器 **`pc-executor.js` 是完整实现，不是壳**：读 execution-envelope → 源文重名 fail-closed 检查（`SOURCE_STALE`/`SOURCE_TEXT_AMBIGUOUS`）→ 逐条 `engine.execute`+`type.edit` → **回读复核**（`READBACK_MISMATCH`）→ `doc.save` → `doc.close` → 写 `executor-result.json`。
- 但它**生产零接线**：`server.js` 里 `require('./pc-executor')` 0 次、`runPhotoCraftExecutor` 0 次、`runPhotoCraftReopen` 0 次、`startServeSession` 0 次、`decideExecuteChannel` 0 次、`executorMode === 'pc'` 0 次。`v15-runner.js`（1120 行）内**没有任何可切到引擎的钩子**，它调的 `launchExecutor` 恒为 PS 版。
- 守卫 `scripts/smoke-pc-wiring-freeze.mjs` **9 条断言**把这件事钉死，其中第 7~10 条是**负向断言**（"不得 require ./pc-executor"、"三个写回导出不得出现在 server.js"、两个 `=== 'pc'` 分发分支不得存在）。想解冻，必须**先解三个 P0，再显式改这个文件并把证据写进注释**。
- 通道判定**只看进程存在性**：`runningPsExe()`（`server.js:482-500`）用 PowerShell `Get-Process -Name Photoshop`。**只要机器上存在任何一个 `Photoshop.exe` 进程，通道恒判 `ps`**——不管它是不是幽灵、是不是能用。
- **没有任何运行时兜底**：PS 在跑但失败 ⇒ 硬失败，走 `classifyExecutionError` 的 PS 错误分类，**不会退到引擎**。
- PS 不在 + 旗标关 ⇒ `refuse/PC_CHANNEL_DISABLED`，用户看到 **`Photoshop 未运行。请先启动 Photoshop，再重新扫描设计文件。`**，状态 `waiting_for_photoshop`，而 `isPsdSelectionReady` 要求 `state==='prepared'` ⇒ **整条流程卡死在这里**。
- 上游其实**有过兜底设计**（`fc287fb`："PS 握手失败但 PhotoCraft 通道可用：兜底接管"），本树**刻意不跟**，正是那两条负向断言要钉死的形状。

**三个 P0 的原始记录**（在容器根 `交付档案/`，**不在仓库树内**；树内唯一痕迹是守卫注释）

**本次新做的实测（三路，独立）**

1. **引擎 `type.edit` 跑得动**：对复制件改一个文字层，rc=0，回执里 13+ 段落字段（`align`/`auto_leading`/`hyphenate`/`first_line_indent_pt`/`space_before_pt`/`space_after_pt`/`start_indent_pt`/`end_indent_pt`/`direction`）**全在**，字符样式（`NotoSans-Regular`/18.34pt/weight 400/颜色）保住，产物 PSD 正常写出。
2. **第三方读取器交叉验证**：`ag-psd`（与引擎无关）读原件与产物**都是 137 个文字层**，产物里靶层从 `79.6mm` 变成 `TYGF-PROBE-99`（层名与文本同步），其余同串图层**分毫未动**。⇒ 写回**确实落进了标准图层数据**，不是引擎自说自话。
3. **字节级取证（决定性）**：原件里 **`Txt2` 键 0 次**；产物里**新生成 1 处文档级 `Txt2`（@3862678）**，其区内**旧串 `79.6mm` 出现 3 次、新串出现 1 次**。
   ⇒ **`#6971` 的签名在当前引擎版本上复现了。**（我的第 1、2 步只证明"文字写进了图层"，第 3 步才暴露"PS 要看的那份没被同步"。）

**对抗性反驳（对"直接打开写回"这个选项）**

- 今天打开写回 = **交付静默错误**：用户拿到文件，PS 里看到的还是**原语言**（`#6971`），甚至 PS 2026 打不开（`#6968`）。**这比拒绝更糟**——拒绝用户知道要装 PS，静默错误用户会直接把错稿交给客户。
- "扫描不了用户的 PS"有两种读法，要分开设计：
  - **PS 根本没装**（真实市场）⇒ 需要引擎成为**默认路径**，而不是藏在开关后面；
  - **PS 装了但坏了** ⇒ 需要**运行时兜底**，而这个今天**不存在**，且被守卫明令禁止。
- 引擎不是 PS 的等价物：栅格化、智能对象（176MB 那份里有 6 个）、图层效果、**以及用户机器上的字体**都不同。本次探针就已经报出 `font 'Adobe Heiti Std' is not installed` / `'Koz Go Pr6N' is not installed` ⇒ 会**按字形回退渲染**。所以"走完一切"必须先定义"一切"的边界。
- **一个绕不开的约束：免 PS 产物好不好，只能靠 PS 打开来判**——而目标用户恰恰没有 PS。⇒ 验证必须在**有 PS 的机器**上做。**这正好就是那台测试机。**

### 2.2 "photocraft" 字面量 —— 产品界面早就干净了，脏的是我们的文档和引擎本体

**事实**

- 全仓 **77 处 / 16 个文件**，**全部**集中在 `AI_MEMORY/`、`download/local-assistant/`、`scripts/`。
- **`src/`、`public/`、`docs/`、`product-specs/`、`changes/`、`config/`、下载页、安装包 —— 零命中。** 我们自己的安装包产物是 `图译工坊引擎.exe` / `图译工坊本地助手.exe` / `tygf-engine-setup-<版本>.exe`，**全是自家名字**。
- 剩下的分三类：
  - **内部标识**：函数名 `runPhotoCraftScan`/`runPhotoCraftExecutor`/`runPhotoCraftReopen`、进度标签 `'photocraft scan activity'` 等；
  - **持久化值**：`pc-scanner.js:278` 写 `engine: 'photocraft'`，**全仓唯一比较点**在 `pc-channel.js:47`——而那个函数（`decideExecuteChannel`）**生产零调用**；
  - **操作者可见文字**：`pc-executor.js:140` 运行时错误 `PhotoCraft 执行器无响应`、启用脚本的报错与用法注释。

- 仓库里**没有**任何关于"改我们的名字"的既有决议记录（`changes/`、`docs/`、`product-specs/` 零命中）。另注：`pc-executor.js:1` 引用的设计依据 `changes/active/20261015-photocraft-integration-plan-v2.md` **在本树不存在**。

**对抗性反驳**

- **您看到"PhotoCraft"最可能是在我的飞书报告和交接文档里**，不是在产品里——那份报告里 `C:\Program Files\PhotoCraft\photocraft-cli.exe` 反复出现。所以**最锋利的一刀是砍我们自己的交付文档，这一刀免费**。
- 但"产品里绝不能出现"这条要分清楚：**内部函数名不面向用户**；**引擎安装目录面向用户**。后者改名＝**重编那个 Rust 分叉**，不是我们仓库里的事。
- **授权问题必须先解决**：一个开源项目被我们打包分发（尤其若捆进安装包），安装目录里却看不到 LICENSE —— 这是合规问题。我这边**网络被拦，取不到上游仓库的 license**，必须由知道是哪个项目的您/Owner 确认。
- 改 `engine: 'photocraft'` 这个**持久化值**今天安全（生产不读它），但一旦将来接线，磁盘上的旧 provenance 会命中 `PC_SCAN_PROVENANCE_PS_SOURCE` 分支（被误判成"PS 扫的件"）⇒ 改值时**必须同时接受旧值**，或**先改值再接线**。

### 2.3 多设计稿 × 每稿不同表格 —— 您的场景今天**不支持**，缺的是浏览器侧

**事实**

- 工作台全程**只有一张表**：`WorkbenchView` 持有单个 `parsed`，同时喂给选表/审查/执行三处。
- `MultiPsdEntry` / `MultiPsdSelection` **没有任何表格字段**；浏览器草稿也只存一份表。
- 而**服务端契约本身就是"一批一表"**：`ExecutionBatch` 单 `translationSetDigest`，报价接口每次请求带 `rows` + `languageCodes`。批量面板自己写着：**「每个设计稿将独立走现有批次链（1 设计稿 × N 语言 = 1 个批次），按列表顺序执行」**。
- ⇒ **服务端已经具备按批次换表的能力，缺的纯粹是浏览器侧的模型 + UI + 路由。**
- **12 是"每批（每稿）语言上限"**（`BATCH_MAX_LANGUAGES = 12`），另有独立的**"每批最多 12 个 PSD"**上限。您举的例子（12 个 SKU）**正好顶在 PSD 上限上**。
- 会被打破的守卫：`smoke-batch-workbench-logic.mjs`（纯函数签名/语义）、`smoke-workbench-ui-contract.mjs`（文案键与阶段结构）、`smoke-batch-workbench-guards.mjs`（`design-file-card` 文案串）、`smoke-batch-limits.mjs`。

**对抗性反驳**

- 这是您六条里**唯一真正的新功能缺口**，且是 **L2 变更**（新能力、改主流程），不是修 bug。
- 设计上有个真问题要先定：映射方向是"**PSD → 表**"还是"**表 → PSD**"。文件夹扫描**已经列出了表格候选**（`folderScan.tables`）——**按文件名约定自动配对 + 允许手工覆盖**是最自然的做法，而"手工覆盖"正是现在缺失的那一环。
- 一处**顺带发现的正确性隐患**：`computeReviewManifestHash` **只哈希表格行**，而信任链另一侧的 `documentFingerprint` 是 **PSD 字节哈希**。引入每稿一表后，"同表不同稿"会让两份不同的稿共享同一个 review manifest 哈希——**这个要一并处理**。

### 2.4 表格上传"非常有误导性" —— 有两处**在许诺不存在的功能**

**逐字证据（最锋利的两条）**

- `design-file-card.tsx:1116`：**「译文表候选 {n} 张（未自动绑定，需在语言区手动指定）」** —— **语言区根本没有表格指定控件**。这句话指向一个不存在的入口。
- `design-file-card.tsx:1019`：**「表格（xlsx / csv / tsv）只列候选，不会自动套用」** —— 暗示后面有一个"套用"动作，实际没有。
- 配套事实：`handleAddFolderResults` **从不读 `folderScan.tables`**，候选只用于展示。

**会让人以为"一张表通吃"的措辞**

- `csvHeaderTitle`「导入多语言译文表（表格 / 粘贴）」—— 单数，全程只有一处导入。
- `csvDropHint`「…可一次选择多个文件」+「多个文件…**自动合并为多语言表**」—— 多文件是**合并成一张**，不是"每稿一张"。
- `csvMergedFileName`「{count} 个表格已合并（{langs}）」—— 强化"一张表 = 全部"。

**产品自己前后矛盾（这条比措辞更严重）**

- FAQ（`siteContent.ts:834`）：「**不要把另一份设计稿的表格直接套过来**：原文看起来相同，不代表对应的图层和位置相同。」——**明说不同稿的表可能不同**。
- 而 `ISSUES.md:615`（#78）把「**跨文档共用表属正常**」当作既定形态。
- ⇒ **同一产品里两句话互相打架。** 光改措辞只会让它"一致但仍错"。

**约束**：`product-specs/workbench-flow.md` 的 **WF-002** 规定「下载示例表格」必须留在导入区右上角、格式说明默认展开、**不得提供"上传图片"入口** —— 改这一片不能碰这三条。

### 2.5 排版定制（内测预览）—— **根因可能根本不在界面上**

**事实**

- 这个面板**没有自己的入口按钮**：面板本身就是入口，而且是一个**默认折叠**的折叠头。
- 它挂在 `workbench-view.tsx:2489`，是「准备素材」阶段内容里的**第 5 个、也是最后一个**兄弟节点——**正好就在页面最底部**、紧贴贴底操作条上方。**和您描述的位置完全一致。**
- **它被两道门锁着**：总开关 `typographyCustomizationEnabled`（**默认 `false`**）＋ 灰度白名单 `typographyBetaUsersV1`（上限 100 人）。判定语义 = **总开关 ∧ 名单非空 ∧ 用户在名单**；**未登录/异常一律 false（fail-closed）；空名单 = 谁都不开。**
- ⇒ **您能看见这个面板，说明您在白名单里；如果您看不见，加多少个悬浮按钮都没用。** 这一条**必须先查**（运营台一分钟的事）。
- 产品里**已有悬浮控件先例**：`inline-edit.css:146-162` 的 `.sc-edit-badge`（`fixed; right:16px; bottom:16px`）；工作台里也已有**两个右抽屉**先例（`objects-drawer.tsx` 左、`object-inspector.tsx` 右）。
- 工作台还有**贴底操作条**（`sticky bottom-0 z-30`）和**顶部常驻状态带**（`sticky top-16 z-30`）——悬浮按钮必须避开这两个。
- 全仓 `src/` 内**零** `safe-area` 处理。
- 守卫 `smoke-typography-customization.mjs:190-195` 断言面板挂载位置**必须夹在 `id="stage-preparation"` 与 `id="stage-review"` 之间** ⇒ 把面板挪出第一阶段（例如改成抽屉）**会撞它**，必须同笔更新。

**对抗性反驳**：您说"怎么没有看到悬浮按钮"——但**从来就没有设计过悬浮按钮**，原设计是内联折叠面板。所以这是一个**新增可供性**的请求，不是修 bug。而且**第一问应该是"您到底能不能看见它"**，不是"按钮放哪"。

### 2.6 免 PS 安装包 —— **打包管线里没有这个形态**，硬做＝一次发布事件

**事实**

- 免 PS 引擎（`photocraft-cli.exe`）**根本不在我们的安装包里**。`installer.iss` 的 `[Files]` 只有 6 类：`图译工坊引擎.exe`、`图译工坊本地助手.exe`、图标、`release-identity.json`、4 个 PS COM 诊断工具。**没有 photocraft。**
- 三个键（`pcExecutorEnabled`/`pcExePath`/`pcExeSha256`）**缺省全关**，开启是**在机器上跑运维脚本**的动作，不是安装包的能力。
- **没有任何"只发安装包、不动站点"的受支持路径**：站点在**构建期**从 `config/release-identity.json` 把兼容契约烘进去；安装包文件名被钉死为 `tygf-engine-setup-${assistantVersion}.exe`；发布器**拒绝同版本第二个二进制**。抬高版本或改 `assistantBuildId` ⇒ **硬拦所有旧安装**（`ASSISTANT_UPDATE_REQUIRED` / `ASSISTANT_CONTRACT_MISMATCH`，三处独立门）。
- **没有变体安装包先例**：命名严格 `tygf-engine-setup-<semver>.exe`，历史上"发布内测安装包"用的也是同一命名。
- 当前安装包**未签名**（`signatureStatus: UnsignedBeta`）；站点要提供下载还需 env `LOCAL_ASSISTANT_ALLOW_UNSIGNED_BETA=1`。`docs/周末上线-P0-检查表.md:48` 写着"未签名内测包只发给已知种子用户"。
- 生产出包还要求**14 天内的五项真机验收记录**（install/pair/scan/batch/report）；测试目标不拦。

**对抗性反驳**：按字面"出一个免 PS 的安装包"，实际是**一次发布事件**（版本号 + 身份传播十余个文件 + 全套门禁 + 硬拦旧安装），而您以为只是发个文件——**而且它里面还不会有引擎**。
