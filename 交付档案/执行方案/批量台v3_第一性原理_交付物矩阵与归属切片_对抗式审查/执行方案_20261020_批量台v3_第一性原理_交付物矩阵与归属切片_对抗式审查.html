02阶段一 · Critical Thinking

这个工作台真正生产的东西不是「表」、不是「文件」，是 (设计稿 × 语种) → 一份新的设计稿。12 SKU × 12 语种 = 144 份交付物。一行译文的键是 (归属, 原文, 序号, 语种)——里面没有「文件」。

公理 A · 交付物轴

交付物的键 ＝ (文件, 语种)

界面主角必须是这 144 个东西。图二那排语言 ＝ 矩阵的一行。

公理 B · 归属轴

译文的键 ＝ (归属, 原文, 序号)

文件不是原语，归属才是；文件只是归属这个维度上的一个取值（或归属缺失）。

公理 C

绑定必须可证，不能靠猜

若产品能接受「猜错了用户自己看出来」，则不需证据分级——但这与「不可逆写进客户文件」不相容。

公理 D

「每稿一表」是安全装置，不是自然法则

v7 的 F11 缺表门是在「绑定无法验证」前提下的兜底。绑定一旦可证，一稿用多稿的表就不是危险，而是合法。

三条结构性结论

①「表」根本不是按文件分的东西。正确形态是「表 ＝ 数据集；文件 ＝ 按归属切出的一片」。于是「每稿一表」与「一套物料共用一张表」不是两种模式，而是同一个动作的两个参数（这片覆盖 1 稿还是 4 稿）。
② 界面之所以是「两份名单」，是因为模型是「两份名单」。不是排版没排好，是代码里表真的按文件存（workbench-view.tsx:349）。
③ 表里从来没有「这是谁的」这一列。模板导出把源文逐字抄自 PSD，却只写 source + 语言列（translation-template.ts:58）——两份文案相同的 SKU，导出的模板逐字节相同。所以「这张表是谁的」这个问题，产品从来没有回答过。

04阶段三 · Deep Thinking（推导）

Dataset（译库）  { datasetId, name, rows[], langColumns[], hasOwnerColumn }
  └─ Slice（片）   { datasetId, ownerValue, rows[]  ← 按归属值切出 }
       └─ Binding   { draftKey → { datasetId, ownerValue, languageScope } }
            └─ Evidence { tier: 实证 | 声明 | 推定 | 存疑 | 不符 }

对照现状：今天只有 parsedTables[draftKey]（一份副本）；新模型是三层引用——表只存一份，每稿只存「哪一片」。

三种「共用」形态被统一

形态数据模型界面人话
每稿一张表1 库 → 1 片独占一片
几个 SKU 共用一张1 库 → N 片（成员显式声明）几稿共用一片
12 个 SKU 一张合表1 库 → 12 片（按「模块」值切）合表按模块切片
Owner 的 O1 问题在这套模型里不再存在

它变成「一片覆盖几稿」的一个参数。术语归内部，界面说人话。

绑定证据分级：把「猜」变成「分级」

档判据界面执行前
实证归属值对上 且这一片的原文集覆盖本稿全部原文绿徽章不拦
声明只有归属值对上（原文集未核）蓝徽章提示
推定无归属列，但原文集覆盖本稿全部原文蓝徽章提示
存疑原文集部分重叠（既没覆盖也没排斥）琥珀徽章要求确认一次
不符归属值指向别的稿，或原文集与本稿无交集红徽章拦批
口径纪律

所有比较必须走 coverage.ts 已有的同一套三档口径（strict / whitespace / substring）。否则会出现「矩阵说 100%、体检说不符」的第二套真值——这正是 coverage.ts:106-110 明文记过的教训（X11）。

模板要带出处（这是整件事的根）

今天：  source | EN 英语 | DE 德语 | FR 法语
改后：  source | 记录编号 | 模块 | EN 英语 | DE 德语 | FR 法语
                ↑ 新增     ↑ 新增（两列的别名解析层早就有了，X3）

「记录编号」＝层级路径的稳定编码（不能由文字生成——同文图层会撞）；「模块」＝归属值。缺这两列的老表自动降级到「推定」档，不影响存量。

界面：交付物矩阵 ＋ 详情 ＝ 图二那一行

交付物矩阵（144 格）：行=物料、列=语种、格=这一份交付物做到哪一步；行头一枚徽章说清「绑定·实证/推定/存疑/不符」＋ 从哪个库哪一片来。详情区＝图二那一行——图二的单稿形态不是另一个页面，是矩阵一行的展开。另加译库与切片视图：一个库 → 它的片，把「12 SKU 一张合表」当场切给 Owner 看。

行身份升级：P0 不做（重要取舍）

理论上行身份应是 (归属, 原文, 序号)（公理 B）。但对「每稿一张独占表」的现有路径，归属是常量，升级零影响；只有「一个库多片且同表同文」才需要改匹配键 ⇒ 那是 P2 独立一单（触发 AGENTS.md 合同变更纪律：四层同步 ＋ fixture）。P0/P1 全部限定在「绑定与展示层」，绝不触碰 binding-core 的匹配键——把一个 UI 任务变成执行合同变更是最常见的跑偏方式。

第一轮：攻击推导本身

#级攻击处置
D1🟠「归属进模型」只是把问题推后——归属是用户写的，可以写错归属不能是唯一判据，必须与「原文集覆盖」交叉验证 ⇒ 「实证」必须是双证据（归属对上 ＋ 覆盖）；单靠归属只算「声明」档

D3🟠按「模块」切可能切错——用户的「模块」含义可能是分区不是 SKU切片不自动发生：只有模块列取值命中候选归属集时才允许切，且切前预览「这一片有 N 行」。仍是「提案→确认」
