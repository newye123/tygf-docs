## 阶段一 · Critical Thinking（第一性原理）

### 1.1 从现象剥到本质

Owner 的现象：「12 个 SKU，每个 SKU 自己的表，怎么区分？」

先问**这是什么**。这个工作台真正生产的东西不是「表」，不是「文件」，是：

> **(设计稿 × 语种) → 一份新的设计稿**

12 SKU × 12 语种 = **144 份交付物**。这才是真正被生产、被交付、被计费的东西。

再问**一行译文是什么**。一行译文不是「某个文件的某句翻译」，它是：

> **(归属, 原文, 出现序号, 语种) → 目标文本**

于是得到两条不可再分的公理：

- **公理 A（交付物轴）**：交付物的键是 **(文件, 语种)**。界面主角必须是这 144 个东西，图二那排语言 = 矩阵的一行。
- **公理 B（归属轴）**：译文的键是 **(归属, 原文, 序号)**。**文件不是原语，归属才是**；文件只是"归属"这个维度上的一个取值（或者归属缺失）。

### 1.2 两条公理推出的三条结构性结论

**结论 1 —— "表"根本不是按文件分的东西。**

现在的数据模型是 `parsedTables[draftKey] = ParsedCsv`（`workbench-view.tsx:349`）：表被当成**文件的属性**。但一行译文的键里有"归属"、有"语种"、有"序号"——**没有"文件"**。所以正确形态是：

> **表 = 数据集（装着所有行）；文件 = 从数据集按归属切出的一片（slice）。**

"每稿一表"与"一套物料共用一张表"因此不是两种模式，而是**同一个动作（指一片）的两个参数**（这片覆盖 1 稿还是 4 稿）。Owner 那句「共用一个语言表格这个方向也没有错」——**在第一性原理下是对的，而且根本不该是"另一种方向"**。

**结论 2 —— 界面之所以是"两份名单"，是因为模型是"两份名单"。**

图一把「文件名单」和「表名单」并排，不是因为排版没排好，是因为**代码里表真的按文件存**。而表之所以只能按文件存，是因为——

**结论 3 —— 表里从来没有"这是谁的"这一列。**

模板导出把源文**逐字抄自 PSD 扫描**（`translation-template.ts:1-4, 53-70`），却只写 `header = ['source', ...codes]`（`:58`）。**出处被扔了**。

> **两份文案相同的 SKU，导出的模板逐字节相同。**

所以「这张表是谁的」这个问题，**产品从来没有回答过**——它只能靠文件名猜、靠规则猜、靠人点。这不是交互问题，是**数据缺失**。

### 1.3 由此得到的公理（可证伪）

| 公理 | 内容 | 证伪条件 |
|---|---|---|
| A | 交付物的键 = (文件, 语种) | 若计费/结算单位不是 (文件, 语种) 则推翻 |
| B | 译文的键 = (归属, 原文, 序号) | 若系统任何一处按"文件+原文"唯一确定一行，则推翻 |
| C | 绑定必须**可证**，不能靠猜 | 若产品能接受"猜错了用户自己看出来"，则不需证据分级 |
| D | "每稿一表"是**安全装置**，不是自然法则 | 若某条铁律要求一稿绝不可用他人数据，则共享需另设机制 |

**D 的关键**：v7 的 F11 缺表门（`workbench-view.tsx:1950-1959`）是在**"绑定无法验证"的前提下**的兜底（缺表总比错表安全）。一旦绑定可证，"一稿用多稿的表"就不是危险，而是合法。

**三处错**：

3. **漏了"错绑 + 无冲突"这一档**：信任链只拦"同原文**不同**译文"（`:665-672`/`:930-939`）；若错绑的表与本稿**没有同原文冲突**，则一路绿灯，**错的译文被写进客户 PSD**（X6）。

## 阶段三 · Deep Thinking（推导出的方案）

### 3.1 三层数据模型

```
Dataset（译库）  { datasetId, name, rows[], langColumns[], hasOwnerColumn }
  └─ Slice（片） { datasetId, ownerValue, rows[]  ← 按归属值切出 }
       └─ Binding（绑定） { draftKey → { datasetId, ownerValue, languageScope } }
            └─ Evidence（证据） { tier: 实证 | 声明 | 推定 | 存疑 | 不符 }
```

**对照现状**：今天只有 `parsedTables[draftKey]`（一份副本）；新模型是**三层引用**，表只存一份、每稿只存"哪一片"。

### 3.2 三种"共用"形态被统一

| 形态 | 数据模型 | 界面人话 |
|---|---|---|
| 每稿一张表 | 1 库 → 1 片 | **独占一片** |
| 几个 SKU 共用一张 | 1 库 → N 片（成员显式声明） | **几稿共用一片** |
| 12 个 SKU 一张合表 | 1 库 → 12 片（按「模块」值切） | **合表按模块切片** |

⇒ **Owner 的 O1 问题（"每稿一表"是硬约束还是默认）在这套模型里不再存在**：它变成"一片覆盖几稿"的一个参数。

### 3.3 绑定证据分级（把"猜"变成"分级"）

| 档 | 判据 | 界面 | 执行前 |
|---|---|---|---|
| **实证** | 归属值对上 **且** 这一片的原文集**覆盖**本稿全部原文 | 绿徽章 | 不拦 |
| **声明** | 只有归属值对上（原文集未核） | 蓝徽章 | 提示 |
| **推定** | 无归属列，但原文集**覆盖**本稿全部原文 | 蓝徽章 | 提示 |
| **存疑** | 原文集**部分**重叠（既没覆盖也没排斥） | 琥珀徽章 | **要求确认一次** |
| **不符** | 归属值指向别的稿，**或**原文集与本稿无交集 | 红徽章 | **拦批** |

**关键**：所有比较必须走 `coverage.ts` 已有的**同一套三档口径**（strict / whitespace / substring），否则会出现"矩阵说 100%、体检说不符"的第二套真值——这正是 `coverage.ts:106-110` 明文记过的教训（X11）。

### 3.4 模板要带出处（这是整件事的根，X1/X2）

导出模板改成：

```
source | 记录编号 | 模块 | EN 英语 | DE 德语 | FR 法语 | …
```

- 「记录编号」= 层级路径的稳定编码（**不是文字的哈希**——两个图层可能文字相同）
- 「模块」= 归属值（SKU 码 / 文件名 / 组名）
- **两列的别名解析层早就有了**（X3）⇒ 解析零改动；用户自带的老表没这两列 ⇒ 自动降级到「推定」档，**不影响存量**

### 3.5 界面：交付物矩阵 ＋ 详情＝图二那一行

- **交付物矩阵**（144 格）：行=物料、列=语种、格=这一份交付物做到哪一步；行头一枚徽章说清「绑定·实证/推定/存疑/不符」+ 从哪个库哪一片来
- **详情区 = 图二那一行**：图二的单稿形态**不是另一个页面**，是矩阵一行的展开
- **译库与切片视图**：一个库 → 它的片；把"12 SKU 一张合表"当场切给 Owner 看

### 3.6 行身份升级：**P0 不做**（重要取舍）

理论上行身份应是 `(归属, 原文, 序号)`（公理 B）。但：

- 对"每稿一张独占表"的现有路径，**归属是常量**，行身份升级 **零影响**
- 只有"一个库多片且同表同文"的场景才需要改匹配键 —— 那是 **P2 独立一单**
- 改匹配键 = 改执行语义 = 触发 AGENTS.md 合同变更纪律（四层同步 + fixture）

⇒ **P0/P1 全部限定在"绑定与展示层"，绝不触碰 `binding-core` 的匹配键**。把一个 UI 任务变成执行合同变更是最常见的跑偏方式。

| **D17** | 🔴 | **我们自己生成的「记录编号」会不会亲手制造 #195 那场生产事故？** | ⇒ **会**。链路已追通：`记录编号` → 行标识（`binding-core.ts:599`）→ `fragment_row_ids`（`:584/:590`）→ 助手清单 → 白名单 `^[A-Za-z0-9][A-Za-z0-9._:-]{0,127}$`（`execution-manifest.js:9`）→ 不合规即 `MANIFEST_FRAGMENT_ROWS_INVALID`（`:168`）＝**#195 的原样事故**（X7/X8/X9）。<br>⇒ **硬约束写进方案：记录编号必须纯 ASCII、只含 `[A-Za-z0-9._:-]`、首字符字母数字、≤128；层级路径里的中文/空格/全角必须先转码再进编号。验收判据里要有这一条。**<br>⇒ 这一条是本轮最有价值的发现：**它正好落在今天刚发生过的事故形态上** |
| **D18** | 🟡 | 覆盖判定该用 strict 还是 loose | ⇒ 必须**分层**且与 `coverage.ts` 三档一致（strict / whitespace / substring，X11）。证据判定若自己另算一套，就会出现"矩阵 100% / 体检不符"的两套真值 |
