## 4. 对本方案自审一轮（先证伪自己）

| 攻击点 | 结论 |
| --- | --- |
| P-4 用 `key` 重挂，会不会把正在填的表单/滚动位置清掉？ | 后台面板都是只读列表＋图表，无输入态；且 Radix 非活动面板本就卸载，切回来本来也是重挂。可接受。 |
| P-3 改渲染派生，会不会**放宽**权限（operator 多出 owner-only 板）？ | 反向风险已核：`visibleAdminNav` 的过滤式 `isOwner || !group.ownerOnly && !item.ownerOnly` 优先级正确（`&&` 先算）；并加断言 2 钉住"导航与渲染一致"。 |
| P-2 加导航项算不算"改变用户可见行为"要产品批准？ | 属恢复既有能力（面板代码在、图标 import 在），不是新增能力；Product Drift Guard 第 2 条"未知意图→保留"正是指向别把它藏着的方向。 |
| P-5 写死 `Asia/Shanghai` 会不会反而错（机器在新加坡，UTC？） | 服务器在**新加坡**（机房），墙钟时区未核实；CF 数据按天聚合，早 8 点跑只是"取昨天"，写死时区把不确定性消掉，比"跟着未知本地钟"更可预期。若 Owner 想要 UTC 语义，改一处即可。 |
| P-6 冒烟前置会不会导致"没排程＝没生效"的误解？ | 顺序改为：安装 → 冒烟 → 成功才 `enable --now`；失败则 disable 并 exit 1，日志明确写"未排程"。比现在"已排程但红着"更可判定。 |
| 更便宜的反方案存在吗？ | P-3/P-4 若只加不改（再写一份条件）＝第三份真相，否。P-5 若去查 TZ 再决定＝依赖到不了的机器，否。 |
