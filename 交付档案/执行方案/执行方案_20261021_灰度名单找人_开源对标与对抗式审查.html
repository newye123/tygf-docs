Owner 在运营台粘了三个邮箱保存，被拒「以下用户不存在」。本轮做三件事：查开源上别人怎么解这个坑、对我自己刚提的方案做对抗式审查、给出可复跑的执行序。全程只读——未改代码、未部署、未写库。

01判定

结论

病根不是文案写坏了，是这张卡只让人手填内部用户 ID，而全站没有任何一个地方能看到这个 ID。
我本来想提的「让后端顺手把邮箱解析成 ID」，被本轮实测数据判死——覆盖率、唯一性、大小写三道全塌。

该做的（B 案）

  • 卡内加搜索选人：输入邮箱/姓名/公司，调现成的 /api/admin/installs?q=，点「加入」把 userId 落进输入框。存的永远还是 ID，服务端形状一字不改。
  • 切分放宽：换行 + 逗号 + 分号 + 空格都切（现在只认换行）。
  • 环境徽标：卡片标题旁显示「生产 / 测试」，数据源现成（profileEnvironment()）。
  • 错误文案改口：说清「这里要的是用户 ID，可用上方搜索按邮箱找人」。

不该做的（C 案）

  • 后端收邮箱自动解析：生产 68 个用户里只有 10 个有可用邮箱凭证；contact 字段 54 个为空、8 个值是 "sw"，且无唯一约束——仓库自己的夹具里两个人共用同一个 contact。
  • 大小写静默失配：SQLite 等值比较实测 CASE_SENSITIVE，大写邮箱查真实数据得 0 行。用户会得到一条永远解释不了的「不存在」。
  • 新建查找路由：smoke-admin-security.mjs:323 断言 admin 路由集合为空，新增即红。复用现成接口天然绕开。

03开源上别人怎么解

六个实现撞在同一处：名单里存「应用自己定义的稳定标识」，人在界面上操作「标签」，键由系统落库——两件事从不混在同一个输入框里。

项目它怎么定位「指定用户」可直接抄的一点
Unleash
（GitLab 用它）		 userWithId 策略收逗号分隔的任意字符串，但要求它必须等于 SDK 传的 context.userId；文档示例里 ID 直接写成邮箱 平台不规定 ID 长什么样，只规定两边一致——我们「存 ID + 服务端 fail-closed」的形状是对的，别动
GitLab 在 userWithId 之上再做「用户列表」对象：先建一个有名字的列表，功能开关引用它 可复用命名名单——100 人规模属过度设计，本轮不做，记「以后再说」
GrowthBook 属性优先：先选属性（id/email/country/plan）→ 操作符 → 值；id 是默认哈希与定向属性，可用 hashAttribute 换 把「你在按什么找人」显式摆到界面上，而不是让用户猜字段
GrowthBook
（输入控件）		 ID 列表是个多选控件，敲进去的陌生值直接变成一枚标签（free-solo），不是报错 未识别的输入先变成候选，不要在保存时才炸
LaunchDarkly 上下文有 kind + key + 属性；官方口径：key 用稳定、非敏感的内部标识，邮箱只是属性；并明说客户端规则不承担真正授权控制 邮箱当键是反模式——PII、可改、可撞
PostHog 发布条件按 person property（含 email）过滤，值选择框拿真实用户值做候选 候选来自自己的库，不来自用户记忆
Django admin raw_id_fields＝手填主键；autocomplete_fields＝搜人话、表单仍提交主键（要求关联模型声明 search_fields） 这就是 B 案的原型——我们缺的正是「autocomplete 那一档」

推翻了自己上一轮的哪句话

上一轮我说「建议改成邮箱和 ID 都收」。本轮 F-102 的三条实测把它推翻：能唯一解析的邮箱源只覆盖 10/68，另一条源是自由文本且无唯一约束。新结论：不做解析，做选人——把「输入键」这个动作从人身上拿走。

另有一处口径修正：上一轮我说「运营台没有任何地方能看到 ID」，严格讲是「没有任何地方能看到别人的 ID」——名单卡保存成功后会回显自己的。这个区别决定了 F-101 的修法要落在选人控件上，而不是只在详情页加一行文本。
