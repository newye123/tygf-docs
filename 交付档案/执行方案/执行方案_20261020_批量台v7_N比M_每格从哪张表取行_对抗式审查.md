## 阶段一 · Critical Thinking：Owner 的推广是对的，我上一版收窄了

### 1.1 我收窄在哪

v5/v6 把绑定说成"**每稿一片**"。那是**实现上的一个特例**，被我说成了模型本身。现实里真实的关系至少有四种：

| 关系 | 真实场景 |
|---|---|
| **1 稿 : 1 表** | 常规：一份 PSD 配一张自己的表 |
| **N 稿 : 1 表** | 一套主文案给 12 个 SKU 变体共用（文案一样、图不同） |
| **1 稿 : M 表** | 日语、韩语由对方单独发；另有几句新文案在补充表里 |
| **N 稿 : M 表** | 上面几种同时出现 |

⇒ 把它压成"每稿一表"，等于**把模型钉死在第一种关系上**——Owner 说得对。

### 1.2 往下再问一层：绑定的原子是什么

- 交付物的原子 = **(设计稿, 语种)**。
- 一行译文的原子 = **(原文, 语种) → 目标文本**。
- **表不是原子**——它是行的容器，而且容器可以横跨多个稿（主表）、也可以只带一门语言（专表）。

⇒ **真正的绑定单元是「(稿 × 语种) → 一组行」。**

> **推论：把绑定下沉到 (稿, 语种) 这一格，四种关系就自动涌现，不再是四种模式。**

| 关系 | 在新模型里是什么 |
|---|---|
| 1 稿 : 1 表 | 默认：每格取主表该语种的行 |
| N 稿 : 1 表 | 多个稿的默认行集都来自同一张表（表内无同原文多译文时才合法，见 R2） |
| 1 稿 : M 表 | 某些语种的行集换成别的表（语种覆盖）＋ 某些行从补充表并进来 |
| N 稿 : M 表 | 上述组合 |

### 1.3 用户要做的操作只有三种

无论多少张表多少种关系，**人要做的事只有三件**：

1. **换这稿的主表**
2. **把某几门语言指到别的表**（语种覆盖）
3. **给这稿加一张补充表**（只并进主表里没有的那几句）

其余 144 格的来源由系统推导并**画出来给人看**——**例外驱动，零操作起步**。

## 阶段三 · Deep Thinking：模型与判据

### 3.1 数据模型（只加三样，不加第四样）

```
Table   { tableId, name, rows[], langColumns[], hasSameSourceConflict }   // 库
Slice   { sliceId, tableId, ownerValue, rowIds[] }                        // 库按归属切出的一片
Binding { draftKey → {
    mainSliceId,                                  // 主表片（默认来源）
    localeOverrides: { locale → sliceId },         // 语种覆盖
    supplements: sliceId[]                        // 补充片（按原文差集并入）
} }
```

**解析一格 (D, locale)**：

```
rows(D, locale) =
    (localeOverrides[locale] ?? mainSlice) 的该语种行
  ∪ supplements 各片中「主表里没有的原文」的行
⇒ 同原文多译文 ⇒ 点名冲突（沿用 X2 的既有检查）
```

### 3.2 「整表共用」vs「必须切片」——**可计算的判据**

> **表内存在「同一原文、不同译文」⇒ 必须切片；不存在 ⇒ 可以整张给多稿共用。**

- 判据来源：表自身的行集合（解析期即可算，与稿无关）⇒ **零配置项、零猜测**。
- 整表共用时，多出来的行由助手判 `EXCLUDED`（X3）⇒ 不会写错，只会少写；界面要如实显示"这稿用到该表的 12/42 行"。

### 3.3 覆盖率与门随之下沉

- 覆盖率：**每格**（稿 × 语种）按**合并后的行集**算，口径仍是 X4 的三档。
- 执行前的门：仍是"每稿每语都确认"（`workbench-view.tsx:1962-1990`）——**逻辑不变**，只是格子从"表"变成"合并行集"。

## 阶段四 · Review（第四轮对抗式审查，针对 N:M 推广本身）

| # | 级 | 攻击 | 处置 |
|---|---|---|---|
| **R1** | 🔴 | **合并粒度必须是 (稿, 语种)，不能是整表。** 若把多张表先合成一张再分发，同原文不同译文的冲突面会被放大到**不相关的稿**之间 | ⇒ 合并**只在每格内**发生（X1 的 `buildRowsByLang` 出口），冲突检查随 X2 原样落在每格 |
| **R2** | 🟠 | **"整表给多稿共用"什么时候合法？** 若表里有「同原文不同译文」，两稿都会命中它 ⇒ 一稿会同时对上两行 | ⇒ **可计算判据**（§3.2）：有冲突 ⇒ 必须切片；无冲突 ⇒ 整表共用合法。**不留成配置项** |
| **R3** | 🟠 | **"1 稿 ← 2 表"会不会逼写入层改语义？** | ⇒ **不会**：合并发生在 fragments 之前（X1），信任链的分组与冲突检查（X2）原样复用 ⇒ **不触发合同变更**（不跑 `test:batch-row-contract` / `test:trust-chain`） |
| **R4** | 🟡 | **多出来的行会怎样？** | ⇒ 助手判 `EXCLUDED`、**不写入、单位 0**（X3）⇒ 风险是**漏**不是**错写**；但**同原文同表内不同稿的译文会命中** ⇒ 这正是 R2 要切片的理由。界面须显示"用到该表的 12/42 行" |
| **R5** | 🟡 | **144 格逐格配置会不会把界面炸掉？** | ⇒ **例外驱动**：默认 12 次（每稿一主表），例外才动手（语种覆盖 / 补充表）。界面呈现的是**系统推导出来的来源矩阵**，人只改例外 |
| **R6** | 🟠 | **"这一格做不做"和"这一格从哪取"是两个轴，容易混成一种颜色** | ⇒ 来源矩阵里，**做/不做**决定格有没有内容，**从哪取**决定内容；两种关系（默认/切片/覆盖/补充）用**第二行小字**标，不与状态色混用 |
| **R7** | ✅ | **证据还是一个数吗？** | ⇒ 是。每格的证据 = 合并行集对该稿的**对稿命中率**；不再有"表对不对得上稿"这种表级判断。表级只保留一个可计算的标签：**可整表共用 / 必须切片** |
| **R8** | ✅ | **会不会退回"自动指派"？** | ⇒ 不会。提案仍只给**排序与例外**，人拍板（v4 的 T1 自我更正继续成立） |
| **R9** | ✅ | **"共享表组"这个概念还要不要留？** | ⇒ **不留**。N:M 下它是"N:1"的一个特例；模型里只剩"多稿指向同一张表或同一切片" |
| **R10** | 🟠 | **主表 / 语种覆盖 / 补充表三种关系会不会打架？** | ⇒ **优先级定死**：语种覆盖 > 主表 > 补充表；**补充表只补"主表里没有的原文"**（按原文集合差集），若补充表带来同原文不同译文 ⇒ 点名冲突，**不静默覆盖** |
| **R11** | 🟠 | **覆盖率口径会不会分裂？** | ⇒ 不会，但**取数口要改**：`calcCoverageMatrixForDraftTables`（X5）从"每稿一表"改成"**每格一行集**"，三档口径（X4）不变 ⇒ 组件与闸仍共用一份（`coverage.ts:106-110` 的纪律） |
| **R12** | 🟡 | **合并后行集变大，性能与缓存怎么办？** | ⇒ 每格行集 = 主表行数 + 覆盖表行数 + 少量补充行；按 **(表指纹 × 稿指纹 × 语种)** 缓存合并结果（`preparation-contract.ts:311` 的指纹已是现成稳定键） |

### 阶段四之二 · 我推翻自己的两处

| # | 上一版说法 | 推翻 |
