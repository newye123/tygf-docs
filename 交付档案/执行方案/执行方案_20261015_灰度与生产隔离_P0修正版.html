灰度开关基础设施 P0′

为「字体排版定制」等高风险功能提供可实时控制、按人放量、默认不生效的灰度开关——只放白名单用户，出问题最坏 30 秒收回，生产站逐字节不受影响。承接《审查报告_20261014_灰度与生产隔离_对抗式审查》§04，全部落在既有链路上。

01一句话路径与判定

核心设计三条

开关默认 false；白名单按人（betaUserId）；判定全部在服务端——客户端只拿「对我开没开」一个布尔，永远不拿名单本身。

02与既有 canary 机制的关系（先读懂再动手）

已有：安装级 canary

  • TYGF_BATCH_EXECUTION_MODE=canary + TYGF_BATCH_CANARY_INSTALL_IDS 白名单（batch-execution-mode.ts:20,70-78,163-171）。
  • 服务端判定、fail-closed、显式 reasonCode——语义是「哪些电脑能用批量执行」。
  • 配置在环境变量里，改名单要动部署——做不到实时。

新增：用户级、库内、实时

  • 「哪些账号能看到和使用灰度功能」——白名单存 SiteSetting，运营台可改。
  • 改名单 = 一次 POST，最坏 30 秒全收敛，不动部署。
  • 两层不冲突：字体功能真正进入执行时，仍要过既有批量门控。
为什么不用环境变量做这一层

白名单是运营数据，不是部署配置；改 env 要动部署，做不到「运营台一点、最坏 30 秒全收敛」。

03P0′ 六步

1

旗标形状扩展（零迁移）

featureFlags.ts 加 typographyCustomizationEnabled: false 并加入运行时覆盖名单（先例 :59-77）。默认必须 false。白名单不放进形状——sanitizeAgainst 对空数组默认值判 undefined（site-settings.ts:227-236），放进去永远存不下来。

2

白名单存储（独立键 + 原子更新）

feature-flags-store.ts 加 get / save 两函数，独立键 typographyBetaUsersV1，子键原子 upsert（照 saveSiteCopyInlineEditOverride 模式 :61-85）。校验：≤100 人、每项非空 ≤64 字符、去重、存在性（BetaUser）核验，未知 ID 返回 400。

3

服务端判定（唯一权威）

新 feature-flag-gating.ts：全局开关 ON 且名单非空且用户在名单。任何异常、未登录、空名单一律 false（fail-closed）。空名单=谁都不开（与批量 canary 的「空=全放」相反，故意从严）。

4

按人读取端点（客户端唯一真相源）

新 api/workbench/feature-access/route.ts：GET，getCurrentUser 解析身份（账号 active、未注销、未过期），返回 { features: { typographyCustomization } }。未登录返回 200 + false，不泄漏信息。

5

客户端收敛（杀开关「最坏 30s」）

use-feature-flags.ts 加 30s TTL + 定时刷新 + visibilitychange（现状 :8-12 永不失效，是「关不掉」病根）。新 use-feature-access.ts 同机制。in-flight 执行不受影响，写进文案。

6

运营台编辑 + 占位探针

admin POST 加名单分支 + writeAuditLog（先例 :45,57,67）；GET 附 { id, name, status }。settings-panel 加「字体定制灰度名单」块（姓名 + 文本框 + 保存）。photoshop-step 加占位块「排版定制（内测预览）」，文案过 #30 检查（ISSUES.md:1172）。

06红线合规检查

  • 不静默降级：开关或名单关闭 = 功能隐藏走旧流程，不是降级运行。
  • 支付 flag 不碰；助手不动（无版本纪律触发）；零 schema 迁移。
  • 审计：白名单每次变更落 AdminAuditLog（writeAuditLog 现成）。
  • 隐私：白名单只存 betaUserId 不存邮箱；端点不向客户端泄漏名单。
  • 生产：产物只在测试站使用；生产部署需 Owner 单点授权，本方案不申请。
  • 文案：用户可见文案过 #30 教训检查（不出现内部计费/灰度术语）。
